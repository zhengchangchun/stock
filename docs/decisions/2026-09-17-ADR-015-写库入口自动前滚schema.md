# ADR-015：写库入口统一走 `ensure_schema` 自动前滚 schema

日期：2026-09-17
状态：已采纳
任务：P33

## 背景

P32 给 `predictions` 加了 `origin` 列，迁移 `migrate_p32_predictions_origin` 只经
`db init` 前滚。真实库当时没前滚 → 收盘链 `predict run` 会在 `insert_prediction`
的 `_INSERT_SQL`（已含 origin）上撞 `sqlite3.OperationalError: table predictions has
no column named origin` = 当天预测永久缺失，而巡检/测试全绿看不出（测试都在
`init_db` 新 shape 库上跑）。根因：**迁移只挂在少数入口，不挂在「写库」这个不变式上**。

## 决策

1. 新增 `stocklab/store/migrate.py::ensure_schema(db_path)` = 「幂等前滚 + 真失败要炸、
   不许静默」。返回本次实际结构变更列表。
2. **写库入口统一接它**：`ingest bars/actions/index`、`predict run`、`verify run` /
   `verify backfill` / `verify pending`、`review daily`、`session tick` /
   `session backfill-close`、`paper init|step`、`features build`、lab 应用（`lab serve`）。
   已直接调 `init_db` 的 `_cmd_ingest_series`（valuation/moneyflow）与 `features build`
   改成调 `ensure_schema` —— **不两套并存**。
3. `init_db` 与 `ensure_schema` **并存但分工**：`init_db` 每次显式调用都先备份
   （语义＝「人工要动库，留退路」，给 `db init` 用）；`ensure_schema` 是写前自动守护，
   **只在确有结构变更时备份一次**、无变更零写零备份（否则每次 `predict run` 产一份备份）。
4. `doctor` 是**只读**入口：只报告 schema 状态（`schema_status`：逐个已知迁移 marker
   在位与否），**不擅自迁移**。迁移是写库入口的职责。

## 为什么 `ensure_schema` 不在每次调用时都备份

`init_db` 的「每次都备份」是给人工 `db init` 的语义：人主动要动库，留一份退路是对的。
但写库入口每天跑很多次，若沿用这个语义，每个 `predict run` 都会在 `data/backups/`
产一份新文件 —— 备份文件爆炸且无意义。因此 `ensure_schema` 先只读探测 `_pending_column_migrations`，
**只在确有结构变更时**才在变更前备份一次（备份的是变更前那份），没有变更则零写。

## 真失败要炸（不许静默）

- 老 shape 表（valuation/money_flow）**已有数据** → `migrate_p28` 抛 `RuntimeError`
  （append-only：历史行不可丢，DROP 重建会删数据，必须停下来让人工决定）；
- `ALTER TABLE ADD COLUMN` 失败 / IO 错误 → 一律向上抛。
宁可让写入口停下报错，也不在坏 schema 上写进口径错误的数据。

## 已知迁移 marker 登记

`_KNOWN_MARKERS`（doctor 逐个报告在位与否）：
`p28_resp_sha256_valuation` / `p28_resp_sha256_moneyflow` / `p32_predictions_origin`。
**新增迁移必须在这里登记**，否则 doctor 看不见它（写进函数注释）。

## 边界（照实声明，不藏）

- **本轮未接**（超出 15:30 收盘链、非本事故路径）：P12 手工账本 `trade add/reverse` /
  `cash add`、离线 `adj rebuild`、P30 `calendar holidays fetch`。它们同属「写库入口」，
  理想上也应接 `ensure_schema`；但与本事故（predictions.origin）无关、且各自有
  fail-closed 或 append-only 前置检查，留待「所有写库入口收口」的统一轮次一并处理，
  避免本轮把测试面铺得过大。
- 背景里 nanobot 写「`_cmd_ingest_series`（index/valuation/moneyflow）」——实测
  `ingest index` 是**独立的** `cmd_ingest_index`，并不调 `init_db`。本轮把它与
  `ingest actions` 一并接上（同一根因的漏网之鱼）。

## 验证证据

- `pytest`（清 `__pycache__`）全绿且只增不减；`verify.sh` all ✅、红线三目标逐位不变（未 `--regen`）。
- 实证：缺 origin 列的副本库上跑写入口，接线前 `OperationalError`、接线后自动前滚并成功写入，
  副本 `count(*)` 不变、老行 NULL 不变。
- 测试：`ensure_schema` 加列/幂等/只在变更时备份 + `schema_status` 只报告不迁移 +
  反向构造缺 origin 库跑 `predict run` 不炸 + doctor 报缺失列且不迁移。
