# ADR-043 插桩资源上限与 G1 监控（P93）

日期：2026-09-27 ｜ 状态：已实施 ｜ 上游：P61 §0.5–§0.7（G1 判据）、P92（业务块范式）

## 背景

P61 §0.6 实测：`[0] * 30000000`（≈+229 MiB）发生在**单个 C 调用**里，
`signal.setitimer` 拦不住，`guard.check_source` 原样放行 ⇒ 一段写错的脚本能把
持有 SQLite 连接与 WAL 的日更链进程 OOM 掉。P61 拍板「子进程沙盒推迟」，
但留下了 **G1**（资源耗尽）这一档不等触发的洞，并要求开「最小档：仍同进程的资源上限」。

## 决定

### 1. 量具只读进程自身（不 fork、不采样）

新增 `stocklab/plugin/resources.py`：`peak_rss_bytes()`（唯一数据源
`resource.getrusage(RUSAGE_SELF).ru_maxrss`）＋ `rss_mark()`。
`ru_maxrss` **darwin 是字节、linux 是千字节** ⇒ 按 `sys.platform` 归一，
**未识别平台抛 `ValueError`**（猜一个单位就是静默错 1024 倍）。
不 fork、不起采样线程、不碰 cgroup。

**已知代价（必须记住）**：`ru_maxrss` 是**高水位**，不回落。于是
`delta = 调用后峰值 − 调用前峰值` 对**正常脚本恒为 0**（实测 m2_a1 = 0 B），
只有「把峰值顶上去」的调用才有非零 delta。这张表因此只能回答「有没有越界」，
**不能**当「每次调用用了多少内存」的时间序列读。

### 2. 两条阈值进主干常量（唯一真源，AI 不可改）

`stocklab/config/limits.py`：`PLUGIN_CALL_RSS_LIMIT_BYTES = 512 MiB`（单次增量）、
`PLUGIN_PROCESS_RSS_LIMIT_BYTES = 1536 MiB`（进程已用峰值）。
1.5 GB 而不是 G1 判据的 2 GB：**要在被打死之前先停** —— 2 GB 是**事后**判据，
本常量是**事前**闸门。两个名字同时加进
`tests/test_p44_constants_guard.py::CONSTANTS`（5 → 7），获得「唯一真源 ＋
无 setattr 覆盖路径 ＋ labweb 零接触」三条既有扫描的保护。

### 3. 两处闸门，**不假装能中断**

`plugin/runtime.py`：**执行前** `peak >= process 上限` ⇒ 抛 `PluginResourceError`，
`run` 一次都不执行；**执行后** `delta >= call 上限` ⇒ 该次结果作废、抛同一异常。
异常消息与模块 docstring 都写明：**本档不声称能阻止那一次分配**（单次 C 调用不可
中断），只声称「判废 ＋ 留痕 ＋ 后续调用被挡」。
真机实证：一次 1.53 GiB 分配把峰值顶到 1543 MiB 后，**下一次**调用被执行前闸门
挡住、`run` 计数 = 0。

`PluginResourceError` 是 `PluginTimeout` 的**兄弟**（都直接继承 `Exception`）；
既有按 `PluginTimeout` 精确匹配的那个 except 点（`cli/candidate.py`）**同时**
接住两者，走同一条通道（exit 1 ＋ 点名）。`m2/channel_a.py::REJECTED` 不含
`PluginTimeout`，**未动**（动了会改变通路 A 的语义）。

### 4. 读数出口 `on_call`（返回类型一字不改）

`load_script(..., on_call=None)`：每次调用结束回调
`{"plugin_id","outcome","duration_ms","rss_delta_bytes","rss_peak_bytes"}`，
`outcome ∈ {"ok","timeout","resource"}`。脚本自己抛的其它异常（契约/`NameError`）
**不**回调 —— 取值域没有第四个词，硬塞一个「其它」会让表变成什么都往里装。
不传 `on_call` 时行为与今天逐字相同（用例钉住）。

### 5. 落库：新 append-only 表 ＋ 唯一写入口

`plugin_resource_events`（`event_id/plugin_id/at/outcome/rss_delta_bytes/
rss_peak_bytes/duration_ms/detail` ＋ `outcome` CHECK ＋ 两触发器），
`store/schema.sql` 建出、`migrate_p93_resource_events` 补触发器前滚、
`_KNOWN_MARKERS` 登记 `p93_plugin_resource_events`。
**写入口只有 `plugin/store.py::record_resource_event`**（源码扫描钉住：
`INSERT INTO plugin_resource_events` 只准出现在那一个文件里 —— 为此该 INSERT
写成**裸字面量常量**，不用表名插值）。
本次接线 **`plugin submit` 的沙盒预检**（唯一会执行未审脚本的地方）；
`candidate run` / `m2_daily` 跑的是已 `active` 脚本，**未接线**（会抛异常但不留行）。

### 6. 巡检第五块 `sandbox_guard`（只展示）

`ops/business.py` 的 `BLOCK_ORDER` 四块 → 五块（P92 四块一字不动），
读最近 20 条事件：空表/缺表 ⇒ `skipped`（**不算异常**），有 `resource` ⇒ `high`。
`high` 与排雷/状态/新鲜度一样**只展示、不进退出码**（`fuse` 仍是唯一进退出码的
业务读数）；`brief_text` 多一行，`summary_line()` 一字不动。
新增词汇 `patrol.HIGH`（与 P92 的 `TRIPPED`/`RISKY` 同款：**不进** `ANOMALY_STATUSES`）。

## 后果 / 边界

- **512 MiB 的 call 闸门抓不到 229 MiB 的探针**：P61 §0.6 的逐字探针在本档下以
  `ok` 收场（增量 228.9 MiB = P61 记录的 0.9999×）。任何会触发闸门的调用至少是
  229 MiB 的 **2.24×**。G3 判据「抛异常」与「增量 0.5–2×」两半**不能同时成立**，
  见 P93 §7.7-①：需要 nanobot 在「降常量」与「放宽带」之间拍板，本档**不动常量**。
- 只覆盖 submit 预检一条调用路径；无事件保留策略。
