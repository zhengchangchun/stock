# ADR-005 实验决策的幂等键取语义不取呈现

日期：2026-09-15 ｜ 状态：已采纳 ｜ 前置：ADR-001（评审决策，append-only 台账）

## 背景

`experiment_decisions`（P8 Task 43）的幂等键原本是
`(variant_id, split, metric, metric_version, report_sha256)`，其中
`report_sha256 = sha256(json.dumps(report_dict, ensure_ascii=False, sort_keys=True))`
—— 哈希的是**整份报告字典**。

代码注释写的是「幂等键含 `report_sha256`（**覆盖全部闸门数字**）」：
**意图**是「键覆盖数字」，**实现**是「键覆盖一切」。两者不等价，而差别落在
**面向人的文本**上：报告里的原因串、措辞、排版全在哈希里。

后果**已经实际发生**（ERROR_DIARY #16 → #17）：修 `sigma-vol-z` 报告里一句谎报
`gate=WIN` 的文案 → 报告文本变 → 哈希变 → 被当成「新决策」→ `inserted: 4`，
该变体台账从 4 行涨到 8 行，全表 16 → 20 行。**闸门数字逐位未动，diff 只有第 23 行**。

危害不是「多几行」：append-only 台账是**决策条数的账本**。按行数统计决策数会**高估**，
同一次实验看起来被「判了两次」；而触发条件极日常 —— **任何文案修正**（包括修 bug 本身）
都会踩到。若不管，下一次没人敢改报告里的一句话。

## 备选方案

1. **键含 `report_sha256`（原状）** — 优点：实现最省事，报告文件与决策行一一对应。
   缺点：把「呈现」当身份，措辞即身份 → 污染台账（已发生）。
2. **键只留 `(variant_id, split, metric, metric_version)`** — 优点：最简单。
   缺点：**键太窄**。同一变体同一段跑两次不同区间/参数，split 名相同 → 被误判成同一条决策，
   新结论**静默吞掉**。这比多行危险得多（丢证据 vs 多几条）。
3. **键取语义**：`(variant_id, split, metric, metric_version, gate_status, delta, ci_low, ci_high)`
   —— 优点：身份 = 决策内容本身；改标点不改身份，改数字必是新决策。
   缺点：DDL 的 `UNIQUE` 与代码键同源，须一起改；老库的约束无法原地改（见「兼容处理」）。

## 决策

**取方案 3：幂等键取语义（决策内容），不取呈现（报告文本）。**

1. `IDEMPOTENCY_KEY = (variant_id, split, metric, metric_version, gate_status, delta, ci_low, ci_high)`。
   措辞 / 时间戳 / 排版 / `report_sha256` 一律不进键。
2. **`report_sha256` 仍在表里**，照写、照可查（审计要它指回报告文件），只是不参与身份判定。
   CLI 不变。
3. **命中键后的比较集 = 键 + `decision`（整场 verdict），排除 `report_sha256`。**
   `decision` 不在键里但属决策内容：它由 `selection_split` / `test_evaluated` 这类开关决定，
   开关不进键 → 「数字全同而 verdict 不同」是可能的，那是**矛盾**（结论来源不同），
   仍旧抛 `DecisionConflict`，不覆盖、不静默 —— 错误路径不因换键而变成死代码。
4. **空值比较用 `IS` 而非 `=`。** `delta` / CI 可为 `NULL`（`INSUFFICIENT` 段无 CI），
   而 SQLite 里 `NULL = NULL` 为假 → 用 `=` 会让「同一条决策」查不到而重复插入。
   键从「必含 sha」改宽后才暴露这个坑（以前 sha 非空，能兜住）。
5. 文档/注释里**不再用「覆盖 X」描述覆盖面更广的机制**（#17 的误述就出在这）。
   键能做什么，直接列字段。

## 兼容处理（20 行历史一行不动）

- **append-only 优先于口径统一**：不回删、不改写、**不加**「已作废」标记字段
  （加字段本身是口径变更，且会让老行含义不完整）。
- **老库不迁移**：SQLite 改 `UNIQUE` 需重建表 = 改写历史，正是本 ADR 要避免的操作。
  既有库里那 4 行同语义重复 = **新键生效前的历史遗留**，在
  `docs/experiments/README.md` 与 `schema.sql` 注释里**显式记账**。
- **新库（含测试临时库）**从 `schema.sql` 建表，直接拿到语义键约束。
- 自证：改键后重跑 `sigma-vol-z` → `inserted: 0, identical: 4`，台账仍 **20 行**，
  闸门数字与上一轮逐位一致（详见 `docs/plans/2026-09-15-p9b-幂等键取语义.md` §6）。

## 后果

**好处**

- 改一个标点不再产生新决策行：报告文案可以放心修，台账不再被措辞刷行。
- 台账行数 ≈ 不同决策的条数（同语义多行只剩历史遗留那 4 行）。
- 键变宽反而**暴露并修掉**了 NULL 比较的隐患。

**代价与后续注意**

- **代价：失去了「决策行 ↔ 报告文件 sha」的直接对应**。同一决策的第二份报告
  （措辞不同）不会留下新行，也就不会记录「后来又出了一版报告」。
  这是**有意的**：那一版报告是同一决策的另一种呈现，不是新决策。
  真要追报告版本，去看 `reports/` 目录本身与 git 历史。
- 既有那 4 行重复**永远留着**：任何按行数统计决策的查询都要先按语义去重，
  或显式排除 `report_sha256='a192a6d6…'`（老键那批）。已在 experiments README 写明。
- 改键属**口径变更**：老库不迁移 → 新老库在同一份代码下行为**一致**
  （都是先按语义键查、命中即 identical），差异只在 DDL 的兜底约束强弱。

## 自查法（写进 ERROR_DIARY #17）

> 问一句：**「只改一个标点，这条记录会变吗？」** 会变 → 键取宽了。
