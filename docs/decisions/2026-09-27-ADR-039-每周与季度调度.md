# ADR-039 每周全量扫描与季度深度复盘的口径与时刻表（P89）

- 日期：2026-09-27 ｜ 状态：已采纳
- 上游：`docs/tasks/2026-09-27-p89-每周与季度调度.md`（D1–D12）、
  07 需求任务 3 / 任务 4、`docs/plans/2026-09-26-需求对照全量审计.md` §2 B3/B4、
  ADR-020（调度载体 = 系统 launchd）

## 背景

07 需求把定时任务分四层。P89 之前只有三层落地：巡检（`com.stocklab.patrol`）、
每日收盘（`com.stocklab.close`）、月度刷新（`com.stocklab.monthly`）。
缺的两层是**每周全量扫描**（B3，`candidate run --run-kind weekly` 早已存在但没有
plist、没有链）与**季度深度复盘**（B4，完全未开工）。

## 决定

### 1. 本档是**编排 + 汇总**，不是新业务逻辑

两条链**只能**调用已有 CLI 命令（`ops/chain.py` 里的 `Step` 是一条 argv）。
唯一的例外是「汇总报告」那一步：它是本档新增的**渲染**（`ops/window_report.py`），
**不读库、不算数**，只把各步的 stdout/stderr 尾部与 `m2 report` 的读数 JSON 摆成
一份 Markdown。所以「报告里的数与链里的数不一致」在结构上不可能。

### 2. `asof` = **最近已收盘交易日**（与 `ops close` 刻意不同）

| 链 | asof | 理由 |
|---|---|---|
| `close` | 运行当天 | 它负责把当天数据落地 |
| `weekly` / `quarterly` | **最近已收盘交易日** | 它们是**读**某一天的数据做汇总；运行当天可能休市（10-05 恰好是周一、国庆） |

取法**复用** `verify.pending.latest_closed_session`（`patrol.check_db` 用的同一个
函数，不是同一套规则的两次实现）。**取不到 ⇒ 整轮拒绝**（exit 2、`steps=[]`）：
猜一个日期会得到一份**看起来正常的空报告**，而且不报错。

### 3. 两条链都**不做**非交易日跳过

与 `ops monthly` 同构（维护/汇总活、全幂等）。休市周跑出来的是与上周同样的读数
—— 无害、可复核；跳过反而会「连续两周没扫」，而每周扫描正是「新增合格标的、
剔除失效标的」的节拍。

### 4. 步骤表（顺序 = 依赖顺序）

`WEEKLY_STEPS` = `candidate run --run-kind weekly` → `candidate review`（**非阻断**）
→ `m2 report` → `m2 lifecycle due` → `plugin list` → 汇总报告。

`QUARTERLY_STEPS` = `ingest financials` → `candidate run --run-kind quarterly`
→ `m2 report` → `m2 lifecycle due` → `m2 attribute scan`（**非阻断**）→ `plugin list`
→ `portfolio show`（**非阻断**）→ 汇总报告。

**本档刻意不做**（D7，都不是遗漏）：① 自动开新验证周期（P87 留待用户拍板，
本档只出 `m2 lifecycle due` 清单）；② 全量 `plugin sandbox` 跑批（一次一个
`script_id`、离线回放，很贵且是人工判断）⇒ 报告只列 active 版本并标注
「**待人工决定是否跑 `plugin sandbox`**」；③ 集中度打分 ⇒ 只出 `portfolio show`
**原始读数**（07 任务4 item4 的答复），自创风控算法须另立任务书。

### 5. 时刻表（**四层两两不同分钟**）

`quarterly` 07:00（5/1、9/1、11/1）／`monthly` 08:00（每月 1 日）／
`patrol` 09:00–14:30（工作日，每 30 分钟）／`close` 15:30（工作日）／
`weekly` 16:30（周一）。

日期取**法定披露截止日的次日**：4/30（年报+一季报）、8/31（中报）、10/31（三季报）。

⚠️ **与任务书 D4 的偏离**：D4 写的是 `quarterly` **09:00**，但它与 `patrol` 的
09:00 槽**真的撞点**（`patrol` 覆盖工作日 09:00–14:30，而季度 entry 不含
`Weekday` ⇒ 每天都命中；2026-05-01 正是周五）。两条链同分钟起跑会同时写同一个
SQLite 库 ⇒ `database is locked` 会把链判成 exit 2（P42 的教训）。所以挪到 **07:00**：
距 `monthly` 的 08:00 仍是 1 小时（与 D4 给 09:00 的理由一致），距 `patrol` 两小时。
**日期不动**。详见任务书 §7 偏离表第 2 条。

### 6. 07 约束 1（串行优先级）的落地方式：**没有队列**

launchd **没有**优先级队列（D-7 已修正过的认知）。落地方式是
「**时间不重叠 + 各自幂等**」，不是排队。两个任务若真同分钟起跑，launchd 不会让谁等谁。
护栏是 `tests/test_ops_close.py::test_no_two_jobs_fire_at_the_same_moment`
（缺 `Weekday` 的 entry 展开成 7 天，**保守**）—— 加任务时撞点当场红。
**任何报告都不许声称有队列。**

## 后果

- `JOBS` 从 3 条变 5 条；`/lab/ops` 页面按 `JOBS` 渲染，不写死条数（D10）；
- 两条链的退出码与既有链同构（0 / 1 / 2），事后体检 `missing`/`stale` 同样判 1；
- `CLOSE_STEPS` / `MONTHLY_STEPS` 逐字节不变；`patrol.py` / `runner.py` /
  `journal.py` / `session/` / `predict/` / `paper/` / `m2/` / `candidate/` /
  `data/` 零改动；
- 站**不执行** `ops schedule install`（改本机 `~/Library/LaunchAgents` 由 nanobot 做）。
