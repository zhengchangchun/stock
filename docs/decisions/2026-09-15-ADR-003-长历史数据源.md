- 关联：`docs/plans/2026-09-14-phase1-4-implementation.md` Task 12（阻塞项 B2）

## 背景

评审把「长历史数据源」列为阻塞项 **B2**：P4 的 walk-forward 需要足够长的样本外窗口，
而 ADR-001 §1 与 P2 上半轮实测**互相矛盾** ——

| 来源 | 记录 | 请求 |
|---|---|---|
| ADR-001 §1 | 801 根 | `fqkline ...,900,qfq`？口径未记全 |
| P2 上半（`docs/tasks/2026-09-14-p2-上半…` §4.1） | 641 根 | `fqkline ...,900,qfq` / `,801,qfq` |

数字对不上，且都不足以判断「到底能回溯多久、受什么限制」。**这个数字直接决定
walk-forward 是否可行**，所以必须先实测定位限制来源，再决定方案。

## 实测（2026-09-15，探针原始输出见 evidence JSON）

### 1. 限制来自 `adj`（复权方式），不是日期

扫 count 旋钮（标的 `sz000333`，不复权 = `adj` 为空）：

| 请求 count | `adj=none`（不复权） | `adj=qfq`（前复权） |
|---|---|---|
| 320 | 320 根 | 320 根 |
| 640 | 640 根 | — |
| 800 | **800 根** | **800 根** |
| 801 | **801 根** ✅ | 640 根 ⚠️ |
| 900 | **900 根** ✅ | 640 根 ⚠️ |
| 1200 | **1200 根** ✅ | — |
| 2000 | **2000 根** ✅ | **640 根** ⚠️ |
| 2500 | `{"msg":"param error"}` ❌ | 同左 ❌ |

**结论：**
- **不复权序列**：单次上限 **2000 根**；>2000 服务端直接报 `param error`。
- **qfq 序列**：单次上限 **800 根**；**801~2000 之间服务端不报错，而是静默降级回 640 根**。
  ADR-001 的「801 根」与上半轮的「641 根」由此解释清楚 —— 前者是 **bfq** 口径，
  后者是 **qfq 静默降级**的结果。**两者都不是「腾讯只给这么多历史」。**
- 这条静默降级本身就是坑：请求 900 根 qfq 拿到 640 根，**没有任何错误信号**，
  调用方若不核对 `len(bars)` 就会把「缺了 260 天」当成完整数据。→ 见「后果」的强制校验。

### 2. 用 `end` 锚点向后翻页 → 可取到**上市首日**

URL 形态 `param={code},day,{beg},{end},{count},{adj}`。实测 **`beg` 被服务端忽略**，
`end` 生效：接口返回「end 往前数 count 根」。

| 标的 | 首页 | 翻页后累计 | 覆盖区间 | 终点 |
|---|---|---|---|---|
| `sz000333` 美的集团 | 2000 根 | **3095 根** / 3 页 | 2013-09-18 ~ 2026-09-14 | 第 3 页返回 0 根 |
| `sh600000` 浦发银行 | 2000 根 | **6388 根** / 5 页 | **1999-11-10** ~ 2026-09-14 | 第 5 页返回 0 根 |

两个终点都恰好等于**上市首日**（000333 于 2013-09-18 由美的电器重组上市；
600000 于 1999-11-10 上市），说明这不是人为截断，而是数据源的真实边界。

### 3. 东财：本环境**完全不可用**

三种 URL 变体（`beg=0`、`beg=19900101`、带/不带 `ut` 参数；`push2his` 与 `push2` 两个域）
**全部** `RemoteDisconnected`（TCP 层被对端直接关闭，DNS 正常解析到 `61.129.129.199`）。
与 ADR-001 §1「返回空响应/限流」的记录一致，本次为**复现**而非新问题。
→ **东财在 v1 只能作为「将来可能可用」的备选，不进入任何自动路径。**

## 备选方案对比

| 方案 | 全量历史 | 成本 | 结论 |
|---|---|---|---|
| A. 腾讯 `fqkline` 不复权 + `end` 翻页 | ✅ 至上市首日 | 3095 根 = 3 次请求；6388 根 = 5 次 | **采用** |
| B. 腾讯 `fqkline` qfq 单次 | ❌ 上限 800 根（≈3.3 年） | 1 次请求 | 否决：且 qfq 是**用最新因子重算的序列**，非 PIT，本就不可作为 `bars_raw` 输入（ADR-001 D-01） |
| C. 东财 `kline/get?beg=…` | 未知 | — | 否决：本环境不可达，无法验证 |
| D. 降低 walk-forward 验收标准 | — | — | 否决：方案 A 已够用，无正当理由降标准 |

## 决策

**采用方案 A**：日K 主源 = 腾讯 `fqkline` **不复权**序列，以 `end` 锚点向后翻页，
`count=2000`/页，翻到返回空为止。

1. `tencent.kline_url(code, count, adj, beg="", end="")` 增加 `end` 参数（默认空 = 兼容旧行为），
   新增常量 `MAX_COUNT = 2000`。
2. 抓取层默认仍然 `adj=""`（不复权）—— 与铁律①一致，**分页与复权无关**。
3. qfq 维持原用途：**只取除权事件 / 交叉校验**，且单次 count 不得超过 800。

## 后果

**收益**：B2 解除。walk-forward 不再受数据长度限制 ——
000333 有 **3095 个交易日**（≈12.7 年）、600000 有 **6388 个交易日**（≈26.3 年）可用，
远超「样本量门槛 120 个交易日」（度量纪律 3），足够做多折滚动训练/验证窗。

**代价 / 必须遵守的事项**：

1. **单次 qfq 请求不得超过 800 根**，且**任何翻页抓取都必须校验返回条数**：
   `len(bars) == count` 不成立时（除最后一页）必须留痕报错，否则会把静默降级
   当成完整历史（本次实测就复现了 900→640 的静默降级）。
2. 翻页需 3~5 次请求/标的 → 采集耗时与限流压力上升（`min_interval=0.35s`，
   单标的约 1~2 秒；20 标的约 30 秒）。属可接受范围。
3. `end` 翻页依赖「返回页首日」计算下个锚点，**必须处理「首日与前页重复」**
   （表示已到尽头），否则会死循环。`scripts/probe_history.py` 已实现该守卫。
4. 除权事件仍取自 **qfq 响应**（事件挂在 kline 行第 7 个元素上），
   因此仍需少量 qfq 请求（单次 ≤800 根）—— 与铁律①不冲突：
   **qfq 价格不落库，只取事件**。

## 复现方式

```bash
.venv/bin/python scripts/probe_history.py            # 全量（~9s）
.venv/bin/python scripts/probe_history.py --quick    # 只跑关键项
```
原始响应同时落 `data/raw_cache/tencent/probe_*`，含 URL / SHA256 / 耗时，可离线复核。
