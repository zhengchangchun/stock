# ADR-037：策略生命周期派生口径（连续优化失败次数 / 冻结到期时间，P87）

- 日期：2026-09-27（P87 站点实施）
- 状态：已实施
- 相关：ADR-016（派生指标不落库）、ADR-021（模块2 状态枚举与主干常量）、
  ADR-023（模块2 绩效指标口径）、ADR-024（D-34/D-36 决策空间）、
  D-1 / D-24（归档是人工闸门）、D-31（判据原文）、D-44（三分支规则表）
- 任务书：`docs/tasks/2026-09-27-p87-策略生命周期闭环.md`
- 需求来源：`00_系统总概.md` §全局硬性约束 6 / `06_核心数据字典摘要.md` §D-6 /
  `07_定时任务调度需求.md` 任务4-2

## 背景

需求两处点名要两个字段：

- 00 §全局硬性约束 6：「**同一策略版本连续 3 次优化验证失败，强制归档，不再迭代。**」
  ＋ 06 §D-6 要求「策略评估记录」加 `连续优化失败次数`（≥3 ⇒ 强制归档）；
- 06 §D-6 还要求加 `冻结到期时间`（冻结 ≤ 90 天，到期强制重评）；07 任务4-2 进一步要
  「冻结到期，**强制开启新一轮 2~3 轮验证周期**」。

审计（`docs/plans/2026-09-26-需求对照全量审计.md` 的 B1/B2）给出的初稿动作是
「`validation_cycles` 前滚加只增列」。**现场核对后否证**：`validation_cycles` 挂着
append-only 触发器（`schema.sql` 的 `trg_validation_cycles_no_update` / `_no_delete`），
一个「累计失败次数」列**根本没法维护** —— 每次判定都要改写那一行，而改写会被
`RAISE(ABORT)` 拒。加列不是「少做一步」，是**做不成**。

## 决定一：两个数**派生**，不落库（零结构变更）

`连续优化失败次数` 与 `冻结到期时间` 一律从 append-only 的既有台账
`m2_judgements` fold 出来。真源只有三个：

| 数 | 真源 |
|---|---|
| 连续失败次数 | `branch` 的**尾部连续**（`optimize` 计一次、`freeze`/`tune` 停、`insufficient` 穿透） |
| 冻结到期时间 | 最新一条 `branch='freeze'` 的 `asof_date` ＋ 该行 `evidence_json.freeze_days` |
| 已到点判据 | `due <= asof` |

**为什么派生比落库好**（不只是「妥协」）：

1. **不可能漂**：落库的计数列一旦某次判定写漏了就永久错了，而派生每次现算，
   与台账逐行一致是**定义上**成立的（没有第二份数据可漂）。
2. **口径可回放**：改口径（比如以后把 `insufficient` 改成归零）只改一处代码，
   **不涉及任何数据重写** —— append-only 的台账一个字不用动。
3. **与既有纪律同款**：`financial_reports` 的派生指标就不落库（ADR-016）。

**需求里那句「加字段」按「有可核对的读出口」满足** —— 这是本站对原文的**唯一**
解释性让步，理由与代价都写在上面。

## 决定二：口径（D2 / D3 / D4）

**连续优化失败次数**（从该 `script_id` **最新**一条判定往回数）：

| 分支 | 计数行为 | 为什么 |
|---|---|---|
| `optimize` | **计一次失败** | 声明要改逻辑、且读数不达标 —— 这一版没成 |
| `freeze` | **归零并停止** | 冻结是「停用该版本」，不是「又失败一次」；重评后的历史不该接在旧连胜上 |
| `tune` | **归零并停止** | 同版本换了参数集 ⇒ 上一版的故事到此为止 |
| `insufficient` | **穿透**（跳过继续往回看） | 它只表示**读数不足**，不是「这一版失败了」 |

D3 的逐字例：`[freeze, optimize, insufficient, optimize]` ⇒ **2**。

**冻结到期日**：取该 `script_id` 最新一条 `branch='freeze'`（`asof_date <= asof`）的
判定，`due = asof_date + freeze_days` 天（**自然日**）。该行没有 `freeze_days`
（或为 `null`）⇒ 无到期日，读出口给 `null` —— **不是** 0、不是空串：
「没有到期日」与「今天到期」是两件事。`due <= asof` 即「已到点」（**相等也算**）。

## 决定三：触发行为**只提示、不执行**（D6）

`fail_streak >= STRATEGY_FAIL_STREAK_LIMIT(=3)` ⇒ `judge()` 的
`evidence.lifecycle.force_archive = true` ＋ 一句 `archive_reason`（带 streak 与阈值
原文），并往 `actions` **追加一句**归档建议。三件事一个字不改：

- `branch` 的**取值域**（`schema.sql` 的 CHECK 与 `m2/config.BRANCHES`）——`archive`
  **不是**新分支，`accept` 它的读法只有 `evidence.lifecycle.force_archive`；
- `conclusion` 仍按 D-44 原规则算；
- **不自动归档** —— 归档仍走人工 `plugin approve`（D-1 / D-24）。

**为什么不自动**：归档是策略版本的**不可逆状态**（`plugin_scripts` 的状态迁移）。
把「连续失败 3 次」直接接到一个不可逆写动作上，等于让一个统计量单独拥有执行权；
而 D-44 的整条纪律就是「判定与执行物理分开」。要真强制归档，得另开一站并**用户拍板**。

## 决定四：读出口是两条只读命令（D7）

- `m2 lifecycle show --script <id> [--asof <day>]` ⇒ `fail_streak` / `limit` /
  `force_archive` / `tail` / `freeze_due` / `overdue` / `archive_reason` / `note`；
- `m2 lifecycle due [--asof <day>]` ⇒「到期或已过期的冻结版本」清单（按 `script_id`
  去重、取各自**最新**一条冻结、按到期日升序、带「过期了几天」）。

两条命令**只读、零写入、零联网**，并且**不调 `ensure_schema`**：它们用
`file:<绝对路径>?mode=ro` 打开（走 `_m2_conn` 会先前滚 schema —— 那是一次写库，
还会把「库不存在」变成「库被建出来」）。`PIT` 守卫写在**唯一取数点**
（`lifecycle.judgement_tail` 的 `asof_date <= asof`），不是写在注释里。

## 沉没成本与已知代价

- 判定台账的 `script_id` 是**判定行自己带的**（不是 JOIN `validation_cycles` 来的）：
  这让读出口不依赖周期表，代价是若某天写入方把 `script_id` 写错，读出口会跟着错
  （这一层的守门在 `judge()` —— 它从周期行取 `script_id`，见 `cycle.py`）。
- `due_freezes` 只按「**最新一条冻结**」判定是否有效：一个 script 冻结后被 `tune`
  （同 script_id）解冻，历史冻结行仍留着但不会被列出（因为不是最新那条）。
  「解冻」这件事当前**没有单独的事件行**，所以「最新冻结是不是还有效」只能靠
  「它是不是最后一条判定」近似 —— 本站在这里是**近似**，如实记下。
- `freeze_days` 用**自然日**而不是交易日：真源写的是「冻结 ≤ 90 天」，07 任务4-2 说
  「到期」。若要改成交易日对齐，只改 `lifecycle._add_days` 一处（派生口径，
  不涉及数据重写）。**本站不做。**
- 「连续 3 次失败 → 强制归档」目前**只是提示**；07 任务4-2 的「到期强制开启新一轮
  验证周期」（自动建 cycle）也**没有**做 —— `due` 只给清单。两者都需要动写入口，
  留待后续站点（审计 §6 排期 B3/B4）并需用户拍板。
