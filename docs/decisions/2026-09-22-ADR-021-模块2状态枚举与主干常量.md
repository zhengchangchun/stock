# ADR-021：模块2 主干 —— 状态枚举扩展与主干常量单一真源

- 日期：2026-09-22
- 状态：已采纳（P44 落地）
- 上游：`docs/plans/2026-09-22-模块2-需求书.md` D-27 / D-28 / D-29；`stock/05_边界_风险_约束文档.md` §业务边界 3
- 关联：ADR-001（append-only）、ADR-005（键取语义不取呈现）、ADR-015（写库入口自动前滚 schema）
- 实现：`stocklab/plugin/lifecycle.py`、`stocklab/plugin/store.py`、`stocklab/config/limits.py`、`stocklab/store/{schema.sql,migrate.py,validation.py}`

## 背景

模块2 要在「模块1 候选池」之上跑验证周期与自评估，需要三样主干地基：

1. 插桩策略版本除了主干 5 态（`draft/pending_review/rejected/active/archived`），
   还要能表达「正在验证」与「已冻结」；
2. 熔断阈值与自评估边界必须是**AI 改不了**的硬约束（05 §业务边界 3）；
3. 每一轮验证用了哪个策略版本、哪组参数、判据原文是什么，要能**永久追溯**。

## 决策

### 1. 状态枚举扩到 7 态，未知事件一律拒绝

在既有事件流折叠里新增两态与 4 个事件：

| 事件 | 状态迁移 | 合法前置状态 |
|---|---|---|
| `start_validation` | → `validating` | `active` |
| `finish_validation` | → `active` | `validating` |
| `freeze` | → `frozen` | `active` / `validating` |
| `unfreeze` | → `active` | `frozen` |

**主干 5 态与 `approve` 闸门一个字节不改**；「已回滚」仍不设独立态（回滚 = 对
`archived` 版本 `approve`，D-3/D-29）。`plugin_scripts` 仍然没有 status 列。

折叠遇到白名单外的事件**抛错而不是跳过**：跳过会让折叠出的状态与事件流不一致，
而下游看到的仍是一个**合法状态**，没有任何一层会报警。三层防御：
① `store.ALLOWED_ACTIONS`（写入侧点名报错）→ ② `apply_event`（折叠侧拒绝）
→ ③ `schema.sql` 的 CHECK（绕过接口也写不进去）。①②之间由
`test_action_whitelist_matches_schema_check` 钉住与 ③ 逐字一致。

### 2. 主干常量集中 `stocklab/config/limits.py`，越界拒绝不 clamp

`CIRCUIT_BREAKER_DRAWDOWN=0.10`、`VALIDATION_ROUNDS_MIN/MAX=2/3`、
`VALIDATION_MAX_DAYS=30`、`FREEZE_MAX_DAYS=90`（D-27/D-28）。
`check_validation_plan` / `check_freeze_days` 越界抛 `PlanOutOfBounds`，
**不返回值、不改参数** —— clamp 会把「不合规方案」悄悄变成合规方案，实验因此无法归因。

### 3. 三条结构保证由源码扫描测试钉住，而不是靠注释纪律

`tests/test_p44_constants_guard.py`（AST 扫描，不用子串匹配）：

| 保证 | 判据 |
|---|---|
| 单一真源 | 这 5 个名字在 `stocklab/` 内**只被绑定一次**（`config/limits.py`） |
| 无外部覆盖路径 | 全仓无 `setattr`/`__setattr__` 触达这些常量 |
| 无 Web 写入口 | `labweb/` 里**零引用**（只读配置视图是 P49 / D-32） |

三条各配一条**反向自检**（喂违规样本必须判红）+ 一条「扫描非空」自检 ——
否则「扫描零个文件」也会全绿（ERROR_DIARY #50）。

### 4. 台账三表 append-only，方案越界进不了库

`validation_cycles` / `validation_rounds` / `validation_events`，各带
`RAISE(ABORT)` 的 UPDATE/DELETE 触发器。`insert_cycle` 在写库**前**调
`check_validation_plan`（越界不落库）；`validation_events` 把触发时的
`at_value`（实测）与 `threshold`（判据阈值）**分列** —— 只留一个数读者无法判断
是否越界。前滚走 `ensure_schema` 单一入口（ADR-015），并登记进
`_KNOWN_MARKERS` 让 doctor 看得见（ERROR_DIARY #41）。

**`plugin_audit` 的 CHECK 放宽必须写显式迁移**：`CREATE TABLE IF NOT EXISTS`
改不了已存在表的形状（ERROR_DIARY #22）。`migrate_p44_plugin_audit_events`
照 P37 的先例重建审计链：单事务 + 逐行搬运 + 内容逐行校验 + 重造触发器与索引。

## 备选方案与为什么不选

| 备选 | 否决理由 |
|---|---|
| 给 `plugin_scripts` 加 status 列 | 与既有设计冲突（设计文档 §5.7）：可 UPDATE 的 status 会抹掉「谁在什么时候批的」，且 §2 明令不改 |
| 常量散落在各自模块 | 无法机械证明「AI 改不了」；本项目已有 `DEFAULT_UNIVERSE` vs `SEED_UNIVERSE` 两个真源并存的教训（ERROR_DIARY #47） |
| 越界时 clamp 到边界 | D-28 明文禁止；clamp 让实验不可归因 |
| 未知事件静默忽略 | 状态与事件流静默不一致，无人察觉（同 `invalidated` 布尔列装不下「判不了」家族） |
| `validation_events` 只存一个数值 | 实测值与阈值混成一个数，读者无法判断是否越界 |

## 后果

- **好的**：状态语义完整、常量不可被 AI 覆盖（有机械证据）、台账可追溯且不可改写；
  主干链与 `approve` 闸门行为不变（既有 2313 条测试全绿）。
- **代价**：`plugin_audit` 需要一次重建式前滚（本项目第二次重写 append-only 表，
  与 P37 并列）；真库尚未前滚，下次任一写库入口会自动触发（见下）。
- **扫描范围限制**：常量扫描只覆盖 `stocklab/`，**不覆盖** `scripts/` 与文档 ——
  那里的数字仍可能被写死（见「未验证口子」）。

## 未验证口子 / 留待后续（A7 点名）

1. **`active_script_id` 只认 `active`**：脚本进入 `validating` 后不再被解析为
   在役版本。P44 **没有任何生产调用者**触发这些事件（只有测试），主干链因此不受影响。
   「验证期算不算在役」留给 **P48** 显式决策；本轮用
   `test_validating_version_is_not_resolved_as_active` 把当前行为钉住，
   将来要改就是一次必须留痕的决策。
2. **常量扫描不覆盖 `scripts/` 与 `docs/`**：若有人在脚本里写死 `0.10`，
   本轮的扫描看不见。
3. **真库尚未前滚**：实测 `pending = ['p44:plugin_audit.action']`、
   `schema_status.ok = False`。已在真库**副本**上验过前滚（25 行 → 25 行、
   触发器重建、新事件可写）；真库本身按 ADR-015 由下一次写库入口自动前滚。
