# 020. 调度载体改用系统（launchd）：项目只生成 plist、只留回执，页面负责展示

- 日期：2026-09-22
- 状态：已接受
- 触发：用户「**其实不需要 nanobot 定时任务，全部在系统里，到时候跑完页面会有展示**」
- 前置：`stock/07_定时任务调度需求.md`（05 行「调度载体：Nanobot 定时能力」）、
  ADR-001 D-05（项目内禁止 cron/守护进程）、ADR-019（判定与退出码搬进项目）、
  错误日记 #53（调度器 ok 与数据链 1 的口径没桥接）

## 背景

ADR-019 把**判定**搬进了项目（`stocklab ops patrol`），但**时钟**仍在 nanobot：
三条任务的正文是一句「跑 `ops patrol --fix`，非 0 就把 stderr 那行贴回来」，
由 nanobot 的 cron 每 30 分钟/每交易日叫醒。这留下三个具体代价：

1. **依赖一个不常驻的网关**：nanobot 网关不跑（升级、重启、没开），三条任务就静默不触发，
   而**没有任何地方会因此报警** —— 09-18 那次网关重置就是这么丢掉四条任务正文的（ADR-019 §背景）。
2. **结论只落在会话里**：agent 把结论说给用户听，说完就散了。想回看「上周三收盘链跑到第几步、
   哪一步 exit=1」，只能去翻聊天记录；nanobot 的任务状态又只回答「这一轮 agent 跑完没」（见 #53）。
3. **判定与调度跨两个版本库**：判据改一次，要同时改项目代码和 cron 正文（正文一改就换 id，
   旧 id 还要手动删）——两份事实源，迟早再次分叉（#53 的成因）。

同时，macOS 自带 launchd 本来就是用户级、登录即生效、不需要 root 的调度器，
`StartCalendarInterval` 表达「工作日 15:30」「每 30 分钟」绰绰有余。

## 备选方案

1. **保持现状（nanobot 当闹钟）**
   - 优点：零改动；能借用 nanobot 的语义能力（异常时用中文对话、自己决定补哪步）。
   - 缺点：三条代价如上；且「补哪步」这件事已经在 `ops patrol --fix` 里了，nanobot 并不需要懂。
2. **系统 launchd + 项目只生成 plist**（选中）
   - 优点：时钟由 OS 负责（不依赖任何常驻进程）；plist 是纯文本、由纯函数生成 ⇒ 可断言、可回看；
     结论落 `reports/ops/latest-*.json` ⇒ 页面能展示；项目里仍然**没有**调度器进程（D-05 不破）。
   - 缺点：强绑 macOS（本机就是 macOS）；launchd 没有 cron 表达式，得把「每 30 分钟」展开成
     65 条 `StartCalendarInterval`；**多一道系统级权限面**（见「后果」里的 TCC）。
3. **`crontab -e`**
   - 缺点：macOS 上 `cron` 需要给 `/usr/sbin/cron` 授「完全磁盘访问权限」才碰得到 `~/Documents`，
     权限面一样存在；且 `cron` 的日志默认进系统日志、没有「上次退出码」可查（`launchctl list` 有）。
4. **项目内常驻 scheduler**
   - 缺点：比 2 更重，且直接破 D-05，把研究型 CLI 项目变成服务。否（与 ADR-019 同）。

## 决策

方案 2。分工被切成三件事，每件只有一个责任人：

| 问题 | 谁回答 | 在哪 |
|---|---|---|
| **什么时候跑** | launchd | `~/Library/LaunchAgents/com.stocklab.{close,patrol,monthly}.plist` |
| **跑什么、什么顺序、什么算异常** | 项目 | `ops/chain.py`（收盘链 12 步）/ `ops/patrol.py`（7 项体检）/ `ops/runner.py`（停止线） |
| **跑了什么结果** | 项目 | `reports/ops/latest-*.json`（回执）＋ `job_runs`（全部作业共用）＋ `data/logs/*.log` |

实现落在 `stocklab/ops/schedule.py`，CLI 是 `stocklab ops schedule <action>`：

| action | 做什么 |
|---|---|
| `generate` | 只打印将要写入的 plist（**不碰文件系统**，纯函数） |
| `install` | 写 plist 到 `~/Library/LaunchAgents/` → （若已加载先 `bootout`）→ `launchctl bootstrap` |
| `uninstall` | `bootout` + 删 plist（没加载过也照删，仍算成功） |
| `status` | 三条任务 `plist_present` / `loaded` / `pid` / `last_exit_status` |
| `kickstart` | 立刻跑一次（安装后的自证；收盘链未收盘会**拒绝执行**，这是设计不是故障） |

三条任务的窗口与命令（顺序 = 页面/`status` 的展示顺序）：

| name | label | 窗口 | argv |
|---|---|---|---|
| `close` | `com.stocklab.close` | 每交易日 15:30 | `ops close` |
| `patrol` | `com.stocklab.patrol` | 工作日 09:00–15:00 每 30 分钟（65 条触发点） | `ops patrol --fix` |
| `monthly` | `com.stocklab.monthly` | 每月 1 日 08:00 | `ops monthly` |

五条边界写进代码：

1. **plist 由纯函数生成**（`render_plist()` 不读时钟、不碰文件系统）⇒ 测试直接断言内容，
   安装动作与 plist 内容可以分开验；`render_plist` 是唯一的格式权威。
2. **`RunAtLoad = False`**：登录/bootout 之后不该立刻跑一条收盘链 —— 今天可能还没收盘。
3. **日志路径显式给**（`data/logs/<name>.{out,err}.log`），且 `write_plist` 先建目录：
   否则 launchd 会静默丢掉输出，而「日志是空的」与「任务没跑」在页面上长得一样。
4. **不代跑 `launchctl`**：谁加载了、上次退出码几，唯一真源是 `launchctl list`；
   页面只把命令给出来，Web 线程里不许起系统命令。页面能答的是另一件事：plist 在不在、回执说了什么。
5. **错过就错过**：`StartCalendarInterval` 错过的触发点由 launchd 在唤醒后补跑一次（它自己合并）。
   这正确 —— 补跑的一轮是幂等的，而 `ops close` 的 asof 取「**运行当天**」，
   所以睡到 18:00 才醒也是写当天，不会因为晚了几小时就写错日期。

配套的展示面：新增 `/lab/ops`（导航「定时任务」，`GET /ops`），只读回执、
**一行 CSS 都不加**（复用 `render.py` 的壳与表格）。三条不可让步的展示纪律：

- 摘要行**逐字等于 launchd 日志里那一行**（同一个 `chain.summary_line` / `patrol.summary_line`），
  所以「页面上说 exit=1」与「日志里说 exit=1」是同一条读法；
- **没跑过 → 「还没有回执」（不写 0）；回执损坏 → 原文报出来（不退回旧数字）**；
- 「下一次触发」是**推算**（从 plist 的 `StartCalendarInterval`），页面明写它不是系统的承诺。

## 后果

- 好处一：**不依赖任何常驻进程**。网关重启、升级、忘开都不会让链路断掉；反过来，
  nanobot 里也不再需要那三条任务正文（正文一改就换 id、旧 id 要删的老问题随之消失）。
- 好处二：**结论可回看**。`reports/ops/latest-*.json` 是文件、`job_runs` 是表，
  页面把两者摆出来 ⇒ 「上周三跑到第几步」不再需要翻聊天记录（#53 的第二个成因被消掉）。
- 好处三：**调度与判定同库同版本**。跑什么只在 `ops/` 里定义一次，测试（`tests/test_ops_close.py` /
  `test_ops_patrol.py` / `test_labweb_ops.py`）钉住；nanobot 侧不再有任何业务知识。
- 代价一：**强绑 macOS**。换 Linux 要重写 `schedule.py` 的落地目录与 `launchctl` 调用
  （`render_plist` 与窗口定义是平台无关的，但 `LaunchAgents`/`launchctl bootstrap gui/$UID` 是）。
- 代价二：**多一道系统级权限面（TCC）**。项目在 `~/Documents/Workspace/stock` 下，
  而 macOS 把「文稿」列为受保护目录：**launchd 起的进程不继承终端已经拿到的那份授权**。
  2026-09-22 实测：`launchctl kickstart` 之后的进程卡在 Python 启动期的 `open()` 里，
  `log show` 的证据是
  `tccd … service=kTCCServiceSystemPolicyDocumentsFolder AUTHREQ_PROMPTING subject=…/python3.12`
  —— 也就是系统在等一个「Python 想访问『文稿』文件夹」的授权框，而 launchd 上下文里没人能点它。
  处置见 `docs/ops/2026-09-22-launchd-定时任务.md`：**要么让用户在框上点「允许」，
  要么给解释器（`/opt/homebrew/…/python3.12`）授「完全磁盘访问权限」**；
  在那之前 plist 已落盘但 `loaded=false`（`launchctl bootout` 已回退），
  **nanobot 的三条暂不撤** —— 否则会出现无人调度的窗口，且两边同时跑会撞 SQLite 写锁。
- 代价三：`ops close` 的**库里备份**步默认写 `data/backups/`，测试必须注入 `backup_dir`
  （conftest 的 `backup_dir_is_tmp` 已兜住，见错误日记 #55）。
- 未变：D-05 没有被破 —— 项目里**没有**常驻进程，它只生成一份文本文件并用系统命令注册；
  「何时跑」这件事实质上交给 OS（与「项目内实现 cron」是两件事，理由写在 §备选方案 4）。
