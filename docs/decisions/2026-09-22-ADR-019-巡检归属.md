# 019. 巡检归属：判定与退出码搬进项目（`ops patrol`），nanobot 只当闹钟

- 日期：2026-09-22
- 状态：已接受
- 触发：用户「巡检不应该是系统内部的么，为什么会挂在 nanobot 上，应该是项目自动的功能啊」
- 前置：`stock/07_定时任务调度需求.md`（04 行「调度载体：Nanobot 定时能力」）、
  ADR-001 D-05（项目内禁止 cron/守护进程）、D-7（07 的调度约束修正：自查前置产物 + 未就绪跳过）

## 背景

「每 30 分钟巡检」此前**没有项目内的实现**，它只存在于 nanobot cron 的任务正文里：7 项体检、
收盘链顺序、什么算异常、汇报格式、退出码怎么读，全是一段中文散文。项目侧只提供原子命令
（`session tick` / `predict run` / `verify pending` / `review daily` / `paper step`）。

这个分工是**有意为之**（07 指定 nanobot 当调度载体，D-05 禁止项目内常驻进程），但它把
「判定」留在了项目的版本库之外，实测付了两次代价：

1. **两个状态口径打架**（2026-09-22 10:02）：nanobot 的任务状态看「这一轮 agent 跑完没」→
   `ok`；项目命令的退出码是「数据链对不对」→ `1`。于是同一时刻，调度器说「一切正常」、
   巡检汇报说「数据链异常」——两句都不是假话，只是没人负责把它们对齐（见错误日记 #53）。
2. **知识不在版本库里**：任务正文丢了（09-18 网关重置丢过一次）只能从
   `docs/ops/cron-2026-09-21-待挂.md` 手抄回来，且**没有任何测试**钉住它。
   正文里的「为什么这一条要跑、缺了它哪一项会坏」全靠注释撑着。

## 备选方案

1. **保持现状**：判定继续留在 cron 正文
   - 优点：零改动，07 的字面要求不变。
   - 缺点：口径继续打架（调度器状态 ≠ 数据链状态）；判定无法被测试；换机器/丢任务就要手抄。
2. **把「巡检」做成项目内一条命令，cron 只负责按时启动 + 播报**（选中）
   - 优点：退出码语义由项目定义且**只有一处**；7 项判定与补步计划可被 pytest 钉住；
     cron 正文缩成一句，丢了也能从 `--help` 恢复；判定逻辑与它判断的命令同库同版本。
   - 缺点：多一个命令要维护；cron 正文改动会换 id，需要重挂。
3. **完全脱离 nanobot**：项目内挂 launchd / crontab
   - 优点：不依赖 nanobot。
   - 缺点：**破 D-05**（项目内不实现定时/守护进程）；丢掉 nanobot 的语义能力
     （异常时能用中文对话、能自己决定补哪步、统一管着 dream/heartbeat）。
4. **项目内做一个常驻 scheduler**
   - 缺点：比 3 更重，且把「研究型 CLI 项目」变成服务，直接否。

## 决策

方案 2。`stocklab ops patrol` = **体检（只读）+ 缺哪步补哪步 + 结论**，五条边界写进代码：

1. **体检只读**：连接走 `file:...?mode=ro`（结构保证，不是纪律）。
2. **补步走子进程、不改主干**：每条补步 = 一条**现成的** CLI 命令，逐字等于 cron 里原来那行；
   本模块不 import 业务函数、不重实现任何规则（07「主干固定不可修改」在这里是结构性的）。
3. **退出码由项目定义**：

   | 码 | 含义 |
   |---|---|
   | 0 | 7 项体检全绿（`ok` / `skipped`） |
   | 1 | 链路完整但有异常（有 `missing`/`stale` 项，或补步有一步非 0） |
   | 2 | **判不了或断链**（最新已收盘交易日判不出 / ④ 判不了 / 库不可读 / 补步致命或超时 / 拒绝跨库补步） |

4. **判不了就说判不了**：`latest_closed_session` 与 ④ 为 `None` 一律 2，不给 0（错误日记 #36）。
5. **`--fix` 不跨库**：采集类命令（`ingest *`）不接受 `--db`，固定写 `paths.DB_PATH`，
   所以计划里含这类步骤而 `--db` 指向别的库时**拒绝执行**——照跑只会让「另一个库看起来也有数据了」。

`unknown` 的待遇刻意分两种，理由写在 `verdict()` 里：④ 判不了 ⇒ 2（这是「不知道有没有缺口」）；
② 判不了（不知道今天是不是交易日）⇒ 不计异常（否则每个交易日都误报一次），但**仍然**去采一次。

## 后果

- 好处：调度器的 `ok`/`failed` 与数据链状态**不再需要人工对齐**——cron 正文只说「非 0 就把那行
  贴回来」；7 项判定进版本库、进测试（`tests/test_ops_patrol.py`，39 条）；补步计划是纯函数
  （`plan()` 不碰库、不读时钟），可直接断言「哪一项缺 → 排哪一步」。
- 代价一类：cron 正文一改就换 id（`cron add` 不复用旧 id），旧 id 要删掉避免重复跑；
  正文的权威副本仍是 `docs/ops/cron-2026-09-21-待挂.md`。
- 代价二类：`ops patrol --fix` 仍会发起联网采集（它调的就是原来那几条 `ingest` 命令）。
  这是**有意的**——它是「缺步补跑」，不是「只读看板」；只读的那一半是默认行为（不加 `--fix`）。
- 后续注意：⑤ 报告项依赖 `report_dir`（默认 `reports/`），测试必须显式传，否则会去读仓库里
  的真报告（错误日记 #51 的同类风险）。
- 未变：07 的四类任务仍然挂在 nanobot（调度载体没换），D-05 也没被破——本 ADR 只把**判定**搬回项目。
