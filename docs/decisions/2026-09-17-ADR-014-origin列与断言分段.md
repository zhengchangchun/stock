# ADR-014：`predictions.origin` 来源列与「断言 vs 推断」分段

日期：2026-09-17
状态：已采纳
任务：P32

## 背景

链路准确率（P26）把回放段与实时段分列，但「这条预测是回放还是实时」此前**没有可靠列**，
只能靠 `created_at` 前 10 位 == `asof_date` **推断**（P11 口径，ERROR_DIARY #16）。
P26 报告里明写「这是推断而非断言」，并建议给 `predictions` 增 `origin` 列。
P32 落地该建议：N3（用真实数据看准确率）的「实时段」从此可信可累积。

## 决策

1. `predictions` 增列 `origin TEXT CHECK (origin IN ('live','replay'))`，放在 `created_at`
   之后（与 `ALTER TABLE ADD COLUMN` 追加到表尾的列序一致）。
2. 来源由**写入路径**确定、入库即写：`predict run` 写 `live`，`verify backfill` 写 `replay`。
   `insert_prediction` 的 `origin` 是**必填**关键字参数（漏传 TypeError，不设默认值）。
3. `chain accuracy` 分段规则：有 `origin` 的行按字段**断言**；`origin IS NULL` 的历史行
   退回 `created_at[:10] == asof_date` 推断。报告里**显式分列**「断言 n 行 / 推断 n 行」
   （`origin_segmentation.asserted / inferred`），不许把两批混在一起当断言。
4. 迁移只 `ALTER TABLE ADD COLUMN`，**不回填**：老行 `origin` 一律 NULL。

## 为什么老行 origin 是 NULL 而不是回填

历史行的来源**只有推断**（created_at 判据），把推断结果回填成 `live`/`replay` 等于
「用猜测冒充事实」，违反项目「不许编造数据」铁律。NULL 的语义 = 「无来源标记，退回推断」，
是诚实且可审计的。CHECK 约束天然放行 NULL（`NULL IN (...)` 判 NULL 非 FALSE），所以
老行无需改任何数据就能共存。等真实运行期的新预测一条条带 `origin` 写进来，「实时段」
的断言行数才会开始累积 —— 这正是 N3 要的「可信可累积」。

## 为什么只动 `chain accuracy`、不动 P11 复盘

`session/review.py::load_rows` 的 `provenance` 仍走 `classify()` 推断，**一字不改**，
保证 P11 每日复盘与 `rolling_accuracy` 逐字节不变（本次验收实测 replay 段
0.3818 ± 0.0070 / Brier 0.6581 / range_80 81.69% 逐位不变）。断言 vs 推断的选择在
`chain/accuracy.py` 里做（`_provenance_of`），两个视图互不干扰。

## 边界（照实声明，不藏）

- `origin` 记录的是**写入路径**，不是「决策时刻」。当天用 `predict run` 补跑一个历史
  `asof`，会被断言成 `live` —— 与旧推断口径同源同边界，只是从「猜」变成「写路径说它是 live」。
- `origin IS NULL` 的行仍受推断口径的全部已知边界约束（`created_at` 是入库时刻）。

## 验证证据

- 真库副本迁移：`PRAGMA table_info` 含 origin；`count(*)` 迁移前后一致（6059）；
  `origin IS NULL` = 6059（全部老行）。
- 写入口：`predict run` → 新行 `origin='live'`；`verify backfill` → 新行 `origin='replay'`。
- 报告 before/after：四段计数、窗口、replay/live metrics 全叶子 0 差异；
  新增 `origin_segmentation {asserted: 0, inferred: 6057}`。
- 反证测试：篡改 origin（live↔replay）→ 分段翻转；抹掉 origin → 退回推断。
