# ADR-041 候选池标的状态事件表（P91 / B7）

- 日期：2026-09-27 ｜ 状态：已采纳
- 上游：`docs/tasks/2026-09-27-p91-候选池标的状态流转.md`（D1–D9）、
  `docs/plans/2026-09-26-需求对照全量审计.md` §2 B7、
  需求 `01` §候选池标的状态枚举 / `07` 任务1-6（「更新候选池标的状态」）、
  `stocklab/candidate/snapshot.py::STATUSES`、`stocklab/store/schema.sql`（append-only 触发器区）

## 背景

枚举与 `CHECK` **都在**，但**没有任何命令**能把某标的置成「已建仓 / 等待买点 /
逻辑证伪移出」：

```
$ grep -n "STATUSES" stocklab/candidate/snapshot.py
35:STATUSES: tuple[str, ...] = ("观察中", "等待买点", "已建仓", "逻辑证伪移出")
$ grep -rn "status=" stocklab/candidate/
snapshot.py:46:    status: str = "观察中"        # ← 唯一入口是 dataclass 默认值
```

`MemberRow.status` 恒为默认值，`candidate_members.status` 里永远只有 `观察中`
（真库 38 行全同）。**枚举写了四个，实际永远只有一个值** —— 与 ERROR_DIARY #83
（字段在、语义已死）同型。

## 决定

### 1. 状态是**事件**（新表 `candidate_status_events`），不是给 `candidate_members` 加列

三条理由（D1 原文）：

- `candidate_members` 挂在 `(asof, run_kind)` 的快照上，写它就**改写已封存的快照**；
- 状态变更的时刻与快照的 `asof` **无关**（人可以周三改、快照是上周的）；
- 本仓 append-only 纪律：变更一律「追加一行」，不 UPDATE。

表结构（`UNIQUE(code, asof_date, status)`、`CHECK` 四值、两条 append-only 触发器
`trg_cand_status_no_update` / `trg_cand_status_no_delete`）**逐字**落在
`store/schema.sql`，与 `candidate_members` 的既有约束**同源不重复**：
`CHECK` 枚举与 `snapshot.py::STATUSES` 的一致由**一条用例**钉住
（`tests/test_candidate_status.py::test_schema_enum_matches_snapshot_statuses`），
不靠人记 —— 两处漂移是这类「枚举在、语义死」最容易复发的地方。

`ensure_schema` 靠 `executescript` 跑整份 `schema.sql` ⇒ 建新表/触发器
**不需要**改 `store/migrate.py`（D7 明令禁改，实测确实不用改）。

### 2. PIT 锚 = `asof_date`（「该状态**从这一天起**生效」）

    status(code, D) = 事件里 asof_date <= D 且 (asof_date, event_id) 最大的那行
    无事件          ⇒ 观察中（与 MemberRow.status 的默认值逐位相同）

`asof_date` 优先于 `event_id`：新一天的事件赢过旧一天后写的。
**同日两条 ⇒ `event_id` 大者赢**（后写覆盖**读侧**，两行都在）——
这正是「写错了只能再追加一行」能成立的原因，也是**不给 delete/update 子命令**
的理由：append-only 的意义就是「写错了也能看见写过什么」。

读侧实现用窗口函数（`ROW_NUMBER() OVER (PARTITION BY code ORDER BY asof_date DESC,
event_id DESC)`，SQLite ≥ 3.25）：一次查完，页面**不做 N+1**。

### 3. 读侧与写入口**分家**：`candidate/status.py` 只读，写入口在 CLI

- `candidate/status.py`：三个纯读函数 `latest_status` / `status_map` / `history`，
  **没有也不许有** INSERT/UPDATE/DELETE（有一条 AST 用例按字面扫它）；
- `candidate status set`（`cli/candidate.py`）是唯一写入口：`--status` 走
  argparse `choices`（非法值 exit 2）、同 `(code, asof_date, status)` 已有行 ⇒
  打印 `already` + **exit 0 + 零写入**（可脚本重跑）、用法错误（`--code` 非 6 位 /
  `--asof` 非法 / `--reason`·`--actor` 空串）**必须先于 `ensure_schema`** 拒掉
  —— `ensure_schema` 是写库动作，用法错误在它之后才报会让「命令敲错了、
  库文件却多出来一个」。

读命令 `candidate status show` **不建库**（库不存在 ⇒ exit 2，与 `candidate
review` 同款）：读路径不该因为敲错一个库路径就凭空造出一个空库。
这一条 D3 没写死，取的是同文件内既有先例（`cmd_candidate_review`），记在此处备查。

### 4. `candidate run` 的快照状态取 overlay（只换一个字段）

`run_candidate` 在 `pools`/`scored` 之后的**组装**那一步用
`status_map(conn, [m.code for m in pipe.members], asof)` 覆写 `MemberRow.status`：
打分口径、`select_top` 的排序与截断**一字未动**（`dataclasses.replace` 只换
`status`）。无任何事件时给的就是 `DEFAULT_STATUS`（逐位等于 dataclass 默认值）
⇒ 既有 `test_candidate_run*.py` / `test_candidate_snapshot.py` **未改一行**仍全绿。

### 5. 页面：状态列取 overlay + 「状态变更」一节 + **零写入口**

- 各池「状态」列取 `as of 当前选中快照的 asof` 的 overlay，**不取**快照里那份
  （快照那份可能已过时 —— 这正是事件表的理由之一）；页面因此只认一个真相；
- 新增一节「状态变更」（`asof_date / code / 名称 / 状态 / 理由 / 记录人`，
  最近 10 条，空表给提示行）。它**在「一条快照都没有」的分支里也出现**：
  状态与快照无关，那正是刚跑完 `candidate status set` 的人会来看的页面；
- **页面零写入口**：状态只能从 CLI 追加。`POST /candidate/status` 与
  `POST /candidate/status/set` 落到路由的兜底 ⇒ **404**（无需改
  `labweb/app.py`，实测如此）。

### 6. **不做**：状态的自动推导与巡检（留给 P92 / B5）

从模拟盘持仓推 `已建仓`、从 m2 信号推 `等待买点`、30 分钟巡检调度 —— 都不在本档。
本档只出机制；**不许**为了让页面好看写死任何推导规则（那会造出第二个口径，
且它是「谁也不知道哪来的」那个）。

## 实测（真库零写入，全部在 `/tmp/p91/copy.db` 副本上）

- `set` 首次 ⇒ exit 0、表 1 行、`event_id=1`；同命令重跑 ⇒ exit 0、含 `already`、
  表**仍 1 行**（幂等零写入）；同日换状态（`已建仓`→`观察中`）⇒ exit 0、**2 行**，
  `show` 两行、第一行是 `观察中`；
- PIT：`latest_status(000333, 2026-09-23)` ⇒ `观察中`（09-24 的事件不泄漏），
  `(2026-09-24)` ⇒ `观察中`（后写赢），`000651` ⇒ `("观察中", None)`；
- `candidate run --run-kind weekly --asof 2026-09-24`（新键）⇒ rc=0，
  落库成员 `status` = overlay 值；把 `已建仓` 追加到 `asof=2026-09-25` 后
  换 `run_kind` 再跑 ⇒ 该 code 落库 `已建仓`；
- append-only 三连拒：`UPDATE` / `DELETE` / `INSERT OR REPLACE`（后者需
  `PRAGMA recursive_triggers=ON`，与 P48/P90 同型）全被 `RAISE(ABORT)` 拒，
  三连之后 `count(*)` 仍 = 原值；
- `scripts/check_redlines.py` 不 regen ⇒ 三目标逐位 == 基线；`data/stocklab.db`
  sha 跑前 == 跑后 == `0f8231f0…`。

## 影响

- `stocklab/store/schema.sql`：新表 + 索引 + 两条触发器（`migrate.py` 零改动）；
- 新增 `stocklab/candidate/status.py`（只读）；`candidate/run.py` 只改组装那一处；
- `stocklab/cli/candidate.py` + `cli/main.py`：新子命令 `candidate status set|show`；
- `stocklab/labweb/cand_data.py` / `cand_render.py`：overlay + 「状态变更」一节；
- 打分/分流/报告口径一字未动（`screen/score/risk_adjust/pools/report/snapshot.py`
  零改动），报告文案零变化（状态不进 candidate 报告，D9）；
- **未做**：自动推导状态、30 分钟巡检（B5/P92）；真库前滚建表由 nanobot 在 §8 做。
