# 0013. 已公告休市表（`market_holidays`）与「未来已知事实」的 PIT 纪律

- 日期：2026-09-17
- 状态：已接受
- 相关：ADR-001（B4 交易日历由已采集日线构建）、ADR-011（PIT 键钉死但不称 PIT-安全）

## 背景

`Calendar` 的语义是「**某个日期是不是已采集到的**交易日」—— 它由**已发生**的指数日线
日期集合构建（ADR-001 B4），本质是**回看**。因此 `predict.service.resolve_target_date`
在日历耗尽时（实测 `trading_calendar` 最晚 = `2026-09-16`）只能退化为**纯工作日外推**
（`weekday_fallback`）→ **节假日被当成交易日**。

后果是具体的、不是理论的：asof = 2026-09-24（周四）时，外推给出的 `target_date` 是
**2026-09-25** —— 而 9/25 是中秋休市日。次日验证器会去 9/25 找行情、找不到，
或者更糟：把 9/28 的行情当成 9/25 的（若验证器按「下一个有行情的日子」取数）。
`target_date` 一旦错，**后面所有验证与归因都建在一个错日期上**。

上交所**提前公告**了全年休市安排。问题是：**用这份公告算不算前视（PIT 违规）？**

## 备选方案

1. **继续用 `weekday_fallback`，什么都不做**
   - 优点：零风险、零新代码。
   - 缺点：每年长假前后必然算错 `target_date`（春节/国庆各错一周），
     而这恰恰是日历耗尽时最常见的场景。等于承认系统在最有价值的时候失准。
2. **把公告日期塞进 `trading_calendar`**
   - 优点：改动最小，`Calendar.load` 一处即可。
   - 缺点：**语义污染**。`trading_calendar` 代表「已采集到」，塞入未来日期后
     `Calendar.load` 会把它当成已发生的交易日 → 污染回测轴与 `predict` 的
     `session_check`（`日历 ∩ 行情轴`）。而且是**静默**污染，两条防线都拦不住。
   - 另一缺点：`INSERT OR IGNORE` 会把「已改期的旧值」静默留住（改期时新公告进不来）。
3. **另起一张表 `market_holidays`，只存「已公告的开/休市」，读取侧按覆盖判据使用**（采纳）
   - 优点：语义单一（前瞻 vs 回看分离）；改期靠「多行 + `published_at` 最新者胜出」
     表达，全程只有 INSERT，不碰 append-only 触发器，也不需要 UPDATE。
   - 缺点：多一张表、多一条采集链路、多一个「覆盖不到怎么办」的分支要如实处理。

## 决策

**采纳方案 3。并明确判定：使用交易所提前公告的休市安排，不构成 PIT 违规。**

理由是**它属于哪一类信息**：休市安排是交易所**提前公告的公开日历事实**，
不是价格、不是成交量、不是任何需要「等它发生」才能知道的东西。在预测时点（asof）
它**已经公开可得**，且描述的是**未来确定会发生的事**（哪几天不开市）。
用它在性质上等同于「用日历查 2026-10-01 是星期几」—— 提前知道未来某天不开市，
**不包含任何关于未来价格的信息**。

对照 ADR-011 的口径纪律：ADR-011 之所以**不称 PIT-安全**，是因为东财会**重算历史**
估值数据 —— 那是「今天看到的过去」。本 ADR 相反：我们看到的是「当时就公告了的未来」。

判定同时给出四条**风险边界**，每条都写清「表答不了什么」：

### 边界 1：临时休市不可预知

台风、熔断、纪念活动导致的**临时休市**没有可靠公开预告源，表里**不会有**。
这类日期仍然会算错 —— 只能事后补录（新公告 = 新行）。

**不假装知道**：本表不包含任何「预测某天会不会临时休市」的逻辑。

### 边界 2：公告改期 → 多行 + `published_at` 最新者胜出，**不覆盖旧行**

主键取 `(date, source_url)` 而不是 `date`。同一日期被年度通知与单节公告各写一条时，
两行内容相同、无害；若上交所**改期**，新公告是**新行**，读取侧
（`load_holiday_table`）按 `published_at` 取最新者。

- **为什么不用 `INSERT OR REPLACE`**：`REPLACE` 会删行重插，而旧行必须原样留着 ——
  它们是「**当时公告怎么说**」的证据。改期后要能回答「我们当时以为是哪天」。
- **为什么不 UPDATE**：本表 append-only，`BEFORE UPDATE/DELETE` 触发器直接
  `RAISE(ABORT)`（实测抛 `IntegrityError: market_holidays is append-only`）。
- 订正记录也走新行：`is_open=1` 的行可以显式表达「某公告说这天开市」。

### 边界 3：覆盖不到的年份 → 如实退回 `weekday_fallback`

只有**年度通知**（`doc_kind='annual'`）才代表「该年**全部**日期的开/休市都已公告」；
单节公告只覆盖那一个节。判据因此是：

```
covers(d) := int(d[:4]) ∈ {annual 行的 covered_year}
```

- 覆盖判据**必须**严格：否则「中秋公告」会让你以为元旦也知道，
  于是把 1 月 1 日当成交易日。
- 2027 年及以后**没有公告** → 那些日期 `covers` 为假 → **原样退回**
  `weekday_fallback`，`notes.target_date` 追加一句说明「有公告但覆盖不到」。
- **不假装知道**：覆盖不到就是覆盖不到，退回最弱的一档并如实标注 `source`。

### 边界 4：`target_date` 不参与任何收益/因子计算

`target_date` 只回答「**算哪一天**」。它不进因子、不进收益、不进任何价格类计算。
因此即便某天休市表出错，错的也只是「日期标签」这个层面的定位，
**不会**把未来价格信息混进因子。这是本方案不构成前视的**结构性**保证 ——
不依赖「表一定对」，而依赖「它就算错了也够不到价格」。

三条防线留在代码里，且 `source` 字段**区分三档强弱**：

| 档 | `target_date_source` | 含义 |
|---|---|---|
| 最强 | `trading_calendar` | 实测交易日（日历里有 > asof 的日期） |
| 中 | `holiday_table` | 日历耗尽 + 休市表覆盖该年 → 用了真实休市公告 |
| 最弱 | `weekday_fallback` | 纯工作日外推，**会算错节假日**，覆盖不到时如实退回 |

`trading_calendar` 分支的文案**逐字节不变**（回归红线 `docs/baselines/redlines.json`
盯的就是两个 predict 载荷的 sha256，它们都走这一支）。

## 后果

**好处**

- 长假前后 `target_date` 不再系统性错一周；错误从「每年必然发生」变成「边界 1 的残余」。
- 前瞻（`market_holidays`）与回看（`trading_calendar`）语义分离，
  `Calendar.load` 与 `session_check` 不受污染。
- 改期可表达、可追溯，且不需要 UPDATE，append-only 不破。
- 三档 `source` 把「查了公告」与「猜的」的差别**留在产物里**，下游看得见。

**代价 / 遗留**

1. **只采上交所**（`www.sse.com.cn`）。深交所入口实测 404，本轮不采 —— 另起一轮。
   深市标的的休市安排与沪市一致（国务院统一安排），但仍属未验证假设。
2. **表覆盖范围 = 已公告的年份**。实测拿到 2024/2025/2026 三年（2025、2026 有年度通知），
   `bounds() = ('2024-04-28', '2026-10-10')`。2027 年及以后仍走 `weekday_fallback`。
3. **临时休市无法预知**（边界 1）。
4. 「周末休市」子句只作补充收录；判「哪天开市」仍以「非休市日 + 非周末」为准。
5. 公告解析失败是 **fail-closed** 的：解析不出抛错、整批不落库。
   代价是「源站改版 → 采集直接失败」，而不是悄悄少几个节 —— 这是**有意的取舍**。

## 验证证据（P30b 实测）

- 真实采集：16 个请求（列表页 + 15 篇公告）**全部 HTTP 200**，合计 453,653 字节
  → `parsed_rows=148`、`inserted=148`、`closed_dates=93`、`annual_years=[2025, 2026]`。
- 幂等：第二次执行 `inserted=0`，表内行数 148 不变。
- append-only：有数据时 `UPDATE`/`DELETE` 均抛 `IntegrityError: market_holidays is append-only`。
- 端到端（离线合成库，asof=2026-09-24）：`target_date=2026-09-28`、
  `target_date_source=holiday_table`（跳过 9/25 中秋 + 9/26、9/27 周末）。
- 变异反证 `scripts/mutations_p30.py`：把 `holidays` 从 `build_predictions`
  摘掉 → 立刻变红 `assert '2026-09-25' == '2026-09-28'`（复现 P30 之前的错法）。
