# ADR-009 raw_cache 当日时效：同日收盘前抓到的快照不算命中

日期：2026-09-15 ｜ 状态：已采纳 ｜ 前置：ADR-001（无 cron / 一次性命令）、评审 B3（首写保留）、评审 C5（fixture 回放）
证据：`data/raw_cache/tencent/kline_sz000333_2026-09-15_2000_.5cc21daad809.json` 与
`/tmp/poisoned-cache/` 同名文件的真实 meta（2026-09-15 事故现场，已复看）

> **编号说明**：任务书指定 009；已确认 `008`（ETF 复权口径）为当前最大号且未被占用冲突，按「编号顺延不回收」取 **ADR-009**。

## 背景

`raw_cache` 的两条既有契约合起来产生了一个**时间维度上的洞**：

1. **首写保留**（评审 B3）：同一 `params_key` 只认第一次写入的 body，后续抓取不覆盖 ——
   这是为了防「源站改写历史数据」污染复现；
2. 而 `params_key` 只带锚点 `end`、**不含 `start`**，也与**抓取时刻**无关：
   `kline:{code}:{end}:{page}:{adj}`。

日K 的 `body` 内容却**同时**取决于窗口和抓取时刻。于是「同一个 key」可以对应多份
内容不同的响应，而缓存永久冻结了最早的那份。

## 事故（2026-09-15，真实发生）

同一 `params_key = kline:sz000333:2026-09-15:2000:` 的两次抓取：

| 文件 | `fetched_at` | 最新一根 K 线 |
|------|--------------|---------------|
| `/tmp/poisoned-cache/…5cc21daad809.bin` | `2026-09-15T00:21:33+08:00` | **2026-09-14** 收 86.8 |
| `data/raw_cache/tencent/…5cc21daad809.bin` | `2026-09-15T15:40:20+08:00` | **2026-09-15** 收 87.23 |

15:30 的收盘链 `ingest bars --days 12000` 命中的是 00:21 那份 → **当日 K 线当日不落库**。
当天靠人工挪走 6 个缓存文件才补上。

**更坏的那一半**：如果抓取发生在**盘中**，被冻结的 body 里那一根是**未完成的盘中价**，
`ingest bars` 会把它当**当日收盘价**写进 `bars_daily` —— 数值完全合法、含义全错，
而且**不报任何错**。次日验证会拿这个假收盘价去比对，直接毁掉准确率结论。

## 根因（三条同时成立才出事）

1. **key 不含 start**：不同窗口共用 key；
2. **首写保留**：共用 key 的多份响应里只有第一份能存活；
3. **无时效概念**：缓存层不知道「这份数据是不是当日未完成的」。

三者缺一，事故都不成立。**注意 ③ 才是关键** —— 前两条是评审 B3 的有意设计，
不能动；能动的只有「什么样的条目算命中」。

## 备选方案

1. **把 `start` 并进 `params_key`** —— ❌ 治不了。事故里两次抓取的 `start` 是同一个
   （`--days 12000` 由 `end` 推算），body 不同的原因是**抓取时刻**。
   这是**时效问题，不是身份问题**（对比 ADR-005：幂等键取语义不取呈现）。
   况且改 key 会让既有 142 个缓存条目全部作废、且不解决盘中价污染。
2. **收盘链强制绕过缓存**（`cache_key=""`，像 `session quotes` 那样） —— ❌ 代价太大。
   日K 是可复现数据，放弃缓存等于放弃 B3/C5 的复现性地基；而且盘中 tick 已经是不联网的，
   真正需要修的是「缓存不能骗人」，不是「别用缓存」。
3. **给缓存加时效判据（选定）** —— 读侧把「同日收盘前的快照」视为未命中，写侧不落盘。
   既不动首写保留、不动 SHA 校验，又让正确的数据一定能进来。

## 决策

判据（**只有**这一条路径变化，`stocklab/data/raw_cache.py::is_intraday_snapshot`）：

```
fetched_at 的本地日 == params_key 第 3 段（锚点 end 日）  且
(fetched_at.hour, fetched_at.minute) < (CLOSE_HOUR, CLOSE_MINUTE)   → 盘中快照
```

收盘口径**复用** `stocklab.session.close.CLOSE_HOUR/CLOSE_MINUTE`，比较方式与
`session/tick.py::_closed_at` 一致（`15:00` 整算已收盘）。

- **读侧**（`load`）：视为**未命中**返回 `None` → 调用方重新联网；
  同时在 meta 的 `conflicts` 追加 `{"reason":"intraday_snapshot","fetched_at":…}`
  （**铁律③：不许静默**）。同一 `fetched_at` 只记一次，避免高频读把 `conflicts` 撑爆。
  **完整性校验排在前**：条目损坏照旧抛 `CacheCorrupt`，不许被时效规则吞掉。
- **写侧**（`store`）：同样条件下**不落正式缓存**，直接返回 body 自己的 SHA256
  （调用方本就只消费正文，`stocklab/` 内无返回值消费者）。
  这样「首写永久冻结一份当日未完成的数据」在物理上不可能发生。
- **`has()` 语义随之收紧**：从「文件在不在」改为「`load` 会不会命中」——
  两者不再是同一件事了。完整性不在这里判（元数据读不了返回 `True`，让 `load()` 去抛）。
- **历史锚点一字不变**：`end != fetched_at 当天` 的条目照旧命中、首写保留、SHA 校验。
- **时钟可注入**：时效判定只读 meta 里的 `fetched_at`（由 `HttpClient.now` 注入，
  `http.py` 早已支持 `now=lambda: …`），`raw_cache` 内**不读裸 `datetime.now()`**，
  否则这个缺陷根本钉不住。

## 显式限制（不许被当成「已经修好了」）

1. **既有毒条目不会被自动修复**。写侧仍然「首写保留」，所以一份修复前落下的同日盘中条目
   会**一直躺在盘上**，读侧每轮忽略它 → 该 key **每轮多一次联网**，
   直到人工删除。这是刻意的：自动覆盖它就等于改掉首写保留语义（那才是更大的口子），
   而留着它反而是事故证据（sha 与 fetched_at 被记进 `conflicts`）。
   排查命令（只列不删）：
   ```bash
   .venv/bin/python - <<'EOF'
   import json, pathlib
   from datetime import datetime
   from stocklab.session.close import CLOSE_HOUR, CLOSE_MINUTE
   for m in pathlib.Path("data/raw_cache").rglob("*.json"):
       d = json.loads(m.read_text()); p = d.get("params_key","").split(":")
       try:
           if datetime.fromisoformat(d["fetched_at"]).date().isoformat() == p[2] \
              and (datetime.fromisoformat(d["fetched_at"]).hour,
                   datetime.fromisoformat(d["fetched_at"]).minute) < (CLOSE_HOUR, CLOSE_MINUTE):
               print(m)
       except Exception: pass
   EOF
   ```
   本仓库实际受影响：**2 条**，均为 `actions:…:2026-09-15:2000`（`fetched_at` 01:31），
   日K 条目在事故当天已被人工挪走，故 kline 侧为 0 条。
2. **只挡「同日收盘前」这一条路径**。跨日的过期条目（例如 `end=2026-09-14` 但次日才抓）
   仍是合法命中 —— 那种 body 的当日收盘已经存在，不是未完成数据。
   本修复**不引入** TTL / max-age 这类通用过期机制。
3. **不改变收盘链的现有行为**：盘中 tick（09:35/11:35/13:35）只跑 `session tick`、**不联网**
   （`cache_key=""`），定时联网的只有 15:30 收盘链；调度侧无需任何改动。

## 后果

**好处**
- 「当日的 body 被冻结」从**静默数据污染**变成**结构性不可能**（写侧）+ **每次显式留痕**（读侧）；
- 首写保留、SHA 校验、`CacheCorrupt` 硬失败这三条既有纪律**一条没松**；
- 事故的两个方向都被反证测试钉住：旧毒条目被回放（读侧）、盘中价被当收盘价写库（写侧）。

**代价**
- 盘中抓取不再产生缓存条目 → 这些响应无法回放（本来就是垃圾数据，不应回放）；
- 既有 2 条 `actions` 条目会翻成未命中，各多一次联网。
