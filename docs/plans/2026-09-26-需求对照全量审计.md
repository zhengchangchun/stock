## 0. 方法与判据

- **逐条对账**：每条需求取原文 → 找**代码证据**（文件/命令/表/页面）→ 定状态。状态词汇：
  `✅已交付`／`🟡部分（写明缺哪一半）`／`❌未做`／`⏸有意推迟（附触发条件）`／`📄文档待订正`。
- **必做 vs 优化**：`必做` = 需求里以「固定/必须/硬约束」措辞写下的**功能缺口**；`优化` = 已有实现但
  有质量/覆盖/口径缺口，或需求自身标为可选（04 §P3）。
- **不采信记忆**：每条都现场跑命令核对（读数见 §7）。
- **已知边界**：本审计只读代码与真库（`mode=ro`），不改任何东西；提出的动作**另开任务书**。

## 2. 必做（缺的硬需求）

### B1｜00 硬约束 6：同一策略版本连续 3 次优化验证失败 → 强制归档　`✅已交付（P87，派生口径）`

> 收口：P87 / ADR-037（2026-09-27）。**原动作「前滚加只增列」被现场否证**：
> `validation_cycles` 是 append-only（`trg_validation_cycles_no_update`），计数列**没法维护**。
> 改为从 `m2_judgements` 派生 `fail_streak`（尾部连续、`insufficient` 穿透），
> `>= 3` 只置 `evidence.lifecycle.force_archive` ＋ `actions` 追加归档建议，
> **不自动归档**（仍走人工 `approve`）。读出口 `m2 lifecycle show`。零结构变更。

- **需求原文**（00 §全局硬性约束 6）：「同一策略版本连续 3 次优化验证失败，强制归档，不再迭代。」
  ＋ 06 §D-6：「『策略评估记录』加 **`连续优化失败次数`**（≥3 → 强制归档，不再迭代）」——**标为「必须补」**。
- **现状**：`grep -rn "连续.*失败|consecutive|failure_count|fail_streak" stocklab/` → **零命中**
  （唯一命中是 `candidate/screen.py` 的「连续跌停」标签，与策略版本无关）。
  `validation_cycles` 表（`schema.sql`）列 = `cycle_id/script_id/account_id/planned_rounds/planned_days/params_json/criteria_text/start_date/created_at`，
  **没有失败计数列**；`m2/selfeval.py` 的三分支（`freeze`/`optimize`/`tune`）不看历史失败次数。
- **后果**：一条策略可以「优化 → 失败 → 再优化」无限循环，与 00 的收敛约束冲突；`archived` 只能靠人工判断。
- **动作**：开一个站（模块2 收口）——`validation_cycles` 前滚加只增列（或新 append-only 台账）＋
  `judge()` 在结论里带上「本版本累计失败次数」＋ ≥3 时把结论强制指向归档（**仍走人工 `approve`**，不自动执行）。

### B2｜06 §D-6 另一必补字段：冻结到期时间　`✅已交付（P87，派生口径）`

> 收口：P87 / ADR-037（2026-09-27）。到期日不落库，从最新一条 `branch='freeze'` 的判定派生：

> **未做**：07 任务4-2 的「到期强制开启新一轮 2~3 轮验证周期」= 自动建 cycle ——
> 要动写入口，留 B3/B4 并需用户拍板（见 `docs/tasks/2026-09-27-p87-...md` §4.2）。
