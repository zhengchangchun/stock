## 3. 拍板一：旧口径行怎么处置（任务书 §2）

### 3.1 实测前提

真库 1443 行**全部是新口径**（`notice_date_source ∈ {f10, statutory}`），
**不存在**用 DMSK `NOTICE_DATE` 落的行。原因是这 1443 行本身就是
2026-09-20 用新采集路径重采回来的。

### 3.2 拍板：**走 ① 的保守版** —— 不建 `dmsk_legacy`、不回填、不重采

| 候选 | 结论 | 理由 |
|---|---|---|
| ① 只前滚 + 旧行回填 `dmsk_legacy` | **部分采纳**：前滚 ✅；回填 ❌ | 库内**零**旧行 → 回填无对象；为不存在的行改 `CHECK` 约束是给未来加负担（且 `CHECK` 改动要重建表，在 append-only 表上是高风险动作） |
| ② 重采覆盖 | **否决** | `financial_reports` 有 `trg_financial_reports_no_update` / `_no_delete` 触发器（`schema.sql:1002-1008`）→ **就是 append-only**，这条路根本走不通（任务书原文的怀疑成立） |

**「不许静默改写历史行」的落实**：本轮**不执行任何** `UPDATE`/`DELETE`，
所有处置都靠**新增列/新增写入行**表达，历史行原样保留。

### 3.3 旧口径若真混进来会怎样（写下来，因为这是唯一的真风险）

主键是 `(code, report_date, notice_date)`。换口径会**改变 `notice_date` 的取值**，
所以**同一 `report_date` 在新旧口径下是两条不同主键的行**（不是覆盖）。
一旦两条并存，读侧 `ORDER BY report_date` 会同时返回它们 → 同一报告期出两个
`(年,季)` → `_value_at` 取到哪条**不确定** → 因子静默算错。

真库 `(code, report_date)` 重复数实测为 **0**，所以**现在没踩**；但读侧
`schema.sql:964-965` 写的是「读取侧取 `notice_date <= asof` 中最晚的那个」，
而 `score.load_financials`（`score.py:56-61`）**并没有实现这条去重**。
→ 见 §7 T7：补上去重，把文档承诺和代码对齐。这是**堵「会算错数」的路**，
不是新能力。

### 3.4 主键与幂等键

**不变**。幂等键就是主键 `(code, report_date, notice_date)`：`ingest_financial_reports`
按这三列查重、命中即跳过（`ingest.py:190-203`）。换口径只影响**新写入行**的
`notice_date` 取值，不改键结构。

## 4. 拍板二：T2 的「同口径」取哪个基准

任务书 T2 要求 `abs(net_margin × asset_turnover × equity_multiplier − roe) < 1e-9`。
现状是 `roe` 用**期初期末均值**权益、`dupont` 用**期末**权益，两者**有意不相等**
（`indicators.py:116-117` 的 docstring、ADR-016「DuPont 恒等式成立」都与之矛盾）。

两个同口径方案（评审 B2 给的正是这两个）：

| 方案 | 做法 | 影响面 |
|---|---|---|
| **A** | 三分项全改**期末**口径 → `roe` 也改期末 | **改 `roe` 取值** → 动横截面分位 → 动三池分数 |
| **B（选定）** | 三分项全改**均值**口径 → `roe` **不动** | 只改 `dupont` 取值 |

**选 B**，理由：

1. `roe` 是**在评分权重里的因子**（`p2_mid.py:9-10` 的 `WEIGHTS`），
   `dupont` **不在** `WEIGHTS` 里（只是 `features` 里给人看的分解）。
   改 `dupont` 的爆炸半径显著小于改 `roe`。
2. 任务书反目标要求「不动中期池的评分公式」。B 让 `ROE` 这个被打分的因子**逐位不变**，
   最贴合该约束。
3. B 让 `dupont` 成为**我们实际上报的那个 `roe` 的分解**——这正是 DuPont 的本义；
   A 则会让 `dupont` 分解一个我们不上报的 ROE。

**改后**：

```
roe              = P_ttm / E_parent_avg
net_margin       = P_ttm / I_ttm
asset_turnover   = I_ttm / A_avg          # A_avg = (A_{y-1,Q4} + A_{y,Q}) / 2
equity_multiplier= A_avg / E_parent_avg
product          = P/I × I/A_avg × A_avg/E_avg = P / E_avg = roe   ✅ 恒等
```

**负例**（任务书要求）：把分母换回 `total_equity`（合计权益，含少数股东），
恒等式**必须失败**——这条负例证明该测试对口径是敏感的，不是恒真的橡皮图章。

**代价**：`A_avg` 需要**上一年年末总资产**。缺这一期时 `dupont` 由「可算」变 `None`
（原来只要期末资产就能算）。这是有意的：宁可显式 NA，也不给一个口径不一致的数。
`roe` 本来就依赖 `E_parent_avg`（同样需要上年年末），故两者可用性**同进同退**。

## 5. 偏离任务书原文的一处（必须记，不静默）

任务书 T1 的质检写成：`report_date < notice_date ≤ report_date + 120 天`，越界 → `warn`。

**实测这条规则会误报 41 行合法数据**：

```
$ 真库只读查询：not (report_date < notice_date and notice_date <= date(report_date,'+120 day'))
41 行，全部 notice_date_source='statutory'，滞后全部 = 121 天
例：('000333','2019-12-31','2020-04-30','statutory',121.0)
    ('600519','2007-12-31','2008-04-30','statutory',121.0)
```

根因：年报法定截止日 4-30 与 12-31 的间隔在**闰年跨 2 月**时是 **121 天**。
即 **120 天上界对 `statutory` 回退行是错的**——回退值本身就是法定期限，它
**定义上**不可能越界，用它去做合理性检查只会年年误报。

**处置（判据照旧满足，落点修正）**：

- 合理性检查**只对「有原始值」的情况有意义**。故把 `resolve` 的回退原因
  拆成两类：`missing`（源站本来没这个字段）与 `implausible`（有值但不合理）。
  只有 **`implausible`** 才发 `warn: notice_date_suspect`。
- `missing` 不是「可疑」，它是评审 A3 说的**「该期公告日为推定」**，
  由 `notice_date_source='statutory'` 如实承载，报告里给口径分布即可（不是 warn）。
- 保留 120 天规则本身（它正是抓 DMSK「指向次年同类公告」那个 bug 的），
  但**不把它套到 `statutory` 回退值上**。
