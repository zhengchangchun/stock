### B1. `patrol` 的 15:30 槽在代码里还在，而本批文档教人「重装」——重装即复现竞态

- **文件:行**：`stocklab/ops/schedule.py:56`（`PATROL_HOURS = tuple(range(9, 16))`）、
  `stocklab/ops/schedule.py:71-74`（`patrol_calendar()`）、`stocklab/ops/schedule.py:108`（`window` 文案）；
  文档侧 `docs/ops/2026-09-22-launchd-定时任务.md:20-22`、`:33`、`:117`，
  `docs/decisions/2026-09-22-ADR-020-调度载体改用系统launchd.md:68`
- **现象（我实测，不是转述）**：

  | 产出物 | 槽位数 | 最后一槽 |
  |---|---|---|
  | 代码生成（`ops schedule generate --job patrol`） | **70** | 工作日 **15:30** |
  | 本机已安装的 `~/Library/LaunchAgents/com.stocklab.patrol.plist` | **65** | 工作日 **15:00** |

  即：**止血只存在于「那台机器上的那个文件」里，源码仍是 70 槽**。而
  `schedule.Job.window` 与两份文档都写着「09:00–15:30 每 30 分钟（70 条触发点）」——
  它们描述的是代码，不是部署物。三份「事实」里有三个不同的答案。
- **为什么是问题**：`PATROL_HOURS=range(9,16) × PATROL_MINUTES=(0,30) × 工作日`
  与 `close` 的 `{Hour:15, Minute:30}` **落在同一分钟**（我用集合求交验证过，
  这是三条任务里**唯一**的撞点，见 §3-12）。15:30 那一轮 `patrol --fix` 会真起子进程跑
  `ingest *`，`close` 会跑整条 12 步链，两个写者对同一个 SQLite 并发写 ⇒ `database is locked`
  ⇒ 某步非 0 ⇒ **收盘链当天断链（exit 2）**。更糟的是：`docs/ops/…launchd-定时任务.md` §2/§3/§4
  把「重装」写成恢复/撤 nanobot 的标准动作（「`ops schedule install` 重装 → `status` 三条
  `loaded=true`」），**照做就把手工止血覆盖掉**。这不是「将来可能」，是「下一个执行文档的人必然」。
- **为什么仍算阻断**：这不是新发现（P42 已立项，T1 就是把它改成 09:00–15:00 / 65 槽），
  但**本批提交时它还没落地**，而本批自带的文档在推着人去重装。提交一个「文档与代码合起来会
  复现已知缺陷」的组合，等于把陷阱交给下一个人。
- **最小改动**：`PATROL_HOURS` → `tuple(range(9, 15 + 1))` 少一小时（或直接写明 `range(9, 15)`
  含 15 点、`PATROL_MINUTES` 去掉 `(15, 30)` 那一格，按 P42 T1「13 槽 × 5 日 = 65」实现），
  同步 `Job.window`、`docs/ops/…`、ADR-020、`docs/ops/cron-2026-09-21-待挂.md` 里的窗口数字；
  并补 P42 T4 的「任意两 job 触发集无交集」通用断言。**这一条本质是 P42，不要在本批里草率改**：
  要么先落 P42 再提交，要么在提交信息里显式写「**P42 落地前任何人不得跑 `ops schedule install`**」。
- **复现方式**：
  ```bash
  .venv/bin/python -m stocklab.cli.main ops schedule generate --job patrol \
    | .venv/bin/python -c "import json,sys;d=json.load(sys.stdin)[0];print(d['triggers'])"

  plutil -convert json -o - ~/Library/LaunchAgents/com.stocklab.patrol.plist \
    | .venv/bin/python -c "import json,sys;c=json.load(sys.stdin)['StartCalendarInterval'];print(len(c),c[-1])"
  ```

## 2. 建议改（不阻断）

### S1. `steps_total` 这个键**从来没人写过**——`_verdict` 里那句「／共 N 步」是死分支

- **文件:行**：`stocklab/labweb/ops_render.py:79-80`
- **现象**：`total = latest.get("steps_total")`；全仓库 `grep -rn steps_total stocklab/ tests/`
  只命中这一行（另有一个 `.pyc`）。`ops/chain.py` 的 `run_close` / `run_monthly` 载荷里
  没有这个键 ⇒ `total` 恒为 `None` ⇒ 页面永远只打「跑完 N 步」，**「／共 12 步」永远不会出现**。
- **为什么是问题**：这正是错误日记 **#52** 的形状（语法合法、测试全绿、页面照渲，
  只是那段永远不执行）。而且 `tests/test_source_no_dead_code.py` 的 AST 规则只抓
  「`return`/`raise`/`break`/`continue` **之后**的同层语句」，**抓不到「分支恒不成立」**这一类 ——
  所以 §4-6 我把它登记为「无机械验证」。
- **最小改动**：二选一 —— ① 在 `chain.run_close`/`run_monthly` 的 `payload` 里补
  `"steps_total": len(CLOSE_STEPS/MONTHLY_STEPS)`（回执是真相源，页面读它最合理）；
  ② 删掉 `steps_total` 分支，直接写「跑完 N 步」。**推荐 ①**：`summary_line` 里已经有
  `steps={len(steps)}/{total}`，两处口径应当同源。
- **复现**：`grep -rn steps_total stocklab/ tests/ docs/`；或看 `reports/ops/latest-patrol.json`
  里没有该键。

### S2. `next_trigger`（页面「下一次触发」）在每月 1 日 08:00 之后返回 `None`，并谎称「形态认不出」

- **文件:行**：`stocklab/labweb/ops_data.py:80-92`（`for i in range(...)` 末尾那个 `break`），
  文案在 `stocklab/labweb/ops_render.py:125`（`"推算不出来（形态认不出）"`）
- **现象（实测）**：
  ```
  monthly now=2026-10-01T07:00  -> 2026-10-01T08:00   ✅
  monthly now=2026-10-01T08:00  -> None               ❌（就在触发点那一分钟）
  monthly now=2026-10-01T09:00  -> None               ❌（应当 2026-11-01T08:00）
  monthly now=2026-10-15T09:00  -> 2026-11-01T08:00   ✅
  ```
  根因：`start_month` 只有**一条** `StartCalendarInterval`，循环找到第一个匹配日（今天，1 日）
  后算出 `08:00 ≤ now`，不更新 `best` 就 `break`，**再也没有机会看下个月的 1 日**。
  `close`/`patrol` 侥幸不受影响（同一天有 5/70 条 entry，别的 entry 会兜住）。
- **为什么是问题**：每月 1 日的 08:00–24:00（共 16 小时）里，`/lab/ops` 页面会显示
  「推算不出来（形态认不出）」——**形态认得出，是这个函数放弃了**，等于页面在说一句假话。
  （页面已声明「下一次触发是推算、不是承诺」，所以不阻断；但「认不出」这个理由是错的。）
- **最小改动**：把末尾的 `break` 改成「只有真的取到候选才 break」：
  ```python
  if cand > now and (best is None or cand < best):
      best = cand
      break           # 这一条 entry 定案
  # 否则继续找下一个匹配日（i+1…）
  ```
  并在 `tests/test_labweb_ops.py` 补一条 `now=2026-10-01T09:00 → 2026-11-01T08:00` 的用例
  （现有 `test_next_trigger_patrol_and_monthly` 用的 `TZ_NOW` 恰好绕过了这个缺陷）。
- **复现**：见上表（脚本见 §5）。

### S3. `paper spec set` 的「冲突」有两个退出码：预检给 1，异常路径给 2

- **文件:行**：`stocklab/cli/main.py:2304-2312`（`EXIT_CONFLICT = 1` + `_spec_conflict`）
  与 `stocklab/cli/main.py:2389-2391`（`except (SpecViolation, DecisionConflict) → _paper_fail`），
  `stocklab/cli/main.py:2184-2188`（`_paper_fail` 恒返回 2）
- **现象**：「同 `(arm, asof)` 已有且不一致」这件事，走预检分支 → exit **1**；
  走 `record_decision` 抛 `DecisionConflict` 分支 → exit **2**。任务书 T5 写的是「冲突 1」。
- **为什么是问题**：两处答案不一致，且语义上 2 在项目里是「你给的东西不合法」——
  而这里输入完全合法、只是撞了历史。当前几乎不可达（预检就在正上方），
  但「同一个语义两个码」是本仓库反复强调要消掉的东西（ADR-019 的整个动机就是退出码只有一个真源）。
- **最小改动**：把 `DecisionConflict` 从那个 `except` 里拆出来单独 `return EXIT_CONFLICT`。
- **复现**：`tests/test_cli_paper_spec.py` 里冲突用例断言的是 1（走预检），
  竞态路径无人覆盖（见 §4）。

### S4. `render_plist` 的注释说「不设 RunAtLoad」，实际**设了** `RunAtLoad: False`

- **文件:行**：`stocklab/ops/schedule.py:150-151`
- **现象**：注释「不设 RunAtLoad：登录/bootout 之后不该立刻跑一条收盘链」，
  下一行却是 `"RunAtLoad": False`。生成的 plist 里 `<key>RunAtLoad</key><false/>` 确实存在
  （ADR-020 写的是 `RunAtLoad = False`，与代码一致）。
- **为什么是问题**：语义（不自动跑）是对的，注释是错的。这正是任务书 §1.5 要的那类
  「文件在说谎」——将来有人为了「加上 RunAtLoad」而改这里，会以为自己动了行为，其实没有。
- **最小改动**：注释改成「显式写 `RunAtLoad=False`（不是省略）：省略在语义上等于 false，
  但显式写下来才能被断言/被看见」。

### S5. `close` 的窗口文案「每交易日 15:30」与 plist 实际触发（工作日，含节假日）不符

- **文件:行**：`stocklab/ops/schedule.py:100-103`（`window="每交易日 15:30"`，
  `calendar=tuple({"Hour":15,"Minute":30,"Weekday":d} for d in WEEKDAYS)`）
- **现象**：`StartCalendarInterval` 只能表达「星期几 15:30」，**做不到「只在交易日」**——
  节假日（如 10-01）也会被拉起，然后由链自己判 `is_trading_day=False` 整轮跳过并 exit 0。
- **为什么是问题**：`/lab/ops` 页面、「为什么」文案、ADR-020 表格都把这个窗口写给人看，
  而「每交易日」会让读者以为节假日不会触发（真跑起来会在节假日写一条 `job_runs(skipped)`）。
  这条不影响正确性（跳过是设计），但影响了「读页面的人对系统行为的预期」。
- **最小改动**：`window` 改成「工作日 15:30（非交易日整轮跳过）」，并与 ADR-020/`docs/ops/` 同步。

### S6. `arm-agent-random` 的空账户在**阶段 1** 就建了（任务书 T6 说阶段 3 才建）

- **文件:行**：`stocklab/paper/engine.py:321-327`；`stocklab/cli/main.py:2301-2303`（`SPEC_ARMS`）
- **现象**：`init` 现在同时创建 `arm-agent` 与 `arm-agent-random` 两个账户（后者 `params_json`
  写 `counter_arm` / `wired_from: 阶段 3…`）；`paper spec set/show --arm arm-agent-random`
  现在也可用。任务书 T6 原话是「`init` 新增 `arm-agent`（**阶段 3 再加** `arm-agent-random` 的空账户）」。
- **为什么是问题**：任务书 §1 要求**反向检查「有没有代码做了设计里没写、也没人拍板的事」**。
  这一处是「比任务书多做一步」，代码里有注释解释、设计 §1/§2 也确实把随机臂列为必需 ——
  属于**良性扩范围**，但它没写进任何一份拍板记录，将来会有人当 bug 追。
- **最小改动**：在任务书 T6 / ADR 或设计 §8 补一句「随机臂的空账户随阶段 1 一起建（只为让
  `paper show` 的对照臂字段有落点），交易仍在阶段 3 才接线」。

### S7. ADR-020 §「落地状态」与 `docs/ops/…launchd-定时任务.md` §3 已与本机现状不符

- **文件:行**：`ADR-020:116-122`、`docs/ops/2026-09-22-launchd-定时任务.md:96-99`
- **现象（只读实测）**：两份文档都写「已 `bootout`、`launchctl list` 里已无 `com.stocklab.*`
  残留、plist 留盘等待重装」；而我此刻读到的是三条**全部 loaded**：
  ```
  $ launchctl list | grep stocklab
  -  0  com.stocklab.monthly
  -  2  com.stocklab.close
  -  0  com.stocklab.patrol
  ```
  且 `reports/ops/latest-close.json`（14:07）是一条真实的 `before_close` 拒绝（exit 2）、
  `latest-patrol.json`（14:30）是 exit 0 —— 说明本机在文档写完之后又装回并跑过了。
- **为什么是问题**：文档写的是**机器状态**，而机器状态会变；「已 bootout」这种句子一旦过期，

    `has_rules=False` ⇒ 只 mark-to-market、不下单；`arm-agent` 与静态臂共用
    `_plan_steps`/`evaluate`（参数不同、代码同一份），T6 说的「不复制纪律臂执行逻辑」成立。
12. **R4 时间线（三条任务的触发时刻 × 写库行为）**：用集合求交（脚本见 §5）实算 ——
    `close`(5 槽) / `patrol`(70 槽) / `monthly`(1 槽) 两两取 `(Hour, Minute)` 交集，结果：
    ```
    close ∩ patrol  = [(15, 30)]     ← 唯一撞点，即 §1-B1 / P42
    close ∩ monthly = ∅
    patrol ∩ monthly = ∅
    ```
    另外三点也已核对：① `RunAtLoad=False`（三条皆是），登录/bootout 不会突发拉起一整条链；
    ② 整轮预算 `close=900s`、`patrol=480s`、`monthly=1800s` ⇒ `monthly`(08:00–08:30)
    与 `patrol`(09:00 起) 不重叠，`close`(15:30–15:45) 与 `patrol` 的 **15:30 槽**重叠
    （正是撞点），修正后（最后一槽 15:00）不再重叠；
    ③ **跨调度器**撞点比进程内更宽：本机 `launchctl list` 三条 **loaded**，而 nanobot 三条
    （A `d2ffe556 30 15 * * 1-5` / B `d52f97b3 */30 9-15 * * 1-5` / C `d412c0d2 0 8 1 *`）按
    `docs/ops/…` §4 **尚未撤除** ⇒ 同一分钟会有**两套调度器各拉一次同样的命令**
    （B 的 `*/30 9-15` 也含 15:30，于是 15:30 那一刻最多是 close + patrol + nanobot-B 三方）——
    这比进程内的 15:30 更宽，撤 nanobot 的前置条件（§4）应是硬门；
    ④ launchd 睡醒后**合并补跑**错过的槽位 ⇒ 「close 与几个错过的 patrol 同时醒来」也是一种
    撞点形状，`StartCalendarInterval` 不提供串行化保证。
