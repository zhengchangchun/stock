# 准确率分桶补上「模型版本」维度：页面/报告不再混算两版

- **日期**：2026-09-21（深夜，接 `MODEL_VERSION → pit-rw-v1.0.2` 之后）
- **触发**：用户「继续优化，我在页面上能看到所有的结果」→ 先修页面上**那个错数**（既是纠错，也是页面可见性）
- **产物**：`stocklab/session/review.py`（`rolling_accuracy` 重写 + `_version_line`）、
  `stocklab/session/tick.py`（`_compact_rolling` 带上版本）、`stocklab/labweb/render.py`、
  `stocklab/dashboard/html.py`、`stocklab/cli/main.py`、`tests/test_session_review.py`（3 条新测试）、
  `docs/errors/ERROR_DIARY.md` #48
- **错误日记**：#48（同一条根因的两个面之一：升版后**读路径**混算）

---

## 1. 问题：页面上的 33.8% 是「第三个数字」

升版后 labweb `/data` 的「验证统计」窗口 30 个交易日（`2026-08-04 ~ 2026-09-21`）读到：

| 读数 | 值 |
|---|---|
| 页面（混合） | `n_rows=1020`、方向 `0.33824`、Brier `0.67777` |

而逐版本分开算是：

| 版本 | 行数 | 方向（按日聚类） | Brier |
|---|---|---|---|
| `pit-rw-v1.0.1` | 510 | **0.34314** | 0.67668 |
| `pit-rw-v1.0.2` | 510 | **0.33333** | 0.67887 |

**510 个 `(target_date, code)` 组合全部被重复计数**（每个版本各一行、各一个 `pred_id`），
按日聚类时同一交易日的标的数从 17 变成 34 —— 混出来的数落在两版之间，
既不离谱到被怀疑，也不等于任何一版。这正是本项目最怕的那类错：**数字合法、结论全错**。

## 2. 根因（一句话）

`session/review.py::rolling_accuracy` 只按 `provenance`（live / replay）分桶，
**没有按 `model_version` 分桶**。「口径分列」被实现成了一维，而它天然是两维。

「一个样本只有一行」这个隐含假设在**升版那一刻**失效：旧行不删（append-only），
新版本重放会为同一批 `(日, 标的)` 再写一批 —— 库里从此同一格有两行。

## 3. 修法：两个桶只含当前版本，旧版本单列

`rolling_accuracy` 的返回结构（**键名兼容**，只增不减）：

| 字段 | 含义 |
|---|---|
| `model_version` | **新增**。下面 `live` / `replay` 两桶的口径版本（不写出来读者只能猜） |
| `provenance.live` / `.replay` | 保持原有键（`n_rows` 等），各自多一个 `model_version`；**只含当前版本** |
| `provenance.by_model_version` | **新增**。窗口内每个版本的 `{live, replay}` 行数（逐版审计） |
| `live` / `replay` | 保持不变，但现在只装当前版本的行 |
| `model_versions` | **新增**。窗口内**每个**版本的完整读数（含当前版本），给「逐版展示」用 |
| `excluded` | **新增**。`n_rows` ＋ `by_model_version` ＋ `note`：被剔除的旧版本行数与「不许相加/平均」的说明 |
| `note` | 追加版本分列句 |

为什么这么选（而不是「两个桶都留着、再加一层」）：

1. **键名不动** → 现有消费者（`cli review daily` 的 JSON、`dashboard/summary.py`、
   `session/tick.py`、labweb、`dashboard/html.py`）不会因为升版静默读错；
   它们**语义上被纠正**成「当前版本」，这正是它们该有的含义。
2. **旧版本不消失**：数字仍在 `model_versions` / `excluded` 里，且**明写**「不与当前版本混算」。
   留档而不是删掉 —— 与「v1.0.0 的错误预测不许混进 v1.0.1」同一条纪律的另一半。
3. **判据按实测行数取值**（ERROR_DIARY #16）：`excluded` 有没有内容由**窗口里真的有没有旧版本行**决定，
   不由「有没有升过版」这类代理开关决定。

## 5. 验证（都是真库/真命令，不是想当然）

1. **单测**：`tests/test_session_review.py` 新增 3 条 —— 两版不混算、窗口只有旧版本时当前桶为 0
   而旧版本行仍在账上、报告里点名版本且旧版本标「剔除/仅作历史参照」。`2058 passed`。
2. **真库读数**（`data/stocklab.db` 只读连接）：`replay n_rows 510`（修前 1020）、
   `excluded.n_rows 510`、`by_model_version` 两版各 510 —— 与上面第 1 节的逐版表一致。
3. **报告渲染**：`review daily --date 2026-09-21`（库副本）§4 逐行核对，旧版本读数
   34.31%（CI [29.49%, 39.14%]）/ Brier 0.6767 与逐版表一致。
4. **页面**：起 `lab serve`（回环 8799）→ `/lab/data` 截图
   `artifacts/labweb/2026-09-21/accuracy-版本分列.png`（已发给用户）。
5. **静态看板**：`dashboard build` 生成的 HTML 含「口径版本」「旧版本读数（共 510 行…）」。
6. `bash scripts/verify.sh`：1–4c 全 ✅，**红线三目标一字未变**（本次改动不碰任何预测/验证数值）。

## 6. 遗留（不藏）

- **`_disclosure` 里的 `38.14% / Brier 0.6581`** 仍是更早一次回放（6 只标的时期）的陈旧引用，
  钉在 `stocklab/paper/config.py`、`dashboard/html.py`、`cli/main.py`、`risk/__init__.py`、
  `session/review.py` 文案里且有测试断言 `"38.14%"` —— 换不换、换成哪一次回放的哪个数，
  仍**待用户一句话**（不在本文件范围内）。
- **`chain accuracy` / `verify report` 已核过，不需要改**：两者的准确率数字都走
  `verify/report.py::summarize`，而它**本来就是按 `model_version` 分组**的（`model_versions` 逐版一节），
  段级只留 `n_rows` / `n_days` 这类**计数**，不产出跨版准确率；`chain` 的 `gate` 取 `len(days)`
  （交易日集合，版本无关）也不会被版本翻倍影响。
- 时间戳不一致：`rolling_accuracy` 的窗口取 `target_date <= end_date` 的最近 N 个交易日，
  与 `verify backfill` 的报告窗口口径不同 —— 这是既有设计，未改。
