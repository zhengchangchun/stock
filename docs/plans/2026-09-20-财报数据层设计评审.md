# 财报数据层与中/长期池因子 · 设计评审

> 评审对象：`docs/superpowers/specs/2026-09-20-财报数据层与中长池因子-design.md`
> （前置）`docs/superpowers/specs/2026-09-18-插桩候选池骨架-design.md`
> 评审日期：2026-09-20
> 评审人：nanobot（对东财 datacenter 做了真实联网实测，证据见 §D）
> 结论：**方向全对（数据/派生分离、PIT 锚、不设绝对阈值、诚实标注自创项），但数据源选型有 3 处硬伤必须先改 —— 尤其是 `NOTICE_DATE` 实测不是 PIT 锚，照原样实现会让 TTM 类因子在一年中大部分时间静默不可算。**

---

## 0. 总体判断

值得肯定的（不展开）：D2「只采可采集数据」、D3「派生不落库」、D4「pass_flag 只判数据有效性」、§6.1 累计→单季→TTM 的自觉、§6.2 三条自创取值逐条列明、§11「买的是能力不是证据」——这些在个人量化项目里都不常见。

**问题集中在「设计假设的数据源事实」与「实测的数据源事实」不一致**：
设计把 `RPT_DMSK_FN_*` 三张简表当成了「干净的三表」，实测它们是**东财的简版汇总表**——行覆盖广（含银行/保险/ETF 空响应）、带 `INDUSTRY_NAME`，但**没有归母权益、`NOTICE_DATE` 语义可疑**。而带正确 `NOTICE_DATE` 与 `TOTAL_PARENT_EQUITY` 的 `RPT_F10_FINANCE_G*` 表，**对银行/保险的资产负债表实测返回空**。两条路都各有缺口，必须先做取舍（§E 给了推荐方案）。

## A. 硬伤（必修，不解决会给错数或「静默不给数」）

### A1. `NOTICE_DATE` 实测不是 PIT 锚 —— 它像是「该表最近一次更新的公告日」【必修】

- **设计原假设**（§4.2）：`notice_date` 是「这份财报被公告的日期」，主键 `(code, report_date, notice_date)`、读侧取最晚。
- **实测**（`000333.SZ`，`RPT_DMSK_FN_BALANCE` / `_INCOME` / `_CASHFLOW` 全量 79 期）：

  | report_date | 资产负债表 | 利润表 | 现金流量表 | 真实公告日（F10 表） |
  |---|---|---|---|---|
  | 2026-06-30 | 2026-08-29 | 2026-08-29 | 2026-08-29 | 2026-08-29 ✅ |
  | 2026-03-31 | 2026-04-30 | 2026-04-30 | 2026-04-30 | 2026-04-30 ✅ |
  | 2025-12-31 | **2026-08-29** | 2026-03-31 | 2026-03-31 | 2026-03-31 ❌ |
  | 2025-06-30 | 2025-08-30 | **2026-08-29** | **2026-08-29** | 2025-08-30 ❌ |
  | 2024-12-31 | **2026-03-31** | **2026-03-31** | **2026-03-31** | 2025-03-29 ❌ |
  | 2023-12-31 | **2025-03-29** | **2025-03-29** | **2025-03-29** | 2024-03-29 ❌ |

  规律：**只有「每种报告类型的最新一期」的 `NOTICE_DATE` 是对的**，历史行的取值往往指向「同类报告的下一次公告日」。跨 5 只标的统计，三表公告日不一致是常态（美的 42/79 期、招行 72/102、长电 73/93、平安 59/83、宁德 25/39），**不一致的跨度中位数正好 365 天**。
- **影响**：照 §4.3.2「取三表最晚者」+ §4.2「读侧取 `notice_date <= asof` 中最晚者」，会得出：
  - 2025 年报的可读日期 = 2026-08-29 → **在 2026-04-30~2026-08-29 之间跑 `candidate run`，2025 年报「尚未公告」**；
  - 于是 `TTM` 需要的 4 个单季凑不齐 → 中期/长期池**全部 `pass_flag=False`**，报告只会说「数据不足」，看不出是源字段错。
  - 反过来说，DoS 里那条 DoD（手工对照美的 2025Q1–2026Q2）**恰好能过**（因为 asof=今天，所有可疑公告日都已过期），**验收抓不到这个 bug**。这是最危险的一类设计缺陷。
- **对策（择一，推荐 ①）**：
  1. **公告日改用 `RPT_F10_FINANCE_GBALANCE` 的 `NOTICE_DATE`**（实测与真实公告日逐期吻合，且该表另有独立 `UPDATE_DATE`），按 `(code, report_date)` 对齐到 DMSK 三表的数据行；取不到对齐的期数回退到法定披露截止日并标 `notice_date_source='statutory'`；
  2. 继续用 DMSK，但**不用它的 `NOTICE_DATE`**，一律用法定披露截止日（年报/一季报 4-30、中报 8-31、三季报 10-31）做**保守锚**；
  3. 只保留「每类型最新一期」的可信公告日，其余回退。
- **配套质检（无论选哪条都要）**：`report_date < notice_date <= report_date + 120 天`，超出即 `warn`（`notice_date_suspect`）——A1 那 6 行有 5 行会被这条抓出来。另加「同 `report_date` 三表公告日相差 > 30 天 → warn」。

### A2. `total_equity` 口径写错：DMSK 的 `TOTAL_EQUITY` 是**含少数股东权益**的所有者权益合计【必修】

- **设计原文**（§4.1）：`total_equity` = 「归母股东权益」。
- **实测**：`TOTAL_ASSETS − TOTAL_LIABILITIES == TOTAL_EQUITY` 逐只成立——
  - 美的 `643,101,789 − 417,308,848 = 225,792,941`（千元）✅
  - 招行 `13,785,280 − 12,431,979 = 1,353,301` ✅；茅台 `309,050,784,569.31 − 46,954,432,394.95 = 262,096,352,174.36` ✅
  - 即它是「所有者权益合计」，**不是归母**。
- **影响**：`roe = 归母净利(TTM) / 平均权益` 会**分子归母、分母含少数股东** → 系统性低估 ROE（美的 归母权益 212,861 vs 合计 225,793，差 **5.7%**）。更糟的是 §6.2 的 `dupont = 净利率 × 周转率 × 权益乘数` —— 三者相乘得到 `归母净利 / 合计权益`，**恒不等于 `roe` 定义值**，两个数在同一份 `features` 里互相打架，且不会报错。
- **对策**：补列 `parent_equity`（来自 `RPT_F10_FINANCE_GBALANCE.TOTAL_PARENT_EQUITY`，实测可用；`MINORITY_EQUITY` 也可拿）。取不到时（银行/保险，见 A2 备注）**把该期的 `roe`/`dupont` 标为口径不一致的近似**，或在 §6 明确改成「净利润(含少数股东损益) / 所有者权益合计」的合并口径——但 DMSK 利润表**只有 `PARENT_NETPROFIT`，没有净利润合计**，所以合并口径在 DMSK 上做不出来 → **结论：`parent_equity` 基本是必需的**。
- **备注（实测）**：`RPT_F10_FINANCE_GBALANCE` 对 `600036.SH`（招行）、`601318.SH`（平安）、`510300.SH`（ETF）返回「返回数据为空」；而 `RPT_F10_FINANCE_GINCOME` 对招行**有**数据（`ORG_TYPE=银行`）。所以「换成 F10」要按 `ORG_TYPE`/行业选报表名并逐只验证覆盖率——**不能想当然认为 F10 全量可用**。
- **必须加的测试**：`assert abs(net_margin × asset_turnover × equity_multiplier − roe) < 1e-9`（同口径下），以及「换口径必失败」的负例。

### A3. 早期期数 `NOTICE_DATE` 为空 → `NOT NULL` 主键装不下【必修】

- **实测**：美的资产负债表 **17/79 期**、现金流量表 **14/79 期** 的 `NOTICE_DATE` 为 NULL（集中在 2004–2007；利润表 0 空）。招行/平安/长电/宁德为 0 空——即**因标的而异**。
- **设计的矛盾**：§4.1 把 `notice_date` 定为 `TEXT NOT NULL` 且是主键、§5 说「采集东财返回的全部历史期数，不截断」→ 采美的第一天就会在这 17 期上失败（要么抛异常整只不入库，要么静默丢历史）。
- **对策**：`notice_date` 保留主键与 NOT NULL，但增加 **`notice_date_source`**（`eastmoney` / `f10` / `statutory`），缺失时回退法定披露截止日；报告与 `features` 里注明「该期公告日为推定」。**不许**用「跳过该期」了事（那就是静默截断历史）。

### A4. 采集层没写分页与页大小 —— 默认口径下每张表 40 页【必修】

- **实测**：`RPT_DMSK_FN_BALANCE` 对 `000333.SZ` 返回 `count=79`；默认页码口径下 `pages=40`（`pageSize` 未给足时）。
- **影响**：3 表 × 21 只 × 40 页 = **2520 次请求**，且 `http.py` 有 `min_interval` 节流 → 采集会非常慢；更糟的是**没写「翻页不足即失败」的 fail-closed**，半截历史会被当成全历史（`valuation_daily` 已有教训：非末页行数 != page_size 就抛）。
- **对策**（照抄 `fetch_valuation_daily` 的模式）：
  - `pageSize=500`（实测 500 可一次取回 79 行，`pages=1`），首请求读 `result.pages`/`count`；
  - 非末页行数 != `pageSize` → `FetchError`；`pages == 0`/`result == null` → `[]`（合法空，见 A6）；
  - 翻页超上限 → `FetchError`；
  - **必须 `columns=ALL`**：实测显式列清单在缺该列的标的上会让**整个请求**返回 `code 9501「XXX返回字段不存在」`（`601318.SH`/`510300.SH` + `INVENTORY` 复现）。这条要写进适配器 docstring。

### A5. 运行时 `features` 也必须是「完整形状 + 显式 NA」【必修】

- 设计只在 §7.2 要求 `PROBE_CTX` 补全空形状。但**运行期**同样会踩：`build_ctx(..., cross_section=None)`（主流程忘了传/该标的无横截面）或某因子不可算时，若直接省掉 `roe_pct` 键，插桩里 `ctx["features"]["roe_pct"]` 会 `KeyError` → 沙盒探针把它判成脚本 bug → **误拒**。这与上一轮 `PROBE_CTX` 那个坑是同一类，只是发生在运行期。
- **对策**：`features` 的键**永远齐全**；不可算的因子给 `None` 并存 `na_reasons: ["gross_margin: operate_cost is NULL", ...]`；分位算不出时给 `None`（不是 0.0——0.0 是「最差」的合法分数，会把「不知道」伪装成「最差」，正好违反 §6.3 的精神）。

### A6. 溯源列装不下三份响应 + raw_cache 让「重述」永不可观测【必修】

- **`resp_sha256` / `cache_key` 各只有一列**，而一份 `financial_reports` 行来自**三个端点**（三份响应）→ 溯源断链。改为 `raw_refs_json`（`[{endpoint, resp_sha256, cache_key, page}]`）或三组列。
- **更隐蔽的一条**：`raw_cache` 是「同一 key 首写保留」，而财报缓存键如果没有「采集批次」维度，**同键重采永远命中旧 body** → 设计 §4.3 风险①（东财按最新口径重算历史）和 A1（公告日会变）在**实测上根本观测不到**，「记 warn 不覆盖」这条防线等于没有输入。注意 `raw_cache._anchor_date` 取 key 的第 3 段当锚点日（ADR-009 时效规则），财报键若不把日期放在第 3 段，则该规则静默不适用。
- **对策**：`cache_key = f"financial:{code}:{fetched_date}:{page}:{page_size}"`（把采集日做成锚点，第 3 段保持 ISO 日期以复用 ADR-009），并在 §5 写明「重采需换批次日（或清缓存），否则等于不重采」。

### A7. 采了行业分类，却没喂给「插桩0 行业特殊排雷」【必修·低成本】

- §1 的需求来源明确包含「插桩0 行业特殊排雷」，但 §3「做」只列了插桩 2/3，§7.3 也只改 2/3，**不做清单里也没写插桩0**——范围与需求来源不一致（要么补上，要么显式列入「不做」，不能含糊）。
- 现状：`candidate/builtin/p0_industry.py` 靠**标的名称关键字**猜行业（`"电器"/"集团" → 家电`）。本轮采到了真实的 `INDUSTRY_NAME`（实测：美的 `白色家电`、招行 `银行Ⅱ`、茅台 `白酒Ⅱ`、平安 `保险Ⅱ`，东财二级行业名，带罗马数字后缀）并写入 `instruments.sector`，但 **`ctx` 里没有 `sector` 字段** → 插桩0 依然只能靠名字猜。
- **对策**：`build_ctx` 增加 `ctx["sector"]`（读 `instruments.sector`）；插桩0 改为优先用 `sector`、名称关键字仅兜底；**并明确 `sector` 与 插桩0 的关键字表只能有一套行业口径**（否则「家电」与「白色家电」会同时存在）。同时把「行业非 PIT」的近似声明从 `screen.py` 复制到 `ctx`/报告里。
- 顺带：§4.5 说「写入 `instruments` 已有的 `sector` 列」——注意 `instruments` 无 append-only 触发器（这一点是对的），但要**留痕改了哪些行**（否则将来无法回答「这个 sector 是什么时候写进去的」，而它已经进了 `ctx`、进了分数）。

## B. 口径与正确性（高优先，属「算错不报错」类）

### B1. 「TTM 需要 4 个单季齐全」不足以覆盖全部 6 个因子

- `gm_yoy_pp` 需要**去年同期**的 TTM 毛利率 → 实际要 8 个单季（≈ 5–6 个累计点 + 期初存量点）。
- 「平均股东权益 / 平均存货」需要**期初存量**，即比 TTM 再多一期资产负债表。
- 因此 §6.3 的有效性判据应写成**每个因子各自的最小期数要求**，并在 `reason` 里写明「缺哪一期」。建议：`build_ctx` 输出 `periods_available`（可用的累计期数）与 `latest_period`，由插桩据此判。
- 参考最小集（`TTM(2026Q2) = 2026H1 + (2025FY − 2025H1)`，**只需 3 个累计点**；加平均值的期初则需 2025-12-31 存量行）：DoD 里那句「2025Q1–2026Q2 五个累计数」够用，但建议**把具体是哪几个报告期写进验收**，否则实现者会凭感觉凑。

### B2. `dupont` 三个分项的口径必须内部自洽，且要交代与 `roe` 的关系

- §6.1 说「需要均值的用期初期末均值」，§6.2 的 `roe` 用平均权益——但 `dupont` 的 `equity_multiplier`（总资产/权益）没说是期末还是均值，`asset_turnover` 也没说分母是期末还是平均总资产。**混用会静默产生两个不同的 ROE**。建议：全部用**期末存量**（教材口径）+ 在 §6.2 注明「与 `roe`（均值口径）存在口径差，故两者不构成恒等，报告需说明」，或者两者都改均值并加恒等断言（A2）。

### B3. 分位相关的三件小事

1. **极性**：`inv_days` 越小越好，但设计没说 `*_pct` 是不是统一「越大越好」。必须写死极性规则（建议全部转成「越大越好」），否则插桩作者极易搞反，而搞反**不会报错，只会让池子选反**。
2. **期次不同质**：横截面里各标的「最新已公告报告期」可能不同（4 月是 2025 年报+2026Q1 混排），拿不同期的指标排序是 stale-comparison。§7.1 已有 `asof_notice_date` ✓，建议再加 `period`（如 `"2026Q2"`）并在报告里给出**期次分布**。
3. **分位的样本集不同**：`inv_days` 对金融股不可算 → 该因子分位的 n 会比 `roe` 小。建议 `features` 里带每个 `*_pct` 的样本量（或统一 `cross_section_n`），报告里体现。

### B4. 「因子不可算」如何汇总成插桩的 `pass_flag` —— 没定义，且直接决定金融股命运

- 实测：招行/平安的 `RPT_DMSK_FN_INCOME` 行里**根本没有 `OPERATE_COST` 字段**（银行/保险报表结构不同），`INVENTORY` 为 NULL → 「营业成本」与「存货周转」对金融股天然不可算（这部分是自动的、好事）。
- 但**后果没被讨论**：若插桩2 要求「毛利率 + 存货周转 + 杜邦」齐备才算有效，则 **中期池会静默地把 3 只金融种子（招行、工行、平安）全部排除**，报告只会显示「pass_flag=False」。这必须成为**显式决策**：要么按行业给替代因子（金融股用 ROE + 权益乘数 + FCF 率），要么明确「金融股不进中期池」并**在报告里单独列一行说明**。
- `fcf_margin` 对银行尤其无意义（经营现金流受存款增减主导）→ 建议给因子加**行业适用性白名单**（哪怕只是 `na_reasons` 里注明），而不是靠 NULL 碰运气。

### B5. PIT 边界：`notice_date <= asof` 还是 `< asof`？

- 公告日通常在**收盘后**才公开。`notice_date == asof` 时当天盘中就把这份财报算进分数 = 轻度前视。项目既有约定是 `features_daily.created_at <= asof`，但财报的「公告时点」和行情不同。建议钉死一条（推荐 `notice_date <= asof`，并在文档里明说「视公告日为当日起可用」），否则将来回放会出现「同一天不同人算出不同的池子」。

### B6. 缺两条最有性价比的质检

1. **单位/量级断言**：§4.1 没写单位（实测为**元**，如 `TOTAL_ASSETS=643,101,789,000`）。建议在表注释与 `FinancialReport` docstring 写明「单位：元」，并加量级规则（如总资产在 `1e8 ~ 1e14` 之外 → `warn`）——量纲错 10000 倍是财报数据的经典事故，且**只会静默给出错数**。
2. **会计恒等式勾稽**：`|TOTAL_ASSETS − (TOTAL_LIABILITIES + TOTAL_EQUITY)| / TOTAL_ASSETS < 1e-6`（实测逐只成立）。这一条既是脏数据探针，也是**口径探针**——A2 那个「TOTAL_EQUITY 是不是归母」的问题，用这条一次就能验出来。建议直接进 §3 的「脏数据校验基本形态」。

### B7. ETF/空响应的处理必须写进设计

实测 `RPT_DMSK_FN_INCOME` 对 `510300.SH` 返回 `result=null / 返回数据为空`。设计 §3 说 ETF 进不了中期/长期池，但采集层会先在 4 只 ETF 上撞到空响应 → 必须明确「空响应 = 合法无数据（`[]`）+ 留痕」，**不许**当成抓取失败（否则 21 只里 4 只永远报错），也**不许**当成「有数据但为零」。

## C. 建议增强（可延后，但成本极低）

| # | 建议 | 依据 |
|---|---|---|
| C1 | 顺手多采几列：`DEDUCT_PARENT_NETPROFIT`（扣非归母净利）、`GOODWILL`（商誉）、`MONETARYFUNDS`/`ACCOUNTS_RECE`、`FIXED_ASSET`、`CURRENCY`、`REPORT_TYPE`/`REPORT_TYPE_CODE` | 均在实测响应里现成；扣非是护城河因子的标配，商誉是排雷的关键项 |
| C2 | 采集支持**多标的一次请求**：`filter=(SECUCODE in ("000333.SZ","600036.SH"))` 实测可用 | 63 次请求可压到个位数（受 pageSize=500 约束） |
| C3 | 留痕**每表覆盖**：报告里给出每只标的的三表期数与最早期（实测三表期数不同：招行 101/102/98、长电 93/96/93、宁德 39/41/41） | §4.4「取并集」是对的，但 NULL 分不清「源站本来没有」和「采集失败」，违反 fail-closed 精神 |
| C4 | `report_type` 由 `report_date` 派生 + 用 `REPORT_TYPE_CODE`（实测 001=年报/002=中报/003=一季报）或 F10 的 `REPORT_TYPE` 文本交叉校验 | 少一个可写错的采集字段，多一条校验 |
| C5 | DoD 增加一个**跨公告窗口**的验收：`asof = 2026-06-15`（一季报后、中报前），断言输出的 `reason` 明确说「该期尚未公告」而不是给出错值 | A1 的 bug 在现有 DoD（asof=今天）下**测不出来** |
| C6 | 补一条 ADR（本轮采集口径：累计→单季、公告日来源与回退、权益口径、行业非 PIT），并在 DoD 里加「文档同步」条目 | 项目惯例（ADR-011 估值/资金流采集口径）；骨架轮 DoD 有这条，本轮 DoD 缺 |
| C7 | 明确把「财报类排雷（审计意见/非标/造假）」写成**不做**并保留 `financial_screen_not_implemented` 语义 | 否则「插桩0 行业特殊排雷」的财报部分会再次无声明地消失（见 A7） |
