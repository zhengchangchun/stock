# P26 · 链路准确率视图（第一切片：报告 + CLI + 测试）

日期：2026-09-16 · 状态：第一切片已完成（见 §7 实施结果）· 预算上限 $6

## 1. 目标 / 非目标

**目标**：给「智能体全链路（股票分析 → 购进方案 → 模拟持仓 → 实际交易 → 持有分析）」
一个**用真实数据、按来源分列**的准确率视图：`.venv/bin/python -m stocklab.cli.main chain accuracy`
→ `reports/<today>-chain-accuracy.{json,md}`。

**非目标（本切片不做）**：不做新指标口径、不改任何预测数字、不加字段/表、不写
`docs/experiments/`、不碰 `predictions`/`verifications` 既有行、不实现调度（调度在 nanobot 侧）。

## 2. 关键设计决策

### D1. 回放 / 实时的判据：**复用** `session/review.py` 已有口径，不另立一套

库里 `predictions` / `verifications` **没有** `origin` 列。已有且唯一的可验证判据是
`session/review.py` 的 `classify()`（ERROR_DIARY #16 定的口径）：

```
LIVE  ⟺  predictions.created_at 的前 10 位 == predictions.asof_date
REPLAY ⟺ 其余（历史回放、事后补跑）
```

本模块 **import 并复用** `review.classify` / `review.PROVENANCE_RULE` / `review.load_rows`，
保证「链路视图」与「每日复盘」在同一个口径上，绝不出现两套判据。

**判据的边界（必须在报告里写明）**：`created_at` 是**入库时刻**而非决策时刻 ——
当天补跑一个历史 `asof` 会被记成 LIVE；反之跨零点补跑当日预测会被记成 REPLAY。
→ 报告里如实写出这条限制，并给**建议方案**（新增 `origin` 标记列，见 §5），
本轮**不加写入路径**（硬约束 3 / 「只报告 + 给方案」）。

### D2. 四段分列且各自独立判定样本量

| 段 | 数据来源 | n_days 定义 | 内容 |
|----|---------|------------|------|
| 回放段 | `verifications` ⋈ `predictions`，`provenance == replay` | 按日聚类后的**交易日数** | 方向命中 / Brier / `range_80` 覆盖率 / 关键位兑现 / 决策层读数 |
| 实时段 | 同上，`provenance == live` | 同上 | 同一套指标 |
| 模拟盘段 | `paper_nav_daily` | 该段 nav 行的**交易日数** | 三臂 vs `index_300` 区间涨跌 + 差值（**只并列**） |
| 实盘段 | `real_trades` + `cash_flows` | 有成交的**交易日数** | 笔数 + 成本合计 + 是否够算准确率 |

### D3. 样本不足是**结构性**的，不是文案

- 阈值 = `verify.report.MIN_DAYS`（120 交易日，全仓同源）。
- `n_days < 120` → `sufficient=false`，`notice = "样本不足（n=X < 120），不构成准确率结论"`。
- **markdown 里不渲染任何准确率表 / 基准对照表**（表格只在 `sufficient=true` 时渲染）
  → 「不给该段任何准确率结论句」由渲染逻辑保证，而不是靠人记得删。
- 按日聚类 CI：方向指标除 `daily_stats` 的正态近似区间外，另给**日度 bootstrap**
  （复用 `risk.kelly.daily_clustered_winrate_ci`，其 `BOOTSTRAP_N/SEED` 是仓库先验固定值）；
  **不新造统计量**。

### D4. 确定性

`render_markdown` 与 `build_*` 都是纯函数式：不读时钟、不含 `created_at`、不输出
`positions_json` 原文；json 用 `sort_keys=True`，md 无生成时刻
→ 「同输入两次运行逐字节一致」是结构性的（沿用 `review`/`verify` 报告的既有纪律）。

## 5. 发现与建议（本轮只报告，不实现）

**缺一个可验证的来源标记列。** 现状靠 `created_at` 前 10 位 vs `asof_date` 推断，
存在 §D1 的两类误分。建议（留给后续 ADR）：

- 给 `predictions` 增加 `origin TEXT CHECK (origin IN ('live','replay'))`，
  由 `predict run` / `verify backfill` 各自显式写入（append-only 表加列 = 迁移，
  既有行填 `'replay'` 并用 `created_at` 判据回填 —— **需要一次单独的口径变更评审**）；
- 在那之前，报告必须逐字写明当前判据与边界（本切片已做）。

## 7. 实施结果（2026-09-16，实测）

`chain accuracy` 跑通，四段实测读数：

| 段 | n_days | 门槛判定 | 已写入预测 | 已打分 |
|----|--------|---------|-----------|--------|
| 回放 | 3097 | 样本充足 | 6055 | 6055 |
| 实时 | **0** | 样本不足（n=0 < 120） | 4 | **0** |
| 模拟盘 | 2 | 样本不足（n=2 < 120） | — | — |
| 实盘 | 1 | 样本不足（n=1 < 120） | — | — |

**与任务书预期不符的一处（如实上报）**：任务书写「当前实时段大约只有 1–2 天」，
实测 **0 天**。原因不是判据错，而是实时的 4 条预测（asof 2026-09-15 → target 09-16、
asof 2026-09-16 → target 09-17）**目标日还没到 / 还没打分** ——
`verifications ⋈ predictions` 里只有被打分过的预测才进准确率分母。
故报告新增 `predictions_written` / `predictions_verified` 两个读数分列，
避免 `n=0` 被读成「没有实时预测」。已记入 ERROR_DIARY #36。

**判定字段（验收判据 5 的答案）**：`predictions.created_at` 前 10 位 vs
`predictions.asof_date`（字符串比较），复用 `session/review.py` 的 `classify()`。
这是**推断**而非断言，边界与建议方案（新增 `origin` 列）写在报告 §0 与 §5。

验证证据：`cmp` 两次运行 md+json 无差异；
`.venv/bin/python -m pytest` → **1536 passed**（基线 1528，+8）；
`bash scripts/verify.sh` → `✅ 验证通过: all`（4c 回归红线三目标全绿，未变红）。
