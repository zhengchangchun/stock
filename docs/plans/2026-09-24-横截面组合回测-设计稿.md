## §0 一句话

「按 `adj_score` 排序选前 N 只」这一步**在既有代码里已经实现了**（`candidate/pools.py::select_top` 就是它，池成员即前 N）；
所以横截面组合回测**不是新引擎**，而是一个**单变量实验**：把「持有集合 = 池内前 N」换成「持有集合 = 池内全部合格标的」，看 Δ 是否显著。
**但实测表明这个实验目前只有一个格子能出结论**（短期池 5 日调仓 + 窗口起点 ≤ 2015-01-01，171 个验证周期）；其余格子结构性 `INCONCLUSIVE`（算术必然，不是缺陷）。

## §2 六个问题的逐条结论

### Q1 —— 它到底要回答什么问题？与既有沙盒的口径关系？

**结论：要回答的是「`adj_score` 排序取前 N」这一步的增量价值（selectivity 有没有 edge），而不是「池等权持有一段时间赚不赚钱」。**
后者**已经答过了**：`period_returns` 持有的就是 `select_top` 选出的前 N，即池等权收益（`replay.py:170-175` 取池成员 → `:208-209` 等权）。

**与既有沙盒的口径关系 = 同一份口径，只换「持有集合的定义」这一个变量。**
- 不新增第二份 verdict / 门槛 / CI / 成本 / 基准：全部走 `plugin/sandbox.py::run_sandbox` 与 `candidate/replay.py`。
- 唯一的新东西 = 一个**对照臂**：「该池**全部合格标的**（`scored[pool]` 在 `select_top` 之前）等权」，与现状「前 N 只」配对求 Δ。
- 这正是「单变量原则」要求的形式，也是既有沙盒**做不到**的事 —— 既有沙盒的 Δ 两端是**同一个池定义、同一个 `select_top`、两个插件版本**（`replay.py:284-337`），从来没测过「选不选」这个变量本身。

**反证方式**：若把 `select_top` 的 `topn` 设成「池内全部合格数」，`period_returns` 的两条调用（cand/base）会逐周期完全相同 ⇒ Δ ≡ 0 ⇒ 实验设计被证伪（说明对照臂没起作用）。

### Q2 —— 有效样本量是多少？要多少标的/多长时间？（本站的核心数字）

**结论一：按日聚类后，有效样本量 = 调仓日数，与标的数无关。**
`period_returns` 每个调仓周期只产出 **1 个**观测（`replay.py:254` `out.append(...)` 在周期循环体内），同期内 21 只标的的日收益是同一持仓的同一天，不构成独立样本。**加标的不增加有效样本量**（p5 的结论在实测下成立）。

**结论二：实测各格子的周期数（`split_train_validate` 的验证段 = 决定 verdict 的那一段）**

| 窗口 | 交易日 | `short`(5) 周期 → 验证 | `mid`(20) | `long`(60) |
|---|---|---|---|---|
| 2024-06-20 → 今（**21 只全满 250 根**） | 553 | 110 → **33** | 27 → 9 | 9 → 3 |
| 2023-01-13 → 今（17 只个股全满） | 897 | 179 → **54** | 44 → 14 | 14 → 5 |
| 2023-09-24 → 今（**当前 CLI 3 年窗**） | 727 | 145 → **44** | 36 → 11 | 12 → 4 |
| 2015-01-01 → 今 | 2852 | 570 → **171** ✅ | 142 → 43 | 47 → 15 |
| 2007-01-15 → 今（日历起点） | 4789 | 958 → **288** ✅ | 240 → 72 | 80 → 24 |

**复现命令**：

```bash
.venv/bin/python -c "
import sqlite3; from stocklab.config import DB_PATH
from stocklab.candidate.replay import rebalance_dates, split_train_validate
c = sqlite3.connect(f'file:{DB_PATH}?mode=ro', uri=True)
days = [r[0] for r in c.execute('select date from trading_calendar order by date')]
for s, e in [('2024-06-20','2026-09-24'),('2023-01-13','2026-09-24'),
             ('2023-09-24','2026-09-24'),('2015-01-01','2026-09-24'),
             ('2007-01-15','2026-09-24')]:
    nd = len([d for d in days if s <= d <= e])
    line = f'{s}~{e} days={nd:5d}'
    for pool, p in (('short',5), ('mid',20), ('long',60)):
        n = len(rebalance_dates(days, period=p, start=s, end=e)) - 1
        tr, va = split_train_validate([0.0] * max(n, 0))
        line += f' | {pool} {len(tr)}+{len(va)}'
    print(line)
"
```

**结论三：越过 `MIN_VALID_PERIODS=120` 所需的时长（纯算术，`397` = 最小总周期数）**

`split_train_validate` 的最小满足点是 **总周期 397 → 验证 120**（`:266-281` 的 `max(1, min(int(n*0.7), n-1))` 算出来；`397 → train 277 / validate 120`，`396 → 119`）。按日历实测 4789 日 / 19.69 年 = **243.2 交易日/年**：

| 池 | 每周期交易日 | 所需交易日 | 所需年数 |
|---|---|---|---|
| `short` | 5 | 397 × 5 = **1985** | **8.2 年** |
| `mid` | 20 | 397 × 20 = **7940** | **32.6 年** |
| `long` | 60 | 397 × 60 = **23820** | **97.9 年** |

**结论四：「需要多少标的」这个问题不成立** —— 标的数不改变有效样本量（结论一）。真正缺的是**时间**。

### Q3 —— PIT 与防前视？

**结论：分数侧的 PIT 已经由 `score_pipeline` 保证，可直接复用；但「价格侧」与 `rules.check_no_lookahead` 的精神只对了一半，存在一个必须披露的口径差异。**

| 项 | 现状 | 位置 |
|---|---|---|
| K 线 PIT | SQL 层挡：`WHERE date <= asof` | `run.py:83`、`m2/context.py:73-77` |
| 财报 PIT | `notice_date <= asof`（全库无 NULL，最早 1991-04-30） | `score.py:86`；实测见 §1.1 |
| 价格 PIT | `_close_on` 用 **`date = d` 精确匹配**（不是「≤ d 的最近一根」） | `replay.py:88-92` |
| **口径差异（要披露）** | `rules.check_no_lookahead` 明确允许 **「停牌时用上一交易日收盘」**（`paper/rules.py:226-228`：「停牌时用上一交易日收盘是合法的（`< asof`）」）；`_close_on` 在停牌日返回 `None`，该只被摈出 gross（`replay.py:193-195`）。**两者对停牌的处理不同**，回放口径更保守（当「不可交易」计，等价于持现金），但**不是同一个语义**。 |
| 已知非 PIT 项 ① | ST 判定取 `Instrument.name` 的**当前**名称 | `screen.py:82-86`（源码自述「非 PIT…仅为近似」） |
| 已知非 PIT 项 ② | 行业分类取 `instruments.sector` 的**当前**值 | `score.py:96-97` |
| 已知非 PIT 项 ③ | 种子宇宙是**事后挑选**的 21 只（21 只白马蓝筹） | `candidate/seeds.py:30-59` |

**「复用 `check_no_lookahead` 精神」的落法（本站的结论）**：给回放侧补一个**结构位**，把 `_close_on` 的返回值包装成 `paper.engine.pit_close` 已经用的那个 `Price(price_asof=...)` 形状，再调 `rules.check_no_lookahead(asof, marks)` —— 复用**同一个函数**，不另写一份守卫（`m2/context.py:251` 也是这么做的：同一个函数在两个入口各跑一遍）。
**这不是本站要做的实现**，是写进方案 B 的实现约束。

**关于 `candidate_members` 的 `adj_score` 是否 PIT**：表里那 38 行是**当期快照**（`status` 是当前状态、`entered_at` 是当时值），但 `status`/`entered_at` 是**状态字段、不进分数**；分数本身由 `score_pipeline` 在 asof 时现算。⇒ 回测**不读** `candidate_members` 的分数，只读它的**字段定义**。

### Q4 —— 成本与执行口径？

**结论：一律复用，一行公式都不另写。** 已逐条列在 §1.4。三个成本常量的落点：

| 口径 | 常量 / 函数 | 位置 |
|---|---|---|
| D-13 名义仓位 | `POSITION_NOTIONAL = 100_000.0` | `stocklab/config/replay.py:18` |
| D-13 换算 | `_qty_for(px) = max(1, int(POSITION_NOTIONAL / px))`（整股截断） | `replay.py:102-110` |
| D-14 滑点 | `(costs.slippage_bps / 10_000) * n_filled / n_hold` | `replay.py:252` |
| 费率表 | `commission 0.025% / min 5 元 / 印花税 仅卖出 0.05%(股票) 0%(ETF) / 过户费 0.001%(股票) 0(ETF) / 滑点 5bps` | `stocklab/config/costs.py:60-67` |
| ETF 口径 | `CostModel(asset_class=...)`，未知口径**抛错**不退化成股票费率 | `costs.py:69-74` |

**必须披露的既知偏差（照实写，不粉饰）**：`period_returns` 只用**单一 stock 口径** `CostModel`（`replay.py:166`），即 4 只 ETF 按股票费率计（多扣印花税/过户费）。`replay.py:152-165` 给了三条理由：①Δ 两端同成本、绝对水平抵消；②方向保守（成本偏高）；③`SEED_UNIVERSE` 里 ETF 只 4/21 且不进短期动量池。**若横截面把 ETF 计入持有集合，理由 ③ 不再成立**（短期池 6 只里可能出现 ETF）⇒ 方案 B 的实现约束里必须写：**持有集合含 ETF 时，逐标的按 `instruments.type` 取 `CostModel`**（ADR-008 的做法）。

**教训引用**：`docs/plans/2026-09-21-回放成本口径-验收记录.md`（D-13/D-15）—— 短期池的净超额被成本口径改写；D-15 记录了「就地改写历史条目」这一留痕事故，本站只**引用**不改。

### Q5 —— 与模块2 通路 A 的关系？（**必须二选一**）

**结论：横截面回测 = 基建，不是策略。自己不出信号。**

理由（三条，都可核）：
1. **A1 已经在做「池内选标的 + 权重」**：`m2_a1` 的返回形状是 `{picks, cash_pct}`（`stocklab/m2/channel_a.py:8`），权重常量 `LIMIT_N=5 / CAP_PCT=25.0 / CASH_FLOOR=10.0 / LOT=100` **写死在插桩源码里**（真库 `plugin_scripts.script_id=14`，`version=1.0.4`），改要发新版本走 `plugin submit`。
2. **若横截面自己出一套选股信号，就形成第二套选股口径** ⇒ 违反模块2 需求书 §5 A5（「同一概念只有一份真源」）、并直接踩 `docs/plans/2026-09-22-模块2-需求书.md` §D-30 的「两处不得混用」。
3. **A1 与沙盒不共用任何驱动代码** —— 这是「基建缺口」的真实位置：
   - 沙盒驱动的是插件 `0–4`（`score.py:27,30,124-129`），**不驱动 `m2_a1`**；
   - `m2_a1` 只在模块2 通路 A 里被调用：`m2/plugin_hooks.py:51-54` → `lifecycle.call_active(conn, 'm2_a1', ctx)`，ctx 由 `m2/context.py:236-283` `channel_ctx` 构造；
   - 要构造那份 ctx 需要**账户状态**（`cash` / `positions` / `total_assets` / `holdings`），即 `paper/engine.py` 的账本 —— 沙盒完全没有这一层。
   ⇒ **给 A1 的改动做「前后对比」的既有机制只有 D-26 的「每策略版本一个 `paper_accounts` 行 + 独立 NAV」，反馈周期 = 实盘交易日数**（`m2/plugin_hooks.py` + `paper/engine.py:845` `step_account`，一天一个观测）。

**所以本站在 Q5 上的两个结论**：
- **横截面回测（方案 B）服务的是模块1 的打分链，不服务 A1**；它测的是「`select_top` 这一步值不值」。
- **给 A1 做历史对比是另一件事**（要驱动 `m2_a1` + 账户层 + 逐日推进），**不在本站范围**（列为方案 C 的一部分／单列一站）。理由：它需要的输入（候选池快照）在库里**只有 2 个 `asof`**，而 `m2/context.py:129` 是**读快照**、不是现算 —— 也就是说 A1 回放**在数据上就先被卡住**，必须先解决「历史快照从哪来」这个问题，那是独立的一站。

### Q6 —— 它跑在哪？占不占 `ops close` 的 900s？进不进红线基线？

**结论：离线只读命令，不进 `ops close`，不进红线基线。**

| 事实 | 位置 |
|---|---|
| `plugin sandbox` 是**离线只读**命令，`help` 自述「离线只读」 | `stocklab/cli/main.py:4359-4372` |
| `ops close` 的 14 步里**没有** sandbox 类步骤 | `stocklab/ops/chain.py:81-114` |
| `ops close` 整轮预算是 900 s | `stocklab/ops/chain.py:71` `CLOSE_TIMEOUT_S = 900.0` |
| `plugin sandbox` **不写** `plugin_backtests`（只有 `plugin submit` 写） | `stocklab/cli/plugin.py:47-72`（docstring 明写「没有对比跑完就没有对比报告可写」） |

**实测耗时（本站亲自跑的只读测量）**：见 §5 ——一次 `short` 池 3 年窗回放（146 个调仓边界 / 145 个周期、两个版本）= **133.3 s**；同一池放到 2015 窗（571 边界 / 570 周期）= **400.1 s**。

**⇒ 设计约束**：方案 B 的命令**不在 `CLOSE_STEPS` 里**、**不写任何表**、**不进 `scripts/verify.sh` 的红线基线**（红线基线是三目标：`pytest` / `verify.sh` / 库指纹；一次几十秒的只读研究命令不该拖慢每日链）。
**但**：`ops close` 的 900 s 预算是**整轮**的（14 步合计），任何新命令若被塞进链里，必须先把这条链的实测总耗时与预算比对再谈 —— 本站不塞。

## §3 三个方案

### 方案 A —— 不做，只留触发条件

**内容**：不建任何基建；在 `docs/plans/2026-09-15-p5-策略库.md` 的「多标的组合层（横截面选股）」一行追加**启动触发条件**。

**触发条件（三条中任一满足才启动）**：
1. 出现**第二个**「验证段 ≥ 120 周期」的格子（现在只有 `short` × 窗口 ≤2015-01-01 一个，见 Q2 表）；
2. 种子宇宙从 21 只扩到 **≥ 100 只**（`screen.py:29` 的 250 根门槛下，21 只上的横截面与「持全部」的差异上限就是 6/21→1，区分度结构性地小）；
3. `m2_a1` 出现需要历史对比的**口径级**改动（不是参数微调）。

**成本**：0（一份文档）。
**风险**：`adj_score` 的 `select_top` 这一步**继续处于「样本内、未经验证」状态**（三个池插桩的 `risk_list` 里自己就这么写的，见真库 `plugin_scripts.script_id=3/4` 的源码），而它是**三池全部输出的形状**。**风险承接者**：模块1 的候选池 —— 池成员每天被 A1 消费。

### 方案 B —— 最小可用（**推荐**）

**内容**：新增**一条离线只读命令**，只做**一个单变量实验**：

> 在**同一个池、同一个窗口、同一套成本与调仓口径**下，
> 比较「持有集合 = `select_top` 前 N 只」（现状，`candidate/pools.py:31`）与
> 「持有集合 = 该池**全部合格标的**」（对照臂）的**逐周期收益差 Δ**，
> 判定走 `plugin/sandbox.py::run_sandbox` 的既有口径（`MIN_VALID_PERIODS=120`、2000 次 bootstrap、CI 下界 > 0 → `WIN`），
> `sh000300` 超额**并列报告**（`replay.py:348-386`）。

**实现约束（六条，全部是「不许另造」）**：
1. 持有集合只作为 `period_returns` 的一个**显式产品参数**传入 —— 不能复用 `_pools_for_test`（`replay.py:116` 明写「**测试接缝**，生产路径不传」）。
2. **只改这一个变量**：调仓日序列、`POSITION_NOTIONAL`、`CostModel`、`_limit_hit`、`floor_lot`、70/30 切分、bootstrap 种子全部不动。
3. 持有集合含 ETF 时，逐标的按 `instruments.type` 取 `CostModel`（修掉 §Q4 的既知偏差；`costs.py:69-74` 的未知口径抛错行为保留）。
4. 窗口**必须显式传**、**必须 ≥ 2015-01-01**，且**在跑之前落盘预注册**（窗口、池、N、判定判据）—— 因为 3 年窗只有 44 个验证周期（Q2 表），而同一个短池在 11 年窗上是 +1.10%/期、在 3 年窗上是 −0.27%/期（§1.1）⇒ **窗口选择就是结论**，不预注册就等于自选区间。
5. 价格侧 PIT 守卫复用 `paper/rules.py::check_no_lookahead`（同一个函数，见 Q3）。
6. 输出落 `reports/`，**不写库**；报告必须并列写出 §Q3 的三条非 PIT 项与 §Q4 的成本口径偏差。

**成本**：**实测**（§5）——推荐窗（`short` × 2015-01-01 起，570 周期、两版本）= **400.1 s**；当前 3 年默认窗 = 133.3 s。另加实现工作量（一条命令 + 一个池定义参数 + 定向测试）。
**风险**：
- **只在 `short` 池出得来结论**（Q2 结论五）。`mid`/`long` 跑出来必是 `INCONCLUSIVE` —— 不许当成「没效果」，那是样本不足。
- **结论天然带选择偏差**：种子是事后挑的 21 只白马（`seeds.py:30-59`）。Δ 若为正，只能说「在这 21 只上、这段历史上，选前 N 比持全部好」，**不能说「选股有效」**。报告里必须写死这句。
- Δ 的 CI 跨 0 ⇒ 结论是「**无可测的选股增量**」并照实上报（`plugin/sandbox.py:221-235` 的 token 是 `LOSE`，但 `LOSE` + CI 跨 0 的读法是「**没有证据表明更好**」，不是「显著更差」——见 ADR-017 `docs/decisions/2026-09-20-ADR-017-沙盒回放口径.md` 的原文）。

### 方案 C —— 完整

**内容**：在 B 之上，把横截面做成**可配置的组合回放**：

| 维度 | 参数化内容 |
|---|---|
| 持有只数 N | 把 `POOL_TOPN`（`pools.py:31`）从模块常量变成**参数** |
| 权重方案 | 等权（现状）／按 `adj_score` 加权 |
| 跨池合并 | 三池**并集去重**后再选（现状是每池独立；三池非互斥，19 槽 → 11 code，见 §1.1） |
| 账户层 | 接 `paper/engine.py`（现金、整手、`plan_target_weight`）产出**连续 NAV 曲线**而非逐周期收益 |
| 逐日推进 | 驱动 `m2_a1` 那一层（`m2/plugin_hooks.py:51-54` + `m2/context.py:236-283`），即 Q5 说的「A1 回放」 |

**成本**：一次回放（400.1 s，§5）× 参数组合数（N × 权重 × 跨池）**线性增长** —— 例：5 个 N 值 × 2 种权重 = **4001 s（≈67 min）一次扫描**。账户层与「A1 逐日回放」是另两站的工作量（Q5：`candidate_members` 只有 2 个 `asof`，历史快照从哪来先要定）。
**风险（这是本站最该拦下的一条）**：
- **参数化 N / 权重 = 打开搜索空间**。在**同一段全样本**上跑 N ∈ {3,5,8,…} × 权重方案，再报「最好的那个」的成绩 —— 这正是 `CLAUDE.md` 反过拟合红线第 1 条（全样本调参后再报全样本成绩）与第 3 条（参数搜索越过 walk-forward 训练窗）。**必须在 B 拍板后单列一站**，且参数搜索只能发生在训练窗内（`replay.py:263` 的 70% 段），验证段只读一次。
- 三池并集去重引入新口径（`m2_a1` v1.0.0 正是在这里踩过 `sqlite3.IntegrityError`，见 `stocklab/m2/channel_a.py:153`）⇒ 必须**复用**已定的去重语义，不能另定一套。
- 账户层会引入 `paper_accounts` 的隔离与熔断常量（D-26/D-27），那是主干硬约束、AI 不可改，成本远大于 B。

## §5 实测耗时

回放的耗时**几乎全在 `score_pipeline`**（`period_returns` 每个周期对**每个版本**各调一次，见 `replay.py:173,180`），
所以下面按「逐调仓日测一次 `score_pipeline` 再线性求和」来测 —— 这是 O(n) 的测法。

**命令（本站亲自跑，真库只读）**：

```bash
cat > /tmp/p60_time_replay4.py <<'EOF'
import sqlite3, time, statistics
from stocklab.config import DB_PATH
conn = sqlite3.connect(f"file:{DB_PATH}?mode=ro", uri=True); conn.row_factory = sqlite3.Row
from stocklab.candidate.replay import rebalance_marks
from stocklab.candidate.run import score_pipeline
for pool, ws, we in (("short", "2023-09-24", "2026-09-24"),
                     ("short", "2015-01-01", "2026-09-24")):
    marks = rebalance_marks(conn, pool=pool, start=ws, end=we)
    ts = []
    for i, d in enumerate(marks):
        t = time.time(); score_pipeline(conn, asof=d); ts.append(time.time() - t)
        if i in (0, 1, 2) or (i + 1) % 50 == 0:
            print(f"  [{pool} {ws}] i={i:4d} asof={d} call_s={ts[-1]:.3f}", flush=True)
    print(f"{pool} {ws}~{we}: marks={len(marks)} periods={len(marks)-1} "
          f"mean_call_s={statistics.fmean(ts):.3f} max_call_s={max(ts):.3f} "
          f"one_version_s={sum(ts):.1f} replay_two_versions_s={2*sum(ts):.1f}")
EOF
PYTHONPATH=. .venv/bin/python /tmp/p60_time_replay4.py
```
