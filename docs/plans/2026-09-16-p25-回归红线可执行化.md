# P25：把「回归红线」从文档快照常量改成仓库内可自动校验的不变量

- **日期**：2026-09-16
- **起点**：`master` @ `90283c6`，`pytest` 1508 passed，`verify.sh` ✅
- **依据**：`docs/errors/ERROR_DIARY.md` #34（红线写成快照常量 → 70 分钟失效无人发现）、#32（先报告再改）
- **预算**：$4

## 1. 问题

P8 的红线以「`predict run --asof 2026-09-14` 报告 sha256 = `a61d026b…`」的**快照常量**形态写在
`docs/plans/2026-09-15-p8-实验流水线.md:20`。`grep -rn a61d026b` 全仓只命中 docs ——
**没有任何测试或脚本在守它**。该值在记下后 70 分钟即因 `be9c343` / `015c466` 给
`evidence.inputs` 加口径回显字段而失效（`MODEL_VERSION` 未变、预测本身未变），
此后多轮提交无人发现，直到 P24 强制重跑才暴露。

同类缺口：P24 的 F1 逐字段比对、P23 的报告复现，都只在 `/tmp` 里临时做过，
**仓库内没有可长期复用、可自动跑的基线**。

## 2. 目标 / 非目标

**目标**：让「报告是否被意外改动」有一条**自动会跑、失败会大声报、且告诉人怎么有意重新基线**的检查；
文档里的旧值 append-only 保留 + 标注失效时间与原因。

**非目标（硬红线，本轮不动）**：不新增变体、不重跑已否证的四条轴、不改任何预测数字/口径/`MODEL_VERSION`、
不碰 `predictions`/`verifications` 既有行、不删历史。

## 3. 关键实测事实（本计划的前提，P25 期间亲自复验）

| 项 | 值 | 出处 |
|---|---|---|
| `predict run --asof 2026-09-14` 报告 sha256 | `b69afb71…910bcb` | 本机 `--db /tmp/p25.db --report /tmp/p25-predict.json`，0.48s |
| `verify backfill 2013-12-23→2026-09-14` md sha256 | `18f2eeef…9d0d` | 本机 CLI 原命令，**3m35s** |
| 同上 json sha256 | `149f1094…2ee6` | 同上 |
| 只读重算（`load_verification_rows`+`summarize`+`render_markdown`） | md/json sha **与上两行逐字节相同** | 本机，**0.7s**，且**不写任何表** |

> 第 4 行是本次设计的关键杠杆：backfill 报告是 `verifications` 行的**纯函数**，
> 所以不必跑 3m35s 的写库回放，只读重算即得同一份字节。CLI 原命令保留为可选复验路径。

## 4. 设计

### 4.1 两层 × 两档

| | 字节级（sha256 逐位相等） | 数字叶子级（递归键路径比对） |
|---|---|---|
| 抓什么 | 字段集被改动（#34 的翻车类型） | 数值漂移，且**容忍纯文字新增** |
| 失败输出 | 期望/实际 sha + 差异叶子摘要 | **差异键路径清单**（changed / added / missing） |

两条红线各跑两档：

- **(a) `predict run --asof 2026-09-14`**：真实库（**跑在库的副本上**，保证零写入）。
- **(b) `verify backfill 2013-12-23 → 2026-09-14`**：只读重算路径（默认）/ CLI 原命令（`--cli-backfill` 可选复验）。

### 4.2 运行形态（诚实标注 hermetic 与否）

1. **hermetic pytest**（`tests/test_redline_baseline.py`）：合成夹具建库 → 跑 `predict run` →
   与基线 `predict_synthetic` 段比 sha + 叶子。**不依赖真实库、不联网**。
   这是「字段集被改动」在**提交时**就能变红的那一道。
2. **非 hermetic 入口**（`scripts/check_redlines.py`）：**显式声明依赖本地真实库**
   `data/stocklab.db`；库不存在时打印醒目「⏭ 跳过（非 hermetic）」并退出 0，
   **绝不假装跑过**。由 `scripts/verify.sh` 调用。

### 4.3 基线落盘

`docs/baselines/redlines.json`（git 跟踪；`reports/` 被 ignore，不放那里）。
每段必须写：取值日期、取值命令、`MODEL_VERSION`、**谁在什么条件下必须重新基线**。

### 4.4 失败信息（把 #34 的教训固化成代码）

三段式：① 先做归因实验（回退改动重跑同命令 `cmp`）；② 确认是有意改动后用哪条命令重新基线；
③ 把新值写进台账/文档（append-only，不删旧值）。

## 6. 验收

- (a) 负向实验：改基线 → 红（失败在目标断言行，贴输出）→ 还原 → 绿。
- (b) `pytest` 1508 + 新增 = 全绿（只增不减）；`bash scripts/verify.sh` 通过。
- (c) `predict run --asof 2026-09-14`（输出 `/tmp`）跑两次，`cmp` 无输出 + sha 相同。
- (d) 文档改动 append-only：`git diff --stat` + hunk 显示只有 `+` 行。
- (e) 增量提交。
- (f) 汇报含命令出处；拿不出出处标「未验证」。

## 7. 风险点（查 ERROR_DIARY 后）

- #34：**别再把红线做成没人守的快照值** —— 必须有自动入口 + 失败大声报。
- #34 教训 2：**「版本号没变」推不出「报告没变」** —— 所以字节级那一档必须保留。
- #32 / #34 教训 4：**先报告再改**；旧值 `a61d026b…` 只追加标注失效，**不删不改**。
- 真实库检查会让「数据被改动」也变红 —— 这是特性不是 bug，但必须在失败文案里说清
  「也可能是数据/库变了，先归因再决定是否重新基线」。
- 跑真实库命令一律**在库副本上跑**，杜绝意外写入 `predictions` / `verifications`。
