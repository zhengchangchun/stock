## 1. 为什么做：那次归因花了约 40 分钟

P25 的两条「真实库」红线（`predict_real_2026-09-14`、`backfill_real_2013-12-23_2026-09-14`）
是拿**冻结的报告 sha256** 当基准（`docs/baselines/redlines.json`）。它们一红，只说明
「今天的报告 ≠ 那天的报告」，**分不清是代码回归还是库变了**。

2026-09-21 实际发生的一次：两条真实库红线变红。当时只能靠**单变量实验 +直查库**逐条试，
约 40 分钟后才归因到「库变了」，共四条：

| 库变异 | 证据 |
|---|---|
| 标的范围 6 → 21 | `predict` 的清单取自**库 `instruments` 表**（不是代码常量）|
| 600690 历史回填 | `n_bars_used 6062 → 7807`，起点 1993-11-19 |
| 账本原本为空 | `predictions`/`verifications` 全 0 行 → 回放补了 42329/42312 行 |
| **复权链原本为空** | `corp_actions`/`adj_factors` 各 0 行 → 0 事件、因子恒 1（静默失真）|

这四条**全都写在一份库指纹里**。本任务就是把它写进基线、并在判红时并排打出来。

## 2. 记录什么

用户要求的三项 + 两项必要补强（见模块 docstring 的表）：

| 节 | 内容 |
|---|---|
| `instruments` | 标的清单（排序后的代码）+ 只数 |
| `bars_daily` | 全表 `n`/`first`/`last` **＋逐标的** `n`/`first`/`last` |
| `predictions` | `n`、按 `origin`（live/replay）分组、按 `model_version` 分组、asof 区间 |
| `verifications` | `n`、target 区间 |
| `corp_actions` / `adj_factors` | 事件数与因子行数（口径变化的直接证据）|
| `valuation_daily` / `money_flow_daily` / `financial_reports` | `n`/区间/标的数 |
| `content_sha256`（**补强 1**）| 关键表（`bars_daily`/`predictions`/`verifications`/`adj_factors`/`corp_actions`）的**内容摘要** |

**补强 1 的理由**：只看行数会漏「**行数相同、内容不同**」——复权口径改变正是这种
（重放不增行，但每一行的价格基准都变了）。判据是 `docs/baselines/redlines.json` 的 sha，
而它的输入就是这些行的内容，所以内容摘要必须进指纹。

**补强 2**：`verifications` 的内容摘要走 `JOIN predictions` 取 `(code, asof_date)` 做身份，
**不用自增 `pred_id`** —— 同一批预测重放一次 id 就全变，用它会让指纹自己变成噪声。

## 3. 两条硬约束（都写成了测试）

1. **零写入**：连接一律 `file:...?mode=ro`（`_connect_ro`）。指纹是**诊断**动作，不能污染被诊断的库
   —— 预测类表都是 append-only，写错一次不可撤。测试：整库 sha256 前后一致；`INSERT`/`DELETE` 必须抛错。
2. **确定性**：不含时间戳、不含自增主键、不含 `fetched_at`/`created_at` 这类入库时刻列。
   同一份库内容两次采集**逐字节相同**（测试钉住）。测试同时反证：改 `fetched_at` → 指纹不变；
   改 `close` → `content_sha256` 变、`rows` 不变。

## 4. 它不是红线

指纹**不一致不判红**：`bars_daily` 每天都在涨，判红等于每条红线天天红。
指纹只有一个职责 —— **在红线红的时候，把「库变了」这件事当场摆出来**：

- 指纹**一致** ⇒ 这次红**不是库涨了**，直接按 #34 三步做**代码**归因实验；
- 指纹**不同** ⇒ 先按「库/口径变异」解释，确认是有意变异后再 `--regen`。

打印顺序按**重要程度**而非字母序：整表规模与内容摘要在前，数十行「某标的 K 线 +1」折叠在后
（测试钉住顺序：`.predictions` 行的位置必须早于 `bars_daily.000000`）。

### 5.3 老基线（加指纹之前生成的）不会因此变红

基线条目里没有 `db_fingerprint` 时，打印的是**明确的提示**（而不是假装有指纹）：

```
📚 库指纹：**基线里没有库指纹**（该条目生成于加指纹之前，无法重建当时的库）。
     —— 归因时请手工比对库现状（check_redlines.py --fingerprint），并按 #34 三步决定是否需要重新基线
        （--regen 会一并补上指纹）。
```

判据（sha / 叶子）行为**完全不变**；`--fingerprint` 不传时不多打任何东西（有测试钉住）。

### 7.1 基线已重基（只重了该重的那一条）

`docs/baselines/redlines.json` 已 `--regen`：`taken_at = 2026-09-21`，两条真实库条目都带上了
`db_fingerprint`。

**只重 `predict_real` 一条**（sha `2f623027…` → **`c38f6f955d896b00…`**）—— 因为两条真实库红线的
失效原因不同：

- `predict_real` 红 = **复权链从空到 417 事件 / 80461 因子行**（上半场那次 regen 发生在
  `ingest actions` 之前）→ 已归因，可以重基；
- `backfill_real` 的输入是 `verifications` 里 42312 条回放行，而它们是**复权链为空时**算的
  → 已知将要失效，**现在重基等于把一份将要失效的值冻进基线**（那正是 `REBASELINE_WHEN` 禁止的）。

为此给 `--regen` 补了 `--only X` **部分重基**（`merge_regen_targets`）：只覆盖 X 的条目，
其余条目连 `taken_at` 一起原样保留（基线条目自带 `taken_at`，所以部分重基在文件里是自洽的）。
顺带修了一个**数据丢失**缺陷：库缺失时 `--regen` 原来会把真实库条目从基线里抹掉。

重基前后逐字段对账（这就是“只改了该改的”的证据）：

## 8. 已知限制（不假装完备）

- 指纹覆盖**固定的一张表清单**；新增表（例如模块2 的 `paper_*`/`real_trades`）要显式加进
  `dbfingerprint._CONTENT_SPEC` / `_RANGE_TABLES` 才会被看见。
- `content_sha256` **刻意排除**入库时刻列（`fetched_at`/`created_at`/`added_at`）、自增主键
  与人工标注列（`attribution_manual`、`notes`）—— 它们变动不代表"库/口径变了"。
  代价：这些列的变化指纹看不见（属有意取舍）。
- 指纹**不判红**（见 §4），所以「库变了但代码没回归」不会自动阻止 CI；它的价值在**归因速度**。
