## 2. 为什么选 X（升版本）而不是 Y（删行重放）

1. **这是项目自己的纪律**：冲突文案原文就是「要出新预测请升 model_version」，
   P8 也有「v1.0.0 的错误预测不许混进 v1.0.1」。
2. **旧行是「带版本号的历史」，不是垃圾**：`v1.0.1` 记录「复权链为空的时期」，
   报告按 `model_version` 分组（`verify/report.py`）天然不混算 —— 不删任何行、不碰触发器。
3. **Y 单独不够**：它只治回放段，LIVE 段那 17 条仍冲突；连它们一起删等于删掉第一批实盘预测。

## 3. 落地时撞到的能力缺口（这一步是必需的，不是顺手）

第一次重放**跑挂在半路**：

```
stocklab.verify.store.VerificationConflict: pred_id=1831 已有一条内容不同的验证记录
（差异字段 ['actual_pct', 'benchmark_pct', 'sim_pnl']）
```

原因：`verify_target` 按 `(target_date, codes)` 取预测，**不带版本**。
于是「新版重放」会把**上一版已评分的行**按**新口径**重算一遍 —— append-only 守卫
**正确地**把它拦下。两个替代都是错的：

- 连带重算旧版行 = 用新口径**篡改历史账本**；
- 把冲突当噪声忽略 = 把守卫关掉。

故补上 `verify_target(..., model_version=None)`（`None` = 全部版本，保持既有语义），
`verify.backfill` 传 `model_version=rep["model_version"]` —— **回放只评自己刚写下的那一批**。
接线用 monkeypatch 记录 kwargs 的测试钉住（不然「有能力但没人用」）。

## 5. 一处**修正我自己先前的说法**（说过头了）

前一轮把它描述成「42312 条回放行全是无复权口径的错误读数」。实测**不准确**：

- 打分是 `adj_close(target)/adj_close(asof) − 1`，是**比值** —— 只有窗口**跨越除权日**时
  才会与不复权口径不同。实测重放前 139 个目标日（`2015-10-09`…`2016-05-05`）时，
  库里已存在的 `v1.0.1` 验证行**逐条 `identical`**，直到 `2016-05-06` 才出现第一条不一致
  （`pred_id=1831`）。
- 真正「整片不同」的是**预测载荷**：价格水平 / 关键位 / 区间按因子整体缩放，
  所以同一 `asof` 的新旧载荷必然不同（`predict run` 冲突的正是这一层）。

结论：口径污染的**影响面**是「预测载荷（全片）+ 验证行（跨除权日的少数行）」，
不是「所有验证行」。`v1.0.1` 的验证行绝大部分与新口径**逐位相同**，这是好事
（说明 4.3 的两列数字可比），但它不改变「必须升版本」这个判断。
