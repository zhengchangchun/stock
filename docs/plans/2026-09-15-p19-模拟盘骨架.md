## 2. 三条固定臂（口径不许改）

起点 `2026-09-15` 收盘、初始资金 20,000 元。

| arm_id | 含义 | 状态来源 | 是否交易 |
|---|---|---|---|
| `arm-hold` | 什么都不做的对照臂 | `init` 时**冻结**的快照 | 永不 |
| `arm-now` | 实盘账本的**镜像** | 每步从 `real_trades`+`cash_flows` 重放 | 永不（无换仓建议） |
| `arm-discipline-05` | 纪律臂 · ETF 目标 5% | 自身 `paper_trades` | 触发纪律才动 |
| `arm-discipline-10` | 纪律臂 · ETF 目标 10% | 同上 | 同上 |
| `arm-discipline-15` | 纪律臂 · ETF 目标 15% | 同上 | 同上 |

### 2.1 arm-hold 与 arm-now 的区别（ADR-010 详述）

起跑日两臂**数值必然相同**（描述同一份状态：美的 100 股 + 现金 11,314.91）。
区别在**之后**：`arm-hold` 冻住不动；`arm-now` 跟着实盘流水走
（用户明天录一笔真成交，`arm-now` 明天就变，`arm-hold` 不变）。
这正是「与实盘流水对照」的用法。若把 arm-now 也冻住，两臂就是同一个东西。

- 起跑状态由**真实账本**推导并**校验**：`real_trades`(09-14 买 100@86.80 fee 5.09)
  + `cash_flows`(09-14 deposit 20000) → cash = 20000 − 8680 − 5.09 = **11,314.91**。
  与声明口径不符 → **报错**（不静默采用账本）。

### 2.2 起跑日实测（真实库，样本内，仅供核对）

```
000333 收盘 87.23（bars_daily, adj_mode='none'）
市值 8,723.00 + 现金 11,314.91 = 总资产 20,037.91
000333 权重 43.53% > 40%   → FAIL（硬约束）
现金    56.47% ∈ 45–60%    → PASS
现价 87.23 ≥ 87.00         → WARN 禁补仓
收盘 87.23 ≥ 85.00 止损线  → PASS
```

### 2.3 arm-discipline 的规则条文（全部来自 `portfolio/discipline.py`，不另抄一份）

1. 单票 ≤ 40%（`DISCIPLINE.single_position_max_pct`）
2. 现金 45%–60%（`DISCIPLINE.cash_band_pct`）
3. 单次动用现金 ≤ 总资产 5%（`DISCIPLINE.cash_per_trade_max_pct`）
4. 单笔金额凑到接近 1,000 元（摊薄 5 元最低佣金）
5. 整手（100 股/份整数倍，`Instrument.lot`）
6. 禁补仓：000333 ≥ 87.00（`PER_CODE_LINES['000333'].no_add_above`）
7. 止损：000333 收盘 < 85.00 → 整清（`stop_loss_close`）
8. 分散白名单**只有** `510880`(红利ETF) / `510300`(沪深300ETF)
   —— 家电股 600690 / 家电 ETF 一律**不在**白名单（换家电不算分散）

### 2.4 两个必须先钉死、否则无法归因的口径

**(a) 「单次动用现金 ≤ 总资产 5%」的「单次」= 每个 `paper step`（每日）累计。**
理由：这是**风险节奏**规则。按「单笔订单」解读会让它形同虚设
（同样 15% 拆成 3 笔即可绕过），而风险规则的方向性错误应当是**少投而非多投**。
若按单笔解读，起跑日一天就能把 15% 档建满 —— 那正是要被这条规则挡住的动作。
（两种解读在起跑日**恰好重合**：5% × 20,037.91 = 1,001.90 ≈ 1,000 元 ≈ 一笔最小佣金摊薄单。）

**(b) 整手约束一律「向下取整到手」，不足 1 手 = 不动。**
复用 `risk/sizing.py` 既有口径（`qty -= lot` 直到 0，宁可不动也不放大仓位），
理由同该模块原话：「不四舍五入买一手：那会把仓位放大到超过 f 允许的风险」。

**推论（起跑日）**：000333 只有 1 手。减到 ≤40% 需卖 8.11 股 →
向下取整到手 = **0 股 → 不动**，并把「FAIL 未消除」如实上报。
这正是验收项 ④ 的场景，且**两种减仓解读给出同一答案**：
- 「减到 40% 所需」→ 8.11 股 → floor → 0
- 「单次减仓 10%」(`trim_light_pct`) → 10 股 → floor → 0
两者都是 0，故本设计在 ④ 上对解读不敏感（测试把两种都断言一遍）。

## 3. 每步决策顺序（固定，写进 ADR）

```
mark to market(PIT 收盘) → 判规则 → 按固定优先级执行 → 落 trades + nav
  a. 止损整清       （硬，安全）  close < 85.00 → 卖光 000333
  b. 超限减仓       （硬，上限）  权重 > 40% → 减到 ≤40%，整手向下取整；0 股则不动
  c. 分散建仓       （触发=首次建仓/ETF 未达目标）
       target = etf_target_pct% × 总资产，均分给 (510300, 510880) 两腿（不给权重偏好）
       本次可动用 = min(缺口, 5%总资产, 现金 − 45%总资产, 1,000 元)
       腿 = 按 code 升序中「缺口最大」的那条（并列取 code 小者）→ 确定性
       qty = floor(可动用 / 含滑点成交价 / 100) × 100；=0 → 不动并记录原因
```

**000333 在本臂没有买入路径**：没有任何一条规则要求增持单票，
且分散工具白名单不含家电股。故「只减不增」是**规则的推论**，不是额外假设。

**约束真的生效时必须留痕**（借 `risk/sizing.py` 的 `binding_constraints` 精神）：
`binding_constraints` 逐条记下是哪条把订单压小了/压没了，不许静默。

**起跑日的一个重要推论（报告必须显式写）**：
000333 占 43.53% + 现金下限 45% = 88.53%，留给 ETF 的上限只有 **11.47%**。
所以 **15% 档在当前持仓下永远建不满** —— 卡在「现金 45% 下限」上，
而不是「没人买」。这是本臂要暴露的结论，不是缺陷。

## 4. 表设计（append-only，只增不改不删，不加滚动清理）

```sql
paper_accounts(account_id PK, arm, etf_target_pct, start_date,
               initial_cash, initial_positions_json, initial_nav,
               params_json, created_at)
paper_trades(trade_id PK AUTOINC, account_id, date, code, side, ref_price,
             fill_price, qty, commission, stamp_tax, transfer_fee,
             slippage_cost, fee_total, asset_class, rule_citation,
             price_source, price_asof, created_at,
             UNIQUE(account_id, date, code, side, qty, rule_citation))
paper_nav_daily(account_id, date, cash, positions_json, market_value, nav,
                drawdown, cum_cost, cum_return, net_deposits,
                index_300_level, index_300_asof, created_at,
                PRIMARY KEY(account_id, date))
```

- 三表各加 `UPDATE`/`DELETE` 双触发器 `RAISE(ABORT, ...)`（同既有 append-only 表）。
- `paper_trades` 的 `UNIQUE` 是**结构性第二道防线**（防同日重复下单），
  第一道是 `paper_nav_daily` 的 (account, date) 存在性判据 —— 顺序必须
  **先查 nav 是否已落库**（ERROR_DIARY #25：预检查与幂等键的优先级写反会把自己的痕迹
  当成重复）。本模块的幂等单元 = `(account_id, date)`：已落 nav → 整个 step 跳过。
- 成本明细**分列存**（佣金/印花税/过户费/滑点），因为「ETF 免印花税」要能被查到
  （验收 ② 直接查 `stamp_tax == 0`），存一个合计就查不出来了。

## 5. 幂等与 PIT

- `paper step --asof D` 幂等：`(account_id, D)` 已有 nav → 跳过；报告/JSON 逐字节一致。
- 一次 step 的全部写入在**一个事务**里（`store.db.transaction`），失败整体回滚，不留半截状态。
- 价格与时钟一律从库里取：价格用 `portfolio/prices.resolve_price`（`bars_daily`,
  `adj_mode='none'`, `date <= asof`）与 `bars_daily` 收盘；`--now` 可注入。
- **禁未来函数**：决策/估值函数的 `Price` 入参带 `price_asof`，
  任何 `price_asof > asof` → 抛 `LookaheadError`（验收 ⑤）。
- 报告正文**不含生成时刻**（同 predict/verify/review 纪律）。

### 9.2 缺陷：`paper show` 默认 asof 不回落（改前 → 改后）

**改前（红灯）**：

```
$ .venv/bin/python -m pytest tests/test_cli_paper.py::test_show_without_asof_falls_back_to_latest_nav_date --tb=line
E   AssertionError: 必须回落到最新有净值的日期
    assert '2026-09-16' == '2026-09-15'
1 failed in 0.28s
```

即：不带 `--asof` 时 asof = 今天（2026-09-16），而 09-16 还没跑过 `step`，
`state_payload` 按「当日有净值」过滤 → **`accounts: []`**，看起来像模拟盘根本没建。
用显式 `--asof 2026-09-16` 可以精确复现旧代码的默认路径：

```
$ .venv/bin/python -m stocklab.cli.main paper show --asof 2026-09-16
asof= 2026-09-16 | source= explicit | accounts= []      ← 旧默认路径的真实输出
```

**改后（真实库，不带任何参数）**：

```
$ .venv/bin/python -m stocklab.cli.main paper show
asof= 2026-09-15 | source= latest_nav | latest= 2026-09-15 | accounts= 5
disclosure[-1]= 今日净值未生成，展示 2026-09-15

$ .venv/bin/python -m stocklab.cli.main paper show          # stderr 摘要
{"accounts": [{"account_id": "arm-discipline-05", ..., "nav": 20027.51},
              {"account_id": "arm-discipline-10", ..., "nav": 20032.46},
              {"account_id": "arm-discipline-15", ..., "nav": 20032.46},
              {"account_id": "arm-hold", ..., "nav": 20037.91},
              {"account_id": "arm-now", ..., "nav": 20037.91}],
 "asof": "2026-09-15", "asof_source": "latest_nav", "latest_nav_date": "2026-09-15"}
```

**实现**（`engine.resolve_show_asof`，顺序即优先级；口径写进 ADR-010 D7）：

1. 显式 `--asof` → 照用（`asof_source=explicit`）；
2. 未给 + 今天已有净值 → 今天（`today`），**不回落**；
3. 未给 + 今天没有净值行 → 回落 `MAX(paper_nav_daily.date)`（`latest_nav`），
   并在 `disclosure` 追加「今日净值未生成，展示 YYYY-MM-DD」（不许静默）；
4. 库里一条净值都没有 → 保持今天，`accounts: []` 此时是真话。

载荷新增 `asof_source` / `latest_nav_date`（stdout 与 stderr 摘要都带）。
CLI 的「今天」改由 `--now` 推出（时钟是参数不是环境，错误日记 #30）。

**测试（先红后绿，3 条）**：① 今日无净值 → 回落 + `latest_nav`；
② 今日有净值 → 不回落 + `today`；③ 显式 `--asof` → `explicit` 照用。
