## 0. 事实复核（先复核任务书的假设，不照抄）

任务书给的背景是「`verifications` 的 `max(target_date)` 只有 `2026-09-14`」。
**实测不是这个值**，两条数都有出入，如实记录：

| 判据 | 任务书写的 | 实测（`.venv/bin/python` 只读查库） |
|------|-----------|-----------------------------------|
| `verifications.max(target_date)` | `2026-09-14` | **`2026-09-15`**（该日已有 4 行） |
| `predictions` 中已到期未评分 | 「2 条 + 09-17 中已到期的部分」 | **2 条**，全部是 `asof_date=2026-09-15 → target_date=2026-09-16`（`pred_id` 6056 `000333` / 6057 `600690`，`created_at=2026-09-15T18:15:18+08:00`） |
| `bars_daily.max(date)` | `2026-09-16` | `2026-09-16` ✅ |
| 全部未评分预测 | — | 4 条（另 2 条 `target_date=2026-09-17`，**目标日未到**，不算缺口） |

**结论（任务书的定性判断成立、定量数字有一处过期）**：确实存在「已到期却从未被打分」的
预测；缺口是 **2 条**，不是 3 条。任务书里 `2026-09-14` 那个读数在写下时可能已过期
（库里 09-15 的 4 行是怎么来的：09-15 收盘链跑了 `verify`，但 09-16 那条链**没跑**
或没跑到验证步）。这属于 ERROR_DIARY #34 的同类现象——**引用别人的读数前先自己重测**。

---

## 1. 根因

收盘链（15:30，由 nanobot 侧 cron 维护）的步骤是：

```
ingest bars → 取 LATEST → session backfill-close → predict run → review daily → paper step → doctor
```

`predict run` 产出的是 **target_date = 次日** 的预测（`predictions` 表）。
**链上没有任何一步会给「今天到期」的预测打分并落库**：

- `verify run --target-date D` 能做这件事，但它**要求显式给出 D**，且 D 上没有预测时
  直接 `NoPredictions` 退出 2 —— 链上没人知道该给哪天；
- `review daily` 按设计**只读不写**（`cmd_review_daily` docstring + `build_review` 全程
  无写操作），所以它只会在报告里写「验证：0 条」，不会补。

于是每天的实时预测**永远不被评分**，`verifications` 里 LIVE 桶永远不增长 →
P26 的「实时段准确率」永远累积不起来。

---

## 2. 方案

### 2.1 新增 `stocklab/verify/pending.py`（纯读 + 一个判定）

两个函数，都**复用既有实现**，不另造口径：

```python
latest_closed_session(conn, now) -> (date | None, evidence: dict)
pending_predictions(conn, now)    -> dict
```

**「最新已收盘交易日」的判定（fail-closed）**：

```
日历侧 = session.tick.closed_through(cal, now)        # 复用既有实现（含 15:00 收盘判据）
行情侧 = MAX(bars_daily.date)，且必须满足
         session.tick.is_trade_date_closed(该日, now)  # 复用既有实现
latest_closed = max(日历侧, 行情侧)   # 两侧都取不到 → None
```

即任务书要的 `trading_calendar ∪ bars_daily`，两侧各自套 `is_closed_snapshot` 那一族的
**收盘时刻判据**（`>= 15:00`，解不出即 `False`）。fail-closed 的三个落点：

1. **未来日不算已收盘**：`is_trade_date_closed` 对 `d > today` 返回 `False`，
   所以即使库里混进未来日期的 bar，也不会被当成「已到期」；
2. **日历为空不报错、降级到行情侧**（复用 `load_calendar` 的既有降级语义）；
3. **两侧都判不出来 → `latest_closed = None`**，此时 `pending_predictions` 返回
   `n = None` + `reason`，**绝不返回 0** —— 0 会被读成「没有缺口」，而真相是「判不了」
   （ERROR_DIARY #36：每一个 0 旁边必须写出为什么是 0）。

**「待验证」的判定**：

```sql
SELECT p.* FROM predictions p
LEFT JOIN verifications v ON v.pred_id = p.pred_id
WHERE v.verification_id IS NULL
  AND p.status = 'ok'                 -- 与 verify_target 的选取条件逐字一致
  AND p.target_date <= :latest_closed
ORDER BY p.target_date, p.code
```

`status='ok'` 这一条**必须与 `verify_target` 一致**：否则会出现「待验证清单里有、
但打分器永远不碰」的行 → 永久假报警。实测库里 6059 行全是 `ok`，所以它今天是空操作，
但它是**不变量**而不是巧合，测试里钉住。

### 2.2 新增 CLI：`verify pending`（幂等 + append-only）

```
stocklab verify pending [--db ...] [--code ...]
```

语义：**把「已到期且没有验证行」的预测补齐**。

- 打分**完全复用** `stocklab/verify/service.verify_target`（不新造阈值/公式）；
- 逐 `target_date` 调用，且**只传该日待验证的 `codes`** —— 已评分的行一个字节都不碰
  （任务书硬禁「改既有行」；用 `codes` 把作用域限制在待验证集合上是最强的保证）；
- **幂等**：靠 `insert_verification` 的四态机 + `ux_verifications_pred` 唯一索引。
  第一次跑写入 N 行；第二次跑**选择集为空** → 报「无待验证」、零写入；
- **append-only**：全程只有 `INSERT`（以及 ADR-002 允许的 `unscorable → scorable` 补分），
  没有任何 `DELETE`，也不碰历史回放区间；
- 命令**自检**：处理完再查一次待验证集合，输出 `pending_after`；
  `pending_after != 0` → 退出码 1（自己证明自己没干完）；
- 退出码：`0` 完成（含无待验证）/ `2` 判不出最新已收盘交易日或库不存在 / `1` 有冲突或没补干净。

### 2.3 缺步检测（自动发现）

`build_review` 增加一个键 `pending`（由 `pending_predictions` 提供），因此：

- `reports/YYYY-MM-DD-review.md` 里多一段「**到期未验证**」，`n > 0` 时写明
  「跑 `stocklab verify pending` 补」；
- `review daily` 的 stdout JSON 多一个顶层字段 `pending_verifications`
  （`n`，判不出时为 `null`）与 `pending_verifications_detail`；
- **不新起 cron、不动 nginx、不动 nanobot 的收盘链命令**。

`review daily` 的 `now` 锚点沿用既有写法 `f"{date}T23:59:59+08:00"`
（该命令的语义就是「这一天走完了，回头看」）→ `build_review` **保持无时钟依赖**，
「同输入两次运行逐字节一致」这条既有性质不受影响。

### 2.4 该插在收盘链的哪一步

```
ingest bars → 取 LATEST → session backfill-close → predict run
    → ★ verify pending ★        ← 新增（打分「今天到期」的预测）
    → review daily              ← 这一步现在能真读到验证行，且能报 pending
    → paper step → doctor
```

理由：必须在 `predict run` **之后**（否则当天新预测还没入库）、在 `review daily`
**之前**（否则复盘读到的还是「验证 0 条」）。**cron 命令由 nanobot 维护，本轮不动。**
