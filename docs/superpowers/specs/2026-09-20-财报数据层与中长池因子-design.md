## 4. 数据模型

### 4.1 新表 `financial_reports`

append-only（`BEFORE UPDATE` / `BEFORE DELETE` 均 `RAISE(ABORT)`，与既有表同款）。**单位一律：元。**

| 列 | 类型 | 说明 |
|---|---|---|
| `code` | TEXT NOT NULL | 标的代码 |
| `report_date` | TEXT NOT NULL | 报告期 `YYYY-MM-DD` |
| `notice_date` | TEXT NOT NULL | 公告日 `YYYY-MM-DD` —— **PIT 锚点**（来源见 §4.3） |
| `notice_date_source` | TEXT NOT NULL | `f10` / `statutory` —— 该公告日是实测还是法定截止日推定 |
| `report_type` | TEXT NOT NULL | `一季报` / `中报` / `三季报` / `年报`（由 `report_date` 派生 + `REPORT_TYPE_CODE` 交叉校验） |
| `total_assets` | REAL | 总资产 |
| **`parent_equity`** | REAL | **归母股东权益**（来自 F10 资产负债表；口径见 §4.6） |
| `total_equity` | REAL | **所有者权益合计（含少数股东权益）** —— 注意不是归母 |
| `total_liabilities` | REAL | 总负债 |
| `inventory` | REAL | 存货 |
| `total_operate_income` | REAL | 营业总收入（**年内累计**） |
| `operate_cost` | REAL | 营业成本（**年内累计**） |
| `parent_netprofit` | REAL | 归母净利润（**年内累计**） |
| `netcash_operate` | REAL | 经营活动现金流净额（**年内累计**） |
| `construct_long_asset` | REAL | 购建固定资产等支付的现金（**年内累计**） |
| `industry_name` | TEXT | 东财 `INDUSTRY_NAME`（**非 PIT**） |
| `source` | TEXT NOT NULL | `eastmoney-datacenter` |
| `fetched_at` / `created_at` | TEXT NOT NULL | |
| **`raw_refs_json`** | TEXT NOT NULL | 溯源数组 `[{endpoint, resp_sha256, cache_key, page}]` —— 一行来自**多个端点**，单列装不下 |
| `cache_key` | TEXT | 主响应键（保留，便于直查） |
| `unit` | TEXT NOT NULL DEFAULT `'CNY'` | 单位守卫（见 §9.3 量级断言） |

**主键 `(code, report_date, notice_date)`**。

### 4.2 为什么主键带 `notice_date`

一份财报被更正/重述时，会是一条**新公告**。带上 `notice_date`，同一报告期即可存在多个版本，读取侧取「`notice_date <= asof` 中最晚的那个」——这是 PIT。

若主键只有 `(code, report_date)`，重述就只能靠覆盖，而覆盖在本项目是禁区（append-only）。既有的 `market_holidays` 处理「改期」用的是同一套路：新公告 = 新行，读侧取最新。

### 4.3 公告日从哪来（**原设计在此处是错的，见评审 A1**）

**原设计假设 `RPT_DMSK_FN_*.NOTICE_DATE` 是「该期财报的公告日」——实测不成立。** 对 `000333.SZ` 复测：

| report_date | DMSK 资产负债表 | F10 资产负债表 | 差 |
|---|---|---|---|
| 2026-06-30 | 2026-08-29 | 2026-08-29 | 0 ✅ |
| 2025-12-31 | **2026-08-29** | 2026-03-31 | **151 天** ❌ |
| 2024-12-31 | **2026-03-31** | 2025-03-29 | **367 天** ❌ |

规律：**只有「每种报告类型的最新一期」是对的**，历史行的 DMSK `NOTICE_DATE` 指向**同类报告的下一次公告日**。三表公告日不一致是常态（美的 42/79 期、招行 72/102、长电 73/93），跨度中位数正好 365 天。

**若照原设计实现**：2025 年报的可读日会算成 2026-08-29 → 在 2026-04-30~2026-08-29 之间跑 `candidate run`，TTM 四季永远凑不齐 → 中期/长期池**全部 `pass_flag=False`**，报告只说「数据不足」，看不出是源字段错。**而原 DoD（asof=今天）恰好测不出这个 bug。**

**对策**（三条一起上）：

1. **公告日改用 F10 三表取并集**。实测 17 只个股覆盖 **1443 期**（与 DMSK 利润表最宽覆盖持平）。**报表名按 `ORG_TYPE` 选**：一般工商 `RPT_F10_FINANCE_GBALANCE`、银行 `…BBALANCE`、保险 `…IBALANCE`（实测三变体分别对美的/招行/平安返回数据；**这一步很关键——银行保险的资产负债表存在，只是报表名不同**）。三张 F10 表各取 `NOTICE_DATE`，取第一个有值的。
2. **合理性检查**：`report_date < notice_date <= report_date + 120 天`。不通过（或无值）→ **回退法定披露截止日**（年报/一季报 `04-30`、中报 `08-31`、三季报 `10-31`），`notice_date_source='statutory'`。实测美的 2004–2007 那几期在 F10 里**有值但可疑**（`2004-12-31 → 2008-02-19`，晚 1146 天），会被这条正确地打回法定兜底。
3. **配套 warn**：同 `report_date` 三表公告日相差 > 30 天 → `notice_date_inconsistent`。

> **删掉了原 §4.3.2「取三表公告日最晚者」** —— 那条正是上面这个 bug 的放大器。

### 4.4 两个已知风险与对策

1. **东财可能按最新口径重算整条历史**（`valuation_daily` 已记录过同类风险）。对策照抄：同一 `(code, report_date, notice_date)` 重采时值若变化 → **首写保留 + 记 warn，不覆盖**。
   ⚠️ **但这条防线需要输入才有效**：`raw_cache` 是「同 key 首写保留」，若缓存键不带采集批次维度，**同键重采永远命中旧 body**，上面的差异根本观测不到。所以 `cache_key` 必须带采集日（见 §5）。
2. **缺失期数的处理**：三表按 `report_date` 取**并集**落库，某张表缺该期则其字段为 `NULL`。理由：资产负债表 + 利润表齐全就够算 ROE，不该因为缺现金流量表而丢掉整期。**字段齐全性由因子层逐因子判定**（§6.3）。**NULL 分不清「源站本来没有」和「采集失败」**，所以报告里必须给出**每表覆盖**（期数 + 最早期，见 §9.4）。

### 4.5 行业分类

`industry_name` 来自 DMSK 三表行内的 `INDUSTRY_NAME`（实测美的 `白色家电`、招行 `银行Ⅱ`、茅台 `白酒Ⅱ`、平安 `保险Ⅱ`，是东财二级行业名，带罗马数字后缀）。写入 `instruments` 已有的 `sector` 列。

**行业口径只允许一套**：`instruments.sector` 与插桩0 的关键字表不能各说各话（否则「家电」与「白色家电」会同时存在）。插桩0 改为**优先用 `ctx["sector"]`**（见 §7.1），名称关键字仅作兜底。

**它非 PIT**：取的是当前行业归属，历史某日的行业无法还原。与 `screen.py` 的 ST 判据同属近似，`ctx`/报告里必须标注。

`instruments` 表没有 append-only 触发器（它是参考数据，不是证据），更新 `sector` 是允许的；但**要留痕改了哪些行**（它已经进了 `ctx`、进了分数）。

### 4.6 权益口径（**原设计在此处也是错的，见评审 A2**）

原设计把 `total_equity` 写成「归母股东权益」——**实测 `TOTAL_EQUITY == TOTAL_ASSETS − TOTAL_LIABILITIES` 逐只恒等**（美的/茅台/招行皆然），即它是**含少数股东权益的所有者权益合计**，不是归母。

后果如果不修：`roe = 归母净利 / 平均权益` 会**分子归母、分母含少数股东** → 系统性低估 ROE（美的 归母 212,861 vs 合计 225,793 千元，差 **5.7%**）；更糟的是 `dupont` 三分项相乘恒不等于 `roe`，**两个数在同一份 `features` 里打架且不报错**。

**对策**：补 `parent_equity` 列，来源是 F10 资产负债表（含 B/I 变体）的 `TOTAL_PARENT_EQUITY`。**`roe` 与 `dupont` 一律用归母口径**，并加恒等式断言（§9.1）。

**两列都留**：`total_equity`（合计）后续做「少数股东占比」类排雷会用得到，且它是实测恒等式的直接来源。

**新增**：
- `data/fetch.py::fetch_financial_reports(client, *, secucode, org_type) -> list[FinancialReport]` —— 拉 DMSK 三表（数值）+ F10 三变体（公告日、归母权益），按 `report_date` 对齐

### 5.1 分页与失败语义（照抄 `fetch_valuation_daily` 的模式）

- **`pageSize=500`** —— 实测 500 可一次取回美的的 79 行（`pages=1`）；默认口径下是 40 页
- **翻页不足即 fail-closed**：非末页行数 != `pageSize` → `FetchError`。**半截历史绝不能被当成全历史**（`valuation_daily` 已有此教训）
- **`pages == 0` / `result == null` → `[]`**，是**合法空**（ETF 无财报，见 §5.3）；**不是抓取失败**，也**不是「有数据但为零」**
- 翻页超上限 → `FetchError`
- **必须 `columns=ALL`**：实测显式列清单在缺该列的标的上会让**整个请求**返回 `code 9501「XXX返回字段不存在」`（`601318.SH` / `510300.SH` + `INVENTORY` 复现）。**这条要写进适配器 docstring**

### 5.2 缓存键必须带采集批次

`raw_cache` 是「同 key 首写保留」。若缓存键不带采集日维度，**同键重采永远命中旧 body** → §4.4 风险①（东财重算历史）与 §4.3（公告日会变）在实测上**根本观测不到**，「记 warn 不覆盖」这条防线等于没有输入。

- `cache_key = f"financial:{code}:{fetched_date}:{endpoint}:{page}"`
- **第 3 段保持 ISO 日期**，以复用 `raw_cache._anchor_date` 的 ADR-009 时效规则（它取 key 第 3 段当锚点日）
- §5 明确写：**重采需换批次日（或清缓存），否则等于不重采**

### 5.3 空响应与缺列的区分

- **ETF 三表全空** → 合法无数据，落 `[]` + 留痕，**不报错**（否则 21 只里 4 只永远报错）
- **字段存在但值为 NULL**（如金融股的 `OPERATE_COST` / `INVENTORY`）→ 是「该报表结构没有这一项」，**不是采集失败**。两者在报告里要分开呈现（§9.4）

### 5.4 采集范围

采集东财返回的**全部历史期数**，不截断。季报数据量小，截断只会让将来的回测缺样本。

**离线约束**：测试一律走 fixture 回放；真实联网只出现在显式标注的录制脚本里（与项目既有约定一致）。

**可选优化**（成本低，建议做）：`filter=(SECUCODE in ("000333.SZ","600036.SH",...))` 实测可用，可把 63 次请求压到个位数。

## 6. 派生指标与因子定义

### 6.1 口径：累计 → 单季 → TTM

**这是本轮最容易出错的地方。** 季报的流量项（营收、成本、净利、现金流）是**年内累计值**：中报 = 上半年累计，三季报 = 前三季累计。直接拿中报算净利率，与年报不可比，**算出来的因子是错的**。

所以所有流量类指标一律：

```
单季(Qn) = 本累计 − 上一累计        （同一会计年度内）
TTM     = 最近 4 个单季之和
```

存量类（总资产、股东权益、存货）用**期末值**；需要均值的（平均股东权益、平均存货）用**期初期末均值**。

### 6.2 六个因子（全部教科书定义）

| 因子 | 定义 | 备注 |
|---|---|---|
| `roe` | 归母净利(TTM) / 平均股东权益 | |
| `gross_margin` | (营收(TTM) − 营业成本(TTM)) / 营收(TTM) | |
| `gm_yoy_pp` | 本期毛利率 − **去年同期**毛利率，单位 pp | 文档的「毛利率弹性」= 同比变化 |
| `inv_days` | 365 / (营业成本(TTM) / 平均存货) | **见下** |
| `fcf_margin` | (经营现金流(TTM) − 购建固定资产(TTM)) / 营收(TTM) | |
| `dupont` | 净利率 × 总资产周转率 × 权益乘数 | **以嵌套 dict 入 `features`**（`{"net_margin","asset_turnover","equity_multiplier"}`），三个分项**分别**可读，插桩据此分辨「利润率驱动」还是「杠杆驱动」 |

**三处自创或存疑的取值，逐条列明**（文档只给了因子名，没给公式与阈值）：

1. **「库存系数」不是标准术语。** 本轮按**存货周转天数**实现，越短越好。若本意是「存货 / 营收比」，换掉插桩即可（采集层不动）。
2. **「毛利率弹性」**按**同比变化**（pp）实现，不做二阶差分或导数那类解读。
3. **「财报断更」判定阈值 540 自然日**是我拍的（见 §6.3）。我编不出来源——它只是「一年半没新财报就别用了」这个直觉的数值化。你觉得不合适就改。

### 6.3 数据有效性：按因子的**最小期数**与**NA 显式化**

原设计写「TTM 需要 4 个单季齐全」——**不足以覆盖全部 6 个因子**（评审 B1）：

| 因子 | 最小期数要求 |
|---|---|
| `roe` | TTM 所需累计点 + **平均权益的期初存量**（比 TTM 再多一期资产负债表） |
| `gross_margin` | TTM 所需累计点 |
| `gm_yoy_pp` | **去年同期**的 TTM 毛利率 → 实际要 8 个单季（约 5–6 个累计点） |
| `inv_days` | TTM 累计点 + **平均存货的期初存量** |
| `fcf_margin` | TTM 所需累计点 |
| `dupont` | 同 `roe` |

**TTM 的算法**（评审 B1 给了最省的口径）：`TTM(2026Q2) = 2026H1 + (2025FY − 2025H1)`，**只需 3 个累计点**；要算平均存量则再加 `2025-12-31` 的存量行。

**过期判定**：最新已公告期的 `notice_date` 距 `asof` 超过 **540 自然日**（§6.2 自创项第 3 条）→ 视为财报断更。

**NA 必须显式**（评审 A5，**运行期同样适用**）：

- `features` 的键**永远齐全**，不可算的因子给 **`None`**，并在 `na_reasons` 写明原因（如 `"gross_margin: operate_cost is NULL"`）
- **分位算不出时给 `None`，不给 `0.0`** —— `0.0` 是「最差」的合法分数，会把「不知道」伪装成「最差」，正好违反本节精神
- **财报缺失时判不可算，不猜、不用行业均值填。** 填出来的分数会被下游当成真的

### 6.3.1 行业适用性（评审 B4 的处置）

实测：**金融股（招行/工行/平安）概念上就没有「营业成本」和「存货」**（字段在、值为空），所以 `operate_cost` 与 `inventory` 对它们天然不可算。而**其他因子全部可算**——归母权益从 F10 的 B（银行）/ I（保险）变体资产负债表可获取，实测三个变体分别覆盖美的/招行/平安：

| | 净利率 | 周转率 | 权益乘数 | **ROE/杜邦** | 毛利率 | 存货周转 |
|---|---|---|---|---|---|---|
| 一般工商（美的） | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 银行（招行/工行） | ✅ | ✅ | ✅ | **✅** | ❌ | ❌ |
| 保险（平安） | ✅ | ✅ | ✅ | **✅** | ❌ | ❌ |

**处置：不写行业特例，用统一机制。** 插桩按**可用因子**加权（权重按可用性归一），金融股自动落在「ROE + 杜邦 + FCF 率」上，代码里**不出现 `if 行业 == 银行`**。NA 的分布与原因在报告里**单独列出**，不靠 NULL 静默消失。

> `fcf_margin` 对银行意义存疑（经营现金流受存款增减主导）——这条记在 `na_reasons` 的说明里，本轮不特殊处理，留给插桩版本迭代时决定。

### 6.4 打分：横截面分位，不设绝对阈值

`score` 不来自我拍的阈值，而来自**当期横截面分位**：

- 横截面 = 每只种子在 `asof` 时点**已公告**的最新一期指标，再排序
- `*_pct` = 分位（0–1），由 `build_ctx` 算好放进 `features`（见 §7.1）
- **`score` 由插桩合成**：它拿 `*_pct` 按本池的侧重加权，再乘 100。加权是**策略层**——换权重就是换插桩版本，采集层不动

**为什么不用行业中性**：21 只种子分布在约 10 个行业（家电 6、金融 4、能源 3、食品 2、科技 2、通信 1），除家电外每行业仅 1–4 只。按行业算分位等于拿 1–3 个点排序，**统计上没有意义**。本轮用全样本分位，并把这一限制写进报告。

**为什么不用绝对阈值**：`ROE > 15%` 这类数字我编不出来源。横截面分位至少让尺子来自数据本身。

**真正的取舍交给 `select_top`**：`pools.select_top` 已经做「按分排序取前 N」（`POOL_TOPN`）。所以插桩只需产出**单调于质量**的分数，不需要自己设门槛。

**极性规则写死**（评审 B3.1）：所有 `*_pct` **统一「越大越好」**。`inv_days` 原值越小越好，所以它的分位要**取反**后再进 `inv_days_pct`。搞反**不会报错，只会让池子选反**，所以这条必须是明文规则 + 有测试。

**期次不同质要标注**（评审 B3.2）：横截面里各标的「最新已公告报告期」可能不同（例如 4 月是 2025 年报与 2026Q1 混排）。`features` 带 `period`（如 `"2026Q2"`），报告里给出**期次分布**。

**分位的样本集大小要标注**（评审 B3.3）：`inv_days` 对金融股不可算 → 该因子分位的 n 会比 `roe` 小。`features` 带每个 `*_pct` 的样本量（或统一 `cross_section_n`），报告里体现。

## 7. `ctx` 与插桩 2/3 改造

### 7.1 `build_ctx` 增加 `features` 与 `sector`

`ctx` 现在有 7 个键（`code`/`name`/`asof`/`pool`/`asset_type`/`board`/`bars`），**没有 `features`、也没有 `sector`**。本轮加上：

```python
ctx["sector"] = "白色家电"          # 来自 instruments.sector（非 PIT，见 §4.5）
ctx["features"] = {
    "period": "2026Q2",                      # 本次用的是哪一期
    "asof_notice_date": "2026-08-29",
    "notice_date_source": "f10",             # 该公告日是实测还是法定兜底
    "cross_section_n": 17,                   # 横截面样本量
    "na_reasons": ["gross_margin: operate_cost is NULL",
                   "inv_days: inventory is NULL"],
    # 值：原始值 + 分位（分位统一「越大越好」，不可算为 None）
    "roe": 0.18,            "roe_pct": 0.76,
    "gross_margin": None,   "gm_pct": None,
    "gm_yoy_pp": None,      "gm_yoy_pct": None,
    "inv_days": None,       "inv_days_pct": None,
    "fcf_margin": 0.09,     "fcf_pct": 0.55,
    "dupont": {"net_margin": 0.09, "asset_turnover": 0.75,
               "equity_multiplier": 2.6},
}
```

- **键永远齐全**（评审 A5）：不可算给 `None`，绝不留空键——否则插桩里 `ctx["features"]["roe_pct"]` 会 `KeyError`，被沙盒探针判成脚本 bug → **误拒**
- 必须**可 JSON 序列化**（延续既有约束，为将来换子进程执行器留路）
- **PIT**：`cross_section` 与 `features` 都只用 `notice_date <= asof` 的期数（评审 B5：**钉死为 `<=`**，与项目既有 `created_at <= asof` 同构，并明说「视公告日为当日起可用」）
- `build_ctx` 签名扩展为 `build_ctx(inst, pool, bars, *, asof, cross_section=None)`；`cross_section` 由主流程**每轮算一次**（不是每只标的算一次）

### 7.1.1 `dupont` 与 `roe` 的口径关系（评审 B2）

`dupont` 三个分项**全部用期末存量**（教材口径），而 `roe` 用**平均权益**——两者**不构成恒等**，存在口径差。这不许含糊：

- §6.2 明文写「两者口径不同，报告需说明」
- 或者两者都改均值并加恒等断言（§9.1）

**本轮取前者**（教材口径的 `dupont` 更有解释力），并在 `features` 里保留 `dupont` 的 `equity_multiplier` 为期末口径标记。

### 7.2 `PROBE_CTX` 必须补齐完整空形状

上一轮踩过的坑：探针曾用 `{}` 调脚本，任何读 `ctx["bars"]` 的正常脚本都会 `KeyError` 被误判为沙盒失败。`features` **和 `sector`** 会重演同一个坑——读 `ctx["features"]["roe"]` 的脚本在 `features={}` 下必挂。

所以 `PROBE_CTX` 必须：`sector` 有值、`features` 的**每个键都在**且值可 JSON 序列化（`0.0` / `None` / `False` / 空列表）。

同时修正注释：它要覆盖的是**所有调用点 ctx 键的并集**，不是 `build_ctx` 一个来源。

### 7.3 插桩 0/2/3 的改造

**插桩0（行业特殊排雷）—— 本轮补上**（评审 A7：原设计采了行业分类却没喂给它，范围与需求来源不一致）：

- 现在它靠**标的名称关键字猜行业**（`"电器"/"集团" → 家电`）
- 改为**优先用 `ctx["sector"]`**（东财 `INDUSTRY_NAME`，如「白色家电」「银行Ⅱ」），名称关键字仅作兜底
- **行业口径只允许一套**（§4.5）；「行业非 PIT」的近似声明要出现在 `ctx`/报告里

**插桩2/3（中期/长期打分）**：

- 删掉现在的占位逻辑（插桩2 用日波动率、插桩3 用 120 日涨幅）
- 改读 `ctx["features"]`，**按可用因子加权**（权重按可用性归一，见 §6.3.1），产出 `score`
- `risk_list`：**删掉**「财务因子未接」（不再成立），换成「**横截面分位排序，样本内，未经验证**」
- 因子不可算时 `pass_flag=False`，`reason` 写明缺哪一期/哪个字段

**插桩5（复盘）** 本轮不动（仍是返回空结果的占位）——它属于 AI 优化子流程，那一环还没建。

## 11. 已知限制（不美化）

1. **本轮产不出任何准确率证据。** 沙盒回放仍是 fail-closed 空实现，`verdict` 恒为 `INCONCLUSIVE`——「加了财务因子之后候选池是不是选得更准」**当前没有任何代码能回答**。
2. **样本量不够。** 21 只 × 季报，一年 4 个观测点；项目的铁律是「不足 120 交易日不算结论」，季报数据远够不着。横截面分位在 21 个点上也很薄。
3. **已有实证结论是负面的。** 项目测过的方向能力 ≈ 0（按日聚类 0.3819±0.0070）。财务因子更可能是**风险/质量的描述**，不是涨跌的预测；本轮不假设它们能提升方向准确率。
4. **行业分类非 PIT**，与 `screen.py` 的 ST 判据同属近似。
5. **过拟合检测仍是 stub**；脏数据校验只覆盖财报的基本形态。
6. **「库存系数」按存货周转天数实现**，是解释性选择，非文档原意确认。
7. **只采公开数据**，因此不掌握任何内部材料带来的信息优势。
8. **金融股的毛利率与存货周转天然不可算**（银行/保险概念上无「营业成本」「存货」）。按 §6.3.1 的机制它们会被 NA 掉、在报告里单列，**不是静默丢弃**；但这也意味着**金融股与一般工商的 `score` 是基于不同因子集算出来的，横截面不可严格直接比**。
9. **公告日有推定成分**：F10 取不到或合理性检查不过的期数回退法定披露截止日（`notice_date_source='statutory'`），比真实公告日保守（最多晚约一个月）。这是**安全方向**的近似，但报告里要能看出哪些期是推定的。
10. **`dupont` 与 `roe` 口径不同**（期末 vs 均值），两者不构成恒等——这是教材口径的选择，已在 §7.1.1 挑明，不是 bug。

### 与准确率的关系（必须说清）

本轮买的是**能力**（能拿到真财报、能算出真指标），**不是证据**。回答「这些因子能不能提升准确率」需要一条现在还缺的路径：

```
沙盒逐调仓日回放（先把 fail-closed 补成真回放）
  → 用 walk-forward + 按日聚类 + 扣成本 + 对照 index_300 评估因子
  → 跑不赢就撤（CLAUDE.md 反过拟合红线）
```

**这条路径是「按结果反推」的前提。** 在它建成之前，任何关于这些因子有效性的说法都是无据的。
