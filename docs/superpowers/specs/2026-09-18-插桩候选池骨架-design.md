## 1. 背景

`stock/` 下的八份需求文档描述的系统与现有实现（P1–P36）架构不同。差异集中在两条：

1. **文档要求「固定主干 + AI 可迭代插桩脚本」**：模块1 候选池筛选系统的全部因子与公式放在 6 个可动态替换的「插桩脚本」里（桩 0–5），主干流程固化不可改。
2. **现有实现里完全没有这套东西**：全仓 30 张表、111 个 py 文件中，没有任何候选池表、插桩版本表、沙盒回测表，也没有任何动态脚本加载代码。

同时，文档中若干**判定口径**（30 天评估周期、以跑赢人工账户为目标）与项目既有工程铁律（120 交易日门槛、walk-forward、按日聚类）在算数上不兼容。

**本设计的第一条前置决策即为此**：**功能照文档，判定口径守铁律**。

## 4. 架构分层

插桩基础设施与股票业务**完全解耦**——这是硬要求，保证将来执行器从方案 A 换成子进程隔离时，业务代码一行不改。

```
stocklab/
├── plugin/                    # 新增：插桩基础设施（不含任何股票业务概念）
│   ├── contract.py            # 脚本接口协议 + 返回值结构校验
│   ├── guard.py               # AST 静态预检
│   ├── runtime.py             # 受限 exec + 超时
│   ├── store.py               # 版本库读写（plugin_scripts / plugin_audit / plugin_backtests）
│   ├── lifecycle.py           # 状态机
│   └── sandbox.py             # 新旧版本对比回测（复用 backtest/）
└── candidate/                 # 新增：模块1 业务
    ├── seeds.py               # 20 只种子清单
    ├── screen.py              # 步骤3 固定前置排雷（主干，AI 不可改）
    ├── pools.py               # 步骤6 三池分流
    ├── score.py               # 步骤7 调用插桩 0-3
    ├── risk_adjust.py         # 步骤8 调用插桩4
    ├── snapshot.py            # 步骤9-10 入库 + 快照
    └── report.py              # 步骤11 Markdown 报告
```

**依赖方向**：`candidate/` → `plugin/` → `store/`。`plugin/` **不得** import `candidate/`（否则基础设施被业务污染）。

## 5. 数据模型

六张新表，全部 **append-only**（沿用现有 `store/schema.sql` 的触发器约定）。

### 5.1 `plugin_scripts` —— 插桩脚本版本库

| 列 | 类型 | 说明 |
|---|---|---|
| `script_id` | INTEGER PK AUTOINCREMENT | |
| `plugin_id` | TEXT NOT NULL | `'0'`–`'5'` / `'A1'`–`'A3'` / `'B1'`；本轮只用 `'0'`–`'5'` |
| `version` | TEXT NOT NULL | 语义版本，如 `1.0.0` |
| `source_text` | TEXT NOT NULL | **脚本文本**（文档 01 §存储 明确要求） |
| `source_sha256` | TEXT NOT NULL | 版本指纹 |
| `created_at` | TEXT NOT NULL | |
| `note` | TEXT | |

`UNIQUE(plugin_id, version)`。**行不可变**：UPDATE 与 DELETE 一律拒绝。

### 5.2 `plugin_audit` —— 审核事件流

| 列 | 类型 | 说明 |
|---|---|---|
| `audit_id` | INTEGER PK AUTOINCREMENT | |
| `script_id` | INTEGER NOT NULL | → `plugin_scripts.script_id` |
| `action` | TEXT NOT NULL | `submit` / `sandbox_pass` / `sandbox_fail` / `approve` / `reject` / `archive`。**没有 `rollback`**——回滚复用 `approve`（见 §9.1） |
| `actor` | TEXT NOT NULL | 由命令的 `--actor` 提供，缺省取当前系统用户名。**不许留空**——审计链上「谁批的」不能是空的 |
| `reason` | TEXT | `approve` / `reject` 必填 |
| `created_at` | TEXT NOT NULL | |

### 5.3 `plugin_backtests` —— 沙盒回测报告

| 列 | 类型 | 说明 |
|---|---|---|
| `backtest_id` | INTEGER PK AUTOINCREMENT | |
| `candidate_script_id` | INTEGER NOT NULL | |
| `baseline_script_id` | INTEGER NULL | **首版无 baseline，允许 NULL** |
| `pool` | TEXT NOT NULL | `short` / `mid` / `long` |
| `window_start` / `window_end` | TEXT NOT NULL | |
| `metrics_json` | TEXT NOT NULL | `{delta, ci_low, ci_high, n_days, train_gap}` |
| `verdict` | TEXT NOT NULL | `WIN` / `LOSE` / `INCONCLUSIVE` |
| `overfit_flag` | TEXT | `none` / `suspected` |
| `report_sha256` | TEXT NOT NULL | |
| `created_at` | TEXT NOT NULL | |

### 5.4 `candidate_snapshots` —— 候选池快照

`snapshot_id`(PK) / `asof` / `run_kind`(`light`/`weekly`/`quarterly`) / `params_json` / `created_at`
`UNIQUE(asof, run_kind)` —— 幂等键，重跑不产生第二条快照。

### 5.5 `candidate_members` —— 快照成员

`snapshot_id` / `code` / `pool` / `raw_score` / `adj_score` / `reason` / `risk_json` / `status` / `entered_at`
主键 `(snapshot_id, code, pool)`；`status` ∈ `观察中/等待买点/已建仓/逻辑证伪移出`。

**`status` 不可变，它是「该快照时点」的状态快照**（对齐文档 06 把状态列为快照记录字段）。标的的当前状态 = **最新快照里的 `status`**，状态变更靠产生新快照表达，不靠改行。

本轮只产出两种状态：`观察中`（入池）与 `逻辑证伪移出`（被淘汰或评分跌破阈值）。`等待买点` / `已建仓` 依赖模块2 的持仓联动，**本轮不实现**，枚举值保留但不会出现。

### 5.6 `candidate_rejects` —— 淘汰标的库

`snapshot_id` / `code` / `stage` / `reason` / `plugin_id`
`stage` ∈ `pre_screen`（步骤3）/ `industry_screen`（步骤4）/ `score`（步骤7）。

### 5.7 一个刻意的设计决定：状态由事件流推导

**`plugin_scripts` 不设可 UPDATE 的 `status` 列。**

当前状态由 `plugin_audit` **推导**：某 `plugin_id` 下最后一次 `approve` 指向的 `script_id` 即 active。

理由：项目铁律是 append-only。`strategy_registry` 那种「行内改 `status` + `promoted_at`」的做法开了口子。插桩版本库是「AI 生成代码 → 人工审核 → 上线」的**审计链**，「这版是谁在什么时候批的」必须永久可查；可改的 status 列会把这信息抹掉。

代价：查当前 active 版本要扫 audit 表。该表极小（一轮迭代几行），加索引 `(script_id, action, created_at)` 足够。

## 6. 插桩契约

### 6.1 脚本形态

每段插桩是一个 Python 源文件文本，**必须定义 `run(ctx)`**：

```python
def run(ctx: dict) -> dict:
    # ctx = {"code","name","asof","pool","bars":[...],"features":{...}}
    return {"score": 78.5, "pass_flag": True, "reason": "...", "risk_list": []}
```

`ctx` 中**只含 ≤ asof 的数据**（PIT）。喂入未来数据必须报错（对齐现有 `LookaheadError` 手法）。

### 6.2 返回结构校验（严格照文档 01 的约定结构体）

| 插桩 | 必填字段 |
|---|---|
| `0` 行业特殊排雷 | `pass_flag: bool`、`risk_note: list[str]` |
| `1` 短期因子打分 | `score: float ∈ [0,100]`、`pass_flag: bool`、`reason: str`、`risk_list: list[str]` |
| `2` 中期景气财务打分 | 同上 |
| `3` 长期护城河打分 | 同上 |
| `4` 风险权重修正 | `final_score: float ∈ [0,100]`、`risk_out: list[str]` |
| `5` 定期复盘分析 | `analysis_result: dict`、`bad_case_list: list` |

**校验在两个时点各做一次**：`submit` 时、`approve`（上线）时。任一不符 → `PluginContractError`，拒绝。

理由：脚本文本一经落库不可变，但校验逻辑会随项目演进而收紧；上线时再校验一次，保证「现在能跑的」就是「当初认证过的」语义。

**数值越界一律拒绝，不做 clamp。** `score = 150` 是脚本的 bug，把它悄悄压到 100 会让一个坏脚本看起来工作正常——这比直接报错危险得多。同理 `score = "high"` 拒绝，`bool` 不算 `float`（Python 里 `True` 是 `int` 的子类，要显式排除）。

### 6.3 静态预检拒绝清单（`guard.py`）

AST 层面拒绝：

- `Import` / `ImportFrom`
- 名字：`__import__` / `eval` / `exec` / `compile` / `open` / `globals` / `locals` / `vars` / `getattr` / `setattr` / `delattr`
- **任何以 `__` 开头的属性访问**（防 `().__class__.__bases__.__subclasses__()` 这类逃逸）
- `Global` / `Nonlocal` 声明

拒绝 → `PluginGuardError`，附违规节点的行号。

### 6.4 执行与超时（`runtime.py`）

在受限命名空间（`__builtins__` 白名单：`abs` `min` `max` `sum` `len` `round` `sorted` `enumerate` `zip` `range` `float` `int` `bool` `str` `list` `dict` `tuple` `set` `any` `all` `map` `filter`）中 `exec` 脚本文本，取 `run` 并用 `signal.setitimer(ITIMER_REAL, timeout)` 包住调用。超时 → `PluginTimeout`。

`signal` 只能在主线程用；CLI 与测试都跑在主线程，满足。**这一条要写进 `runtime.py` 的模块 docstring**，否则将来有人从线程池里调用会得到 `ValueError` 而非超时。

## 7. 主流程（模块1 十二步）

`candidate run --asof <date> [--run-kind weekly]`

| 文档步骤 | 实现 |
|---|---|
| 1 任务启动 | CLI 入口，解析 `asof` |
| 2 拉取标准化输入 | 读 `bars_daily` + `features_daily`（PIT，`created_at` ≤ asof） |
| 3 **固定前置通用排雷** | `screen.py`，**主干，AI 不可改**（判据见 §7.1） |
| 4 插桩0 行业特殊排雷 | `plugin` 调用 |
| 5 过滤不通过 → 淘汰库 | 写 `candidate_rejects`，记 `stage` 与 `reason` |
| 6 三池分流路由 | `pools.py`（规则见 §7.2） |
| 7 插桩1/2/3 分别打分 | `score.py` |
| 8 插桩4 风险权重修正 | `risk_adjust.py` |
| 9 候选池入库 + 更新状态 | `candidate_members` |
| 10 保存快照 | `candidate_snapshots`（幂等键 `(asof, run_kind)`） |
| 11 Markdown 候选池报告 | `report.py` |
| 12 判断是否触发 AI 优化子任务 | 本轮**只记标志**，不真跑 |

### 7.1 步骤 3 判据（主干，阈值可配但代码内写死）

| 判据 | 阈值 | 淘汰原因标签 |
|---|---|---|
| 历史数据不足 | 有效 K 线 < 250 交易日 | `insufficient_history` |
| 上市时间不足 | 首根 K 线距今 < 250 交易日 | `too_new` |
| 连续跌停 | 连续 ≥ 3 日跌停 | `consecutive_limit_down` |
| 停牌 | 最近 20 日内无成交 > 5 日 | `suspended` |
| ST 标记 | 名称含 `ST` / `*ST` | `st_flag` |

**已知近似**：ST 判据取自腾讯行情的名称字段，**不是 PIT**（历史某日的 ST 状态取不到）。报告与 `reason` 里必须显式标注为近似，不得当作严格历史事实。

**财报类排雷**（审计非标意见、财务造假）本轮**留桩**，淘汰原因标签 `financial_screen_not_implemented`，并在报告中显式列出「数据未接」。

### 7.2 三池分流规则

| 池 | 准入 |
|---|---|
| 短期 | 全部通过排雷的标的 |
| 中期 | `asset_type == 'stock'`（ETF 无财报，进不了中期池） |
| 长期 | `asset_type == 'stock'` |

文档 01 §候选池数量建议：短期 3–6 / 中期 4–8 / 长期 3–5，一只标的可同入多池。本轮按 `adj_score` 降序取前 N，**默认 N 取各池建议值上限：短期 6 / 中期 8 / 长期 5**（配置项 `POOL_TOPN`，写死在 `pools.py`，不随插桩版本变）。

## 8. 沙盒回测

### 8.1 问题

插桩输出 `score` / `pass_flag`，**没有直接收益指标**，无法直接比新旧版本。

### 8.2 固定下游链路

```
plugin sandbox <script_id> [--window-start D --window-end D]
  → 取窗口内全部调仓日（默认窗口 = 最近 3 年；PIT，只用 ≤ 当日数据）
  → 每个调仓日重放候选池
  → 池内标的按【固定规则】等权持有到下个调仓日，扣成本，对照 index_300
  → 新旧版本逐日对比 → 按日聚类 bootstrap 95% CI
```

**下游转换规则写死在 `sandbox.py`，不随插桩版本变化**——否则「改下游也能提分」会毁掉归因（对应 `CLAUDE.md` 单变量原则）。

调仓周期按池分档：**短期 5 日 / 中期 20 日 / 长期 60 日**。

### 8.3 判定（铁律落点）

| 条件 | verdict |
|---|---|
| 有效交易日 < 120 | `INCONCLUSIVE` —— 报告逐字写「样本不足，不构成结论」 |
| Δ 的 95% CI 不跨 0 且方向为正 | `WIN` |
| CI 跨 0，或方向为负 | `LOSE` |

**「有效交易日」的定义**：窗口内实际产生了持仓收益、且当日两只版本都有观测的**不同交易日数**（按日聚类，不是行数）。A 股同涨同跌，20 只标的同一天 ≠ 20 个独立样本——这条直接对齐 `CLAUDE.md`《度量纪律》第 2 条。

### 8.4 过拟合标记

比对**训练段与验证段**的表现差（`train_gap`）。差距超过阈值 → `overfit_flag = 'suspected'`，报告显式提示。

### 8.5 诚实边界

某个 `plugin_id` 的**首个版本没有 baseline**，沙盒只能跑绝对表现，`verdict` 一律 `INCONCLUSIVE`，`baseline_script_id` 为 NULL。只有第 2 版起才有新旧对比。**不美化**。

## 9. 审核闸门

### 9.1 状态机

状态由 `plugin_audit` 事件流推导（§5.7），事件与状态的对应：

```
脚本落库（无 audit 事件）              = draft
  └─ submit + sandbox_pass          = pending_review
  └─ submit + sandbox_fail          = rejected
pending_review ─ approve ──────────> active
active         ─ 该 plugin_id 有新版本 approve ─> archived
archived       ─ approve ──────────> active        （回滚，复用同一条路径）
```

- 非法迁移（`draft → active` 跳过沙盒、`rejected → active`）必须抛 `PluginStateError`
- **回滚不是独立命令**：对任一 `archived` 版本执行 `approve` 即为回滚，旧 active 转为 `archived`。这样「回滚」与「上线」走同一条已审计的路径，不会成为绕过审核的后门（对应文档 05 运维约束 1「支持一键回滚旧版本」）

### 9.2 命令

| 命令 | 作用 |
|---|---|
| `plugin submit <file> --plugin-id 3 --version 1.0.0` | 预检 + 契约校验 → 落库 `draft` → 跑沙盒 → `pending_review` 或 `rejected` |
| `plugin approve <script_id> --reason "..."` | 该 `plugin_id` 的新 active，旧 active → `archived` |
| `plugin reject <script_id> --reason "..."` | → `rejected` |
| `plugin list --plugin-id 3` | 版本历史 + 推导出的当前状态 |

### 9.3 硬约束

**`approve` 只能由人工 CLI 命令触发，代码中不存在任何自动批准路径**——对应文档 00 全局约束 2「禁止 AI 自动上线策略」。用**源码扫描测试**钉住（照搬现有 `test_paper_never_imports_model_or_kelly` 的手法）。

主流程只调用各 `plugin_id` 下**当前 active** 的版本；**没有 active 版本 → 明确报错，不兜底**（沿用 `strategies/registry.py` 的哲学：不返回默认策略、不自动兜底）。

## 11. 测试策略

**全部离线**（fixture / raw 缓存重放），禁止真实联网。

### 11.1 负面测试是重点

骨架轮最容易自欺的地方是「以为预检安全了」。

| 测试 | 断言 |
|---|---|
| 逃逸样本：`import os` / `open()` / `__import__()` / `().__class__.__bases__` | 各一条，必须抛 `PluginGuardError` |
| 死循环 `while True: pass` | 必须抛 `PluginTimeout`，且主进程不挂 |
| 契约违规：`score=150` / `score="high"` / 缺 `pass_flag` | 各一条，必须拒 |
| 非法状态迁移：`draft→active` / `rejected→active` | 必须拒 |
| `approve` 不可自动化 | 源码扫描断言 |
| PIT 钉子：喂含未来日期的 `ctx` | 必须报错 |
| `plugin_scripts` 不可改 | `UPDATE` / `DELETE` 抛 `IntegrityError` |

### 11.2 正向测试

- 候选池：固定 fixture 数据 → 期望的分池结果与分数
- 沙盒：构造已知序列 → 期望 verdict（含 `INCONCLUSIVE` 的样本不足分支）
- 可复现：同 `asof` 跑两次，报告 md + json 逐字节一致

## 13. 已知限制与未决项

### 已知限制（不美化，写进报告）

1. **执行器不是真沙盒**：AST 预检可被绕过，超时拦不住内存爆炸。威胁模型是「AI 写的脚本会出错」，不是「恶意攻击」。
2. **ST 判据非 PIT**：取自当前名称字段，历史某日的 ST 状态取不到。

5. **样本不足**：20 只标的的候选池在 120 交易日门槛下，短期内所有结论都只能是「观察」。
