# 预测定型闸门与 2026-09-22 的当日口径（P46）

> 两个问题合在一页：① 为什么 `predict run --asof 今天` 需要一道「定型」闸门、判据为什么是它；
> ② 库里 2026-09-22 那 17 条 LIVE 预测是**什么口径**。
> 事故全过程与教训见 `docs/errors/ERROR_DIARY.md` #60。

## 1. ⚠️ 库内口径声明（先读这条）

**`predictions` 里 `asof_date = 2026-09-22` 的 17 条 `pit-rw-v1.0.2` 预测是「收盘前口径」。**

```sql
-- 复核命令（只读）
SELECT code, asof_date, target_date, model_version, created_at
  FROM predictions WHERE asof_date = '2026-09-22';
-- 17 行，created_at 全部 = 2026-09-22T15:05:22+08:00
```

| 事 | 值 |
|---|---|
| 这 17 行的 `created_at` | `2026-09-22T15:05:22+08:00` |
| 当天 K 线的**终值**入库时刻 | `bars_daily.fetched_at = 2026-09-22T15:30:03+08:00` |
| 用途限制 | **不得**当作「用 09-22 收盘价算出的预测」使用；断面/归因分析须显式注明它的输入是 15:05 的盘中 K 线 |
| 为什么不能改 | `predictions` 是 append-only（触发器 `RAISE(ABORT)`），改写历史要升 `MODEL_VERSION`，代价不成比例 |

这不是「数据脏了」，而是**一份口径不同的历史记录**：它的输入是 09-22 15:05 的盘中价。
把它当收盘口径用，误差会一路混进验证与归因。**升版重算留到下一次正常的 `MODEL_VERSION`
变更时一起做**，本轮不改库。

## 2. 为什么需要这道闸门

`is_trade_date_closed(今天, now)` 在 **15:00:00** 就为真，而当天 K 线要到 **15:30**
收盘链的 `ingest bars` 才被刷成终值。两者之间的 30 分钟里，「今天已收盘」为真、
「今天的收盘价」还不存在 —— 任何在这段窗口里跑的 `predict run --asof 今天`
写下的都是**基于半截 bar** 的预测，且写完退不回来。

所以 `predict run --asof <今天>` 有前置判据：**当天的 K 线定型了吗**。

## 3. 判据：`bars_daily.fetched_at ≥ 当日 15:00`

`stocklab/session/close.py::bars_finalized_on(conn, trade_date)`：

- 取当天全部 `adj_mode='none'` 的行，**任一行**的 `fetched_at` 早于 15:00 → 判未定型；
- `fetched_at` 是这一行**最后一次从源站采到的时刻**（`repo.insert_bars` 的
  `ON CONFLICT DO UPDATE` 会刷新它，`repo.py:102`）。早于收盘 ⇒ 那时市场还没收盘
  ⇒ 这根 K 线的 `close` 只能是盘中值；
- **fail-closed**：当天一行 bar 都没有、或 `fetched_at` 读不出时刻 → 同样判未定型；
- **不看墙上时钟**（签名里就没有「现在几点」）。节假日、临时休市、机器睡醒补跑都会
  骗过「时间 ≥ 15:30」这类判据，P46 明令不许拿它当唯一判据。

### 为什么不用另外两个更顺手的判据（都实测过，都恒放行）

| 候选判据 | 事故当天的实测值 | 结论 |
|---|---|---|
| `session backfill-close` 当天已跑过且有成功回执 | 15:05:19 那次 **exit 0** | 放行 ❌ |
| 当天 bar 的 `amount` 非 NULL | `session tick` **自己就会回填**（`session/tick.py:229`），15:05:19 已填好 17 只 | 放行 ❌ |

两者度量的是「**快照/回填这一步跑没跑**」，而问题问的是「**那根 K 线的收盘价是不是终值**」——
`backfill_close_amounts` 只补 `amount`/`turnover`，**一行都不碰 `close`**（`close.py:54-59`）。

### 边界

- **只在 `asof == 今天` 时生效**：`asof` 是历史日（回放）时闸门完全不参与 ——
  历史日复算不受影响，那是整套预测体系的立足点；
- 拒绝时 **exit 2、一行不写**（不落 `predictions`、也不落报告文件）。

## 4. 三层防御各管什么

| 层 | 在哪 | 拦的是 |
|---|---|---|
| T1 排班 | `ops/schedule.py`（patrol 窗口 09:00–**14:30**，60 条） | patrol 根本不在收盘后开工 |
| T2 职责 | `ops/patrol.py::plan()`（今天 asof 的 predict 进 `skipped`） | 机器睡醒补跑、手工 kickstart 时 patrol 也不碰当日预测 |
| T3 数据 | `cli/main.py::cmd_predict_run` + `session/close.py::bars_finalized_on` | **任何**调用者都写不进未定型的当日预测 |
| T4 可见性 | 回执 `plan.skipped` / `summary_line` 的 `skip=` / `/lab/ops` | 「被跳过」「被拒绝」一眼可见，不折进折叠区 |

> 三层不是重复：T1/T2 防的是**已知的那个调用者**，T3 防的是**还没出现的调用者**
> （新链路、手工误敲、睡醒补跑）。

## 5. 真机 plist 的现状（**有意不一致**）

`~/Library/LaunchAgents/com.stocklab.patrol.plist` 仍是 **P42 的 65 槽**版本。
生成器已改成 60 槽，但**产物要重装才生效**：

```bash
.venv/bin/python -m stocklab.cli.main ops schedule install --job patrol   # nanobot 收尾动作
.venv/bin/python -m stocklab.cli.main ops schedule status
```

P46 的**反目标**明确写了开工时不许执行 `ops schedule install`（改真机 plist 是收尾动作），
所以「源码 60 槽 / 本机 plist 65 槽」是**已知且有意**的中间态，不是漏跑。
在那 15:00 那一槽真正从 plist 里消失之前，**T2 + T3 已经兜住它**（跳过 + 闸门），
不会再产生当日收盘前口径的预测。
