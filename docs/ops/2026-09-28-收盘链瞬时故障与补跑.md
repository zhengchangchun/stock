# 2026-09-28 收盘链瞬时故障：一整天的链被一次 DNS 失败判死（＋补跑姿势）

> 事故本身**没有**丢数据（`bars` 等照常入库），丢的是那一天的**派生层**：live 预测、
> 验证行、复盘报告、模拟盘推进、AI 决策。修法不是「让 DNS 不挂」（修不了），而是
> 「一次瞬时失败不许判死一整天」——见 P100 任务书与 [ADR-046](../decisions/2026-09-29-ADR-046-采集步重试与fail-closed边界.md)。
>
> 本文件是**下一次同类事故的 runbook**：先照 §1 认形状，再照 §4 补跑。

## 2. 因果链（一条都不许简化）

1. **15:30 那一刻 DNS 挂了**（三台 K 线 host 全解析失败；报错点名的是 P74a 回退链的
   最后一台 `proxy.finance.qq.com`）。**瞬时**：次日复核三台 DNS 全部正常
   （116.130.229.114 / 116.130.223.103 / 116.130.223.103）。
2. `ingest index` 失败 ⇒ **`trading_calendar` 没有前滚**（它是日历的**唯一**来源）：
   日历 max 停在 `2026-09-24`。
3. ⇒ `predict run --asof 2026-09-28` 被 `predict/service.py::assert_session` 判「非交易日」
   拒绝（**fail-closed 是对的**，见 ADR-046：不许改）。日历是**判据**，不是提示 ——
   允许「日历没覆盖也照样跑」等于允许在不确定的日子里写 append-only 的预测。
4. ⇒ 整条链停在 **9/14** 步：当天没有 live 预测、没有验证行、没有
   `reports/2026-09-28-review.md`、`paper step` 没跑。
5. **二次伤害**：18:30 的 AI 操盘手日更第 1 步问「今天是不是交易日」拿到 `unknown`
   （日历未覆盖 09-28）⇒ 那一轮 7.6 s 就结束、**零决策零净值**。
   （这一条的修法在 nanobot 侧的 cron prompt，**不在本项目里**。）
6. **自愈只在下一个交易日早上**：09-29 09:06 的 `ops patrol --fix` 排了
   `fixed=ingest_index,session_tick,session_backfill_close,predict_run,review_daily,paper_step`
   —— 它把日历补到 09-29，并顺手补了 09-28 的那几步。**但 09-28 的净值/决策时段回不来。**

```
09-29 09:06:24 patrol failed  latest_closed=2026-09-28 calendar=ok ⑥missing
                              fixed=ingest_index,session_tick,session_backfill_close,
                                    predict_run,review_daily,paper_step
```

> 为什么当天白天那 60 次巡检都没看出问题？巡检第 8 项（日历经）比的是
> **最新已收盘交易日**：09-28 白天行情侧最晚只到 09-24 且 `is_trade_date_closed`
> 在 15:00 前为假 ⇒ `latest_closed` 一直钉在 09-24 ⇒ `calendar=ok`（09-28 全天
> 每轮巡检的 `detail` 都是 `latest_closed=2026-09-24 calendar=ok`）。
> 09-28 的巡检槽到 14:30 为止，等收盘后 `latest_closed` 能前滚时已无人再看。
> **这不是巡检的 bug**（它的判据是自洽的），但「同一天里日历没前滚」这件事
> **收盘链自己的回执**从 P100 起会点名说出来（`anomalies[].kind="calendar_not_forward_rolled"`）。

## 4. 补跑姿势（runbook）

**先决条件**：`ingest index` 先成功一次（日历前滚到目标日之后）。`ops patrol` 本身
就是**只读**体检（**不加** `--fix` 才是只读），先看它报的日历 max 与
`latest_closed`：

```bash
.venv/bin/python -m stocklab.cli.main ops patrol        # 只读：日历 max / latest_closed
```

补跑**那一天整条链**（`--now` 取目标日的收盘后时刻；asof = `--now` 的日期）：

```bash
.venv/bin/python -m stocklab.cli.main ops close \
  --now 2026-09-28T16:00:00+08:00 \
  --report-dir reports --backup-dir data/backups
```

它会先判「09-28 是不是交易日」（日历已前滚 ⇒ 是）与「收盘了没」（`--now` 16:00 ⇒ 是），
然后逐步重跑；`ingest *` 步失败会自动重试（P100）。

### 为什么 `bars_finalized_on` 在次日重采后能过

`predict run` 的定型闸门（`session/close.py::bars_finalized_on`）**只在
`asof == 今天` 时生效**（`cli/main.py` 里那句 `if args.asof == _today()`）：
它拦的是「当天 K 线还是半截 bar 就出预测」（ERROR_DIARY #60）。补跑历史日时
`asof != 今天` ⇒ 这道闸门**根本不参与**，而历史日的 K 线早已定型。

**但有一个同形的坑**（记下来，别再踩）：该闸门对「当天」的判据是
`bars_daily.fetched_at` 的**时刻**（不含日期）必须 ≥ 15:00。09-29 早上那次
`ingest index` 给**前一天**写了 `sh000300 2026-09-28` 一行、`fetched_at =
2026-09-29T09:06:28` —— 若**当天**（asof==今天）再跑 `predict run`，这一行会被读成
「09:06 采到的、早于收盘」⇒ 判未定型。补跑历史日不受影响（闸门不生效），
但**当天重跑**遇到这个形状时，先让 `ingest bars` 把当天那一行刷新一次。

### 补跑**不许**做什么

- 不许为了让链跑绿去动 `assert_session`（fail-closed 是对的）或手工往
  `trading_calendar` 塞一行 —— 日历是指数日线的产物，第二来源迟早与源站分叉；
- 不许重跑已经写成 append-only 的步（`predictions` 撞冲突只会多几条噪声）；
- 补跑**不会**补回当晚的 AI 决策与净值时段 —— 那只能靠「当天就得跑成」。

## 5. 从这一天起，代码怎么变了（P100）

| 变化 | 位置 | 作用 |
|---|---|---|
| `retry_plan` / `RETRY_DELAY_S=15.0` / `RETRY_ATTEMPTS=3` | `ops/runner.py` | 可选的每步重试（缺省 `None` ⇒ 零行为变化；`timeout` 不重试；等待装不进 deadline 就按 `budget_exhausted` 收尾） |
| `CLOSE_RETRY_PLAN` / `MONTHLY_RETRY_PLAN` | `ops/chain.py` | 只有 `ingest *` 步声明可重试（幂等且联网络） |
| `retried_steps` / `step_retried` / `calendar_not_forward_rolled` | `ops/chain.py` | 重试过就**看得见**；日历没前滚时回执点名「`ingest_index` 是日历唯一来源，它失败会连带 `predict_run` 判非交易日」 |

**这一条救不了什么**：DNS 连续挂超过 30 s（三次尝试全在同一个坏窗口里）、
或源站本身不可用 —— 那时链照旧如实报红，只是不再把「一次瞬时抖动」读成「一整天」。

## 6. 同一个晚上，AI 操盘手日更也断了（2026-09-29 核出，与本档不同一条线）

09-28 的 AI 六臂决策与净值缺口，**不是**收盘链那条线造成的，而是 nanobot cron 自己的
agent 轮次没跑成：`~/.nanobot/workspace/cron/runs/c3a99ae8_1790594910897_735f5c3a.json`
里 `status = "ok"`，但 `response` 是一段 provider 错误 ——

```
Error: {'error': {'message': 'Forward failed: Upstream request failed: [DNS]
url=https://api-code-maker.nie.netease.com/anthropic/v1/messages -> client error
(Connect) -> dns error -> failed to lookup address information: nodename nor
servname provided, or not known', 'type': 'proxy_error'}}
```

⇒ 两轮 `ai-trader.py`（轮 A `--no-run` / 轮 B 统一 run）**一次都没起**。

**教训（与 ERROR_DIARY #53 同型，这是它在 AI 操盘链上的第一个实例）**：cron 的 `status`
只回答「这轮 agent 跑完没」，不回答「活干成了没」；判 AI 日更只能看**台账三件套** ——
`paper_agent_decisions`（三条臂齐）／`paper_agent_reviews`（v4 一行）／`paper_nav_daily`（每臂一行）。
P100 的采集步重试**救不了这条路**：它在另一个进程里、不经 `ops/runner.py`。

**09-29 复核**：`api-code-maker.nie.netease.com` 与 `api.commandcode.ai` 两个模型端点
DNS 与连通都正常（403/401 为无凭据的预期响应）⇒ 09-28 是**瞬时**故障，不是配置问题。

**防**：2026-09-29 起挂「当晚 19:45 核账」一次性任务 —— 读上面三件套，缺任何一条就先看
那份 run JSON 的 `response`：是 provider/DNS 类错误就按 cron 原文自己补起两轮，两轮跑过
但没落库就如实报错、**不补造决策**（决策不可回放，缺口只记账）。
