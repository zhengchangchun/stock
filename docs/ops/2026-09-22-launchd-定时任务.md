# stocklab 定时任务：改用系统 launchd 的安装与回退（2026-09-22）

> 决策见 **ADR-020**（`docs/decisions/2026-09-22-ADR-020-调度载体改用系统launchd.md`）。
> 本文件是**操作手册**：装什么、怎么自证、被什么挡住、怎么退回来。
> nanobot cron 那份老清单（`docs/ops/cron-2026-09-21-待挂.md`）是历史记录，
> 其中三条任务在 launchd 自证通过后**要删掉** —— 撤除前置条件见 §4。

## 1. 三件事各有唯一责任人

| 问题 | 谁回答 | 在哪 |
|---|---|---|
| 什么时候跑 | launchd | `~/Library/LaunchAgents/com.stocklab.{close,patrol,monthly}.plist` |
| 跑什么 / 顺序 / 什么算异常 | 项目 | `ops/chain.py`、`ops/patrol.py`、`ops/runner.py` |
| 跑了什么结果 | 项目 | `reports/ops/latest-*.json`、`job_runs`、`data/logs/*.log` |

三条任务的窗口与命令：

| name | label | 窗口 | argv |
|---|---|---|---|
| `close` | `com.stocklab.close` | 每交易日 15:30 | `ops close` |
| `patrol` | `com.stocklab.patrol` | 工作日 09:00–15:00 每 30 分钟（65 条触发点） | `ops patrol --fix` |
| `monthly` | `com.stocklab.monthly` | 每月 1 日 08:00 | `ops monthly` |

⚠️ **patrol 为什么少了 15:30 那一格**（P42，错峰）：patrol 曾覆盖到 15:30，与 `close`
撞在同一分钟 —— `patrol --fix` 会真起子进程补步、`close` 会跑整条 12 步链，两个写者并发写
同一个 SQLite 库 → `database is locked` → 收盘链**断链（exit 2）**。收盘后补缺口的职责本
就归 `close`，15:30 那轮巡逻是冗余的，故 patrol 窗口收到 09:00–15:00。
护栏：`tests/test_ops_close.py::test_no_two_jobs_fire_at_the_same_moment`（任意两 job
触发时刻无交集），再加任务时撞点会当场红。

## 2. 安装（本机 macOS）

```bash
cd ~/Documents/Workspace/stock

# ① 先看将要写进系统的 plist（纯函数输出，不碰文件系统）
.venv/bin/python -m stocklab.cli.main ops schedule generate --job close

# ② 装三条（写 ~/Library/LaunchAgents/ + launchctl bootstrap；已加载会先 bootout）
.venv/bin/python -m stocklab.cli.main ops schedule install
#   单条：  … schedule install --job patrol
#   指定解释器/仓库根（默认当前 sys.executable 与仓库根）：
#   … schedule install --python /opt/homebrew/.../python3.12 --project-root "$PWD"

# ③ 自证：加载了没、上次退出码几
.venv/bin/python -m stocklab.cli.main ops schedule status
launchctl list | grep stocklab

# ④ 立刻跑一次（巡检可安全自证；收盘链在未收盘时会拒绝执行，这是设计）
.venv/bin/python -m stocklab.cli.main ops schedule kickstart --job patrol
```

回退：

```bash
.venv/bin/python -m stocklab.cli.main ops schedule uninstall            # 三条
.venv/bin/python -m stocklab.cli.main ops schedule uninstall --job close
launchctl bootout gui/$UID/com.stocklab.close     # 只停不删 plist 的等价写法
```

页面：`lab serve` 之后看 **`/lab/ops`**（导航「定时任务」）—— 三条任务的窗口/命令/plist/回执/
逐步退出码/摘要行/历史，以及「库里最近跑了什么」。
**页面不代跑 `launchctl`**：谁加载了、上次退出码几，唯一真源是 `launchctl list` 与 `ops schedule status`。

## 3. ⚠️ 已知阻塞：macOS TCC 挡住 `~/Documents` 下的 launchd 进程

**现象（2026-09-22 12:19 实测）**：`install` 三条都 `bootstrap` 成功、`status` 三条
`loaded=true`、plist 落盘齐全；但 `kickstart --job close` 起的进程（pid 69249）
**卡死在 Python 启动期的 `open()` 里**，不产出回执、不写日志。

**证据**（`/usr/bin/log show --last 45m --predicate 'process == "tccd"'`）：

```
12:19:40 tccd  AUTHREQ_CTX: msgID=92539.492, function=TCCAccessRequest,
              service=kTCCServiceSystemPolicyDocumentsFolder, preflight=no
12:19:40 tccd  AUTHREQ_ATTRIBUTION: {responsible={TCCDProcess: identifier=python3-5555…,
              pid=69249, …, responsible_path=/opt/homebrew/Cellar/python@3.12/3.12.9/
              Frameworks/Python.framework/Versions/3.12/bin/python3.12, …},
              requesting={… com.apple.sandboxd …}}
12:19:40 tccd  AUTHREQ_PROMPTING: service=kTCCServiceSystemPolicyDocumentsFolder,
              subject=…/python3.12
```

读法：macOS 认为「Python 要访问『文稿』文件夹」，正在**等一个授权弹框**；
launchd 上下文里没有前台会话，没人能点那个框 ⇒ 进程一直等下去。

**为什么终端里手动跑没事**：终端（iTerm/Terminal）自己已经拿到了那份授权，
子进程借用的是**终端**的授权；launchd 起的进程不继承它，于是第一次运行必然撞墙。

**两条解法（任选其一）**：

1. **让它弹、然后点「允许」**：`ops schedule kickstart --job close`（或 `ops patrol`）之后，
   前台会（或曾经）出现「"Python" 想访问『文稿』文件夹中的文件」→ 点**允许**；
   若框已经消失，去 **系统设置 › 隐私与安全性 › 文件与文件夹** 里找 Python 那一项打开「文稿文件夹」。
   ⚠️ 授权是**按解释器路径**记的：换 python 版本、换 homebrew Cellar 路径，要重新授权。
2. **给解释器「完全磁盘访问权限」**：**系统设置 › 隐私与安全性 › 完全磁盘访问权限** →
   `+` → `⌘⇧G` 粘 `/opt/homebrew/Cellar/python@3.12/3.12.9/Frameworks/Python.framework/Versions/3.12/bin/python3.12`
   → 打开并勾选。（项目的 `.venv/bin/python` 是指向它的符号链接，最终仍是这个二进制。）

**第三条路（不推荐，仅记录）**：把仓库挪到 `~/Documents` 之外（如 `~/Workspace/stock`）。
它绕开的是 TCC 而不是问题本身 —— 大量路径、脚本文档、cron 正文都得跟着改。

**当前处置（12:2x）**：已 `kill 69249` 并
`launchctl bootout gui/$UID/com.stocklab.{close,patrol,monthly}`；
**plist 文件留在盘上**（下次 `ops schedule install` 直接覆盖重装），
`launchctl list` 里已无 `com.stocklab.*` 残留，也无孤儿进程。

## 4. 撤 nanobot 三条的**前置条件**（一条都不能少）

nanobot 现在仍挂着（`cron list` 以机器上的现值为准）：

| | 任务 | 理由 |
|---|---|---|
| A | `d2ffe556` 收盘链（`30 15 * * 1-5`） | 与 launchd `close` 同窗口 |
| B | `d52f97b3` 巡检（`*/30 9-15 * * 1-5`） | 与 launchd `patrol` 同窗口 —— ⚠️ P42 后 patrol 只到 15:00，B 仍多 15:30 一格，那一格会与 launchd `close` 撞点 |
| C | `d412c0d2` 月度刷新（`0 8 1 * *`） | 与 launchd `monthly` 同窗口 |

**为什么不能提前删**：launchd 现在跑不起来（§3），先删 nanobot 就会出现**无人调度的窗口**；
而两边同时活着，`ops close` 与 nanobot 的采集步会在同一时刻写同一个 SQLite 库 ⇒ 撞写锁。

撤除顺序（每条都要有证据）：

1. 用户完成 §3 的授权；
2. `ops schedule install` 重装 → `ops schedule status` 三条 `loaded=true`；
3. `ops schedule kickstart` 自证至少一条真实跑通（`patrol` 最安全；
   收盘链要等 15:30 后，或看当天的 `reports/ops/latest-close.json` 自然出现）；
4. 观察**一个完整交易日**：launchd 的 `data/logs/<job>.{out,err}.log` 与
   `reports/ops/latest-*.json` 有内容、`job_runs` 有对应行，且 nanobot 侧无重复跑；
5. 再删 nanobot 三条（`cron remove`），并在 `docs/README.md` / 本文件把状态改成「已切换」。

## 5. 退出码怎么读（页面 / launchd 日志 / 人工排查共用同一份）

| 码 | 含义 |
|---|---|
| 0 | 全绿（含非交易日整轮跳过） |
| 1 | 链路跑完了，但有异常（`missing`/`stale`，或某一步如实报了 1） |
| 2 | 判不了或断链（库不在 / 还没收盘 / 预算用尽 / 某步 ≥2 / 事后体检判不了） |

`ops close` 的**拒绝执行**（还没收盘 ⇒ 2）是**设计**：半截 bar 与当日 LIVE 预测都是 append-only，
写错了退不回来。`ops patrol` 判不出「今天是不是交易日」时**仍**照采一次 —— 但那是另一个口径，
两个决定都写在各自模块的 docstring 里。
