## 2026-09-14: 非交互调用时 `--permission-mode acceptEdits` 不批准 Bash

### 错误描述
上一次 P1 会话以 `--permission-mode acceptEdits` 启动，Claude Code 可以编辑文件，
但**每一次 Bash 调用都需要人工批准**。无人值守场景下没人按「允许」，
于是整个会话无法执行任何命令（建 venv、跑 pytest、git 提交全部做不了），最终空转失败。

### 根本原因
`acceptEdits` 只自动批准**文件编辑**类工具，不覆盖 Bash。
把它当成「无人值守模式」是错的。

### 教训
非交互（nanobot 驱动）时，Bash 必须可用，否则等于没开工。

### 检查清单（下次必查）
- [ ] 非交互会话使用 `IS_SANDBOX=1` + `--permission-mode bypassPermissions`
- [ ] 开工第一件事：跑一条无害命令（`git status`）确认 Bash 真能用
- [ ] 沙箱环境**不要**用 `--dangerously-skip-permissions`

## 2026-09-14: Claude Code Bash 工具的 PATH 被插件覆盖

### 错误描述
Bash 已获批准，但 `git`、`python3` 等命令找不到（command not found），
原因是插件（superpowers 等）注入的 PATH 覆盖了系统 PATH。

### 根本原因
Claude Code 的 Bash 工具使用 settings 里 `env.PATH`；

### 教训
PATH 必须显式写死并保留系统基础目录，不依赖继承。

### 检查清单（下次必查）
- [ ] 项目 `.claude/settings.json` 的 `env.PATH` 含 `/usr/bin`、`/bin`、`/usr/local/bin`
- [ ] 新项目初始化后立即验证 `git --version` / `python3 -V`

### 错误描述
`docs/plans/2026-09-14-phase1-4-implementation.md` Task 3 的
`test_small_trade_costs_more_than_proportional` 断言
`small > large * 100`。按同一份计划里的成本模型实算：
小额费率 = 5.01/1000 = 0.501%，大额费率 = 260/1e6 = 0.026%，

## 2026-09-14: 触发器 ABORT 后隐式事务残留，下一次 BEGIN 报错

### 错误描述
append-only 表被 UPDATE 时应抛 `IntegrityError` —— 这没问题。
但抛错之后，再执行 `with transaction(conn): INSERT ...` 会报
`sqlite3.OperationalError: cannot start a transaction within a transaction`。
计划里的测试 `test_insert_still_works_after_failed_update` 正好抓到了这个真实缺陷。

### 根本原因
Python `sqlite3` 默认是 legacy 事务控制（`isolation_level=""`）：
DML 语句会**隐式**开启事务。被 `RAISE(ABORT)` 中止的语句只回滚该语句本身，
**显式事务之外的这个隐式事务仍然开着**，于是下一条 `BEGIN` 失败。
（注意 ABORT ≠ ROLLBACK：ABORT 只撤销当前语句。）

### 教训
不要依赖驱动层的隐式事务；显式打开、显式关闭，语义才可预测。

### 检查清单（下次必查）
- [ ] `sqlite3.connect(..., isolation_level=None)`，让连接处于 autocommit
- [ ] 所有写入包在显式 `transaction()` 里，并在其中检测嵌套（`conn.in_transaction`）
- [ ] 任何「约束/触发器抛错」的测试，后面要再跟一条写入，验证连接仍可用

## 2026-09-14: 计划里的 DDL 与它自己的测试互斥

### 错误描述
Task 4 的 `schema.sql` 把 `created_at` / `params_hash` / `data_version` /
`source` / `fetched_at` 定义为 `NOT NULL`（无默认值），
但同一 Task 的测试却按 5 列、8 列插入，必然触发 `NOT NULL constraint failed`。
DDL 与测试互相矛盾，谁先跑谁错。

### 根本原因
DDL 和测试是两处手写产物，没有同源校验；写计划时只想着「字段要全」，
写测试时只想着「断言要短」。

### 教训
遇到这种冲突，**不要把 NOT NULL 放宽成可空来迁就测试** ——
那会削弱可复现性（append-only 表的 `created_at`/`params_hash` 丢了就再也补不回来）。
正确做法是补齐测试数据，并记录这是「测试服从 DDL」。

### 检查清单（下次必查）
- [ ] 新增 NOT NULL 列时，同步更新所有 INSERT 测试
- [ ] 冲突时先问「哪个意图更强」，而不是「哪个改起来方便」
- [ ] 记录偏离：在 docs/tasks 里写明改了哪几条测试、为什么

## 2026-09-14: `.gitignore` 的裸 `data/` 吞掉 Python 包 `stocklab/data/`

### 错误描述
P2 要提交 `stocklab/data/http.py`，`git add` 报
`The following paths are ignored by one of your .gitignore files: stocklab/data`。
进一步检查发现：P1 的 `stocklab/data/errors.py` 与 `stocklab/data/__init__.py`
**从来没有进过版本库**（`git ls-files stocklab` 里没有它们）。
后果：仓库处于「测试能跑、但新克隆一定挂」的状态 ——
`stocklab/config/universe.py` 第 5 行 `from stocklab.data.errors import HostNotAllowed`
在新克隆里必然 `ModuleNotFoundError`。P1 的 73 个测试全绿也**完全掩盖**了这个问题，
因为它们跑的是本地未提交的工作区。

### 根本原因
`.gitignore` 写的是 `data/`（本意是项目数据目录），而 gitignore 的 `data/` 会匹配
**任意层级**名为 `data` 的目录 —— 包括 Python 包 `stocklab/data/`。
另外「本地全绿」与「仓库自洽」是两件事，只跑测试不检查 `git ls-files` 就发现不了。

### 教训
1. 忽略规则要么根锚定（`/data/`），要么写清层级。
2. **「测试全绿」不等于「仓库完整」**：测试跑的是工作区，仓库缺文件照样全绿。
3. 提交前用 `git status --ignored` / `git ls-files <包名>` 核对一次源码是否真的入库。

### 检查清单（下次必查）
- [ ] `.gitignore` 里凡是要忽略的目录，都加根锚定前缀 `/`
- [ ] 新增 Python 包后，`git ls-files <pkg>/` 必须列出该包所有 `.py`
- [ ] 阶段性验收时额外跑一次 `git ls-files | grep <新目录>` 抽查

## 2026-09-14: 离线守卫把 `socket.socket` 换成函数 → `import ssl` 直接崩

### 错误描述
为实现「测试禁止联网」，conftest 里写了
`monkeypatch.setattr(socket, "socket", _boom)`（`_boom` 是函数）。
结果 `tests/test_data_raw_cache.py` 大面积报
`TypeError: function() argument 'code' must be code, not str`，
栈顶落在 `ssl.py:955` 的 `class SSLSocket(socket):`。

### 根本原因
`ssl` 模块在**导入时**执行 `class SSLSocket(socket)`，即把 `socket.socket` 当**基类**用。
基类必须是类，函数不行。P1 的日历测试没踩到，只是因为那些测试运行时 `ssl`
早就被 `requests` 间接导入过了 —— **同一个守卫，踩不踩得到取决于导入顺序**。

### 教训
替换一个「会被继承的类」时，必须替换成**子类**而不是函数；
子类既能被继承，又能通过覆写 `connect` / `connect_ex` 拦住真实连接。
另外：模块级副作用型缺陷，只在「首次导入」时暴露 —— 测试必须能复现首次导入，
否则修了也证明不了（本次用子进程重跑一次新解释器来钉死）。

### 补充（同日复踩一半）：守卫只拦 socket，不拦 DNS

修好子类问题后，在**无网络命名空间**（`unshare -n`）里跑全量测试，
`test_requests_cannot_reach_network` 反而失败了：只拦 `socket.socket` /
`create_connection` 时，DNS 不可用的环境里 urllib3 会先在 `getaddrinfo`
抛 `gaierror`，**永远走不到我们的守卫**。
于是「守卫有效」的测试实际在断言「本机 DNS 恰好可用」——
换个环境就变味，这正是守卫要防的那类问题。
→ 守卫必须**同时**拦住 `socket.getaddrinfo`；测试也跟着补一条解析阶段的断言。

### 检查清单（下次必查）
- [ ] monkeypatch 替换 `socket.socket` / `ssl.SSLSocket` 这类可能被继承的对象时，用子类
- [ ] 「导入期行为」的修复，必须补一个**子进程/新解释器**的回归测试
- [ ] 全局 autouse 守卫上线后，跑一次全量测试确认没有模块被它弄崩
- [ ] 网络守卫要覆盖**全部**出网路径：DNS 解析 + 连接（+ 代理），缺一层就只剩环境巧合
- [ ] 「能拦住」的测试，要在**真的没有网**的环境里再跑一遍（`unshare -n`）才算证明

## 2026-09-14: 测试替身 `sleep` 让时钟静止，限流与退避互相污染

### 错误描述
Task 8 的退避重试测试断言 `slept == [1.0, 2.0, 4.0]`，实际得到
`[1.0, 0.35, 2.0, 0.35, ...]` —— 多出来的 0.35 是**限流间隔**的 sleep。

### 根本原因
`HttpClient` 用同一个 `sleep` 通道做两件事：限流等待（`min_interval`）与退避重试。
测试把 `sleep` 换成假函数后，**真实时间不再流逝**（假 sleep 立即返回），
于是第二次请求时 `now - last ≈ 0 < min_interval` → 每次重试都额外触发一次限流等待。
即：替身让时钟静止 → 限流逻辑在测试里比生产环境更频繁地生效。

### 教训
一个测试只验证一个机制。测退避就把限流显式关掉（`min_interval=0.0`），
测限流就固定 `clock` 并让重试不发生。**不要靠"环境恰好不会触发另一条分支"**。

### 检查清单（下次必查）
- [ ] 同一函数里有多条「等待/重试」逻辑时，单测逐条隔离验证
- [ ] 替换 `sleep`/`clock` 的测试，先想清楚「时间静止后哪些分支会变成必然触发」
- [ ] 断言「睡了多久」时，用 `min_interval=0` 或显式 clock 隔离无关等待

## 2026-09-14: 解析器「取不到就回退」，把复权价标成不复权

### 错误描述
腾讯日K 适配器最初写成：
`keys = ("qfqday", "day") if adj_mode == "qfq" else ("day", "qfqday")` ——
即「要 day 拿不到就退回 qfqday」。于是一个只含 `qfqday` 的响应，
会在 `adj_mode="none"` 下被解析出来，**价格是前复权的，标签却是不复权**。
更糟的是我自己写的测试把这个行为当成期望值断言了下来。

### 根本原因
「宽松回退」看着像健壮性，实则是在**复权口径**这种不可混淆的语义上做静默降级。
本项目铁律①要求「抓取层绝不下发复权后的价格」，而回退恰好制造了这种数据。
下游拿到的是「贴了错误标签的价格」，比拿不到数据危险得多 ——
因为它会一路算进因子链和回测，且没有任何报错。

### 教训
口径/单位/币种这类**语义契约**不允许 fallback：不匹配就返回空，
让调用方看到「0 根」而不是「一堆贴错标签的价格」。
**写测试时如果发现「当前实现这么写也能过」，要反问一句：这是我要的行为吗？**

### 检查清单（下次必查）
- [ ] 解析/取值路径里不许有跨口径、跨单位、跨币种的 fallback
- [ ] 语义不匹配时返回空/抛错，并让调用方留痕
- [ ] 复权、单位、时区相关的分支，必须有「反向测试」：不匹配时必须取不到数据

## 2026-09-15: 上游接口「静默降级」：请求 900 根回 640 根，不报错

### 错误描述
腾讯 `fqkline` 接口请求 `,900,qfq` 只返回 **640** 根，请求 `,800,qfq` 正常返回 800 根，
请求 `,2000,qfq` 依然返回 **640** 根 —— **HTTP 200、JSON 合法、`msg` 为空、无任何错误信号**。
（同口径不复权 `,900,` / `,2000,` 则如实返回 900 / 2000 根。）

### 教训
1. **HTTP 200 + 合法 JSON ≠ 数据完整。** 必须核对「请求条数 vs 返回条数」。
2. 对已知有上限的接口，**在客户端把上限做成硬守卫**（超限直接 `ValueError`），
   让静默降级在本地就变成显式失败 —— 而不是指望每次都记得核对。
3. 实测结论必须连**完整请求 URI（含全部参数）**一起记录。本次矛盾的根源就是
   ADR-001 只记了「801 根」却没记清 `adj` 口径，导致后续无法解释。

### 检查清单（下次必查）
- [ ] 分页/限量接口：客户端显式校验 `count` 上限，超限直接报错
- [ ] 任何「条数少于请求」的情况都要留痕，除非确认是最后一页
- [ ] 记录实测结论时，把完整 URL（含参数）与响应 SHA256 一起落盘（本项目已有 raw_cache）

## 2026-09-15: 计划里的断言只有「前视」才成立 —— 照抄就得违反 R2

### 错误描述
Task 17 的 `test_percentile_rank` 断言（5 元素序列、`window=5`）：
```python
assert out.iloc[4] == pytest.approx(1.0)     # 最大值 → 100 分位
assert out.iloc[0] == pytest.approx(0.2)     # 最小值 → 20 分位
```
按同一份计划里的实现（`rolling(window=5, min_periods=5)`）实跑：
`iloc[0]` 只有 1 个观测 → **NaN**，断言失败（实测 `Obtained: nan`）。
要让 `iloc[0]` 得到 0.2，唯一的办法是拿**全样本**排名去算 —— 那就是前视（R2 违规）。

### 根本原因
写计划时脑子里想的是「分位数 = 这个值在全序列里的排名」（统计课上的定义），
而写实现时用的是「过去 window 期内的排名」（PIT 定义）。两个定义都不错，
但**不可能同时满足这两个断言**。同类型问题已第 4 次出现
（NOT NULL vs INSERT 列数 → fixture vs 解析器守卫 → PK vs 「不同口径视为不同记录」
→ 本次断言 vs 实现）。

### 教训
1. **同一测试里两个断言互相矛盾，就是「计划写错了」的信号**，不是实现不够聪明。
   本例：最大值断言要求窗口 = 全序列，最小值断言要求窗口 ≠ 全序列。
2. 冲突时问「哪个意图更强」：R2（无前视）是本项目的铁律，比「照抄计划」强。
   所以**改断言、不改实现** —— 若反过来改实现，过的是测试，坏的是全系统。
3. 改断言必须留痕并写明实测值（本次：实测 `nan`，改为用下降序列验证 20 分位）。

### 检查清单（下次必查）
- [ ] 从计划抄测试后，先问「这个期望值在 PIT 定义下能否达到」
- [ ] 断言涉及「全序列统计量」（排名/分位/均值/标准差）时，一律当成前视嫌疑
- [ ] 改断言的每一处，在 `docs/tasks/` 写明：原断言 / 实测值 / 为什么改测试而非改实现

## 2026-09-15 复权因子链（P4 前置）四条新教训

### 1. 判「事件是否存在」的字段，不能同时用来判「条款是什么」
`parse_corp_actions` 原先要求 `fh_sh` 非空，**静默丢弃**了 600690 的 9/36 条事件

**避免**：存在性只认定位字段（`cqr`）；内容只认原文（`FHcontent`）；`fh_sh` 是参考值不是判据。
复查时问自己：「这个字段为空时，是『没有』还是『没填』？」两者必须能区分。

腾讯 qfq 的 000333 2013-09-18 = **−12.649 元**（原价 − 累计每股派息）。负价让任何比率类特征
跨零点翻号，且**看不出来**（数值合法、JSON 合法、HTTP 200）。
**避免**：任何外部复权序列在使用前先断言「价格恒正 + 与不复权序列的比值单调」，否则自建。

### 3. 「参数缺失」的推理必须落到「哪个日期的哪个量」上，不能停在「大致等价」
我曾论证「被略过的除权事件其 k 在分子分母中相消，所以只需按 `usable_from` 卡 as_of」——
错。k 根本没进链，相消不成立；**精确后果是只有跨该事件那一天的那一笔收益错**。
**避免**：写「不影响」之前，把式子逐项写出来，指出「哪一个输出、在哪个输入下、错多少」。
凭印象的等价关系是本项目最贵的错。

**避免**：脚手架里的每个期望值都从实际数据反算，不写「看起来对」的表达式；
构造数据后先断言其形状（首/末日期、条数）再用于被测逻辑。

## 2026-09-15 回测引擎（Task 21-23）五条新教训

### 1. 逐行布尔标记表达不了「窗口相关谓词」
复权缺口的可用性不是「这一天可不可用」，而是「**从 x 到 y 的窗口**可不可用」：
600690 在 2001-01-15 之前的窗口全废，从 2001-01-15 起完全可用。
我最初想在 `adj_factors` 上加 `usable` 列 —— 那会让下游把「从可用起点开始的合法区间」
也一并丢掉，而且丢得**静默**（少算了收益，没有人报错）。
**避免**：判断一个数据属性时先问「它依赖查询的哪个维度」。若依赖窗口/起点，就必须存
**事件**（`adj_factor_blackout(code, cqr, ...)`）或在读取层现算，不能用行级标记。

### 2. 手动重算被「静默降级」过的字段等于没算
我在正文里写下「引擎 fee 25.86 ≠ 手算 25.85」并差点当成 bug 上报。真实原因是我的复核脚本
把**已含滑点的成交价**又当 `ref_price` 传回 `Portfolio.buy`（滑点被叠加两次）。
**避免**：手算复核必须从**读取层给出的原始价**出发，一步步走到引擎输出，每一步都打印中间量；
中间量对不上就在那一步停下，不要跳到结论。差值 0.01 元往往是「同一笔费用被算了两次」。

### 3. 变异测试要打在「数据流顺序」上，不是打在「函数返回什么」上
Task 19 的教训是「裁剪在前，变异指标测不出来」。这次有意选**执行顺序**做变异
（把信号生成挪到执行之前 + 成交价 open→close），一次打红 6 个测试。
**避免**：设计变异时先问「这个 bug 会改变哪个**顺序/时点**」，选结构性的改动，
而不是改数值常量 —— 后者只能证明「常数被写死在测试里」。

### 4. `Trade.price` 是含滑点成交价，不是参考价
`CostModel.fill_price()` 的买入价 = 参考价 × 1.0005。任何展示/核对成交价的代码
都必须说清是哪一个（本任务的 CLI 输出的是**成交价**，因此 `price × qty ≠ 成交额的分母口径` 会让人算错）。
**避免**：价格字段命名带口径后缀（`ref_price` / `fill_price`），或在 dataclass docstring 里写死。

### 5. 用户口述的「数量」也要复核 —— 说 5 个，实测 4 个
用户描述 `600690` 有 5 个无法定价的除权事件，实测 **4** 个（36 个事件中 32 个可定价）。
同一句话里「1745 根 bars 在 2001-01-15 之前」却完全吻合。
**避免**：口述数字与实测冲突时，**以实测为准并显式上报差异**；不要为了「和需求一致」
去凑一个数字，也不要因为「用户说的」就跳过复核。

## 2026-09-15 Walk-forward 切分器（Task 24/25）三条新教训

### 1. 手写「达标所需历史」的粗算 391，精确值 376 —— 同类型第 5 次

我在测试里写下 `min_sessions_required == train + 120 + test`（= 391），
实现给出 **376**，实测失败。原因是我的「粗算」漏了 ceil：
要 120 个样本外交易日、每折 test=21，需要 `ceil(120/21) = 6` 折（共 126 天 > 120），
所以最少历史 = `250 + 21 + 5×21 = 376`，**比 391 少**（多的 5 天由第 6 折覆盖）。

**根因**：`min_sessions` 里含 `ceil(threshold/test)`，这是**不能口算**的量。
这已是「计划/手写断言与实现互斥」的第 5 次（NOT NULL→fixture→PK→前视断言→本次）。

**教训**：凡断言里出现 `ceil`/`floor`/取整/复合不等式，先在实现里把中间量打印出来，
再回填断言值；**改的是断言，但要写清精确值是怎么来的**（本次在测试里补了完整算式注释）。

### 2. 「行数」看起来更像样本量，于是很容易把它当样本量

报告里同时出现两个数字：`oos_trading_days = 2835` 与 `oos_rows = 5670`（2 标的）。
后者数字更大、更像「样本量」，但按日聚类下 A 股同涨同跌：
**20 个标的的同一天 ≠ 20 个独立样本**，有效样本量只能是交易日数。

**教训**：凡是「样本量」类字段，命名里必须带口径（`*_days` / `*_rows`），
并在报告里写死一句「`effective_n` = 交易日数，行数不得用于统计」。
反过来，「加标的能补样本」是错的直觉 —— 加标的只增加**高度相关**的行数。

## 2026-09-15 · 重叠训练窗里的同一笔成本，不能按折摊派

## 2026-09-15 · 程序化调 pytest 时 `-k "a or b"` 必须是一个 argv token

## 2026-09-15 #6 · 已在算 z 了，就别再喂一个带 mu/sigma 的分布

**现象**：P6 预测器在真实数据上首次跑通，载荷里 `key_levels` 的 4 个价位
`p_touch` **全是 `0.0`**。000333 的阻力位 88.50 距离现价 86.80 只有 ~2%，
却报告「触及概率 0」——数字合法、无任何报错、结论完全错误。

**根因**：`statistics.NormalDist(mu, sigma).cdf(x)` 内部会自己做一次
`(x - mu) / sigma`。而代码里的 `z` 已经是标准化后的值：

```python
z = (math.log(level / ref) - mu) / sigma   # 已经标准化
p = 1.0 - float(nd.cdf(z))                 # nd = NormalDist(mu, sigma) → 又除一次
```

二次标准化后 `(z - mu)/sigma ≈ 0.52/0.013 ≈ 40`，`cdf` 直接饱和成 1.0，
于是 `p_touch` 恒为 0 或 1。

**为什么单元测试没抓到**：同一个文件里 `direction` 的三个概率是**正确**的
（它们把**原始**对数收益喂给 `nd.cdf`，没有二次标准化），而且
`test_key_levels_are_measured_from_the_window` 只断言 `0 <= p_touch <= 1`
—— 饱和值 0.0 完美满足这个区间。**「值域合法」不等于「值有意义」**：
一个恒为 0 的概率看起来像「不会触及」，是最难发现的那类错误。
发现它的是**真实数据回放**，不是测试。

**如何避免**：
1. 变量名里带 `z` 的，一律配**标准**正态 `NormalDist()`；要喂 `NormalDist(mu, sigma)`
   就必须喂**原始量纲**的值。两者不允许交叉。
2. 断言概率时不要只断言值域，要断言**它等于手算的公式值**（本文件
   `test_probabilities_match_the_documented_formula` 早就是这么做的，触及概率漏了）。
3. 守卫要写成「不许**整体**饱和」（`any(...)`），而不是「每个都不许饱和」——
   支撑位离现价很远时 `p_touch ≈ 0` 是**正确**结论，要求它非 0 等于逼模型编数。
4. **跑一次真实数据**。这条 bug 在 fixture 里活了整个开发周期。

**修复**：`stocklab/predict/model.py` 改用标准正态；载荷因此改变 →
`MODEL_VERSION` 升到 `pit-rw-v1.0.1`（v1.0.0 两行预测原样留在库里，不被覆盖）。
反证见 `scripts/mutations_p6.py` 变异 5。

## 2026-09-15 · 验证器（P7 Task 32-36）三条新教训

### #7 · `NOT NULL` 的布尔列装不下「无法判定」这第三种状态

**现象**：`verifications.invalidated` 在 schema 里是 `INTEGER NOT NULL DEFAULT 0`，
但打分器对 `invalidate_if` 解析不出条件时**必须**写「判不了」（`_pred(invalidate_if="跌破就减仓")`）。
插入 `None` 会被 SQLite 用 `NOT NULL constraint failed` 直接顶回来。

**当时的诱惑**：写 0 就完事了 —— 反正「没失效」是多数情况，看起来无害。

**为什么不能这么算了**：写 0 等于**说了一句假话**（「这条预测没被失效」），
而真值是「不知道」。报告里若把它算进分母，失效率会被系统性低估 ——
恰恰是把「不知道」当成「没有」的那类静默污染。

**做法**：列里写 0（被 schema 逼的），但**真值另存**在 `notes.undetermined = ["invalidate_if", ...]`，
并在**读取侧**（`report._UNDETERMINED_INVALIDATED`）把这些行从失效率的分母里剔掉，
报告单列 `n_known` / `n_undetermined`。写入侧 `store._to_columns` 里留了长注释说明这是被迫的妥协。

**推广**：凡「布尔列 + 代码判不了」的组合，都是在悄悄制造假数据。
要么把列改成可空三态，要么在读取侧用另一个字段把第三态重建出来 ——
**不允许**「两种状态 + 一个默认值」糊过去。

### #8 · 测试名承诺的范围必须等于断言实际检查的范围

**现象**：`test_unscorable_carries_no_score_at_all` 这个名字承诺「没有任何分数」，
实现却只断言了 `total_score is None` 一行。变异 3（把不可评分行的
`hit_direction`/`score_direction` 写成 1）打过去，这条测试**照绿**，
只有另一条测试变红 —— 4 条变异里唯一一次「1 failed, 1 passed」。

**为什么危险**：名字比断言强，等于给后来的人一个**假的安全感**：
读测试列表以为「不可评分不进分母」被钉住了，实际只钉住了 1/11 个列。
而且这条恰恰是最要命的列 —— 聚合器判「算不算进分母」看的就是结果列是否为 `None`。

**做法**：改成 `parametrize` 四种不可评分路径（`NO_BAR_TARGET` / `SUSPENDED` /
`NO_BAR_ASOF` / `NOT_ADJUSTABLE`）× 全部 11 个分数列逐个断言 `is None`。
改完变异 3 从 `1 failed, 1 passed` 变成 `5 failed`。

**推广**：写测试时**照着名字写断言**；变异测试若出现「部分变红」，
不要庆幸「至少抓到了」，要去看**没红的那条为什么没红** —— 那通常是名字与断言脱节的信号。

### #9 · 把变异测试的「打红」当成验收标准，而不是「我注入了 bug」

**现象**：变异脚本第一次写出来时，四个变异的「打红」步骤都用
`run_pytest(...)` 的返回码判断。但 `pytest` 在**一个测试都没匹配到**时返回码是 5（非 0），
如果把判据写成 `rc != 0`，「锚点路径写错 → 零个测试被收集」会被误判成**打红成功**。

**做法**（`mutations_p6.py` 起就有的规矩，本次继续沿用并显式写进脚本 docstring）：
打红判据 = `rc != 0` **且** 输出里**不含** `no tests ran`。
「没跑测试」不是红，是**无效实验**；空跑的绿比红更贵，因为它会让人以为反证做过了。

### #10 · 幂等比较必须比「库里的样子」，不能比「内存里的对象」

**现象**：全历史回放（3096 个交易日、6055 条 verification）第二次跑，
在 `pred_id=27`（2014-01-08，000333 当天缺 K 线）上抛：

```
VerificationConflict: pred_id=27 已有一条内容不同的验证记录（差异字段 ['invalidated']）
```

**现状值得先肯定一半**：冲突被**显式抛出**而不是静默覆盖 —— 防线本身是对的，
问题在判据把它**误报**了。

**根因**：`verifications.invalidated` 是 `INTEGER NOT NULL DEFAULT 0`，
而不可评分的行在内存里 `invalidated=None`（语义是「判不了」），插入时被 `_to_columns`
逼成 `0`。幂等判定却拿**未规约的新载荷**（`None`）去比 `verification_from_row`
读出来的**已规约旧行**（`0`）→ 恒不相等。修法是 hash 前两边都过 `store._canonical()`。

**为什么单测没抓到**：fixture 造的行情序列**没有缺口**，
所以「不可评分」这条分支在测试库里从未写进行，`None→0` 的规约也就从未被比较过。
**只有真实数据（13/6051 条有缺口）能把它逼出来** —— 与 P6 `p_touch` 那条同一个教训：
`fixture 全绿` 与 `真实数据跑通` 是两件事。

**如何避免**：
1. 「写进去的值」与「读出来的值」之间的**任何规约（类型强转、默认值、None→0）**，
   都必须同时作用于**比较的两侧**。只规约一侧 = 制造一个必然误报的判据。
2. 幂等的标准表述是「**读出来的东西再写一次，结果不变**」——
   所以要拿 `verification_from_row(row)` 的产物做基准，而不是调用方手里那个对象。
3. **全量回放本身就是一次测试**。凡是有「缺数据 / 停牌 / 除权」这类边界分支的功能，
   回归测试必须**造出缺口**（本案补了 `test_cli_backfill_is_idempotent_across_a_data_gap`），
   否则覆盖率是虚的。

### #11 · 长任务要把「可工作的增量」中途提交，不要攒到收尾

**现象**：P8 上半（实验流水线）跑完后，代码（`stocklab/experiments/`、5 个测试文件、
`scripts/mutations_p8.py`、两份实验报告 15KB×2）**全部已落盘且 `pytest` 720 全绿**，
但任务在**「填结论 → 写文档 → 提交」这一步**撞上 `--max-budget-usd` 上限被中断。
结果是：成果**全在工作树里、一次都没提交**，任何一次误操作（`git checkout .` /
`git stash` / 并发的 `git add -A` 提交把自己 sweep 走）都能让几个小时的工作归零。
更糟的是它**看起来像「任务没做完」**，而实际是「做完了但没交付」。

**为什么要紧**：`未提交 = 未交付`。而代码是否「能用」与它是否「已保存」之间
**没有任何关系** —— 720 个测试全绿也保不住一个没 commit 的目录。
另外本目录有个已知的并发风险（见记忆：别的 nanobot actor 会中途 `git add -A`
把在途文件 sweep 走），「攒着不提交」这个习惯在**多 actor 环境**里格外危险。

**如何避免**（写进 P8 及以后所有多任务会话的做法）：
1. **每个可独立验证的单元一绿就提交**，不要把「feat + docs」留到最后一起打。
   本次若在 `pytest 720 passed` 那一刻就 `git commit`，中断的损失只是「少两行索引」。
2. **收尾步骤（填结论/写索引/提交）本身要提前做掉，而不是排在实验之后**。
   即：跑实验之前先把「结论模板 + README 索引占位行 + 提交脚本」准备好；
   实验一跑完就能立刻落盘并提交。
3. **预算纪律**：长任务用 `--max-budget-usd` 兜底时，要**预估收尾成本**并把它
   从实验成本里预留出来；本次是把全部预算花在了「跑通实验」上，
   留给「交付」的是 0 —— 而实验跑得再好，不交付就是白跑。
4. `git status` 应当是**每个阶段结束时的必查项**；看到一堆 `??` 新文件就该警觉：
   要么它有主人（即将提交），要么它正在裸奔。

### #12 · 台账里引用的「口径」必须读实现确认，不能抄文档里的一句话

**现象**：给 `index-mom-dir` 台账写结论时，我想解释「为什么指数方向明明看着有用，
变体却没用」。报告基准表里 `index_300` 在 validate 段按日聚类
**0.5438**，远高于模型（0.3687）—— 很容易顺手写成
「指数当日方向作为预测器有 54% 准确率」。**这句话是错的**（或至少会被读成错的）：
`index_pct` 的实际口径是 `index[target]/index[asof] - 1`
（`stocklab/verify/service.py:100 index_pct_for`），是**与个股被预测窗口完全相同的
同期涨跌** —— 它度量的是「A 股同涨同跌」的**同期共动**，**不是领先信号**。
这个数字和变体的失败**并不矛盾**：同期共动很强，领先信息 ≈ 0。
差点写进台账的是一个**把同期误读成领先**的错误归因，而且它会永久留在 append-only 的台账里。

**根因**：`report.py:212` 的 `note` 写的是「index_300 **当日方向**作为「预测」」——
「当日」这个词在没有说明窗口的情况下极易被读成「asof 当天 → 猜次日」。
我几乎就照着这句 note 下了结论，而 note 不是实现。

**如何避免**：
1. **任何要写进台账/文档的因果归因，必须回代码里把口径读一遍**（哪个字段、哪段窗口、
   哪两个日期相减），而不是抄文档里的自然语言描述。本案读
   `index_pct_for` 只花了 30 秒，却决定了结论对不对。
2. 见到「基准/对照」类数字，先问一句：**它和被测对象用的是同一段窗口吗？**
   同期对照（contemporaneous）与领先对照（leading）是两种东西，
   前者**不可交易**，把它当「上界」或「目标」都会导致错误的方向判断。
3. 顺带记下一条待办（本次**不改**，因为改口径字符串会动报告产物）：
   `report.py` 那个 note 建议改成不易误读的「**同期**（asof→target）指数涨跌」。

### #13 · 否证也要措辞准确：「符号错」不等于「显著变差」

**现象**：写 `rw-mu0` 台账 §5 时，我第一稿写的是
「样本内 Brier 显著变好 → 样本外**显著变差**」。**这是错的**：
样本外方向 Δ=-0.0376，95% CI **[-0.0806, +0.0053] 跨 0** ——
它的正确描述是「**符号是错的**（且不显著）」，机器 gate 的原话也是
「至少一个指标的差值**符号是错的** —— 前提被证伪」，**不是**「显著变差」。

**为什么危险**：本项目的纪律一直在防「把失败救回来」（把「差一点」写成「趋势向好」）。
但**反方向的夸大同样违纪**，而且更隐蔽 —— 它看起来像「诚实」，实际是
**用一个更强的结论（显著变差）去覆盖一个较弱的结论（符号错）**。
台账是 append-only 的、会被后来的人当证据用：写「显著变差」会让人以为
「`mu` 置 0 有统计显著的**负**效应」，从而可能去推导「那反过来 `mu` 加倍会更好」——
这个推论在数据上**没有根据**。措辞夸大和口径漂移是同一类错误。

**如何避免**：
1. 写任何「变好/变差/有效/无效」的结论时，**同时把 CI 抄在结论旁边**，

### #14 · 「部分变红」有两种成因，必须区分：#8 是缺陷，本次是纵深防御

## 2026-09-15 #15 · 分组键由「明天」决定时，事后纯度不是样本外能力

**现象**：P7 报告里一条看起来很硬的观察 —— 命中 `invalidate_if` 的 **665/6038** 行

   预测 `down` 时对称。预测与边界是**同一个窗口形态**的两个函数。

**为什么危险**：这是**最像真发现、其实最不可交易**的那类数字。
它不需要任何前视就能「算出来」，所以 PIT 测试全绿；它的分组键在明天，

2. **判据不能停在「子群之间数字不同」**，要做**决定性检验**：
   构造一个**只用预测时点信息**的选行规则，看它能否复现该子群。
   复现不出来 → 是结果条件子群，不是异质性。
   顺手再做一个**反向对照**（本例：选最宽边界），方向应相反；没相反就说明机制不存在。
3. 「机械共定」有个 30 秒自查法：**把条件的定义写出来，看它是否只用到结果本身。**
   `close_t > resistance` 里的 `close_t` 就是被预测的那个量 —— 一眼可判。
4. 子群内「比常数猜法高」**不构成**技能证据，还要看**边界距离/预测符号**这类
   共享输入是否足以解释（本例解释了）。

**检查清单（下次必查）**
- [ ] 分子群报准确率前，先确认分组键在预测时点**可观测**
- [ ] 结果条件子群必须显式标注「不可交易」，且**禁止**作为变体假设来源

- [ ] 子群准确率高于 `always_*` 时，先查预测与分组键是否**共享输入**

## 2026-09-15 #16 · 封存原因串按开关而非按实际 gate 取值 → 报告谎报 gate=WIN

**现象**：`reports/2026-09-15-exp-sigma-vol-z.md` 第 23 行写着
「原因：validate 段 gate=WIN，但本轮预注册声明封存 test（`--keep-test-sealed`）」，
而同一份报告正文档里的 gate 是 **`LOSE`**、`test_evaluated = False`。
一条报告里同时出现「gate=WIN」与「gate=LOSE」。

**根本原因**：`stocklab/experiments/runner.py` 的 `test_not_evaluated_reason`
用**三元表达式按开关分支**：

```python
... if not evaluate_test_on_win else f"... gate={validate_gate['status']}（未达 WIN）..."
```

`not evaluate_test_on_win` 只回答「有没有带 `--keep-test-sealed`」，**完全没看实际 gate**。
于是「带了封存开关」被直接当成「gate=WIN」—— 把封存**声明**和封存**原因**混为一谈，
而两者是互相独立的事实（gate 可以是 `LOSE`，同时预注册又声明「即使 WIN 也封存」）。

**影响面（为什么危险）**：报告是给**审计者**看的，也是复盘时唯一的机器证据面。
「gate=WIN，只是封存了 test」会让读者以为**变体赢了**、只是纪律上没开 test；
实际是 validate 输了。修好前三份 P9-a 报告都带着这句错话，而三份台账正文
（人写的）写的是 `falsified` → **机器报告与人工台账互相矛盾**。
若只看 JSON 不看正文，结论会被**整体反转**（不采纳 → 值得复现）。
这是「口径错误直接反转结论」，不是排版问题。

**如何避免**：
1. **原因串按「事实」取值，不按「开关」取值。** 分支条件必须是**被描述的那个量本身**
   （这里是 `gate_status`），不是它的代理（`--keep-test-sealed`）。写分支前先问：
   「这个条件能推出我要写的结论吗？」
2. **一个原因串只描述一件事**；有多个独立事实（gate 状态 / 封存声明）就都写出来，
   并指明**主因**。`A if X else B` 的二选一结构天然表达不了「LOSE 且已封存」。
3. **测试要钉「内容」，不是「非空」。** 原测试只断言
   `assert rep["test_not_evaluated_reason"]` —— 写什么谎话都绿。
   新测试断言 `"gate=LOSE" in reason` 且 `"gate=WIN" not in reason`。
   **凡「报告里的一句话」，测试就该断言它的关键子串，而不是它存在。**
4. 自查法：报告里出现两个互相矛盾的字段时，**说明分支条件和它描述的对象不是同一个量**。

**检查清单（下次必查）**
- [ ] 面向审计者的字符串，分支条件必须是**它描述的那个量**，不能是代理开关
- [ ] 多个独立事实要能**同时**表达，不许 `A if X else B` 二选一
- [ ] 报告类字段的测试断言**内容**（关键子串 / 不得出现的子串），不是断言非空
- [ ] 同一份报告内出现自相矛盾的两个字段 → 当作真实性 bug，不是排版问题

**现象**：P10-a 预注册写死了**两个** Brier CI —— (a1) gate 的 `ci95`（正态近似）
与 (a2) **按日聚类的 bootstrap CI**（2000 次、seed 固定），且声明「两者不一致则保守取值」。
真跑完才发现：**报告 dict / 报告 JSON 里根本没有 (a2) 的输入** ——
`metrics.bootstrap_daily_ci` 要的是配对**行**，而报告只留聚合量

但**没有把它接到报告的产物里** —— 判据被预注册了，产物却没留它的输入。
「判据存在」与「判据可复算」是两件事；前者靠函数，后者靠**落盘的中间量**。

**影响面**：这不是数字错误（两次跑逐位一致，结论未变），而是**审计成本**问题：
- 复算一个预注册判据需要**重跑整个实验**（2606 个交易日 × 2 标的 × 2 侧），

- 更危险的一种是**根本算不出来**：若哪天配对行依赖内存态而无法重放，
  预注册的 (a2) 就会变成一句「写了但没法验证」的话，而它**参与判定** ——
  等于判据里混进一个不可复算的分支。

**如何避免**：
1. **预注册里每一个判据，都要问「它在产物里的落点是什么」。** 落点 = 报告里能读到、
   能独立复算的字段。落点不存在 → 这条判据**先别写进预注册**（或把落点一起做进 T6）。
2. **判据的输入要么进报告，要么进一个可复现的命令**。本轮的正确做法是把
   逐日配对 Δ（651 天 × 每天一个均值，不是 1302 行原始行）落进报告
   —— 它就是 (a2) 的**充分统计量**，体积小、可复算、无需重放。
3. 自查法：拿预注册的判据表**逐行**问「这一行的数字从哪个文件的哪个键读出来？」
   答不上来的那一行，就是本轮 (a2) 的下场。

**本轮未修**（不改代码是硬约束）：如实记在案，下一轮走形状轴时把
`bootstrap_daily_ci` 的输入（逐日配对 Δ 序列）作为报告字段落盘（新口径 → 需 ADR）。
本轮 (a2) 的复算路径与两次跑逐位一致的比对，已写在台账 §7.1。

## 2026-09-15 #19 · `ON CONFLICT DO UPDATE` 照抄 `excluded` → 「源站没给」被当成「源站说要清空」

**现象**：`repo.insert_bars` 的冲突分支原本写 `amount = excluded.amount`。
腾讯日K 的响应里**没有** `amount` / `turnover` 这两个字段，所以 `excluded.amount` 恒为
NULL —— 于是**每天重跑一次 `ingest bars`，就会把前一天刚回填好的 `amount` 抹回 NULL**。

**根本原因**：把「本次载荷里的值」当成了「合并后的真相」。`excluded` 是**这一次写进来
什么**，不是**这行应该是什么**。当一个数据源只提供**部分字段**时，「整行照抄 excluded」
这条合并策略等价于「用缺失去擦除已有」。而 `amount` 在 P11 之前从来没人写过（恒 NULL），
所以这个子句长期看不出问题 —— 它要等到「开始积累 amount」那天才发作。

**影响面**：**无声**，而且伪装成成功。每次 `ingest bars` 都返回正常、
`updated: 1` 也照报，只是数据永远积累不起来：第一天回填 → 第二天被自己擦掉 →
第三天再回填…… 所有准确率/净值指标**都不受影响**（它们不读 amount），
所以没有任何一条现成的红灯会亮。这类「数据静默回到原点」的 bug 只能靠
**语义断言**抓，不能靠数值断言抓。

**如何避免**：
1. **数据源是「部分字段」时，UPDATE 子句必须逐字段表态**：「本次没给」算什么？
   如果答案是「保留原值」，就写 `COALESCE(excluded.x, t.x)`。
2. 自查法（一句话）：**「这个字段今天没采到，重跑一次会不会把昨天采到的擦掉？」**
   会 → 就是本条的 bug。
3. **对称性检查**：一条链上有两个写者时（回填写 amount、采集也写 amount），
   两个方向的合并策略都要「只补 NULL」，否则会互相擦 —— 本项目最终两边都是
   `COALESCE`，**双向都不覆盖**。
4. **这类 bug 的测试必须跑两次**：先写值、再用 NULL 重写同一主键，断言值还在。
   一次性的写入测试对它完全免疫。钉住它的测试是
   `tests/test_session_close.py::test_repository_reinsert_does_not_wipe_a_filled_value`。
5. 顺带一条纪律：**回填的准入与作用域都要在 SQL 层面锁死**（`WHERE code=? AND date=?`
   + `adj_mode='none'`），让「够不到别的行」是语句的性质，而不是调用方的自觉。

| 3 | 构造样本时**没按判据构造** | 判据是 `created_at[:10] == asof_date`，却用一个「差一天」的 `now` 去入库预测 → 该行按判据是 REPLAY，测的却是 LIVE 桶 |
| 4 | 断言要求**样本异质**，fixture 却全是同质样本 | `assert hi - lo > 0.5`（「区间要宽到能看出还不知道」），而两天结果完全相同 → `stdev=0` → 区间退化成 `[1.0, 1.0]` |
| 5 | fixture 只是**「搭个场景」**，场景其实由被测对象的遍历顺序决定 | 期望 `skipped_missing_bar == [CODE]`，却连一条快照都没插 —— 回填是**按快照逐标的**遍历的，压根进不到「检查 bar」那一步 |

**根本原因**：测试是**照着当时的心智模型**写的，而心智模型没跟着实现/ fixture 一起更新。
第 1、3 类尤其阴：红灯是在**别人的提交**里炸的（fixture 从 30 根放宽到 124 根、
`classify` 的判据定稿），改的人根本不知道有这些断言在等他。

**影响面**：修红时最容易顺手做的事是「把断言改松」或「把生产语义掰弯」——
两者都会把红灯变成**假绿**（断言不再检查任何东西）。这类「绿灯其实什么都没测」
比红灯危险得多。

**如何避免**：
1. **断言要从 fixture 推导，不要抄**：`== len(_bars())` 而不是 `== 30`。
   抄来的数字在 fixture 变化时不会报错，只会变成假的。
2. **断言产物时，先打印真实产物再写断言**。第 2 类只要看一次实际 md 就没了。
3. **写「实盘 / 回放」这类口径样本前，先把判据念一遍**，再检查 `now` 是否满足它。
   判据写在 `PROVENANCE_RULE` 里就是为了这句自查。
4. **要求「区间宽 / 有不确定性」的断言，fixture 必须有异质样本**。同质样本下
   `stdev=0`，此时断言要么恒假，要么（放宽后）恒真 —— 两种都没在测东西。
   本轮的做法是**把 fixture 改成「一命中一落空」**（把 target 日的 close 抬 +5%，
   超过 `FLAT_BAND`），并顺手加一条 `direction_accuracy_daily == 0.5` 把异质性本身钉住。
5. **构造「缺数据」场景时，先问被测对象是「按什么」遍历的**。按快照遍历时，
   「没有快照」和「有快照但没 bar」是两个完全不同的分支，只有后者会进 `skipped_missing_bar`。
6. 修红的正确姿势：**先把完整报错拿到手**（`--tb=long`，别用被截断的 `sq...`），
   判断「测试错 / 生产错」，再决定改哪边；改测试时在 commit message 里写明
   **为什么新的期望值是对的**（本轮 4 条的推理都写进了 commit message）。

## 2026-09-15: 纯 `CREATE IF NOT EXISTS` 的迁移改不了已存在表的主键（#22）

### 错误描述

本项目的迁移策略是「幂等前滚」：`init_db()` 每次把整份 `schema.sql`
用 `executescript` 跑一遍，全部 DDL 都是 `CREATE TABLE IF NOT EXISTS`。

P12 先建了 `ledger_idem`（`PRIMARY KEY (idem_key)`），随后测试暴露出 scope 应该进主键，
改成 `PRIMARY KEY (idem_key, scope)` 并重跑 `db init` —— **表结构纹丝不动**，
sqlite_master 里还是老的主键。`CREATE TABLE IF NOT EXISTS` 见表已存在就跳过，**不管内容**。

### 根本原因

前滚迁移只保证「新增对象」，**不保证「改变已有对象」**。
它没有 ALTER、没有 DROP、没有版本号比对 —— 这是刻意的简化（ADR-001 D4：不做 down migration），
代价就是**改已有对象的形状必须手工介入**。

### 教训

- 改 schema 里**已存在**对象的形状时，`db init` 跑绿 ≠ 结构已更新。
  必须 `SELECT sql FROM sqlite_master WHERE name=?` 实测比对。
- 该表当时是**本轮刚建的空表**（0 行），所以 DROP 重建是安全的；
  若表里已有历史数据，DROP 就是删历史数据 —— 那种情况**必须**走新表 + 迁移脚本，
  绝不能 DROP。
- 判断前先查行数，把「它是空的」当成重建的前提写进命令里（`assert count == 0`）。

### 检查清单（下次必查）

- [ ] 我这次改的是**新对象**还是**已有对象**？已有对象的形状改动，前滚一定不生效
- [ ] 重建前先 `SELECT COUNT(*)` 并用断言钉住「是空的」
- [ ] 改完 `SELECT sql FROM sqlite_master` 实测 Diff，别只看 `db init` 输出

## #30 2026-09-15 raw_cache 把「当日盘中抓到的 body」永久冻结（P18，数据链完整性）

**错误**：15:30 收盘链 `ingest bars --days 12000` 抓 000333 的当日 K 线，命中的是**当天 00:21**
抓的那份缓存 —— 那份 body 最新一根是 09-14 收盘 86.8。结果是 **09-15 的 K 线当天没落库**，

（更没被发现的那一半：若抓取发生在**盘中**，冻结进缓存的是一根**未完成的盘中价**，
`ingest bars` 会把它当**当日收盘价**写进 `bars_daily` —— 数值合法、含义全错、**不报任何错**。）

**根本原因（三条同时成立才出事）**
1. `params_key` 只带锚点 `end`、**不含 `start`**：`kline:sz000333:2026-09-15:2000:` ——
   不同窗口共用同一个 key；
2. `RawCache` **首写保留**（评审 B3 的有意设计，防源站改写历史污染复现）；
3. 缓存层**没有时效概念** —— 它不知道「这份数据是不是当日未完成的」。

日K 的 body **同时**取决于窗口与**抓取时刻**，而 key 只编码了前者。
于是「同一个 key」对应多份内容不同的响应，缓存永久冻结了最早那份。

**为什么三个小时后才发现**：它**不报错**。缓存命中是**成功路径**，
失败表现是「当日数据没到」（一个看起来像源站延迟的现象），而不是异常。
`RawCache` 的两条硬纪律（SHA 校验、首写保留）反而让这份毒数据显得**完全可信**。

**防御**
1. **读侧显式忽略**：`is_intraday_snapshot()` —— `fetched_at` 本地日 == 锚点日 且
   时刻 < 收盘（复用 `session.close.CLOSE_HOUR/CLOSE_MINUTE`，口径同 `tick._closed_at`）
   → `load` 返回 `None`（让调用方重新联网），并在 meta `conflicts` 追加
   `intraday_snapshot`（**铁律③：不许静默**，否则下次还是查不出原因的哑巴故障）。
2. **写侧不落盘**：同样条件下 `store` 不写正式缓存 → 「首写永久冻结一份当日未完成数据」
   在物理上不可能发生。
3. **反证测试先红后绿**：`test_legacy_intraday_snapshot_is_not_a_hit` 与
   `test_http_refetches_instead_of_replaying_legacy_intraday_snapshot` ——
   修复前实测失败信息就是事故复现：读侧把 `stale-intraday` 原样回放，没有联网。
4. **历史锚点反证**：`end != fetched_at 当天` 的条目照旧命中、首写保留、SHA 校验不松。
5. **时钟可注入**：判定只读 meta 的 `fetched_at`（由 `HttpClient.now` 注入），

3. **sha 对不上时的标准动作是归因实验，不是修文档**：先回退改动重跑一次
   （改前/改后同命令 `cmp`），再决定是「我改坏了」还是「红线过期了」。
   本次若跳过这一步，就会把一条与 P24 无关的漂移写成「P24 违反回归红线」。
4. **本轮不改那条过期常量**：改它属于口径变更（谁批准、以哪次运行为准），

1. **两个数必须分列**：`predictions_written`（该来源写了多少条预测）与

   旁边必须写出「为什么是 0」。
2. **验收标准里给的预期数字不是事实。** 任务书写「大约 1–2 天」，实测 0 就写 0，
   并解释 0 的来源。若照抄预期值，这份报告第一次交付就是错的。
3. **证明「判据读的是字段」不能靠改既有行。** 本轮的测试想 `UPDATE predictions
   SET created_at=...` 来翻转分桶，被 append-only 触发器 `ABORT`（这是红线在起作用）。
   正确做法：**另建一个只差这一个字段的库**做对照 —— 既有行一个字节都不动。
4. 反过来看：这次 0 是**判据正确的证据**，不是缺陷。它同时证明了

## #37 2026-09-16：验证步的 cutoff 只有一个证据源，而那个源天生滞后一天（P27）

### 错误描述

P26 交付后「实时段 n_days = 0」，任务书归因为「收盘链缺一步验证」。
复核后这个定性**方向对、机制不对**：`session tick` **本来就有**验证逻辑（步骤③，
2026-09-15 11:50 起就在），而且当天跑了 6 次（09:35 / 14:30 / 15:18 / 15:20 /
15:23:27 / 15:23:35），每次的 `job_runs.detail` 都是 `verify_inserted+0`。

实测根因：

```
trading_calendar 的 2026-09-16 行 created_at = 2026-09-16T15:32:56+08:00
当天最后一次 session_tick                = 2026-09-16T15:23:35+08:00   ← 早 9 分钟
```

`session tick` 步骤③ 的 cutoff **只来自日历**（`closed_through(cal, now)`）。
日历行由 `ingest index` 在 15:30+ 才写，所以 15:23 那次 tick 的 cutoff 只能是
`2026-09-15` —— 它把昨天那 4 行重算了一遍（全 `identical`）→ `inserted=0`，
**「今天到期」的预测永远轮不到它**。而 15:30 的收盘链跑的是
`session backfill-close`（只回填 amount/turnover），**不跑 `session tick`**。

结果：每天真实产出的预测**永远不会被打分**，LIVE 桶永远不增长。

### 根本原因

**判据的证据源单一，而那个源在时间上落后于使用它的时刻。**
「今天已收盘」这件事在 15:23 时**已经是真的**（行情走完了），但唯一被采信的
证据（`trading_calendar` 的行）要到 15:32 才存在。判据看不见已知的事实 →
每天稳定地漏掉一格。同型：#31（「默认取今天」在数据还没产生时返回空）。

第二条：**「跑了 6 次都 0」不等于「没有缺口」，也不等于「没有这一步」。**
`verify_inserted+0` 这个数字本身不区分三件事——
(a) 没有这一步、(b) 有这一步但选择集为空、(c) 有这一步但选择集永远选错。
本次是 (c)。若只看 detail 字符串就下结论，会去加一个**已经存在**的步骤。

### 教训

1. **判据的每个输入都要问一句「它什么时候才有值」。** 如果输入的产生时刻晚于
   判据被调用的时刻，这个判据就是**结构性失明**，跑多少次都一样。
   修法不是「多跑几次」，而是**补第二个证据源**：日 K 只在收盘后入库，
   「`bars_daily` 里有这一天」本身就是收盘已完成的正面证据 —— 取
   `trading_calendar ∪ bars_daily` 两侧的 max。
2. **看到一串「+0」先分类再动手**：是「没这一步」「选择集为空」还是「选错了」？
   分辨方法很便宜 —— 把选择集**打印出来**（本次 `due` 一打就看见它是空的）。
3. **引用别人的读数前先自己重测**（#34 的延续）。任务书给的
   `verifications.max(target_date) = 2026-09-14` 实测是 `2026-09-15`。
   差一天在这里是**关键**：正好说明「昨天那批已经被别的路径打过分了」。
4. **「判不了」不许写成 0。** 新的判据在两侧都取不到值时返回 `None` 并给出
   `reason`，报告里显示成「**判不了**」而不是 `0`（#36 的延续）。
5. **反过拟合自查**：本轮补出来的样本量是 **1 个交易日**。`chain accuracy` 实时段
   从 0 变 1 天**不是**「准确率出现了」，报告里如实只印「样本不足（n=1 < 120），
   不构成准确率结论」。把 1 天当成绩就是本项目最贵的那类错。

## #38 2026-09-17：「比值接近 100」被当成「量纲关系确证」；「ETF 没数据」被当成一个事实而不是两个（P28b）

### 错误描述

P28 的计划 §2.1 与 `sources/sina.py` / `models.py` 的注释里，都写死了这句话：

> `turnover` 是**百分数值 ×100**，与 `bars_daily.turnover`（%）**差 100 倍**。

它的证据来源是**两个观测**：`43.346 vs 0.43`（比值 100.80）、`28.1749 vs 0.29`（比值 97.15）。
两个观测的比值都**接近** 100，于是被写成了「差 100 倍」这个**看起来确证的事实**。

P28b 把观测扩到 6 个（3 个交易日 × 2 标的）：

```
101.0785 / 100.8108 / 97.1548 / 100.1657 / 100.8047 / 98.7349
n=6  min=97.1548  max=101.0785  mean=99.7916
```

**比值散布 97.15–101.08。** 4/6 能落在腾讯 2 位小数的舍入范围内，**2/6 超出**
（-2.85%、-1.27%）—— 说明除舍入外还有约 1–3% 的残余差，**成因判定不了**。
「差 100 倍」在字面上就不成立，而它已经在代码注释里躺了一轮。

同型的第二处：计划 §6 写「ETF → 源没有估值/资金流行时，写一条 warn」。
这句话把**两件独立的事**压缩成了一个按标的类型的一刀切。P28b 真跑两个源：

- 估值源（东财）：4 只 ETF **全部 rows=0** → 假设成立；
- 资金流源（新浪）：4 只 ETF **全部有数据**（各 43 行，字段零 NULL 零 0）→ **假设被否证**。

代码里 `if not rows and inst.is_etf` 恰好只在「真的没数据」时才 warn，所以**行为是对的**——
但**文档的表述是错的**，而且错的那一半会诱导下一个人写出「按 `asset_type == 'etf'` 跳过资金流」的优化。

### 根本原因

**第一条：比值是一个观测，不是一个判据。**
两个量的比值接近 100，至少有三种互不相容的解释：
(a) 量纲差 100、口径相同；(b) 量纲相同、口径差 100 倍；(c) 量纲和口径都不同、凑巧比值接近 100。
只看比值，**这三种分不开**。而它们对下游的含义完全相反 —— (a) 可以 `/100` 对齐，(b)(c) 对齐就是污染。

正确的判据是**独立反推**：找一个**已知量**做第三方交叉验证，让三种解释给出**不同的预测**。
本次用的独立量是腾讯自带的 `float_mv` / `total_mv` / `amount`：

```
以流通股为分母算换手率 = 0.2631% / 0.3722%  ← 两源同时吻合
以总股本为分母算换手率 = 0.2374% / 0.2472%  ← 两源同时不符（差 8–10%）
```

两源**同时**吻合流通股分母、**同时**不符总股本分母 → 口径相同，量纲差 100，**(a)**。
这一步才叫确证。附带还捞出第三条证据：腾讯 `total_mv/close` 与东财 `total_shares`
偏差 **0.0000%** —— 两个源的**总股本**口径完全一致。**这是比值给不了的。**

**第二条：把「按类型的一刀切」当成「按事实的判断」。**
「ETF 没数据」听起来是一个事实，其实是**两个源各自的属性**。把 `asset_type='etf'`
这种**标的分类**当成**数据可得性**的代理，是把两个不同维度绑死了。同型：#36（把「写了几条」
当成「样本量」）、#37（把「跑了 6 次都 0」当成「没有缺口」）—— 都是**把代理指标当成事实本身**。

### 教训

1. **比值接近某个数 ≠ 该数被确证。** 报单位/口径关系时，判据必须是**独立反推**
   （第三方已知量交叉验证），不是比值。「比值 100.80 和 97.15，所以差 100 倍」是**不成立的推理**。
2. **判据给不出唯一解时，如实写「未确证」并列出全部候选解释**，不要选一个最好看的。
   本次最终写法：「同口径**确证** / 量纲差 100 **确证** / 精确倍数**未确证**（97.15–101.08，
   残余 1–3% **判定不了成因**）」—— 三分法是诚实的最小单位。
3. **任何「按类型跳过」的优化都要先问：这个类型是事实，还是代理？**
   `asset_type='etf'` 是**分类**，不是**数据可得性**。覆盖记录要按 `(code, source)` **逐对**判定。
4. **覆盖度不足时要先说覆盖度。** 任务书要 ≥5 个交易日，实测**只有 3 天**两侧有值
   （`bars_daily.turnover` 全库仅 4 行非空，腾讯历史日 K 接口根本不返回换手率）。
   这个限制**必须写在结论前面**，否则读者会以为 3 天是抽样选择。
5. **上一轮报告/注释里的数字，引用前重测。** 「差 100 倍」在注释里躺了一整轮没人碰
   （#34、#37 的延续）。**注释里的数字也是需要证据的断言。**

- [ ] 这个判据能不能**区分**「量纲不同」「口径不同」「都不同」？区分不了就不能下结论。
- [ ] 我写的是**确证**、**未确证**、还是**判定不了**？三者有没有混成一句「约等于」？

## #45 2026-09-21：候选池「跑一次」按钮在工作线程里必炸 —— 插桩沙盒的 `signal` 超时只能跑主线程

### 现象

候选池页面（模块1 展示层）的写路径原来按设计文档写成「请求线程里直接调
`run_candidate`」。测试真起 `ThreadingHTTPServer` 打 POST 时，5 条写用例全红：

```
http.client.RemoteDisconnected: Remote end closed connection without response
ValueError: signal only works in main thread of the main interpreter
  stocklab/plugin/runtime.py:51 in _time_limit  →  signal.signal(SIGALRM, ...)
```

写路径改为**起子进程跑 CLI**（`python -m stocklab.cli.main candidate run …`）：

- 子进程的主线程让 `signal` 可用，**沙盒一行不改**（不去偷偷降级超时）；
- 页面与命令行两条路径跑的是同一段生产代码，报告落同一处；
- 附了超时（300s）、非零退出码、以及「退出码 0 却没落快照」三种失败分支，
  都把子进程的原话渲染到页面上，不吞。

### 教训

1. **「同一段生产代码」不等于「同一个进程」**。设计里写「内部调 `X()`」时，
   要顺带回答「在哪个线程调」——线程模型是接口的一部分，不是实现细节。
2. **文档里已经写下的约束要当成硬约束读**：`plugin/runtime.py` 的 docstring
   明确说了不能进线程池，本轮写代码时没读它，白跑了一轮。
3. **失败模式要按「客户端看到什么」验，不按服务端栈验**：服务端有完整 traceback，
   客户端只是 `RemoteDisconnected` —— 只跑 `handle()` 单测是发现不了的，
   必须真起服务打 HTTP（这条纪律 P15 就立过，这次是它救的场）。

### 检查清单（下次必查）

- [ ] 这个写路径跑在**主线程**还是工作线程？它调用的东西对线程有要求吗？
- [ ] 目标模块的 docstring 里有没有「只能主线程 / 不能并行 / 不能重入」这类硬约束？
- [ ] 这条写路径的失败，客户端看到的是可读页面还是「连接被断开」？

## #49 2026-09-21：止损规则产出「卖 0 股」→ 整个 `paper step` 事务回滚（明天必炸）

### 现象

模拟盘第一次真止损发生在 `2026-09-21`（000333 收盘 80.90 < 止损线 82.14）：
三条纪律臂当天把 100 股全部清掉、`positions` 变成空。

**第二个交易日**（`2026-09-22`）再跑 `paper step` 时：

```
sqlite3.IntegrityError: CHECK constraint failed: qty > 0
```

`step` 是**一个事务**（「任一账户失败就整体回滚」是刻意设计），所以这一天
**五个账户一条净值都没落**。真库复现（拷贝到 `/tmp/repro-0922.db`）：

```
STEP FAILED: IntegrityError CHECK constraint failed: qty > 0
```

这不是理论风险：`paper step` 是 15:30 收盘链的第 5 步，第二天收盘就会红。

### 根因

`rules.plan_stop_loss(qty=0)` 在「收盘跌破止损线」时**无条件**返回
`action="sell", qty=0`（规则只说「整清」，没问「手里还有没有货」）。
而 `Decision.is_trade` 当时只判方向：

```python
return self.action in ("buy", "sell")     # 卖 0 股也算「成交」
```

于是「卖 0 股」通过了下游每一道 `is_trade` 守卫，一直到写入层的
`CHECK (qty > 0)` 才被拦住 —— 报的还是 sqlite 的话，排查方向会跑到 schema 上。

`plan_trim`（`sell <= 0` → hold）与 `plan_etf_buy`（`qty <= 0` → hold）**都有这道守卫**，
只有止损这一条漏了。三条规则里两条有、一条没有，是典型的「同一模式写了三遍，
漏了一处」——守卫写在每个规则函数里，而不是写在不变量上。

### 修法

1. **规则层**：`plan_stop_loss` 在「跌破但持仓 0 股」时回 `hold`，理由写明
   「持仓为 0 股 → 无可执行动作（不是忘了卖）」。`evaluate` 里照样能看到这条判定
   （不动的理由也要留痕），只是它不再是成交。
2. **不变量层**：`Decision.is_trade` 改成 `action in ("buy","sell") and qty > 0`。
   「只有方向没有股数的成交」不是一个成交 —— 这句话应该由类型表达，
   不该由每个调用点自己记得判。
3. **写入层**：`store.insert_trade` 直接校验 `action` 与 `qty`，报**带规则的
   `ValueError`**（点名是规则层的问题），不再让 `CHECK` 兜底。

### 教训

1. **「0 股」是规则层的合法结论，不是可执行的成交**。凡是「清仓/减仓」类规则，
   先问「有没有货」；产出 `qty=0` 的成交是把空操作伪装成动作。
2. **一个 step 一个事务 = 一条坏规则能拖垮整天的账**。这是好事（不留下半截状态），
   但也意味着**规则层的异常必须在自己那层被消掉**，不能指望写入层「反正会拦」：
   拦下来的是异常，代价是当天所有账户。
3. **幂等的另一面**：`2026-09-21` 那天已经整清、`2026-09-22` 状态没变，
   于是规则**每天**都会重新产出同一条卖 0 股 —— 这种 bug 不会自愈，
   它会**每天**把收盘链打红一次。
4. **守卫写在三个平级的规则函数里，就是三份要各自维护的真相**。
   能提到不可变量上的（`is_trade`），就不要留在每个函数里。

### 检查清单（新增/改一条规则时）

- [ ] 这条规则有没有可能产出 `qty == 0` 却带方向的动作？
- [ ] 它依赖「有持仓」吗？依赖的话，没持仓时返回的是什么？
- [ ] 新加的守卫是写在**规则函数**里，还是能提到 `Decision.is_trade` 这类不变量上？
- [ ] 写入层的错误信息能不能**点名是哪一层的问题**（而不是 sqlite 的 CHECK 名）？
- [ ] 有没有一条**跨两天**的测试：今天清仓 → 明天同方向触发仍然返回 hold？

### 现象

3. 同类静默失效一并覆盖：`raise` 之后补的赋值、`continue` 之后补的清理。

### 教训

1. **「不报错」不是「生效了」**。判断一段新逻辑是否真的跑了，只有两条路：

## #54 2026-09-22：一步都没跑成的链报**绿码** —— 「没跑完」与「跑完了都成功」在返回值上不可区分

### 现象

写 `ops close` 的用例时，把整轮预算调成 0 秒（`timeout_s=0`）想验「预算用尽会停下」，
拿到的却是**绿码**：一步都没跑，`exit_code` 却是 **0**。

### 根因

`worst_code(steps_out, aborted)` 只做了两件事：

```python
fatal = any(s["exit_code"] is None or s["exit_code"] >= 2 for s in steps_out)
soft  = any(s["exit_code"] == 1 for s in steps_out)
return 2 if fatal else (1 if soft else 0)
```

它**只看已跑完的步骤**。预算用尽是**在这一步之前**发生的：`aborted={"kind": "budget_exhausted"}`
挂在返回值里，却根本没有参与判定 ⇒ `steps_out == []` ⇒ 没有非 0 ⇒ **0**。
于是「今天这条链一步都没跑」和「今天全绿」在退出码上长得一模一样，
而 launchd/nanobot 侧**只看退出码** —— 那就是一则会被当成好消息的假报告。

第二处：第一版断言写的是 `payload["exit_code"] >= 1`。`>=` 把「1 还是 2」这个区别
从测试里抹掉了 —— 而这两句话的意思完全不同：`1` = 跑完了但如实报了异常，`2` = 这一轮**没跑完**。
**断言宽松的地方，恰好就是判据要精确的地方。**

### 修法

三条停止线（整轮预算用尽 / 单步超时 / 单步退出码 ≥2）**一律算 2**，即使一步都没跑成：

```python
if (aborted or {}).get("kind") in ("budget_exhausted", "step_timeout",
                                   "step_error", "step_fatal"):
    fatal = True
```

理由写进 `ops/runner.py` 的模块 docstring：它们统一意味着「这一轮没跑完」，
而 1 的含义是「跑完了但有异常」——把「没跑完」读成 1，launchd 侧就会看到「绿了一天」。
同时把`__init__` 里 `aborted` 的语义定为**只增不减的事实**（写进去的都必须参与判定）。

### 验证

- `tests/test_ops_close.py::test_budget_exhausted_stops_at_the_first_step`：断言
  `runner.calls == []`（**一次子进程都没起**）＋ `aborted["kind"] == "budget_exhausted"`
  ＋ `exit_code == 2`。
- `tests/test_ops_patrol.py::test_budget_exhausted_runs_nothing_and_is_recorded`：
  同上，并且**缺口仍在**（`check_review` 仍在 anomalies 里）——「2 分」与「缺口」两件事都如实留下。
- 真库只读复跑：`ops patrol` → `patrol: exit=0 … anomalies=0`（正常路径不受影响）。

### 教训

1. **退出码是调度器唯一能读的字**。任何「这一轮没跑完」的形状，都必须映射到非 0；
   否则「没跑」会被读成「一切正常」，而这种错误**不会自己暴露**（没人会去查一个绿码的作业）。
2. **判定只能来自「跑了什么」，也必须包含「没跑成什么」**。只统计已执行步骤的最大值，
   天然看不见「一步都没执行」这一类。
3. **`>=` / `!= None` 这类宽松断言，在语义分叉处一律换成 `==`**。「1 还是 2」不是细节，
   它是这个项目里两句不同的话。
4. **docstring 里写了「真出过这个形状」的注释，是修法的一部分**：下一个人（或下一个我）
   看 `worst_code` 时，需要知道为什么预算用尽要单独拉出来算 2。

「运行中」这个状态会永远留在页面上，看起来像卡住了。

### 修法（三层，缺一层都还会复发）

1. **用例侧**：CLI 用例显式 `monkeypatch.setattr(chain, "default_runner", FakeRunner())`
   （CLI 没有 `--runner` 注入点，但 `run_close` 是**运行时**读那个全局，打补丁有效），
   并补 `--backup-dir`。断言里加 `runner.calls == []` 之类的**「一次子进程都没起」**判据。
2. **夹具侧**：`tests/conftest.py` 新增 autouse `backup_dir_is_tmp`，把 `paths.BACKUP_DIR`
   指到 `tmp_path/backups` —— 与既有的 `report_dir_is_tmp`（#51）同一个理由：
   **「忘了传参」的用例不许写进仓库**。
3. **收尾**：删掉 `data/backups/` 里那 20 多份 `close.preclose.*.db`（含 `-wal`/`-shm`）；
   真库三条永久 `running` 用 `repo.finish_job` 改成 `failed`，detail 写
   `中断（进程被终止；无结果）` —— **不删行**，保留「发生过一次没跑完」这个事实。
   真库里那根半截 bar **不手工修**：`insert_bars` 是 `ON CONFLICT(code,date) DO UPDATE`，
   当天 15:30 的收盘链会 upsert 自愈（已复核 upsert 语义）。

### 验证

- `data/backups/` 只剩正经备份（`ls -lt` 复核：`stocklab-2026-09-21.db` 等）；
- 真库 `job_runs` 49/52/72 三条为 `failed`，`detail` 为「中断（进程被终止；无结果）」；
- 修完复跑 `tests/test_ops_close.py` 全绿，且**真库行数不再变化**（用例起子进程数为 0）。

### 教训

1. **「默认参数指向真实资源」的代码，在测试里是雷**（`runner=default_runner`、
   `backup_dir=BACKUP_DIR`、`report_dir=REPORT_DIR`）。三处都踩过同一个形状
   （#51 报告 → #55 备份 → 本次的真库写入）。
2. **采集类命令没有 `--db`，是这起事故的放大器**。凡是「参数看起来指到临时目标」
   的调用，都要问一句：**这条路径里的真实落点到底由谁决定**。
3. **`.gitignore` 让污染隐形**。`git status` 干净不代表仓库干净 ——
   判据要落在**具体资源**上（`ls -lt`、`SELECT` 真库、`job_runs` 状态）。
4. **测试全绿 ≠ 没有副作用**。断言只覆盖返回值；副作用要靠「起子进程数 / 落盘路径」
   这种**外部可观测**的判据来钉。
5. **中断的作业要留痕，不要静默清理**。把 `running` 改成 `failed` 并写清原因，
   比删掉那三行更有价值 —— 下次看到「运行中」时，就知道它可能是**没人收尾**，而不是还在跑。

## #56 2026-09-22：永久报红的守卫 —— 选日过宽，每天拿今天的口径重算昨天口径的账本（P39）

### 现象

`session tick` **每轮** exit 1，`anomalies` 恒为两条 `verification_conflict`：

| pred_id | code | asof | target | 差异字段 |
|---|---|---|---|---|
| 42293 | 601318 | 2026-09-09 | 2026-09-10 | `actual_pct`/`benchmark_pct`/`sim_pnl`/`score_direction`/`score_action`/`total_score` |
| 42312 | 603868 | 2026-09-10 | 2026-09-11 | 同上 + `hit_direction` |

`ops patrol` 于是每天记一次 `step_anomaly`。**真异常（若真有）会淹没在这条永久噪声里**
—— 这比「漏报一次」更糟：它把「报警」这个信号本身贬值了。

### 根因

**守卫是对的，错的是选日。** 那两条验证行写于 `2026-09-21T16:24:07`，当时
`adj_factors` **为空**（复权链尚未采到）；同夜 `MODEL_VERSION` 升到 `v1.0.2`（复权口径）。
以 601318 为例，**同一份预测、同一根 bar**，两种口径：

```
库里存的  actual_pct = -0.013153   ← 不复权 56.26 → 55.52
按现在的复权链 55.28 → 55.52 = +0.4342%
```

即「复权链为空时期」的历史账本与今天的口径**必然**算不出同一个数。append-only 守卫报冲突
是**正确行为**，旧行不许改写。

真正缺陷在 `session/tick.py` 步骤③ 的选日：

```sql
SELECT DISTINCT target_date FROM predictions WHERE status='ok' AND target_date <= ?
```

它**完全不看「该日是否还有未验证的预测」**。实测全库 `predictions` 84658 行、只有 34 条
没有验证行，历史日期 **100% 已完全验证**。所以每天都要白重算最多 `window=10` 个日期
（每日期约 34 行）——**并且必然踩到那两条旧口径账本**。

反证实测（真库副本，把修改前那几行原样跑一遍）：

```
cutoff = 2026-09-22 | due_dates(旧) = 2661 | 选了 window=10 个
  2026-09-22: {'inserted': 34}
  2026-09-14: {'identical': 34}
  2026-09-11: ❌ VerificationConflict: pred_id=42312 已有一条内容不同的验证记录…
  2026-09-10: ❌ VerificationConflict: pred_id=42293 已有一条内容不同的验证记录…
  …（另外 6 个日期各 34 行 identical，纯浪费）
conflicts = 2
```

修后同一条命令（`session tick --now 2026-09-22T15:40 --no-capture`）：
`due_dates=1`（只有真正有缺口的 `2026-09-22`）、`anomalies=[]`、`exit_code=0`、
`inserted=34`；既有 84624 行**逐字段 0 改动**。

### 修法

1. **选日收窄**：tick 步骤③ 改为复用 `stocklab/verify/pending.py::pending_predictions()`
   —— 与 CLI `verify pending` **同一份**实现（**禁止**在 tick 里另写平行 SQL；
   两处走样正是这类缺陷的来源）。
2. **逐日只评缺口**：`verify_target(conn, d, codes=<该日未验证的 codes>, now=now)`，
   与 CLI 逐字一致。**不改** `verify_target` 的默认语义（不传 `codes` 时仍评该日全部预测）
   —— CLI `verify run` 的人工补分依赖它。
3. **判不了不许写成 0**：`pending_predictions` 返回 `n is None` 时沿用既有 skip 分支，
   摘要里 `due_dates: None` + `reason`，**不是** `0`（延续 #36 / #37）。
4. **「有验证行但不可评分」不在自动补分范围内**（有意的收窄）：那 38 条全是
   `NO_BAR_TARGET`（停牌/无 bar）的永久缺口，**已经有验证行**。要补分须人工跑
   `stocklab verify run --target-date <d>`（保留全量语义）。自动纳入它会在
   `reason_code` 一变时制造**新的假冲突**。
5. 契约只增不减：`due_dates`（新语义 = 含未验证预测的到期日数）/ `verified_dates` /
   `backlog_skipped` / `inserted` / `identical` / `rescored_after_data_gap` /
   `unscorable` 全部保留。

### 教训

1. **「每天都报的异常」不是异常，是背景噪声**。判定「报警值不值得看」的第一条：
   这个报警**有没有可能自己停下来**？不会停 = 判据必然有问题，先去查判据，
   而不是查被报的那个对象（本次差点去查复权链）。
2. **枚举驱动的工作要问「枚举集合是谁给的」**。选日的集合是
   `SELECT DISTINCT target_date`——**全部历史**；而工作的语义是「补缺口」——
   集合应当是**缺口**。集合比语义大一圈，就每天重复做已经做完的事，
   而且是在**状态已经变了**之后重复做。
3. **「幂等」只保证「写了不重复写」，不保证「算了不重算」**。旧实现在
   `identical` 状态上看着很健康（日志里全是 `identical`，没有任何异常），
   但重算本身就是**用今天的口径碰昨天的账本**——幂等挡不住口径漂移。
4. **append-only 守卫 + 过宽的枚举 = 永久假红**。守卫报冲突是正确的；把守卫
   和「每天扫全历史」放在一起，就得到一个永远红、且无法通过任何修复变绿的判据。
   修的方向**不是**关守卫、也不是「冲突自动忽略」，而是**别去碰那些行**。
5. **两处判据必须同源**。选日逻辑此前在 `pending.py`（CLI）与 `tick.py`（调度）
   各有一份，只改了前者 —— 后者于是原地保留了一个更宽的版本。凡是「同一个问题
   有两处答案」，迟早有一处开始漂。

### 检查清单（新增/修改「按日期枚举」的批处理时）

- [ ] 这个枚举集合的**判据**，与「工作语义」是同一件事吗？（「所有日期」vs「有缺口的日期」）
- [ ] 会不会拿到**已经处理完**的日期？处理完再处理一次的后果是什么（重算/冲突/污染）？
- [ ] 这条路径里的判据，别处是不是已经有一份？能不能只留一份？
- [ ] 判据依赖的**口径**（复权链、成本模型、模型版本）会不会随时间变？
      会变的话，「重复处理历史」就是在制造冲突。
- [ ] 这个异常会不会**每天都出现**？会 → 先查判据，别查被报的对象。

## #57 2026-09-22：两个定时任务撞在同一分钟 —— 「已修」的只是磁盘上那份 plist，生成器里还留着

### 症状

`com.stocklab.patrol` 最后一槽（工作日 15:30）与 `com.stocklab.close`（工作日 15:30）
**同一分钟触发**。`patrol --fix` 会起子进程补步、`close` 会起子进程采集 —— 两个进程
并发写**同一个 SQLite**，收盘链容易撞 `database is locked` 而 exit 2。
**在这条链第一次真跑之前就被发现了**（2026-09-22 14:0x，P38 手测 `kickstart` 时顺手比对
三条任务的触发时刻），所以没有产生任何坏数据。

### 根因

1. **分档写死了「避开收盘」的意图，却没写成机器判据**：`patrol` 排到 15:30 的理由是
   「收盘后补当日缺口」，但收盘后的补缺口本来就归 `close`；两件事的职责边界没落到时刻表上。
2. **修法做在半路上**：当时只手工编辑了 `~/Library/LaunchAgents/com.stocklab.patrol.plist`
   （70 → 65 槽）并 `bootout/bootstrap`，**源码 `schedule.py` 仍生成 70 槽**。
   于是同一件事有了**两份事实源**，而两份是矛盾的。
3. **文档把「重装」教成了标准动作**：`docs/ops/2026-09-22-launchd-定时任务.md` 的
   「重装 / 撤 nanobot」都写 `ops schedule install`，而该文与 `Job.window`、ADR-020
   三处都写「09:00–15:30 / 70 条」—— **照文档做一次就把手工止血覆盖掉，缺陷原样复活**。

### 修法（P42，先红后绿）

- `schedule.py`：`PATROL_HOURS/MINUTES` → `PATROL_TIMES`（13 槽 `09:00–15:00`），
  `patrol_calendar()` 由 70 条降为 **65** 条；模块 docstring 写明「为什么去掉 15:30」；
  `patrol.window` / `patrol.why` 同步（补当日缺口的职责归还 `close`）。
- 新增三条 plist 断言（`plistlib` 回读**注入 tmp 目录**里生成的文件）：
  patrol 槽数 = 65、`含 15:30 == False`、**「任意两个 job 触发时刻无交集」**。
  改代码前同一批用例红（`assert 70 == 65` ＋ 打印出撞点清单 `(1,15,30)…(5,15,30)`）。
- 文档三处（`docs/ops` 窗口表、ADR-020、任务书）由 70 改为 65，并在表下加错峰说明。

### 教训

1. **手工止血必须同时落到生成器，否则它只是「本机此刻的巧合」**。判断标准很简单：
   把你手改的那份文件删掉、让系统重新生成一次，缺陷还在不在？还在 = 没修。
2. **「文件被生成」的目录里不允许有人改的痕迹**。生成物是**产物**，唯一的输入是代码；
   在产物上手改，等于悄悄引入第二份事实源，而且没有任何测试能看见它。
3. **文档里的操作步骤就是代码**。写「重装即可恢复」之前，先问一句：
   照这句话做，会不会把某个人工修补覆盖掉？会 → 要么先修代码，要么在文档里显式写禁用。
4. **时刻表冲突要靠断言，不靠眼睛**。两条任务的触发集合是可计算的（`StartCalendarInterval`），
   交集为空是一行代码就能钉住的不变量 —— 「人工比对过没问题」不构成护栏。
5. **职责边界要写成时刻表**。「收盘后补缺口」这种描述天然会滑到收盘那一刻，
   与收盘链撞车；正确的表达是「`close` 负责收盘后，`patrol` 只负责盘中」。

### 检查清单（新增/修改任何定时任务时）

- [ ] 新时点与**所有既有任务**的触发集合，交集为空吗？（用断言，不靠肉眼）
- [ ] 这个时点上，会不会有**另一个写者**（子进程 / 另一条链 / 手工 CLI）在写同一个库？
- [ ] 我这次的修改，**生成器里改了吗**？还是只改了本机的产物文件？
- [ ] 文档里的「安装 / 重装 / 恢复」步骤，跑一遍会不会**覆盖**某个人工修补？
- [ ] `window` / `why` 这类展示文案，与 plist 的实际触发规则是同一件事吗？

## #58 2026-09-22：任务书里的「字段名」不是代码里的真源；`| tail` 又一次吃掉了退出码（P45）

### 现象（两件，同一轮里）

**第一件**：P45 任务书 §2 把 `m2_a3`/`m2_b1` 的输出写成
`range_lo/hi` + `p_up/p_flat/p_down`。照字面实现，契约里就会出现一套**代码里不存在**
的字段名 —— 真源 `predict/model.py::CONTRACT_FIELDS` 是 `range_80` +
`direction{up,flat,down}`，而 `range_lo/range_hi` 只是 `predict/store.py::payload_to_row`
落库时的**列名**。

**第二件**：收尾跑 `bash scripts/verify.sh 2>&1 | tail -40; echo "EXIT=$?"`，
拿到 `EXIT=0` 就准备写进报告。实际那个 0 是 **`tail` 的退出码**，不是 `verify.sh` 的。
重跑一次不接管道：`bash scripts/verify.sh > log 2>&1; echo $?` → 0（结果没变，
但**上一次的判据本身是无效的**）。

### 根因

1. **把「文档里的字段名」当成「代码里的字段名」**。#32（口径落地选择 vs 预注册原文）、
   #42（判据括号歧义）的同一家族第 N 次：文档写形状时引用的名字，只有回代码里
   指到才算数。这次的陷阱更精致——括号里给的名字**看起来像**真源，
   而且它确实是真源（只不过真源在**另一个层**：DB 列 vs 载荷字段）。
2. **`| tail` 收尾的管道，`$?` 是末位命令的**。#46 记过一模一样的坑，
   这次是「换了个场景自己又踩」。幸运的是这次结果恰好相同，所以它是
   **无效判据**而不是错误结论 —— 而无效判据比错误结论更危险：它看起来像证据。

### 教训

1. **写任务书/契约时引用的每个字段名，回代码里 `grep` 一次**，并写清
   「这是载荷字段还是 DB 列」。两层同名不同形是**歧义源**，不是细节。
   本轮处置：按任务书自带的「字段名可微调」取真源名，并把「⊆ 真源」写成一条测试
   （`test_forecast_field_names_come_from_the_canonical_payload`），
   让「另造一套口径」变成读得懂的失败；偏离记进 ADR-022 与验收记录。
2. **报退出码必须单独跑一次**，或用 `set -o pipefail` / `${PIPESTATUS[0]}`。
   「屏幕上写着 ✅」与「退出码是 0」是两件事。
3. 顺带：本轮发现 `docs/decisions/README.md` 缺 ADR-021 的索引行（P44 漏的）——
   **索引与目录的对账要当成一条断言**，否则漏掉的那条永远不会自己冒出来。

### 检查清单（下次必查）

- [ ] 我写进契约/文档的字段名，`grep` 到真源了吗？它是**载荷字段**还是 **DB 列**？
- [ ] 这个退出码是我要的那个命令的吗？（管道！`PIPESTATUS`！）
- [ ] 新增 ADR / 文档后，索引文件对账过了吗？
