## §0.6 为什么窗口是 `(d₋₅, d₀]` 的**日期区间**、而不是「最近 5 个交易日的集合」

P95 §5.4 原文写的是 `notice_date ∈ (asof − 5 个交易日, asof]` —— 这是**区间记法**，逐字执行
就是 L2 的日期区间（左端由交易日算术算出、右端闭）。两种读法的差别不是术语洁癖，是**1/5 的样本**：

- nanobot 2026-09-30 在真库只读实测（`mode=ro`，宇宙 = `csi300-500` 800 只）：

  | asof | 窗口（日期区间） | 0 值占比 | 截面 P50 | max | 窗口内公告总数 |
  |---|---|---|---|---|---|
  | 2016-03-15 | 2016-03-08 → 03-15 | 0.626 | 0 | 40 | 1,537 |
  | 2020-07-01 | 2020-06-22 → 07-01 | 0.369 | 1 | 42 | 2,303 |
  | 2024-09-02 | 2024-08-26 → 09-02 | 0.156 | 6 | 30 | 5,234 |
  | 2026-09-24 | 2026-09-17 → 09-24 | 0.404 | 1 | 19 | 1,367 |

- **`announcements` 里 19.5% 的行 `notice_date` 落在周六/周日**（220,271 / 1,128,199）。
  若按「只数那 5 个交易日当天的公告」（集合读法），这 19.5% 的公告**永远不会落入任何窗口**、
  被静默丢弃；区间读法把它们保留在「这 5 个交易日的时段内」，这才是「最近 5 个交易日内的公告密度」。
- 另一条事实（**推论已修正，写在这里防将来误引**）：零值占比实测 **0.156–0.626**，
  比 P95 §5.4 预估的「零值会是多数」要温和 ⇒ **并列诊断仍要做（L8），但不必预判本因子分辨率不足**。

新增（放在 `ep_ttm` 一族之后、`_research_map` 之前，保持「机制层 → 具体因子」的现有阅读顺序）：

```python
def _ann_count_5d_map(conn: sqlite3.Connection, asof: str,
                      members: Iterable[str]) -> dict[str, float]:
    """`{code: 窗口内公告条数}`，窗口 = `(d₋₅, d₀]`（P95 §5.4 EV-A）。

    …（窗口定义 / PIT 锚 / 「0 是真值」例外 / 复杂度）…
    """

def ann_count_5d(conn: sqlite3.Connection, code: str, asof: str) -> float:
    """单只标的的 `ann_count_5d`（**真 0**，永不 `None`）。"""
```

要点：
- 日历那条 SQL 复用既有 `_recent_trading_dates(conn, asof=asof, n=6)`；`len(...) < 6` ⇒ `{}`
  （不拿「有几日算几日」顶替，与 `_mf_ratio_5d_map` 同规）。
- 窗口那条 SQL：`SELECT code, COUNT(*) FROM announcements WHERE notice_date > ? AND notice_date <= ? GROUP BY code`
  （左端 `>` = 开区间，右端 `<=` = 闭区间）。**不许**用 `display_time`、**不许**用 `title`/`column_name` 过筛
  （本因子是**全类型**公告计数，不是「回购」那种事件型；`ev_回购` 是另一个尚未立项的因子）。
- 补齐：`out = {code: 0.0 for code in members}` 再覆盖计数 —— 注意 `members` 可能含**库外 code**，
  一律给 `0.0`（不是 `None`）。
- docstring 里给出出处（P95 §5.4）与 §0.6 的实测读数（**只作注释，不作断言**：不要在代码里
  `assert` 任何覆盖数字）。
- `ann_count_5d(conn, code, asof)`：直接按窗口 `COUNT(*)`（内部一句 SQL），空窗/无行 ⇒ `0.0`。

## §3 T3 并列／零值诊断（L8）

- 在**研究侧因子**的读数块里新增两个键（`zero_ratio_p50` / `tie_ratio_p50`），算法：
  逐调仓日取该日截面值（`ann_count_5d` 即「800 个成员的值」），
  `zero_ratio = #{v == 0} / n`、`tie_ratio = #{v 在截面内的出现次数 ≥ 2} / n`（浮点比较用
  `==` 即可，值是整数计数 ⇒ 无容差问题），再对调仓日取**中位数**（`statistics.median`，
  与既有 `clip_diag` 的 `ratio_p50` 同形）。
- **只增键**：`--factor` 缺省时这些键**必须不出现**（否则违反 L10）。若既有用例钉住了研究侧块的键集合，
  按「只增键」同步更新并在 §7 逐条说明。
- 这两个键**不参与** verdict（判据一个都不许动，L11）；它们只是分辨率披露。

- **公告深度**：`announcements` 的 `MIN(notice_date) = 2014-12-19`（P96 的 `--days 4300` cutoff）
  ⇒ 2014-12 末的窗口左边被截断（只影响 2015-01-01 前几天的 `asof`），**必须在预注册里点名**。
- **并列分辨率**：实测 0 值占比 0.156–0.626（§0.6）⇒ 分辨率比 P95 预估好，但早期年份（2016）
  仍偏高；诊断键落读数后由 nanobot 在实验报告里判读，**站不许替它下结论**。
- **查询计划（已实测，别再优化）**：`WHERE notice_date > ? AND notice_date <= ? GROUP BY code` 的计划是
  `SCAN announcements USING COVERING INDEX idx_announcements_code_notice`（索引首列是 `code`，
  日期条件只能过滤 ⇒ 全索引扫）—— 因而是 covering index，**不是**回表扫全表。
  nanobot 实测 5 个 `asof` 合 3.78 s（≈0.76 s/`asof`）⇒ 全窗 571 个调仓日外推 **≈7.2 min**
  （相对本站其它开销可忽略）。**不加新索引**（反目标 2）：加 `notice_date` 首列索引会改 schema，
  而收益只有几分钟。
