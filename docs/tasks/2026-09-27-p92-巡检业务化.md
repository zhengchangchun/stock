## 0. 背景：现在每 30 分钟跑的是**数据链体检**，不是**业务巡检**

需求原文（`stock/07_定时任务调度需求.md` §任务1「轻量巡检｜每 30 分钟」）：

```
1. 拉候选池内标的行情、北向、公告
2. 执行插桩0【行业特殊排雷脚本】，重校验风险
3. 更新模拟账户 / 镜像账户市值
4. 跑插桩A3/B1 刷新收益概率并落库
5. 检测是否触发熔断风控（账户回撤阈值），触发则标记告警
6. 更新候选池标的状态
7. 保存本次轻量快照；输出简短巡检简报
```

现状（审计 v1 实测，`stocklab/ops/patrol.py`）：巡检跑的是 7 项**数据链体检**
（`CHECK_ORDER = bars / snapshot / predictions / verifications / review / paper_nav / pit_tables`）
＋缺步补跑。逐条对照：

| 需求 | 现状 |
|---|---|
| ① 行情 / 北向 / 公告 | 行情 ✓（⑦）；**北向、公告 ✗** —— P88 已建表 `northbound_holdings` / `announcements`，巡检里一个字都没有 |
| ② 插桩0 重校验风险 | **✗** 完全没有；插桩0 只在 `candidate run` 里跑一次 |
| ③ 更新模拟/镜像账户市值 | 由 `ops close` 的 `m2_daily` **每日一次**覆盖（频率不符） |
| ④ A3/B1 刷新收益概率 | 同上（在 `m2_daily` 内）—— **本档不实现**，见 D6 |
| ⑤ 熔断检测 | **✗ 无调度**：`m2 cycle fuse-check` 只有 CLI，没有任何地方每 30 分钟看一次 |
| ⑥ 更新候选池标的状态 | **✗** P91 已给写入口（`candidate status set`，append-only、幂等），但没人调它 |
| ⑦ 快照 ＋ 巡检简报 | 快照 ✓（`quote_snapshots`）；**简报 ✗** |

⇒ 本档把「**能做的业务巡检**」并进 `ops patrol`（不新建常驻进程、不改调度面），

## 0.5 锁定口径（D1–D10；要改先回来说）

**D1 业务块挂在 payload 的新键下，形状固定** —— `check_chain()` 的返回快照新增顶层键
`business`（**键只增不减**；既有 `checks` / `calendar` / `latest_closed_session` 等一字不动）：

```python
business = {
  "risk_screen":      {"status": ..., "n_members": int, "n_checked": int,
                       "n_risky": int, "risky": [{"code": str, "note": str}],
                       "reason": str},
  "fuse":             {"status": ..., "cycle_id": int|None, "at_value": float|None,
                       "threshold": float|None, "tripped": bool, "window": str|None,
                       "reason": str},
  "candidate_status": {"status": ..., "counts": {状态: n}, "would_set": [...],
                       "applied": [...], "reason": str},
  "freshness":        {"status": ..., "announcements": {...}, "northbound": {...},
                       "reason": str},
}
```

- 四个子块的 `status` **复用** `patrol.py` 已有的状态常量（`OK/WARN/UNKNOWN/SKIPPED` 一类），
  **不新造第二套**；
- 每个子块必须有 `reason`（人话，含关键数字），不许只给 `status`。

**D2 熔断只读** —— 巡检**绝不允许**调 `m2 cycle fuse-check`（它会往 append-only
台账追加 `circuit_breaker` / `validation_end` 事件 ⇒ 30 分钟一轮会把台账写花）。
只读做法：读出进行中的周期（`validation_cycles` 无收尾行的那条）⇒ 用
`m2.selfeval.fuse_verdict(...)`（**必须复用**，禁止重写回撤算法）算窗口回撤；
`at_value >= circuit_breaker_drawdown` ⇒ `tripped=True`。
- `validation_cycles` 为空 ⇒ `status=skipped`、`reason="没有进行中的验证周期"`，**不计异常**。
- **只有 `fuse.tripped == True` 才计入退出码**（走 `verdict()` 现有 `EXIT_ANOMALY=1` 通道，
  在 `_anomalies()` 里以 `kind="business_fuse"` 露面）；其余三个子块**只展示、不计异常**
  —— 盘中每 30 分钟报一次假警会把巡检变成噪音（对照 ①②：`unknown` 的待遇为什么分开，
  见 `verdict()` docstring）。

**D3 候选池状态：默认**只算不写**（dry-read）** ——
- 推导规则**白名单只有一条**：池内成员若被**任一 `live=1` 的 `paper_accounts` 账户**实际持有，
  目标状态 ＝ `已建仓`；其余三个状态（观察中/等待买点/逻辑证伪移出）**不可自动推导**，只能人工。
- 默认（不加开关）：`would_set` 列出「如果打开开关会写哪几条」，**一行都不写**；
  `status` 取 `OK`（有差异）/ `SKIPPED`（无差异）。
- 显式 `--update-status` 打开后才真写：**用子进程逐字调 P91 的 CLI**
  （`candidate status set --code <c> --asof <L> --status 已建仓 --actor patrol --reason ...`），
  **不许 import 业务函数**（本仓 `ops` 纪律：补步一律子进程复用现有 CLI）。
  幂等性由 P91 的表保证：同 `(code, asof, status)` 三元组 ⇒ 打印 `already`、exit 0、零写入。

**D4 巡检简报** —— 每轮写两个文件（`--report-dir` 之下）：
- `<report_dir>/ops/brief/<YYYY-MM-DD>.md`：当日**追加**一节（同日第二轮不许覆盖第一轮）；
- `<report_dir>/ops/latest-patrol-brief.md`：**覆盖**为最新一轮。
- 一节的内容**只由本轮 payload 生成**（不许现场再查一次库、不许引入新的判定）：
  时刻 / 交易日 / 退出码 / 异常项 / 四项业务读数各一行 / 补了哪几步 / 下一轮建议一句。
- 简报是**产物不阻断**：写失败 ⇒ 记进 detail、**不改退出码**（与 P58 的非阻断步同款纪律）。

**D5 命令载荷不变** —— 新增开关 `--update-status` **默认关**，因此
`ops patrol --fix` 这条载荷（＝ launchd plist 里那条）逐字节不变。
`ops schedule generate` 的 `patrol` 载荷 sha 必须仍是 `73649b8a0bd6b25b…`、槽数仍 60。
**若你判断必须改载荷 ⇒ 停下回来说**，不许自己改 plist 或 `schedule.py`。

**D6 A3/B1 高频刷新：本档不实现（明确不做，别顺手做）** —— 理由：
盘中 `bars` 未定型（`ops close` 的 P46 口径＝「当天 `fetched_at ≥ 15:00` 才算定型」），
30 分钟重复跑 A3/B1 会拿半天数据反复写 append-only 台账，并与 `m2_daily` 的收盘口径打架。
本档只在 §7 里给出**评估结论**（含「要做的话需要什么前置」），实现与否由 nanobot 另立任务书。
**不许改 `m2_daily`、不许加高频钩子。**

**D7 只读纪律** —— 业务块**不得**写任何业务表；唯一例外是 `--update-status` 打开时的
`candidate_status_events` 追加。`job_runs` 每轮一行的回执照旧（那是巡检本来就有的）。
**不许**顺手加「自动补采公告/北向」这类写路径。

**D8 真库零写入** —— 站的全部写实测只在 `/tmp` 副本（`cp -c` APFS 克隆）；真库只用
`file:…?mode=ro` 只读。真库 sha 必须跑前==跑后（G9）。

**D9 红线不 regen** —— `scripts/check_redlines.py` 三目标必须仍 == 基线（本轮不许动
`predict/`、不许重新生成基线）。

**D10 落点** —— 新增 `stocklab/ops/business.py`（业务检查实现，单一职责）；`patrol.py`
只做**接线**（组装 `business` 块、把 `business.fuse` 接进 `verdict()`/`_anomalies()`、
调简报写入、加 CLI 开关）。`ops/chain.py`、`CLOSE_STEPS`、`MONTHLY_STEPS`、
`WEEKLY_STEPS`、`stocklab/ops/schedule.py` **一字不动**。
允许在 `m2/lifecycle.py`（P87 的**只读**模块）加只读函数，但 `m2/cycle.py`
的判定逻辑与 `m2/selfeval.py` 的算法**零改动**。

### 7.6 偏离任务书

1. **`status` 词汇表加了两个词**（D1 说「复用已有的，不新造第二套」）。
   `patrol.py` 新增 `TRIPPED = "tripped"`（熔断已触发）与 `RISKY = "risky"`（排雷命中），
   两者**都不进** `ANOMALY_STATUSES` —— 既有词汇表里没有一个词能同时表达
   「这是个必须看见的异常」与「它不应走通用异常通道」。既有的 6 个常量一字未动。
2. **简报成功时不往 payload 加键**。D4 只要求写文件；G3 的措辞是「只多 business 键」，
   所以 `brief_error` **只在写失败时**出现，成功的两个文件路径不进载荷（可从
   `report_dir` 确定导出）。代价：看载荷看不出简报写过。
3. **`business` 只在第一趟体检算**（复检传 `with_business=False`）。D1 没说算几遍；
   重算是白烧插桩0 沙盒，而熔断不会被补步修好 ⇒ `run_patrol` 把它的异常与
   `EXIT_ANOMALY` **单独**带进最终结果（`final = max(after, worst_code, 1 if fuse else 0)`）。
4. **`risk_screen` 横截面用默认宇宙**（`candidate/run.py::_cross_section_map` 的
   `universe=None` ⇒ `SEED_UNIVERSE`）。若最新快照是别的宇宙跑的，池内不在该集合里的
   代码会**少吃几个横截面因子**（`build_ctx` 的 `if ... in cross_section` 守卫）。
   本档不还原快照宇宙（那是另一次口径变更），如实记。
5. **`check_db` 默认算业务块** ⇒ `ops/chain.py`（D10 规定一字不动）每轮 3 次
   `check_db` 各多付约 0.5s。实测业务块 0.51s，在收盘链 480s 预算里可忽略，但照实说。
