## 1. 设计稿必须回答的问题

1. **威胁模型**：要挡的到底是哪一类？
   ① 脚本作者（外部编码 agent）手滑写出 `open()`/`socket`（现在靠 `_ALLOWED_BUILTINS` 白名单挡）；
   ② 恶意脚本主动逃逸（`__subclasses__` 遍历、`ctypes`、`gc` 拿对象等 —— 白名单挡不挡得住？给实证）；
   ③ 资源耗尽（CPU 死循环/内存爆）—— 现在只有 `setitimer` 的墙上时间，**内存与 CPU 时间无上限**。
   逐条说清「现状挡得住/挡不住」，**给可复现的探针脚本**（在 `/tmp` 副本上跑，不动真库）。
2. **升级方案与代价**：子进程（`subprocess` + `resource.setrlimit`）＋ IPC（JSON 过管道）＋ 超时 kill ＋
   （可选）macOS 上的网络/文件沙盒（`sandbox-exec` 已废弃？给现状与替代）。
   写清**每案的兼容性风险**：
   - 契约与探针（`plugin/contract.py::PROBE_CTX`、`validate_return`）必须逐字不变；
   - `signal.setitimer` **只能主线程**（ERROR_DIARY #45）而 labweb 是 `ThreadingHTTPServer` ⇒ 子进程化其实**解开**了这个约束，
     但要说明 `labweb` 与 CLI 两条路径的行为差异；
   - 既有脚本（`candidate/builtin/*`、`m2/builtin/*`、真库 7 条）在两案下**必须逐字同输出**（给对比方法）；
   - 性能：候选池 `candidate run` 现在跑 5 支脚本；子进程化后每支的启动开销与整体耗时（**给实测数字**）。
3. **不做会怎样 / 现在做值不值**：这是 04 的 **P3 可选增值** ⇒ 明确写出「不做的后果」与「触发条件」
   （例如：等模块1/模块2 的脚本来源里出现**非受信作者**再升级）。**若结论是「暂不做」，就把触发条件写成可执行的判据。**
4. **落地顺序**：若做，拆成几步（限内存/CPU → 子进程 → IPC → 文件/网络隔离），每步独立可验收、每步不破坏既有测试。
