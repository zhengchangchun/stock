## 1. 现象（P64 独立复现，真库副本、`asof=2026-09-23`）

账户 `arm-agent-v1`：`total_assets = 19,567`，其中 **`000333 ×100 @ ¥82.47 = ¥8,247`（42%）是存量持仓**、
可用现金 ¥11,320（58%）。A1 `1.0.2` 产出 5 只等权 18%（Σ=90%、`cash_pct=10`），全部成交，随后：

```
paper_nav_daily(arm-agent-v1, 2026-09-23):
    cash = -4490.01   market_value = 24024.00   nav = 19533.99
    持仓 6 只 = 000333(存量) + 603868/600900/002415/601398/002508(本次)
```

- **总敞口 = 24,024 / 19,567 = 122.8%**（透支 ¥4,490，= 总资产的 −23%）；
- 结构原因：目标敞口按 **`total_assets × 18% × 5 = ¥17,610`** 算，而**真正能动的钱只有 ¥11,320**；
  那 42% 的 `000333` **不在 5 条 pick 里**（排名不够前）、**A2 也不卖它**（它还在池内、无止损止盈）
  ⇒ 既不被重算、也不被释放。
- 执行层**没有资金闸门**：`paper/agent_decide.py` 的成交-结算处直接 `cash += gross - fee`（卖）
  / `cash -= (gross + fee)`（买，第 619 行），**允许为负**；
  `agent_decide` 只校验「收到的 `Σ target_weight_pct + cash_pct == 100`」（第 185 行，「多出来的
  部分就是杠杆（借钱买入）」），管不到「与存量持仓叠加后的总敞口」。
- **这个透支一直被上一个 bug 遮蔽**：`1.0.1` 的「按目标市值算股数、整手向下取整 ⇒ 0 股」**意外**当了闸门
  （只成交 3 笔 ⇒ 现金仍 +¥2,055）。P64 修掉「买不起一手」，净结果是把一个此前看不见的杠杆缺陷
  变成了当日的真实持仓。⇒ **不能只回退 1.0.2 了事**：那条偶然闸门迟早还会被别的改动拆掉。

### 3.2 T2 A1 权重基数（Q2-A）· 脚本版本 `1.0.3`

**口径**：`Σw ≤ (100 − CASH_FLOOR) − 未在 picks 的存量持仓占比`；等权 `w = min(CAP_PCT, 该上限 / n)`，
`cash_pct = 100 − w × len(picks)`（逐位自洽）。**`LIMIT_N` / `CAP_PCT` / `CASH_FLOOR` / `LOT` 四个常量的数值一个字都不改。**

`ctx["holdings"]` 每项**已经**带 `code`/`qty`/`close`/`market_value`/**`weight_pct`**
（`m2/context.py::holdings_ctx` 第 206–227 行）⇒ **不需要新增契约字段**。

**算法必须确定性、纯函数、至多两轮（写进源文本头部注释）**：

1. `reserved0 = Σ over ctx["holdings"] of weight_pct`（**保守**：先把全部存量当占用，非循环依赖）；
2. 对 `n` 从 `min(LIMIT_N, 去重后只数)` 往下（沿用 1.0.2 的下降式循环）：
   `w0 = round(min(CAP_PCT, ((100 − CASH_FLOOR) − reserved0) / n), 2)`；
   `S = 在 w0 下买得起的前 n 只`（affordability 沿用 1.0.2 的 `_affordable`，**「不知道」≠「买不起」**）；
3. **一次细化**：`reserved1 = Σ over holdings whose code ∉ S of weight_pct`；
   `w1 = round(min(CAP_PCT, ((100 − CASH_FLOOR) − reserved1) / n), 2)`；
   若 `w1 > w0` ⇒ 用 `w1` 重跑一次 affordability（w 变大只会让更多标的买得起 ⇒ 单调、必然收敛），
   取最终 `(S, w1)`；否则取 `(S, w0)`。**最多两轮，不做迭代到不动点。**
4. `reserved` 的退化口径：`total_assets is None`、或 holdings 缺 `weight_pct`（探针 ctx / 无 PIT 价）
   ⇒ `reserved = 0.0`，**行为与 1.0.2 逐位相同**；`holdings` 为空 ⇒ 与 **1.0.1/1.0.2 逐位相同**。
5. `SOURCE` 头注释标为 **`1.0.3`**，并把「v1.0.2 的偶然闸门已被 T1 的显式闸门取代」写清楚
   （P64 §1 的教训：不能靠「整手向下取整 ⇒ 0 股」当闸门）。

**判据**

- [ ] 真库 09-23 形态（`holdings=[000333×100]`、`market_value=8247.00`、`total_assets=19567.00`、marks 同 P64 §3）

      成交后 `cash ≥ 0`、`market_value / total_assets ≤ 90%`（约 10% 现金下限回到设计意图）。
- [ ] **无存量持仓 ⇒ 与 1.0.1 逐位相同**（只数、权重、`cash_pct`、picks 顺序）—— 回归钉住。
- [ ] 存量持仓**就在 picks 里**的场景：`reserved` 只算**不在 picks** 的那些（贴一行实测，说明细化那一步真的生效）。
- [ ] 两遍同 ctx ⇒ 逐字节同输出（沿用 P64 T6 的钉法）。

### 7.3 ⚠️ T2 的判据读数与实现不符（**如实记，未改判据**）

§3.2 的判据写「`cap = 47.853`、**5 只各 9.57%**、`cash_pct = 52.15`」。实测是
**3 只各 15.95% / `cash_pct = 52.15`**（副本端到端与单元用例一致）：

```
无存量         → 5 只各 18.00% / cash 10.00     （同 1.0.1）
存量 42.1475%  → 3 只各 15.95% / cash 52.15     ← 实测（不是 5 只各 9.57%）
存量在 picks 里 → 4 只各 22.50% / cash 10.00     （细化那一步生效）
total_assets=None → 5 只各 18.00%               （同 1.0.2）
```

**根因**：§3.2 步骤 2 自己要求 affordability **沿用 1.0.2 的 `_affordable`**，
而同一段又把 `w0` 写成「已扣 reserved」的值。`w0 = 9.57%` 时目标市值只有
¥1,872.56，`603868`（一手 ¥3,126）、`600900`（¥2,808）、`002415`（¥3,311）
**全都买不起** ⇒ 凑不齐 5 只 ⇒ 下降式循环一路降到 `n=3`（`w0 = 15.95%`，
目标 ¥3,120.94）才凑齐。两组解的 `w × n` **都等于那个 47.85 的上限**，
所以 `cap` 与 `cash_pct = 52.15` 两个判据数**都对得上**，差别只在**只数**。

**我按步骤 2 的公式原文实现**（而不是按判据里那个数字），理由：另一种读法
（用不扣 reserved 的 w 定 n=5、只把最终权重压到 9.57%）会让 3 只**不可执行**的
标的进 picks ⇒ 0 股、现金停在 ~41%，正是 P64 §1 那个病（「计划与执行在报告里
长得一样」）复发。⇒ **判据未改，结论如实记。**
