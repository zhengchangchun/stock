## 0.5 锁定口径（D1–D12；要改先回来说）

**D1｜本档只做两层调度，且复用现有命令。** 新增 `ops weekly` / `ops quarterly` 两条链
＋ 两条 plist；站**不得**修改任何业务口径、不得为「凑齐需求条目」新写计算逻辑。

**D2｜`asof` 取「最近已收盘交易日」，不取运行当天。**
- 为什么与 `ops close` 不同：收盘链必须写**当天**（它负责把当天数据落地）；
  周/季度链是**读当天数据做汇总**，运行当天可能是休市（10-05 恰好是周一、国庆休市）。
- 取法：复用 `patrol.load_calendar/load_holiday_table/session_day` 的同一份判定 +
  库内 `bars_daily` 最大日，得到 `L = 最近已收盘交易日`。
- **fail-closed**：取不到 `L`（库不在 / 日历读不了 / `bars_daily` 空）⇒ **整轮拒绝**、
  exit 2、零步执行。不许猜一个日期跑。

**D3｜两条链都不做「非交易日跳过」。** 与 `ops monthly` 同构（维护/汇总活，幂等）。
理由：10-05 这类「周一恰逢休市」的周如果跳过，就**连续两周没扫**，而每周扫描正是要
「新增合格标的、剔除失效标的」的节拍。休市周跑出来的是与上周同样的读数 —— 无害、可复核。

**D4｜时刻表（必须与既有三条互不撞点）。**
- `weekly`：**周一 16:30**（`StartCalendarInterval` 5 槽，`Weekday=1`）。
  为什么不是 15:30/15:40：`close` 在 15:30 起跑、整轮预算 900 s（15 min），两条链
  都要**写同一个 SQLite 库** ⇒ 必须留 ≥45 min 余量，否则撞 `database is locked`，
  把收盘链判成 exit 2（P42 的教训，`test_no_two_jobs_fire_at_the_same_moment` 钉住）。
- `quarterly`：**5/1、9/1、11/1 09:00**（3 槽/年）。对应**财报法定披露截止日之后**：
  4/30（年报+一季报）、8/31（中报）、10/31（三季报）。选 09:00 而不是 08:00 是为了
  避开 `monthly` 的「每月 1 日 08:00」（间隔 1 h，且 monthly 自身预算 1800 s）。
- **07 约束 1（串行优先级）落地方式**：launchd **没有优先级队列**（这是 D-7 已修正过的
  认知）⇒ 用「时间不重叠 + 各自幂等」代替排队：季度 09:00 / 每周一 16:30 /
  每日 15:30 / 巡检 <15:00，四层两两不同分钟。**报告里必须写清这一条**，不许声称有队列。

**D5｜weekly 链（`WEEKLY_STEPS`）＝ 5 步 + 汇总报告。顺序 = 依赖顺序。**
1. `candidate run --run-kind weekly --asof {asof}`（模块1 全流程 → 新快照；**阻断**）
2. `candidate review --asof {asof}`（插桩5 复盘：错判案例回流台账；**非阻断**）
3. `m2 report --asof {asof}`（双账户 + 双基准绩效；**阻断**）
4. `m2 lifecycle due --asof {asof}`（冻结到期清单；**阻断**——失败说明台账读不了）
5. `plugin list`（版本清单；**阻断**）
6. **汇总报告**（本档新增的**渲染**步骤）：把上面 5 步的 stdout 载荷 + `m2 report`
   的 JSON 汇总成 `reports/weekly/<asof>-weekly.md`。**只汇总，不重算**。

**D6｜quarterly 链（`QUARTERLY_STEPS`）＝ 5 步 + 汇总报告。**
1. `ingest financials`（三表复核 → 重估基本面；**阻断**）
2. `candidate run --run-kind quarterly --asof {asof}`（**全量重打分**；**阻断**）
3. `m2 report --asof {asof}`（**阻断**）
4. `m2 lifecycle due --asof {asof}`（冻结到期/过期清单；**阻断**）
5. `m2 attribute scan --asof {asof}`（归因**候选**扫描；**非阻断**）
6. `plugin list`（**阻断**）
7. **汇总报告** → `reports/quarterly/<asof>-quarterly.md`。

**D7｜`ops quarterly` 不做「自动开新验证周期」、不做「全量 sandbox 跑批」。**
- 自动建新周期：P87 §4.2 明确**留待用户拍板**，本档**只出清单**（`m2 lifecycle due`）。
- 全量过拟合检测：`plugin sandbox` 是「一次一个 script_id、离线回放」且**多版本连跑很贵**；
  本档**只在报告里列出 active 版本清单 + 各自最近一次沙盒结论**，把它标成
  「**待人工决定是否逐个跑 `plugin sandbox`**」。不许静默跳过、也不许假装跑过。
- 风控全量复核（07 任务4 item4「行业集中度 / 单票仓位风险」）：**本档只出 `portfolio show`
  原始读数**。真要做集中度打分是**新口径**，另立任务书（本档不得自创风控算法）。

**D8｜报告落盘位置与「读得到」。**
- `reports/weekly/<asof>-weekly.md`、`reports/quarterly/<asof>-quarterly.md`
  （`reports/` 在 `.gitignore` 里；回执仍在 `<报告根>/ops/latest-{weekly,quarterly}.json`）。
- 报告必须**自带数据出处**：每个数字旁注明它来自哪一步 / 哪张表 / 哪个报告文件。
  无数据时写「无数据（原因）」——**不允许写 0 或留空**（ERROR_DIARY #50 同型的教训）。

**D9｜退出码语义与既有链同构。**
- `0` 全绿（含非交易日照跑）/ `1` 链跑完但有非 0 步或事后体检 `missing/stale` /
  `2` 断链（库不在 / 取不到 asof / 某步 ≥2 / 预算用尽 / 跨库守卫拒）。
- 整轮预算：`weekly`/`quarterly` 各 **1800 s**（候选池全量 + 财报复核是长跑）。
- 走 `ops/runner.py` 的 `run_steps` ＋ `journal.seal`，**不新写执行器**；
  跨库守卫（`cross_db_refusal`）照旧生效：链里含 `ingest *`/`doctor` ⇒ 非默认库直接拒。

**D10｜`/lab/ops` 页面同步到 4 条任务。** 页面现在写着「三条任务」；新增两条后要
把它改成读 `schedule.JOBS`（不得再写死 3），并把回执/日志/逐步退出码照旧展示。

**D11｜真库零写入。** 本档所有验证（含两条链的端到端演练）在 `/tmp/p89/copy.db`
副本上做；真库只允许**只读**。**站不执行 `ops schedule install`**（那是改本机
`~/Library/LaunchAgents` 的系统动作，留给 nanobot 在复核通过后做）。

**D12｜红线不 regen。** 三目标 sha 必须与基线逐位相同（`docs/baselines/redlines.json`）。

### 7.5 坑

1. **`m2 report` 的读数 JSON 在 stderr，不在 stdout。** D5.6/§0.2 都假设 stdout
   （「各步 stdout 载荷 + m2 report 的 JSON」）。只读真跑一次就露馅：stdout 只有长文本，
   `grep -c '^{' /tmp/p89/m2.txt` = 0。读 `cmd_m2_report` 才看到
   `print(json.dumps({...}), file=sys.stderr)`（`cli/main.py:4234`，`sort_keys=True`
   单行）。修法：`window_report.m2_json()` 先扫 `stderr_tail`、再回退 `stdout_tail`
   （实现若挪回 stdout 不该判失败）。**这条不改 D5 的口径（汇总 ≢ 重算），只改取材流。**
2. **只在副本上真跑一个写库命令，就能看出 `candidate run` 不幂等**：
   `candidate run --run-kind weekly --asof 2026-09-24 --db /tmp/p89/copy.db` → `exit 1`，
   stderr `IntegrityError: UNIQUE constraint failed: candidate_rejects.snapshot_id, code, stage`
   （该 asof 的 snapshot/rejects 已存在）。⇒ 周一 16:30 那一轮**若同 asof 重跑**
   （launchd 唤醒补跑 + 人工重试都会），会记 exit 1。`candidate/` 本档零改动，
   **未修**，见 7.7 未决 1。
3. **`report_dir` 同名遮蔽**：模块函数与函数参数同名 → `'PosixPath' object is not
   callable`。TDD 的第一次红就是这个，不是我预想的「模块不存在」。

### 7.7 偏离与未决（判据说「不知道」的地方，按最保守选项做）

**偏离（D 系列口径，需 nanobot 复核）**

1. **`QUARTERLY_STEPS` 是 8 步，不是 D6 标题的「5 步」。** D6 标题写「＝ 5 步 + 汇总报告」，
   正文却列了 **6** 项（标题与正文自相矛盾）。取**正文的显式清单**（正文是操作性的、
   而且多一步＝多一份证据）。另按 **D7.3**（「本档只出 `portfolio show` 原始读数」）
   把 `portfolio_show` 加为第 7 步（`--asof`、非阻断）—— D5/D6 的清单里没有它，
   但不加它就**没有任何地方**能产出 D7.3 要求的那份读数。合起来 = 7 步 + 汇总报告。
2. **`quarterly` 时刻 07:00，不是 D4 的 09:00。** D4 的 09:00 与 `patrol` 的 09:00 槽
   **真撞点**（2026-05-01 是周五；详见 ADR-039 §5）。两条硬要求
   （「09:00」与「与既有三条无同时刻槽」）互斥，**无同时满足的落点** ⇒ 保日期、挪时刻到
   07:00（距 `monthly` 08:00 仍 1 小时，与 D4 给 09:00 的理由一致），并在
   `test_quarterly_does_not_collide_with_patrol` 里留下 09:00 会撞的**反证**。
3. **G7 的 `job_runs` 很可惜不是 `blocked` 这个值。** `schema.sql` 的
   `job_runs.status` 有 `CHECK (status IN ('running','ok','failed'))` —— **写不出
   `'blocked'`**。要满足字面判据只能改 `store/schema.sql` 或 `journal.py`，
   而 `journal.py` 在 G9 的**零改动**名单里、`schema.sql` 不在 §1 允许改动清单里。
   ⇒ 取最保守落点：**照常 `seal`**（`job_runs` 写一行、回执文件也落），`status='failed'`、
   `detail` 里逐字带 `blocked`（`chain.summary_line` 对 `error`/`refused` 就是输出
   `…: blocked exit=2（…）`）。**未改 schema、未改 journal。**
4. **`weekly` 的 5 槽是 5 条相同 entry（都 `{16,30,1}`）。** D4 正文只说得通「周一 16:30」，
   但 §G8 逐字要求「5 槽全 `Weekday=1,16:30`」。5 条相同 entry 与 1 条**语义等价**
   （launchd 数组 = 命中任一条即触发），所以它同时满足 D4 正文与 G8 字面；**它不是
   「周一到周五」，更不是跑 5 次**，这一点写进了 `schedule.py` 的注释与测试。
5. **D9 提到「事后体检 `missing`/`stale` ⇒ 1」，D5/D6 的步骤清单里没有体检步。**
   本档按 D9 实现（两条链都跑 `check_db` 并取较大者），**未**把体检加成第 N 步
   （那会再动一次步骤清单）。真库副本上 `check_db` = exit 0，所以 G5/G6 是 0。

**未决（交 nanobot）**

1. **`candidate run` 同 asof 重跑不幂等**（7.5 第 2 条）：`{run_kind}` 的任一重复执行
   都会撞 `candidate_rejects` 的 UNIQUE。修它在 `candidate/`（本档禁改）。在修之前，
   `ops weekly` 的**周一那一轮若被 launchd 补跑或人工重试就会 exit 1**（链本身没错）。
   建议要么给 `candidate run` 加 `INSERT OR IGNORE`/幂等键，要么让链把这一步读成
   「已跑过（幂等）」——**都不是本档能定的**。
2. **`ops schedule install` 未执行**（D11）：5 条 plist 已能生成并逐槽断言，但装到
   `~/Library/LaunchAgents` 是 nanobot 的动作。装之前请留意**旧的 3 条 plist 还在本机**
   （`com.stocklab.{close,patrol,monthly}.plist`），新增的 2 条要 `install --job weekly
   --job quarterly`（或全部重装）。
3. **D4 说 `weekly` 是「周一 16:30」**，但 16:30 距 `close` 的 15:30 只有 1 小时，
   而 D4 自己要求「≥45 min 余量」—— 满足，但没有 D4 声称的「四层两两不同分钟」
   之外的额外余量说明。若 nanobot 认为 16:30 太紧，改的是**时刻表**，请回任务书。
4. **报告里 `plugin_list` 的 active 清单是「原文引用」不是「解析后的表」**：
   `plugin list` 打的是**文本表**（14 行；`script_id / version / status`），本档
   **刻意不解析**它（解析一段人读文本比引用它更脆）。所以 §五 那段让读者去第四节看原文。
   若要结构化的 active 清单，应给 `plugin list` 加 `--json`（新命令面，另立任务书）。
