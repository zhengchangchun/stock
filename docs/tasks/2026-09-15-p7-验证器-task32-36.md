### 4. 幂等性证据（**第一次没通过，抓到真 bug**）

第二次回放**崩了**，而且崩得对：

```
VerificationConflict: pred_id=27 已有一条内容不同的验证记录（差异字段 ['invalidated']）
```

追查根因（详见 ERROR_DIARY #10）：`verifications.invalidated` 是 `INTEGER NOT NULL`，
不可评分的行在内存里 `invalidated=None`、入库被逼成 `0`。而幂等比较当时是拿
**未规约的新载荷**（`None`）去比**已规约的旧行**（`0`）—— 同一份结果被自己判成「内容不同」。
**全历史回放里恰有 13 条不可评分记录**，所以这个问题只在真实全量回放上暴露，
fixture 里（无数据缺口）永远测不到。

修复：hash 之前两边都过 `store._canonical()`；补两条回归测试
（`test_undetermined_invalidated_is_idempotent_on_rerun` × 2 例、
`test_cli_backfill_is_idempotent_across_a_data_gap` —— 后者专门造出数据缺口）。

修好后：

```
run1  报告 sha256 = 7b4c3cd7841160716455bb1721eed2e56536db86a03b3f19804e4fa165dedb2d
run3  报告 sha256 = 7b4c3cd7841160716455bb1721eed2e56536db86a03b3f19804e4fa165dedb2d   ← 逐字节一致
      verifications 行数不变（6055，其中 17 条不可评分）
```

报告内容**不含生成时间**，故 sha256 可直接作为幂等证据。
注意：`run1` 的**数字**没有被这次修复改动（报告逐字节一致）—— 修的是幂等判定，不是打分口径。

## 口径决策（可复查）

- **`verifications` 结构**：`pred_id` 上唯一索引；身份列不可变、结果列可更新、`DELETE` 全禁（ADR-002）。
  唯一允许的 UPDATE 是 `rescored_after_data_gap`（不可评分 → 可评分），反向（可评分 → 不可评分）**明确拒绝**。
- **不可评分**写库时结果列全为 `NULL` → 结构上不可能进任何分母；同时保留完整审计痕迹。
- **`invalidated` 是 `INTEGER NOT NULL`**，「判不了」只能写 0；真值放在 `notes.undetermined`，
  读取侧（`report._UNDETERMINED_INVALIDATED`）据此把这类行剔出失效率分母（错误日记 #7）。
- **回放 = 同一个算法**：`backfill` 走的与 `predict run` 完全同一条代码路径，
  `test_backfill_payloads_match_predict_run` 逐日比对 `payload_sha256` 钉住这一点。
  这是「历史回放即合法样本外评估」的前提 —— 模型纯 PIT、无参数拟合，一旦哪天开始拟合，本报告立刻失效。
