## 0. 一句话

`web.ifzq.gtimg.cn`（本仓唯一的日K源 host）现在对**所有**请求返回腾讯 WAF 的
`HTTP 501` 页面（非 JSON）；同载荷镜像 host `ifzq.gtimg.cn` 与
`proxy.finance.qq.com/ifzqgtimg/...` 返回**逐字节相同**的合法 JSON。本站给日K 取数加
**镜像 host 回退链**，并把两个镜像 host 加进白名单；**首选 host 可用时路径逐位不变**。

## 0.1 证据（2026-09-25 04:20–04:35 实测，可复现）

1. **首选 host 已死**：`curl 'https://web.ifzq.gtimg.cn/appstock/app/fqkline/get?param=sh688498,day,,2026-09-25,320,'`
   → `501`，body 是 `waf.tencent.com/501page.html?u=…` 的跳转脚本（326 B，**非 JSON**）。
   加 `Referer: https://gu.qq.com/` / `Origin` / 完整浏览器头（UA+Accept+Accept-Language）**仍 501**
   ⇒ 不是缺头，是该 host 的 WAF 拦截。
2. **镜像 host 可用且同构**：同 param 换 host → `https://ifzq.gtimg.cn/appstock/app/fqkline/get` = `200`、
   `https://proxy.finance.qq.com/ifzqgtimg/appstock/app/fqkline/get` = `200`；两者 body **完全相同**
   （24675 B）。喂进本仓 `tencent.parse_kline`（`sh600519`，`end=2025-06-08`）→ **320 根**
   （`2024-02-02 → 2025-06-06`，`close_last=1506.39`）⇒ 解析器零改动可用。
3. **其它源不受影响**：`qt.gtimg.cn/q=`、`datacenter-web.eastmoney.com`、`vip.stock.finance.sina.com.cn`
   实测均 `200` ⇒ 只有日K 这一条链断。
4. **现场损失**：真库 `extend_history --universe csi300-500`（800 只，02:17:11 起）首轮
   **03:23:20 exit=1**；`universe_memberships` 800 只里**有 bars 的只有 230 只**（`bars_daily`
   97,323 → 1,290,384 行）；重试段 25 s 内行数**冻结**（每只撞 501 → `http.py` 对 5xx 重试 4 次
   ≈6–8 s 后抛 `FetchError`）⇒ 重试注定再失败，只是白跑。
5. 失败集中在扫描序**靠后**的段（`603xxx/688xxx/002xxx/601xxx` 大片缺失）＝与「撞墙越久越失败」一致。

### 7.7 偏离与说明

① **T2 里第二处调用点的名字对不上。** 任务书写「`fetch_daily_bars`（约 87 行）与
   `fetch_index_bars`（约 214 行）」，但 `fetch.py` 里第 214 行的 `tencent.kline_url` 在
   **`fetch_corp_actions`** 内；`fetch_index_daily`（117 行）本身是**委托给
   `fetch_daily_bars` 的壳**。按「两处取数」的字面意图（= `fetch.py` 里两个
   `kline_url` 调用点）落地：**两处都加回退**（指数那条自动继承；除权事件那条另有
   专门的用例覆盖 URL / 缓存键形状）。若只改 `fetch_daily_bars`，`ingest actions`
   这条链仍会撞死 host。

② **F2 括号里的「翻页上限」没有被当成换 host 的触发条件。** 翻页上限是**整段取数**
   的失败（外层 `for…else`），不是某个 host 的属性；且 T2 明令「不许把换 host 做成
   换页重放」。⇒ 落地口径：**某个 base 抛 `FetchError` ⇒ 换下一个**；触发集 =
   {5xx / 连接异常 / 空响应 / 正文非 JSON}，**不含**翻页上限（仍在原处抛。
   见 `fetch.py::_kline_page` docstring 与 ADR-028 ②的表格）。

③ **T6-2 / T6-3 未达 exit 0：1 条既有用例被工作区里的未跟踪产物打红。**
   `tests/test_universe_cli.py::test_sync_missing_universe_file_exits_2_and_writes_nothing`
   断言「`csi300-500` 宇宙文件**缺失** ⇒ exit 2」，而工作区里躺着 P71 未提交的
   `config/universes/csi300-500.{csv,meta.json}` ⇒ 该文件不缺失，sync 正常跑完
   （输出 `投影=800 行 … sha=eff7b478…`），于是 `assert 0 == 2` 失败。
   **与本站改动无关的证明**（把本站 6 个改动文件全部 stash，未跟踪文件原地保留）：

   ```
   $ git stash push -- stocklab docs tests
   $ .venv/bin/python -m pytest -o addopts="" -q tests/test_universe_cli.py::test_sync_missing_universe_file_exits_2_and_writes_nothing
   tests/test_universe_cli.py:172: AssertionError
   universe=csi300-500 投影=800 行 新增 instruments=799 只 补空 sector=1 只 sha=eff7b478…
   1 failed in 0.23s
   $ git stash pop
   ```

   ⇒ 这是**工作区既有条件**（判据隐含前提 =「宇宙文件不存在」，与 P72 的 821 是同一族）。
   本站**没有**改这条既有断言，也**没有**删除/移动那两个文件 —— 删了会当场打断
   nanobot 正在跑的那一轮采集（PID 21090 的 `extend_history --universe csi300-500`
   要读它们）。按 F5「真库/流水线归 nanobot」的边界，处置留给 nanobot。

④ **T6-6「跑前 == 跑后」在本环境下不可达成**（真库被 nanobot 流水线持续写入）。
   不达成的是**判据的字面形式**，判据的**意图**（本站不写真库）有四条证据：
   1. 站空闲时真库仍在变 —— 4 次读数（04:35:09 / :15 / :20 / :25）size
      468164608 → 470126592 → 471592960 → 472698880，sha 每次都不同；
   2. 写入者点名可查：`ps -o pid,etime,command -p 60048` =
      `… -m stocklab.cli.main ingest valuation --universe csi300-500`（pid 60048）；
      同轮还有 pid 21090 `extend_history --universe csi300-500`（跑满 58 min 后 04:34:43 退出）；
   3. probe 前后（同一动作的 30 s 窗口）sha **逐位相同**：`b0a60a8f…`；
   4. 站这一侧**没有任何库写入面**：改动集 `grep -niE "conn|sqlite|INSERT|UPDATE|\.db"` 零命中，
      probe 用 `HttpClient(cache=None)`，`data/raw_cache` 在 04:20 后无新文件 —
      `fetch_daily_bars` 只做「取数＋解析」，从不落库（本仓既有边界）。

⑤ **额外收紧一条（F2 未写）：`HostNotAllowed` 也不换 host。** 白名单是本站自己的
   闸门（R13）；静默降级到镜像会让「白名单漏配」永远不可见。方向上与 F2 的
   「4xx 不换」一致（都是「我这边的问题」而不是「源坏了」），属**收紧**不属放宽。

⑥ **「4xx 不换」的实现方式是认 `http.py` 的文案标记 `"（不重试）"`。** F6 要求
   `http.py` 零改动 ⇒ 无法给它加异常子类或状态码属性，只能认文案。已在代码注释与
   ADR-028 里点明这层耦合，并写清退化方向：标记若消失 → 行为变成「4xx 也换 host」
   （多打两次注定失败的请求），**不会**静默取到错数据。这是一个已知的脆弱点，
   见 §7.8-①。

⑦ **ADR 索引未同步**：`docs/decisions/README.md` 的索引里没有 ADR-026/027（既有现状），
   本站不扩大改动面，ADR-028 也不入索引。

### 7.8 未验证口子

① **第三级回退（`proxy.finance.qq.com`）没有在真实源上单独实测过。** 真机 probe 走到
   第二级就成功了；F7 的额度不该用来「把第二级也打掉」。它进链的依据是任务书 §0.1 的
   实测（与 `ifzq.gtimg.cn` 的 body 逐字节相同）＋ 离线用例覆盖了链序。⇒
   「第二级也挂时第三级顶得住」目前**只有假 client 的证据**。

② **「首选恢复后自动回到原路径」没有实测**（此刻它仍 501）。逻辑上由链首即首选保证，
   代码级证据是 `KLINE_URLS[0] == KLINE_URL` 与「首选可用时镜像零请求」的用例。

③ **4xx 分支的端到端耦合是「认文案」**（§7.7-⑥）：只覆盖了 `http.py` 当前产出的文案
   形状（`tests/test_data_fetch_mirror.py` 里手工构造 `FetchError("HTTP 404（不重试）")`）。
   如果哪天 `http.py` 改了这句话，**没有**任何用例会红 —— 这是本轮刻意留下的
   「零改动 `http.py`」的代价。

④ **没有在「干净工作区」上验过全量 pytest 全绿**（§7.7-③）：需要移走 nanobot 正在用的
   `config/universes/*`，超出本站边界。⇒ 3202 总数里那条 failed 的「本来会通过」是
   **推断**（stash 证明它现在必红；它在基线 3188 的计数里，故当时是绿的）。

⑤ **800 只的批量补采结果不在本站范围**（F5：真库写入归 nanobot）。本站只证「单只三例
   经镜像 host 取到非空 bars」，**不**证「800 只都能补上」—— 那取决于真库与流水线。
