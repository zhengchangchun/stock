# P39 验证选日与已评分行隔离 —— 消除 `session tick` 每轮 `verification_conflict`

创建：2026-09-22 ｜ 提出：nanobot（需求澄清+诊断）｜ 实现：Claude Code
前置阅读：`CLAUDE.md`、`docs/errors/ERROR_DIARY.md`（**必读**，尤其 #10 / #36 / #48 / #55）

---

## 0. 一句话

`session tick` 的「验证到期预测」步骤**选日条件过宽**：它把**已经全部验证过**的日期也每天
重扫一遍，于是必然会用**今天的复权/成本口径**去重算**昨天口径下写的账本**，append-only 守卫
（正确地）报冲突 → 每轮 tick exit 1、`ops patrol` 每天记 `step_anomaly`。修法＝选日只挑
**含未验证预测**的日期、且只把**该日未验证的预测**交给打分器（与 `verify pending` 同一份选取逻辑）。

## 1. 实测证据（2026-09-22 13:5x，库副本 `/tmp/diag-conflict.db`，只读核对）

现象：`session tick` 每轮 exit 1，`anomalies` 恒为两条 `verification_conflict`：

| pred_id | code | asof | target | model_version | origin | 差异字段 |
|---|---|---|---|---|---|---|
| 42293 | 601318 | 2026-09-09 | 2026-09-10 | pit-rw-v1.0.1 | replay | `actual_pct`/`benchmark_pct`/`sim_pnl`/`score_direction`/`score_action`/`total_score` |
| 42312 | 603868 | 2026-09-10 | 2026-09-11 | pit-rw-v1.0.1 | replay | 同上 + `hit_direction` |

**根因（已核，不是猜测）**：这两条验证行写于 `2026-09-21T16:24:07+08:00`，当时 `adj_factors`
**为空**（复权链尚未采到）。以 601318 为例，同一根 bar 两种口径：

- 库里存的 `actual_pct = -0.013153` ＝ **不复权**价 56.26 → 55.52（−1.3153%）；
- 按现在的复权链算：55.28 → 55.52 ＝ **+0.4342%**。

即：**同一份预测、同一根 bar、因为复权口径升级（v1.0.1→v1.0.2，2026-09-21 深夜）必然算出不同结果**
→ 守卫报冲突是**正确行为**，旧行是「复权链为空时期」的历史账本，**不许改写**。

**真正的缺陷是选日**：`stocklab/session/tick.py` 步骤③（约 240–279 行）用

```sql
SELECT DISTINCT target_date FROM predictions WHERE status='ok' AND target_date <= ?
ORDER BY target_date DESC
```

—— 它不过滤「该日是否还有未验证的预测」。实测全库：`predictions` 84658 行，**只有 34 条没有验证行**
（全部 `target_date = 2026-09-22`，来自 09-22 12:06 误起子进程写下的盘中预测），历史日期 **100% 已完全验证**。
所以每天 tick 都会白重算最多 `window` 个日期 × 约 34 行/日，并且**必然**踩到上面两条旧口径账本 →
`step_anomaly` 永久复现、exit 码永久为 1（真异常被噪声淹没）。

## 2. 目标行为（验收判据）

- **T1 选日收窄**：tick 步骤③ 只挑「存在**没有验证行**的到期预测」的 `target_date`；选取逻辑**复用**
  `stocklab/verify/pending.py::pending_predictions()`（与 CLI `verify pending` **同一份**实现，
  禁止在 tick 里另写一份平行 SQL）。
  - `pending_predictions` 返回 `n is None`（两侧都判不出已收盘日）时，行为与现状一致：**不给 0**、
    如实记录（沿用现有 skip/异常分支，不许静默当作「无缺口」）。
- **T2 逐日只评缺口**：每个目标日只把该日**未验证的** `codes` 传给打分器，
  即 `verify_target(conn, d, codes=<该日未验证的 codes>, now=now)`（与 CLI `verify pending` 的做法逐字一致）。
  已评分的行**一个字节不碰**（不重算、不写、不更新）。
- **T3 自证（真实库副本，非真库）**：`session tick --now <收盘后时刻>` 后
  ①`verification_conflict` 归零、`exit_code == 0`；②`verify pending` 第二次跑仍「无待验证、零写入」。
- **T4 补分出口写清（有意的收窄，不许默默改）**：本次**不**把「有验证行但不可评分」的预测纳入自动重算
  ——全库 38 条 unscorable 均为 `NO_BAR_TARGET` 类（停牌/无 bar）永久缺口；若纳入，`reason_code`
  一旦变化就会制造新的假冲突。因此：在 `session/tick.py` 步骤③ 的注释里写明「不可评分行的补分需人工跑
  `stocklab verify run --target-date <d>`（该命令保留全量评分语义）」，并在
  `docs/errors/ERROR_DIARY.md` 追加一条（编号顺延）。
- **T5 契约不变**：`summary` 键名**只增不减**（`due_dates` / `verified_dates` / `backlog_skipped` /
  `inserted` / `identical` / `rescored_after_data_gap` / `unscorable` 保留，语义按新判据如实描述）；
  `verifications` 既有行 **0 改动**；`MODEL_VERSION` 不动；`predictions` 不动。

### 8.5 剩余不确定性（哪些没验、为什么）

1. **真实 15:30 收盘链**没跑（现在是盘中 14:10，真库既未收盘、`ops close` 也被
   自身的「未收盘拒绝执行」守卫挡住）。T3 用的是**库副本 + `--now` 注入**，
   不是真实链路。结论：`session tick` 在**注入的收盘后时刻**下已自证；
   「15:30 真实链路是否整链绿」需等收盘后由 nanobot 的 cron 验证。
2. **`ops patrol` 的 tick 步未被本次覆盖**：`patrol.plan()` 只在「今日快照缺失」时
   才排 `session_tick`（`patrol.py:435`），而今日快照 12:06 已存在 —— 所以 patrol
   近几轮（12:21–14:01）都报 `exit=0`，**它的这条路径本就没在跑 tick**。
   因此「patrol 从此每天绿」**不能**由本次自证推出；能确定的是：
   tick 步骤③ 在**任何** cutoff 下都不会再重扫已评分日期（反证见 8.2 ②）。
3. **`n is None` 分支的退出码**保持现状（skip 分支不记 anomaly → `exit_code 0`），
   只把「判不了」如实写进 `reason` / `due_dates: None`。按任务书 §2 T1「行为与现状
   一致」执行 —— 若希望「判不了」也非 0，属**退出码语义变更**，须另开任务（同 #54 的
   「0/1/2 各代表什么」）。
4. **真实库里那 34 条 `target_date=2026-09-22` 的缺口**本轮**没有**在真库上补
   （只在副本上验证）—— 真库的 15:30 收盘链会自然补上；这 34 条是 09-22 12:06
   误起子进程写下的盘中预测（见 #55），**是否应该被打分**是另一个问题（它们的
   `asof` 是当天盘中），本任务不动它。
