## 0. 背景：P61 说了「暂不做」，但留了一档**不等触发条件**的洞

P61 §0.5 的结论是：子进程沙盒**推迟**（脚本来源目前是半受信：CC 写 ＋ 人工 `approve`）。
但它同时留了一条 —— **资源耗尽**。P61 §0.6 的实测（nanobot 2026-09-24 自跑）逐字如下：

```python
def run(ctx):
    bomb = [0] * 30000000          # 一次性分配 ≈240MB，发生在**单个 C 调用**里
    return {"ok": True, "n": len(bomb)}
```

| 闸门 | 结果 |
|---|---|
| `guard.check_source`（AST 预检） | **原样放行** |
| `signal.setitimer` 5 秒墙钟超时 | **拦不住**（SIGALRM 只在字节码之间投递） |
| 实测读数 | 用时 **0.06 s**、进程峰值 RSS **15MB → 244MB（+229MB）** |

⇒ 把 `3e7` 后面加两个零就是 24GB：**持有数据库连接与 WAL 的进程会被直接 OOM 掉**。
这不是「有人要攻破沙盒」，是「一段写错的脚本能把日更链带走」。

G1 的判据（P61 §0.7）＝「CLI 或 labweb 进程 RSS > **2GB**，或进程非零退出且日志有
`MemoryError`/被杀记录」⇒ **开最小档：`resource.setrlimit` 的 CPU/内存上限（仍同进程）**。
本档就是那一档的**最小落地 ＋ 常驻监控**。

## 0.5 锁定口径（D1–D9；要改先回来说）

- **D1 量具只读进程自身**：新增 `stocklab/plugin/resources.py`，两个只读函数
  `peak_rss_bytes()`（`resource.getrusage(resource.RUSAGE_SELF).ru_maxrss`，
  **darwin 单位是字节、linux 是千字节 ⇒ 必须按 `sys.platform` 归一并在 docstring 写明**）
  与 `rss_mark()`（上下文管理器，给出 `delta` 与调用前后峰值）。**不 fork、不采样子进程**。
- **D2 两条阈值进 `stocklab/config/limits.py`**（唯一真源，与 `CIRCUIT_BREAKER_DRAWDOWN`
  同级，AI 不可改，不做参数搜索、不自动调参）：
  - `PLUGIN_CALL_RSS_LIMIT_BYTES = 512 * 1024 ** 2`：**单次调用**的峰值增量上限。
  - `PLUGIN_PROCESS_RSS_LIMIT_BYTES = 1536 * 1024 ** 2`：**进程已用峰值**上限，
    超了就连脚本都不执行。为什么是 1.5GB 而不是 G1 判据的 2GB：**要在被打死之前先停**，
    2GB 是事后判据、不是事前闸门，两者不是一回事（写进常量注释）。
- **D3 fail-closed 的两处闸门（`plugin/runtime.py`）**，语义必须分开写清楚：
  1. **执行前**：`peak_rss_bytes() >= PLUGIN_PROCESS_RSS_LIMIT_BYTES` ⇒ 抛新异常
     `PluginResourceError`，**一个字节的脚本都不执行**（用计数器证明 `run` 没被调用）。
  2. **执行后**：本次调用峰值增量 `>= PLUGIN_CALL_RSS_LIMIT_BYTES` ⇒ 该次结果**作废**，
     抛 `PluginResourceError`（消息里带实测增量与阈值）。
  - **不做中途 kill** —— P61 §0.6 已实测「单次 C 调用不可中断」，本档**不假装能中断**。
    闸门的作用是「判废 ＋ 留痕 ＋ 后续调用被挡住」，把这件事写在异常消息与模块 docstring 里。
  - `PluginResourceError` 是 `PluginTimeout` 的**兄弟**（都直接继承 `Exception`），
    既有 except 点若按 `PluginTimeout` 精确匹配 ⇒ 必须**同时**接住两者，走**同一条**容错路径
    （点名 ＋ `log_event` error ＋ `continue` ＋ 收尾 `return 1`），**不许静默吞**。
- **D4 读数出口，键只增不减**：`load_script(...)` 新增可选参数
  `on_call: Callable[[dict], None] | None = None`；每次调用结束（成功 / 超时 / 资源越界）
  都回调一条 `{"plugin_id","outcome","duration_ms","rss_delta_bytes","rss_peak_bytes"}`
  （`outcome ∈ {"ok","timeout","resource"}`）。**返回类型一字不改**（仍是 `_call(ctx) -> dict`），
  不传 `on_call` 时行为与今天逐字相同。
- **D5 落库 = 新的 append-only 表**（本档唯一的结构变更）：
  `plugin_resource_events(event_id INTEGER PRIMARY KEY AUTOINCREMENT, plugin_id TEXT NOT NULL,
  at TEXT NOT NULL, outcome TEXT NOT NULL, rss_delta_bytes INTEGER NOT NULL,
  rss_peak_bytes INTEGER NOT NULL, duration_ms REAL, detail TEXT)` ＋ 两条触发器
  （`trg_plugin_resource_no_update` / `trg_plugin_resource_no_delete`，照 P91/P92 的写法）
  ＋ `stocklab/store/schema.sql` 同步 ＋ `migrate.ensure_schema` 前滚（幂等，重入返 `[]`）。
  **写入口只有一个**：`stocklab/plugin/store.py::record_resource_event(...)`。
  **谁调用**：`plugin/store.py` 里 `plugin submit` 的沙盒预检路径 —— 那是唯一会
  执行未审脚本的地方（`candidate run` / `m2_daily` 跑的是已 `active` 的脚本，也要记，
  由调用方自行决定；**本档至少要覆盖 submit 预检这一条**，其余调用点作为可选加分项如实记）。
- **D6 巡检第五块 `sandbox_guard`**（`ops/business.py`，**键只增不减**，P92 那四块一字不动）：
  读 `plugin_resource_events` 最近 N 条（默认 20）⇒
  `{"status": ok|high|skipped, "n_events", "max_delta_bytes", "max_peak_bytes",
    "limits": {...}, "reason"}`。
  - **空表 ⇒ `skipped`**（真库现在就是空表，空是预期）**不算异常**。
  - `status=high`（任一 `outcome="resource"`）也是**只展示、不进退出码** ——
    与 P92 D2 同一纪律（盘中每 30 分钟报一次假警会把巡检变成噪音）。
  - `fuse` 仍是**唯一**进退出码的业务读数，这条不改。
- **D7 简报一行**：`ops/business.py::brief_text` 追加 `sandbox_guard` 一行；
  `summary_line()` 与既有字段**一字不动**（launchd 日志与回执文案不许变）。
- **D8 只读边界与调度面**：`ops/chain.py`、`CLOSE_STEPS` / `MONTHLY_STEPS` / `WEEKLY_STEPS`、
  `ops/schedule.py` **一字不动**；`ops schedule generate` 的 5 条 plist 载荷 sha
  必须逐字不变；真库**零写入**；红线**不 regen**。
- **D9 既有脚本必须逐位同输出**：`candidate/builtin/*`、`m2/builtin/*` 走新路径的返回值
  与今天逐字相同，且正常脚本**一次都不该**触发新阈值（正常脚本的 delta 应是 MB 量级，
  给实测数字）。

### 7.7 未决 / 未验证口子

- **① G3 的判据内部互斥（点名，不改判据）**：在 D2 的 `PLUGIN_CALL_RSS_LIMIT_BYTES
  = 512 MiB` 下，`[0]*30000000`（+228.9 MiB）**必然**以 `ok` 收场；而任何增量
  ≥ 512 MiB 的调用至少是 229 MiB 的 **2.24×**，永远落不进 G3 自定的 0.5–2× 带。
  即 G3 的「抛 `PluginResourceError`」与「增量同量级」两半不能同时成立。
  两条出路都要改口径（把常量降到 ≤512 MB 以下，或把带放宽到 ≥2.24×），
  **本档两条都没做**，按「硬约束优先」停在 D2 的常量上。⇒ 需要 nanobot 拍板。
- **② 量具只看得见**高水位**：正常脚本的单次 delta 恒为 0**（G5 实测 m2_a1 = 0 B）。
  含义：`plugin_resource_events` 只能证明「有过一次越界」，不能当「每次调用用了多少
  内存」的时间序列读。D1 选 `ru_maxrss` 就是这个代价；要当前值得换量具（RSS 采样
  或 `tracemalloc`），那是另一个决定。
- **③ 只覆盖 `plugin submit` 预检一条路径**：`candidate run` / `m2_daily` 跑的是已
  `active` 的脚本，本档**没**接线（D5 允许作为可选项，如实记）。它们若越界会抛
  `PluginResourceError`（既有的 `candidate.py` 精确 except 已接住），但**不会留行**。
- **④ `m2/channel_a.py::REJECTED` 未加 `PluginResourceError`**：它本来就不含
  `PluginTimeout`，不是「按 `PluginTimeout` 精确匹配」的点，故未动（动了会改变
  通路 A 的语义：资源越界从「上抛」变成「记为一次拒绝运行」）。
- **⑤ `plugin_resource_events` 会随每次 submit 增长**：没有保留策略（同 P92 简报）。
