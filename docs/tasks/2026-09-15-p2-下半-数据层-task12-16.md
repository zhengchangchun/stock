## 1. 上半轮遗留问题 → 本轮结论（逐条）

### 1.1 ✅ 已解决：Task 12 的核心矛盾（801 vs 641）

**结论：两个数字都不是「腾讯只给这么多历史」，而是复权口径不同 + 服务端静默降级。**
详见 `docs/decisions/2026-09-15-ADR-003-长历史数据源.md`。要点：

| 口径 | 单次上限 | 超过上限的行为 |
|---|---|---|
| 不复权（`adj=""`） | **2000 根** | >2000 报 `{"msg":"param error"}`（显式失败） |
| 前复权（`adj=qfq`） | **800 根** | 801~2000 **静默降级回 640 根，无任何错误信号** |

- ADR-001 的「801 根」是 **bfq（不复权）**口径的请求；
- 上半轮的「641 根」是 **qfq** 请求 801~900 根时被静默降级的结果。
- **受限的不是 count，而是 adj**；且 `end` 参数可作锚点向后翻页，**beg 被服务端忽略**。

**实测覆盖（见 §4.1 原始输出）**：
`sz000333` 累计 **3095 根**（2013-09-18 上市首日 ~ 2026-09-14）；
`sh600000` 累计 **6388 根**（1999-11-10 上市首日 ~ 2026-09-14）。

→ **B2 解除**：数据窗口远超 walk-forward 所需（度量纪律要求样本 ≥120 交易日）。
ADR-001 D-02「接受 900 根（≈3.7 年）」**作废**（已在 ADR-001 §8.2 标注）。

### 1.2 ✅ 已解决：`RetryPolicy` 与 `config/settings.py` 未接线

`stocklab/data/fetch.py::policy_from_settings(settings)` 把 5 个字段
（`retry_attempts` / `retry_base_delay` / `retry_max_delay` / `http_min_interval` /
`http_timeout`）全部接上，CLI 用它构造 `HttpClient`。
测试：`test_policy_from_settings_wires_every_field`（逐字段断言，不只看是否非空）。

### 1.3 ✅ 已处理：东财无真实 fixture

- 本环境东财**完全不可达**：三种 URL 变体（`beg=0` / `beg=19900101` / 带 `ut`）
  在 `push2his` 与 `push2` 两个域上**全部** `RemoteDisconnected`（DNS 正常解析）。
  与 ADR-001 §1 记录一致，属**复现**而非新问题。
- **因此本轮没有制造任何东财「真实 fixture」**，也没有把合成样本伪装成真实响应。
  旧的 `tests/test_source_eastmoney.py` 仍按其文件内的**合成样本**声明运行（未改动）。

- **决策**：东财退出主路径。日K 主源 = 腾讯不复权 + 分页。

## 2. 计划文件与实测不符之处（实测优先，逐条留痕）

### 2.1 Task 12：探针脚本本身要能区分「口径」与「条数」两个旋钮

计划给的探针只请求两个固定 URL（东财一个、腾讯 `,320,qfq` 一个），
**无法解释 801 vs 641 的矛盾** —— 因为它没有把 `count`/`beg`/`end`/`adj`
四个旋钮分开扫。
→ 重写为 `count_cap` / `pagination` / `eastmoney` / `pagination_old_stock` 四组探测，
每组输出 URL + 条数 + 首末日期 + 耗时 + 响应 SHA256，并落盘 JSON 供离线复核。

### 2.2 Task 12：计划的预期值（东财 1500 根）与实测（东财不可达）相反

计划写「Expected（东财可用时）：count 1500」并规定「若东财 < 400 或报错 → B2 未解决，停下来」。
**实测东财完全不可达**，但**B2 依然解决了** —— 因为计划的隐含前提（必须靠东财取长历史）
是错的：腾讯不复权 + 分页即可取到上市首日。
→ 按「结论以实测为准」处理，未按计划的「停下来上报」执行；差异记录于此与 ADR-003。

### 2.3 Task 14：计划的 `insert_bars` 接口与 schema 的 PK **互斥**（第三次踩同类问题）

计划接口写「`INSERT OR REPLACE`；`adj_mode` 不同视为不同记录」，
但 `schema.sql` 的 PK 是 `PRIMARY KEY (code, date)` —— 同一天**物理上放不下**两条口径。
若照计划实现，qfq 会**静默覆盖**当天的不复权价，下游拿到贴错标签的价格且无报错。

→ 按 ERROR_DIARY「冲突时先问哪个意图更强」处理：**铁律①优先**。
`insert_bars` 改为**拒绝** `adj_mode != "none"` 的整批数据（`ValueError`），
而不是放宽 DDL。同时把 `INSERT OR REPLACE` 换成 `ON CONFLICT DO UPDATE`
（`REPLACE` 会连带清空未列出的列，`added_at` 这类"首次入库时间"会被抹掉）。
测试：`test_insert_bars_rejects_adjusted_bars{,_atomically}` +
`test_upsert_instruments` 里对 `added_at` 不变性的断言。

### 2.4 Task 16：计划的 CLI 抓取路径（东财主 + 腾讯 qfq 降级）**两处都不可用**

计划 `cmd_ingest_bars` 的 fetch 是「东财为主，取不到则降级腾讯 **qfq**」。实测：

1. 东财不可达（§1.3）；
2. 降级用的 qfq **会被 `insert_bars` 拒绝**（§2.3），且 qfq 本身违反铁律①。

→ fetch 改为**腾讯不复权 + `end` 锚点分页**（ADR-003）。
**没有**保留「降级到 qfq」的分支：宁可失败留痕，也不写口径错误的数据
（ERROR_DIARY 2026-09-14「解析器取不到就回退」同源教训）。

### 2.5 Task 16：抓取逻辑从 `cli/main.py` 提到 `stocklab/data/fetch.py`

计划把分页/解析全写在 CLI 的闭包里 —— 那样联网代码**无法离线测试**。
→ 抽出 `fetch_daily_bars()`（纯「取数+解析+翻页」），CLI 只做接线。
代价：多一个模块；收益：12 条基于**真实响应 fixture** 的离线回放测试（含 4 条错误路径）。

### 2.6 Task 13/14/15：计划未覆盖的边界（本轮补齐，共 +16 条测试）

- `Issue` frozen 不可变；空输入不报错；gap 的 `code`/`date`/`severity` 归属。
- 仓储层：空序列 noop、`adj_mode` 拒绝的**原子性**、`latest_bar_date` 不串标的、
  质量问题按 `source` 分隔去重、零成交量写 `is_suspended=1`、写完不留未结事务。
- 采集编排：窗口外数据被过滤、**空结果算成功而非失败**（新上市标的）、
  `warn` 不阻断写入、`fetch` 未注入时不联网、`IngestResult` frozen、
  同一问题跨两次运行只累加 `occurrences`。
