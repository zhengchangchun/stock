# 工作流详细指引

配合 `/task` skill 使用，提供各阶段的详细执行指南。
每个阶段的「具体做法」优先使用对应的 superpowers 技能。

## 1. 需求澄清（brainstorming）

- 先问「要解决什么问题」，而不是「要写什么代码」
- 明确 **目标 / 非目标 / 验收标准**
- 有歧义就问，不要猜

## 2. 任务拆分规范

### 拆分粒度
- 每个任务是**可独立验证的最小单元**，只做一件事
- 无法直接验证的步骤 → 继续拆

### 好例子 ❌ vs ✅

| 错误（太粗） | 正确（可验证） |
|-------------|---------------|
| 实现登录功能 | 1. 创建登录表单组件 |
| | 2. 实现表单验证逻辑 |
| | 3. 对接登录 API |
| | 4. 处理登录错误状态 |

### 任务结构

```
Task: [动词+名词]
描述: 一句话说明做什么
实现步骤:
  1. 具体做法
  2. ...
验证方式:
  - [ ] 验证项 1
  - [ ] 验证项 2
```

## 3. 计划落盘（writing-plans）

写 `docs/plans/YYYY-MM-DD-<task>.md`，假设读者对本项目零上下文：
改哪些文件、写什么代码、怎么测、怎么回滚。

## 4. 实现（TDD + 隔离工作区）

- 先 `using-git-worktrees` 保证隔离
- 先写失败测试 → 跑一遍看它失败 → 写最小实现 → 跑通
- **没亲眼看到测试失败，就不知道测试测的是不是对的东西**

## 5. 验证执行规范

```markdown
## 验证: [任务名]

### 执行步骤
1. `命令` → ✅ 通过（贴关键输出）
2. `命令` → ❌ 失败（贴报错）

### 结果分析
- 是否符合预期？
- 边界情况是否覆盖？
```

### 交付前必须确认

1. **功能正确性** — 代码符合需求
2. **边界情况** — 空值、极限值、错误输入
3. **错误处理** — 失败时有明确提示
4. **代码质量** — 无死代码、无调试残留
5. **文档同步** — 相关文档已更新
6. **错误日记** — 如有新教训已记录

## 6. 文档同步规则

| 变更类型 | 需更新的文档 |
|---------|------------|
| 新增功能 | `docs/architecture/` + `docs/tasks/` |
| 修改逻辑 | `docs/architecture/`（对应模块） |
| 修复 Bug | `docs/errors/ERROR_DIARY.md`（如有教训） |
| 设计选择 | `docs/decisions/`（ADR） |

- 修改代码时同步更新，而不是做完再补
- 记录「为什么这么做」，不重复代码逻辑
- 删除代码时把对应文档标记为「已废弃」

## 7. 错误日记使用规范

### 什么时候记录
- 花费超过 15 分钟定位的 Bug
- 重复出现两次以上的问题
- 改了一处却导致另一处出错（耦合教训）
- 文档和代码不一致导致的问题

### 记录格式

```markdown
## YYYY-MM-DD: [错误简述]

### 错误描述
发生了什么？

### 根本原因
为什么会发生？

### 教训
以后如何避免？

### 检查清单（下次必查）
- [ ] ...
```

## 8. 收尾（finishing-a-development-branch）

验证全绿后再决定 merge / PR / 保留分支，并清理临时 worktree。
