# 07_定时任务调度需求.md
## 概述
本系统依赖分层定时任务驱动整个闭环，分为【轻量巡检任务、每日收盘任务、每周全量扫描任务、季度深度复盘任务】；
所有定时任务**触发主流程主干代码，主干逻辑固定不可修改**；定时任务仅负责调度，不修改业务规则、插桩脚本、约束边界。
> 调度载体：**系统定时能力（macOS launchd）**
> ⚠️ **已修正（D-23 / ADR-020，2026-09-22）**：原文是「Nanobot 定时能力（支持每30分钟、每日、每周、季度调度）」。
> 用户拍板「其实不需要 nanobot 定时任务，全部在系统里，到时候跑完页面会有展示」⇒ 时钟交给 launchd
> （`~/Library/LaunchAgents/com.stocklab.{close,patrol,monthly}.plist`，由 `stocklab ops schedule`
> 生成/安装/查询），跑什么与结论仍在项目（`ops/chain.py` / `ops/patrol.py` /
> `reports/ops/latest-*.json`），展示在页面 `/lab/ops`。

## 定时任务总清单
### 任务1：轻量巡检任务｜执行频率：每30分钟
触发模块：模块1候选池、模块2模拟&人工账户
目标：不做全市场扫描，只刷新**已经进入候选池内**的标的，轻量化更新状态
执行内容：
1. 拉取候选池内个股最新行情、价格、北向持仓、最新公告
2. 执行插桩0【行业特殊排雷脚本】，重校验风险
3. 更新模拟账户、人工镜像账户的持仓市值、浮动盈亏
4. 执行插桩A3、B1，刷新持仓收益概率预测，并写入预测库
5. 检测是否触发熔断风控（账户回撤阈值），触发则标记告警
6. 更新候选池标的状态（观察中 / 等待买点 / 逻辑证伪移出）
7. 保存本次轻量快照；输出简短巡检简报
限制：不执行全市场筛选、不触发AI策略优化、不跑完整策略评估周期。

### 任务2：每日收盘任务｜执行频率：每个交易日收盘后（15:30）
触发模块：模块2预测验证模块
执行内容：
1. 加载当日收盘最终价格，修正行情数据（前复权）
2. 执行【预测验证校验模块】：检索所有到期的历史预测记录，比对预测值与真实行情
3. 统计当日预测偏差、预测胜率，生成错判案例集合
4. 把错判案例、预测偏差数据暂存，等待每周任务统一回流模块1
5. 执行数据质量校验，标记当日脏数据、停牌、异常价格
6. 输出每日预测校验报告，写入日志库

### 任务3：每周全量扫描任务｜执行频率：每周一收盘后（每周1次）
触发模块：模块1完整候选池流程 + 模块2策略评估与AI优化
执行内容：
1. 模块1：**全标的扫描**，完整跑一遍候选池筛选全流程，更新短期/中期/长期候选池；新增合格标的、剔除失效标的，生成完整候选池快照与报告
2. 模块2：
    - 读取AI模拟账户、人工镜像账户，计算本周绩效指标
    - 执行策略自评估逻辑：检查当前正在评估的策略版本，判断是否跑完2~3轮验证周期（总时长≤30天）
    - 策略判定：冻结 / 触发优化 / 小幅调参
    - 如果判定需要优化：启动AI优化子任务，生成新版插桩脚本，进入沙盒回测
3. 将本周所有错判案例、预测偏差，回流至模块1的AI优化任务
4. 基准指数（沪深300/中证500）同周期绩效计算，用于对比
5. 输出完整周度报告：候选池清单、双账户绩效对比、策略评估结论、告警清单

### 任务4：季度深度复盘任务｜执行频率：每季度财报结束后（每3个月一次）
触发模块：模块1、模块2、风控复核
执行内容：
1. 模块1：拉取最新财报数据，对全部候选池标的重新完整打分，重估基本面
2. 模块2：
    - 对当前所有【冻结状态】的策略，强制复核（冻结策略最长有效期90天）
    - 冻结策略到期，强制开启新一轮2~3轮验证周期，防止策略随市场失效
3. 全量过拟合检测，扫描所有线上策略版本
4. 全量风控规则复核，检查行业集中度、单票仓位风险
5. 生成季度深度复盘报告

## 定时任务调度约束（主干固定，AI不可修改）
1. 任务串行优先级：
    季度复盘 > 每周全量扫描 > 每日收盘任务 > 30分钟轻量巡检
    若多个任务同时触发，低优先级任务排队等待，禁止并发重跑同一套业务流程，防止数据错乱。
    > ⚠️ **已修正（D-7）**：本条的「排队等待」与 nanobot cron 实际能力不符（cron 与用户会话共用一条会话，是抢占式排队，不是优先级队列）。以本文件末节《和原有系统集成关系》的修正版为准。
2. 任务超时保护：每个定时任务设置最大运行超时时间；超时直接终止，记录告警，不继续执行。
3. 任务幂等性：任务重复触发不会重复生成多条快照、重复跑多次回测；依靠快照版本ID保证幂等。
4. 任务失败重试：轻量巡检最多重试2次；每日/每周任务重试1次；重试失败，触发告警，人工介入。
5. 定时任务**不可以修改业务规则、插桩脚本、策略评估边界**，仅负责调度执行已有流程。

## 任务状态枚举
待执行｜运行中｜执行成功｜执行失败｜超时终止｜排队等待

## 调度输出
每次定时任务执行完毕，输出：
1. 任务执行日志（开始时间、结束时间、耗时、处理记录、异常告警）
2. 对应业务快照（候选池/账户快照）
3. Markdown简报报告

## 和原有系统集成关系（2026-09-21 补写）

**结论：包一层，不重写。**

现有 `stocklab/session/`（P11 调度链）已经在做本文件「任务1 / 任务2」的相当一部分：盘中快照采集 → 收盘回填 → 到期验证 → 复盘报告；其口径已被 P26 / P27 等任务钉过并有验收记录。

| 本文件 | 现有实现 | 关系 |
|---|---|---|
| 任务2 每日收盘任务（15:30） | `stocklab/session/` 收盘链 | **同一件事**：07 的「预测验证校验」= 收盘链的「到期验证」步。**不重写**，调度层直接调现有命令 |
| 任务1 轻量巡检（每 30 分钟） | 无（原为 nanobot 侧巡检，现未挂） | 新增调度，但**复用** `session` 的采集/回填命令，不新造业务逻辑 |
| 任务3 每周全量扫描 | `candidate run --run-kind weekly` | 命令已存在，缺的是**调度** + 「策略自评估」段（模块2 未开工） |

项目只生成 plist 文本并用 `launchctl` 注册，**没有常驻进程**。
⚠️ **载体已于 2026-09-22 从 nanobot cron 换成系统 launchd**（D-23 / ADR-020）；
下面提到「nanobot cron」的地方读成「当时的载体」，现存操作见

### 调度约束的修正（D-7）

§调度约束 1 要求「多任务同时触发则低优先级排队等待，禁止并发」。这条**按 nanobot cron 的实际能力不可实现**，改为：

1. **不承诺优先级队列，改为「自查前置产物 + 跳过」**：载体（nanobot cron 或 launchd）与用户会话
   都不提供优先级队列；任务每轮**自己检查前置产物是否就绪**，未就绪则跳过本轮并记 `job_runs`，
   靠幂等重跑兜底。（launchd 侧另有两条：同一 label 不会并发跑；错过的触发点在唤醒后补跑一次。）
2. **缺步补跑**：每轮巡检先做「当天链路体检」（今日 bars / 明日预测 / 当日复盘报告 / 模拟盘净值），缺哪步按收盘链顺序补哪步。
3. **超时与重试**：保持原文（巡检重试 2 次；每日/每周重试 1 次；超时终止并告警）。
4. **每日任务新增固定一步：库备份**。库是唯一不可再生资产（行情可重采，回测结论与快照不可重建），备份到 `data/backups/`。
